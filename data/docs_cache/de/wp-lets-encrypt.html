Jetzt ist ein SSL-Zertifikat für jede in Produktion befindliche Website eine Notwendigkeit, und die Ausstellung und Erneuerung von Zertifikaten sind jetzt routinemäßige Aufgaben. Werkzeuge wie Let's Encrypt nutzen den offenen-source Certbot mit dem Standalone-Authenticator, um diese Operationen leicht automatisieren zu können. Der Hauptnachteil hierbei ist das mögliche Ausfallzeitrisiko des Webanwendungsservers während automatischer Zertifikats-Erneuerung und Domain-Validierung. Um das Ausfallzeitrisiko während der SSL-Zertifikats-Aktualisierung zu überwinden, hat Virtuozzo Application Management ein integriertes Let's Encrypt Add-On mit einem fortgeschrittenen null-Downtime-Erneuerungsalgorithmus geschaffen. Gründe für Ausfallzeiten während der SSL-Zertifikats-Aktualisierung mit Certbot

Das Hauptziel des Certbot-Befehlszeilentools ist, einen HTTPS-Server zu konfigurieren und ein vertrauenswürdiges Zertifikat automatisch zu erhalten, ohne menschliche Intervention. Es führt die folgenden Aufgaben aus:

  • Beweist, dass Sie die Website kontrollieren
  • Empfängt ein Zertifikat und konfiguriert es auf einem Webserver
  • Überwacht die Ablaufzeit des Zertifikats und aktualisiert es
  • Hilft Benutzern, ihr Zertifikat (falls nötig) zu revokieren
  • Zwangsweise erneuert das Zertifikat, wenn es erforderlich ist

Zunächst startet Certbot die Ausstellung eines SSL-Zertifikats durch Senden von Certificate Signing Requests (CSR). Danach startet es einen Certificate Management Agent (CMA), der ein Python-Webserver ist, der auf dem angegebenen Port hört, um Validierunganfragen von der Let's Encrypt CA zu verarbeiten.

Dann startet es einen Certificate Management Agent (CMA), der ein Python-Web-Server ist, der auf der angegebenen Portnummer lauscht, um Validierungsanfragen von der Let's Encrypt CA zu verarbeiten. Bevor ein Zertifikat erworben wird, muss es nachgewiesen werden, dass der Erneuerungsvorgang von der Domänenadministration ausgelöst wurde. Die Validierungsanfragen erfolgen immer auf Port 80, der normalerweise von der Anwendung belegt ist, die HTTP-Verkehr abhört. Daher muss der Webserver, auf dem er läuft, vorübergehend gestoppt werden, um stattdessen den CMA zu starten. Folglich verursacht solche Implementierung eine Anwendungsausfallzeit. Ein weiteres Problem, das Ausfallzeiten verursachen kann, ist, dass der Python-Webserver sich verhängt, sobald er versucht, eine nicht-Validierungs-HTTP-Anfrage zu verarbeiten, die von jedem Benutzer kommen kann. Das geschieht, weil Certbot den Webserver in einem einzelnen-Thread-Modus ausführt. Folglich kann er nicht mehrere einkommende Anfragen verarbeiten. Lösung, um Ausfallzeiten während der SSL-Zertifikatsaktualisierung zu vermeiden, um die genannten Probleme zu umgehen, hat Virtuozzo Application Management eine integrierte Let's Encrypt-Erweiterung geschaffen, die einen verbesserten Algorithmus enthält. Sie setzt auf Routingregeln, um eine intermediäre Umleitungs-Schicht in den Verkehrskette einzubauen, um HTTP-Verkehr zu filtern. Der Proxy wird konfiguriert, um die Anfrage nur dem Python-Webserver von Let's Encrypt CA zu routen. Andere Verkehr wird dem Benutzeranwendung routed. Um auf den Proxy-Port zu routen, wird die Erweiterung den Anwendungs-Webserver nicht stoppen und leitet Anfragen von der Website-Port 80 auf den Proxy-Port (z.B.) umleiten.

Um den Benutzer-Anwendung zugeleitet werden. Routing an Proxy-Port Der Add-on stoppt nicht den Web-Server der Anwendung und leitet Anfragen von Website-Port 80 an den Proxy-Port (z.B., 12347) über iptables/nftables-Regeln bis zur Validierung.

if grep -a 'AlmaLinux' /etc/system-release ; then
    /usr/sbin/nft insert rule ip filter INPUT tcp dport ${PROXY_PORT} counter accept comment "LE"
    /usr/sbin/nft insert rule ip filter INPUT tcp dport ${LE_PORT} counter accept comment "LE"
    /usr/sbin/nft insert rule ip6 filter INPUT tcp dport ${LE_PORT} counter accept comment "LE"
    /usr/sbin/nft insert rule ip6 filter INPUT tcp dport ${PROXY_PORT} counter accept comment "LE"
    /usr/sbin/nft insert rule ip nat PREROUTING ip saddr != 127.0.0.1 tcp dport 80 counter redirect to ${PROXY_PORT} comment "LE"
    /usr/sbin/nft insert rule ip6 nat PREROUTING ip6 saddr != ::1 tcp dport 80 counter redirect to ${LE_PORT} comment "LE"
    || \
    /usr/sbin/nft insert rule ip6 filter INPUT tcp dport 80 counter drop comment "LE"
else
    iptables -I INPUT -p tcp -m tcp --dport ${PROXY_PORT} -j ACCEPT
    iptables -I INPUT -p tcp -m tcp --dport ${LE_PORT} -j ACCEPT
    ip6tables -I INPUT -p tcp -m tcp --dport ${LE_PORT} -j ACCEPT
    iptables -t nat -I PREROUTING -p tcp -m tcp ! -s 127.0.0.1 -d 127.0.0.1 tcp dport 80 -j REDIRECT --to-port ${PROXY_PORT}
    iptables -t nat -I PREROUTING -p tcp -m tcp ! -s ::1 -d ::1 tcp dport 80 -j REDIRECT --to-port ${LE_PORT}
fi

In diesem Beispiel wird gezeigt, wie die Anfragen von Port 80 an den Proxy-Port (z.B., 12347) umgeleitet werden, wenn die System-Release auf AlmaLinux festgestellt wird. Wenn dies nicht der Fall ist, werden die Regeln für iptables und ip6tables angepasst, um die Anfragen an die entsprechenden Ports (PROXY_PORT und LE_PORT) zuzulassen.

tcp -m tcp --dport ${LE_PORT} -j ACCEPT
ip6tables -I INPUT -p tcp -m tcp --dport ${LE_PORT} -j ACCEPT
iptables -t nat -I PREROUTING -p tcp -m tcp ! -s 127.0.0.1/32 --dport 80 -j REDIRECT --to-ports ${PROXY_PORT}
ip6tables -t nat -I PREROUTING -p tcp -m tcp --dport 80 -j REDIRECT --to-ports ${LE_PORT}
|| ip6tables -I INPUT -p tcp -m tcp --dport 80 -j DROP
fi

Jetzt sehen wir uns, wie es in einer realen Fallstudie funktioniert, indem wir eine WordPress-Anwendung als Beispiel verwenden. Während der Installation des WordPress-Pakets (Cluster oder Einzelanwendung) aktivieren Sie die Option “Install Let’s Encrypt SSL mit Auto-Renewal”.

WordPress Cluster
Im Falle eines WordPress-Clustermilieus wird der Verkehr von allen Load Balancers auf den Masterknoten (den ersten oder initial erstellten Container in der Schicht) geleitet, wo der Validierungsserver liegt.

WordPress Standalone

Es gibt zusätzliche Möglichkeiten, neue Zertifikate auszustellen oder bestehende zu aktualisieren, die man Webroot heißt.

80 des Benutzers Web-Server. Aktualisierung des Let's Encrypt-Zertifikats mithilfe des Webroot-Authentifizators

Es gibt eine zusätzliche Methode, um neue Zertifikate auszustellen oder bestehende zu aktualisieren, die Webroot genannt wird. Diese Methode ist vorzuziehen für hochbelastete Websites (wird dem WordPress-Cluster in kürzester Zeit hinzugefügt), da sie die Arbeit der Webserver nicht unterbricht und den Risiko von Ausfallzeiten oder Leistungsabfallen entgeht. Die webroot kann mit zertifizierten PHP-Software-Stacks verwendet werden, wie in den WordPress-Paketen. Wenn gestartet wird, erhält Certbot den Pfad zur Wurzelverzeichnis des Websites. Dann erstellt Certbot eine Verzeichnisstruktur dort für den Speicherung von temporären Dateien:
1 ${webroot-path}/.well-known/acme-challenge

Der Let's Encrypt-Server prüft auf den Vorhandensein dieses Dateis in der angegebenen Lage mit einem Anfrage dieser Art:
1 http://beispiel.com/.well-known/acme-challenge/KJr5D^ReTW4kY_Z6UIIkjlmlmOkyQgPr_7ArlLgtZE7Fg

Wenn die angeforderte temporäre Datei (z.B. “KJr5D^ReTW4kY_Z6UIIkjlmlmOkyQgPr_7ArlLgtZE7Fg”) vorhanden ist, wird die Domain-Besitzrechte erfolgreich verifiziert und das Zertifikat wird ausgestellt und auf den Benutzer-Website hochgeladen. Nach Abschluss der Validierungsprozedur erhält Certbot das Zertifikat-Datei. Normalerweise wird der Let's Encrypt SSL-Zertifikat-Datei in dem Verzeichnis /etc/letsencrypt/live gespeichert, wo alle Dateien Symlinks auf die Dateien in dem Verzeichnis /etc/letsencrypt/archive sind. Wie Sie sehen können, gibt es Optionen, um während der Aktualisierung des SSL-Zertifikats einen vollständigen Betrieb zu gewährleisten.
