WordPress-Sicherheitsoptimierung: Hacking und Cyber-Angriffe können große Probleme mit der Serverleistung verursachen, wenn sie nicht ausgesetzt sind. Viele Menschen haben keinen Einblick in die Häufigkeit der Serverangriffe, weil sie die Logs nie sehen. Jeder Server wird mehrere Tausende Mal (manchmal innerhalb einer Stunde) jeden Monat angegriffen. Ihre Seite könnte auch jetzt angegriffen werden, aber Sie wissen es nicht. Die Abwehr gegen diese Angriffe erfordert eine feine Balance. Sie wollen keinen Server, der Hackern ungehindert ihre Ports und Ressourcen zugänglich macht. Aber Sie wollen auch keinen Server, der zu sicher ist und allen Verkehr so stark auditet, dass er die Benutzer verlangsamt oder schlimmer (legitime Benutzer blockiert). Tip: Diese Anleitung nutzt großartige Tipps aus The Ultimate WordPress Speed Optimization Guide, geschrieben von Johnny Nguyen. Ports, die von bestimmten Personen verwendet werden (SSH, FTP) – nur Sie oder wenige andere. Führen Sie eine IP-Whitelist ein und blockieren Sie den Rest.

Achtung jedoch, denn jemand, der reist, verliert Zugang! Ports, die nur von bestimmten Ländern angegriffen werden – wenn Sie viele Angriffe von bestimmten Ländern oder Regionen erhalten, können Sie die Blockade durch Land oder ganze IP-Bereiche einrichten. Brute-Force-Schutz auf wp-login.php (ANFANG, HÖCHST) Die WordPress-Admin-Anmeldeseite wird oft von Bots bombardiert, die zufällige Benutzernamen und Passwörter versuchen, um durchzukommen. Ob sie es schaffen oder nicht, ihre ständigen Versuche verbrauchen viel Ressourcen. Es gibt mehrere Möglichkeiten, sie zu verhindern, jede mit ihren Vorteilen und Nachteilen. Server-basierter Brute-Force-Schutz – einfach und effizient, kann jedoch auf lebensvolleren Servern mit Seiten, die Cloudflare verwenden, legitime Nutzer sperren. Der Problem ist, dass Brute-Force-Sperrungen durch IP blockiert werden und Besucher, die über Cloudflare eintreten, alle den gleichen (Proxy-)IP teilen. Ja, Sie können konfigurieren, um den wahren Client-IP über Cloudflare-Headers zu übermitteln, aber das verzögert die Seitenladezeit! Anwendungsebene-Brute-Force-Schutz – viele WordPress-Sicherheits-Plugins können das tun. Sie sichern die Anmeldeseite, indem sie Benutzer mit schlechten Anmeldeinformationen sperren. Einige Plugins verbergen die Anmeldeseite – sie verschieben sie auf eine andere URL. Bitte sicherheit, dass die Standard-Anmelde-URL entweder blockiert oder gespeichert wird, um die Ressourcenverbrauchung durch Besuche an ihr zu verhindern. Andere Plugins schützen die Anmeldeformular durch die Einführung einer Captcha und das Sperren bestimmter Robots, Crawler und Geräte. Das kann gut funktionieren, aber könnte legitime Nutzer irritieren oder falsch flaggen. Die einzige Server, die ich kenne, die nativ Brute-Force-Schutz auf wp-login.php hat, ist LiteSpeed. Alle anderen Server (Apache & NGINX) müssen dies aktivieren, indem sie entweder eine Sicherheits-Plugin oder HTTP-Auth verwenden.

Deaktivieren Sie das XML-RPC-Protokoll (ANFANG, MITTEL)
Das XML-RPC-Protokoll ermöglicht es externen Apps (z.B. mobile Apps), sich bei Ihrer WordPress-Seite anzumelden und Inhalte zu bearbeiten oder WooCommerce-Verkäufe anzuzeigen. Wenn Sie keinen Zugang zu Ihrem Server haben, können Sie Sicherheits-Plugins verwenden. Ja, Sicherheit wird effizienter durchgeführt, wenn sie auf Server-Ebene (näher an der Rohrechnleistung) statt auf Anwendungsebene (langsamerer PHP-Verarbeitung) erfolgt.

Ihr Server, können Sie Sicherheits-Plugins nutzen. Ja, Sicherheit wird effizienter auf Server-Ebene (näher an der Rohrechnleistung) als auf Anwendungsebene (langsamerer PHP-Verarbeitung) durchgeführt. Allerdings kann es manchmal schwierig sein, globale Sicherheitsregeln festzulegen, wenn Sie viele Kunden/Seiten haben und jede etwas anderes benötigt. Dennoch ist ein Sicherheits-Plugin wie WordFence trotzdem eine nützliche Option, um Angriffe zu blockieren, die der Server nicht und/oder um geschädigte Seiten weitere Schäden zu verhindern. Mein Lieblings-WordPress-Sicherheits-Plugin ist WordFence. Die wichtigste Funktion von Sicherheits-Plugins IMO ist das Scannen von Malware. Scannen Sie manuell oder planen Sie während niedrig-verkehrszeiten. Diese Funktion verbessert nicht notwendigerweise die Website-Geschwindigkeit, sie erkennt System-Löcher und verhindert, dass sie Ressourcen (Hosting von Spam-Seiten oder Angriffen auf andere Server) nutzen. Die Firewall-Funktionen in Sicherheits-Plugins sind wahrscheinlich nicht notwendig, wenn Sie bereits einen Server-Firewall verfügen. Firewalls, die aktiviert werden auf PHP-Ebene, verzögern alle einkommenden Anfragen. Der Leistungsproblem mit Sicherheits-Plugins entsteht durch übermäßig aggressives Filtern aller einkommenden Verkehrs und Scannen zu oft. Beide verbrauchen viele Ressourcen, insbesondere auf großen Seiten mit vielen Seiten und Besuchern. Ich empfehle es nicht, ein Software-Firewall zu verwenden, und auch die Malware-Scans auf eine langsameren Geschwindigkeit zu setzen. Konfiguration von DNS-Edge-Level-Sicherheit (BEG, MED) Erinnerte ich mich, dass Sicherheit effizienter an Server-Ebene als an Anwendungsebene durchgeführt wird? Wenn Sie es an der Edge-Ebene (DNS-Ebene) durchführen, kann es sogar noch effizienter sein als an Ihrer Server-Ebene, da es auf Fremdserver basiert. Es gibt einige Leistungsauswirkungen zwischen der Sicherheitsverwaltung an der Edge VS auf Ihrem Server. Sie können entscheiden, was für Ihr Fall am besten funktioniert. Die Sicherheitsverwaltung auf Ihrem Server kann konvenienter sein, da Sie mehr Kontrolle haben. Sie können für Ihre spezifische Anwendung optimieren. Der einzige Nachteil ist, dass es Ihre Server-Ressourcen verwendet und auch dass Sie Administrator-Kenntnisse benötigen. Die Sicherheitsverwaltung über einen anderen Server (z.B. DNS-Proxy, Cloudflare) oder Sicherheitsdienst (Sucuri) spart Ihren Server wertvolle Ressourcen, aber könnte leichte Verzögerungen bei der Ladung hinzufügen, da Besucher über ein zusätzliches Proxy vor Ihrer Web-Server-Anwendung passieren. Je schwächer Ihr Server und Ihre Server-Administrator-Kenntnisse, desto wahrscheinlicher ist es, dass eine Sicherheitsdienstleistung effizienter ist, DDOS-Anfragen abzufangen. Tatsächlich müssen jedoch die meisten Menschen nicht mit DDOS-Angriffen rechnen, ok?

Wichtig: Vermeiden Sie es, übermäßig aggressives DDOS-Sicherheitsniveau an beide Ebenen (DNS und Server) zu setzen. Dies kann falsche Positiv-Ergebnisse verursachen, bei denen legitime Besucher wegen der Tatsache, dass alle Besucher (gut und schlecht) den gleichen IP-Adresse teilen, wenn sie über ein Proxy kommen, blockiert werden.

Die meisten Menschen müssen sich nicht um DDOS-Angriffe kümmern, ja? Die meisten niedrigstufigen DDOS-Angriffe können leicht von Ihrem Server abgewehrt werden. Die höchststufigen DDOS-Angriffe sind die, die Server (auch mit guter Sicherheit) überfluten, aber sie kosten Geld und konzentriertes Aufwand von Hackern. Bis jemand speziell auf Sie zielt, müssen Sie sich nicht um sie kümmern. Die einfachste Methode, um hohestufige DDOS-Angriffe zu behandeln, ist sofort eine Sicherheitsfirma wie Sucuri zu beauftragen (wenn es passiert). Ich empfehle es nicht, für teure Sicherheitsdienste zu zahlen, die Sie meistens nicht benötigen. HTTPS und HTTPS-Umleitung (BEG, LOW) Sie sollten absolut HTTPS nutzen. (Es ist das einzige Möglichkeit, die Vorteile des HTTP/2-Protokolls zu nutzen.) Stellen Sie 301 HTTPS-Umleitungen auf Ihrem Server ein, damit Besucher schnell umgeleitet werden können auf die korrekte HTTPS-Protokoll- und Domainversion Ihrer Seite (mit oder ohne „www“). Ohne diese Server-Umleitungen kann WordPress es noch tun, aber es dauert etwas länger. Außerdem sollten Sie sich sicher sein, dass alle Ihre internen URLs HTTPS nutzen. Vertrauen Sie nicht auf SSL-Plugins (unnotwendig) oder WordPress (langsam), um Sie umzuleiten. Setzen Sie die Umleitungen von der Serverseite! Bonustip: Wenn Sie Cloudflare verwenden, legen Sie eine Seitenregel fest, um Ihre HTTPS 301-Umleitungen dort auch zu setzen (schneller als von der lokalen Serverseite). Was kommt nach?
