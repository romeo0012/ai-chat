Sicherheitskonfiguration¶ mod_security¶ Es ist möglich, mod_security auf der Web ADC-Ebene zu aktivieren, jedoch empfehlen wir dies nicht. Die Verwendung von mod_security auf ADC-Ebene wird die Datenverteilung dramatisch verlangsamen. Stattdessen sollten Sie die Backend-LiteSpeed Web Server, um die schweren Lasten, die durch die Laden, Prüfung und Filtern von mod_security-Regeln entstehen, zu bewältigen. Sollten Sie trotzdem mod_security aktivieren wollen, können Sie dies nach unseren LiteSpeed Web Server-Anweisungen tun. Anti-DDoS Konfiguration (ConfigServer oder iptables)¶ Die Anti-DDoS-Funktion von LiteSpeed ADC kann verwendet werden, um eine Firewall über ifconfig und ipset zu modifizieren, um verdächtige IP-Adressen zu blockieren. Dieser Leitfaden erklärt, wie die ADC-Anti-DDoS-Funktion mit ConfigServer Security & Firewall (csf) oder iptables integriert werden kann. LiteSpeed ADC-Konfiguration¶ Melden Sie sich bei der WebAdmin Console des ADCs an, indem Sie sich hier anmelden: https://SERVER_IP:7090. Navigieren Sie anschließend zu Konfiguration > Sicherheit. Setzen Sie Enable Anti-DDoS Schutz und Enable Firewall Modifikation auf Ja, um Anti-DDoS-Schutz zu aktivieren. ConfigServer Security & Firewall-Konfiguration¶ Für csf erstellt Sie die Datei /etc/csf/csfpost.sh und fügen Sie folgenden Inhalt hinzu:

#!/bin/bash
ipset create ls-anti-ddos hash:ip hashsize 4096
ipset create ls-quic-ports bitmap:port range 0-65535 -exist
iptables -I INPUT -m set --match-set ls-anti-ddos src -j DROP
iptables -I FORWARD -m set --match-set ls-anti-ddos src -j DROP
iptables -I INPUT -p udp -m set --match-set ls-quic-ports dst -j ACCEPT
Reloaden Sie mit dem Befehl csf -r.

Modifizieren Sie die Berechtigungen für die Datei, indem Sie den Befehl chmod +x /etc/csf/csfpost.sh ausführen. Aktivieren Sie csf mit dem Befehl csf -a.

-j DROP iptables -I INPUT -p udp -m set --match-set ls-quic-ports dst -j ACCEPT Lade mit dem Befehl csf -r neu. Für iptables führen Sie die folgenden Befehle aus, um die Liste und Regeln zu erstellen:

WordPress Brute Force Attack Protection¶
Ein 'brute force' Login-Angriff ist eine Art von Angriff gegen eine Website, um Zugriff auf die Seite zu erlangen, indem man den Benutzernamen und das Passwort wiederholt versucht. WordPress ist das beliebteste CMS und daher häufiges Ziel dieses Typs von Angriffen. Die Seiten wp-login.php und xmlrpc.php sind die häufigsten Ziele eines brute force Angriffes über die POST-Methode. WordPress hat keine eingebaute Schutzmaßnahme, um dies zu verhindern, weshalb die Notwendigkeit für eine dritte-Partei-Lösung besteht. LiteSpeed Web ADC hat ein eingebautes System für WordPress Brute Force Attack Protection. Es schützt WordPress-Umgebungen für gemeinschaftliche Hosting vor großskaligen brute force Angriffen, die das Potenzial haben, ganze Server zu bringen.

Die Übersetzung der technischen Terme, Codeblöcke, Befehle, Dateipfade und URLs wurde nicht durchgeführt, da sie im Original erhalten bleiben sollten.

Die folgende Regel schützt WordPress-Umgebnisse in shared hosting von großskaligen Brute-Force-Angriffen, die die Möglichkeit haben, ganze Server abzustürzen. Wie funktioniert Brute-Force-Schutz?¶ Die WordPress-Schutzsbefehl ist: [Throttle, Deny, Drop, Disable ] Der Aktion wird optional zugeordnet und hat standardmäßig den Wert Disable. Die erlaubten Anmeldeversuche können als Wert des (0|1|5-1000) festgelegt werden. 0 deaktiviert WordPress-Schutz. 1, wenn von einem virtuellen Host verwendet, übernimmt es die Einstellung, die vom Server verwendet wird. 5-1000 aktiviert WordPress-Schutz und gibt zusätzlich den Anmeldewert an. (Werte unter 5 werden als 5 behandelt, und Werte über 1000 werden als 1000 behandelt) Der erlaubte Anmeldeversuchswert gibt die maximale Anzahl von Versuchen an, die für wp-login.php und xmlrpc.php innerhalb von 5 Minuten erlaubt sind, bevor die IP-Adresse gesperrt wird. Dieser erlaubte Anmeldeversuchswert wird mithilfe eines Zugriffssystems verwaltet, das wie folgt funktioniert: Der Zugriff beginnt mit dem angegebenen erlaubten Anmeldeversuchswert. Jede POST-Versuche verringert den Zugriff um 1
Wenn der Zugriff auf die Hälfte des Wertes sinkt, wird die IP-Adresse verlangsamt. Wenn der Zugriff auf 0 sinkt, wird die gewünschte Aktion (drop, deny, oder verlangsamen) durchgeführt. Über den Zeitraum von 5 Minuten ohne weitere POST-Versuche steigt der Zugriff allmählich wieder auf den festgelegten erlaubten Anmeldeversuchswert zurück. Neustarten von LSADC setzt den Zugriff zurück auf den festgelegten Wert. Beispiel Sei der erlaubte Anmeldeversuchswert auf 10 festgelegt.

LSADC wird die Quote auf den angegebenen Wert zurücksetzen. Beispiel Sei die zulässige Anzahl an Loginversuchen auf 10 festgelegt. Wenn innerhalb eines kurzen Zeitraums mehr als 5 Versuche erfolgen, wird die IP-Adresse gedrosselt. Sobald die Quote auf 0 sinkt, wird die gewünschte Aktion (drop, deny oder throttle) durchgeführt. Jede 30 Sekunden (5 Minuten geteilt durch den Wert = 30 Sekunden) wird, wenn es keine weiteren POST-Versuche gibt, die Quote um 1 erhöht. Beispiel Sei der Wert auf 300 festgelegt. Wenn innerhalb eines kurzen Zeitraums mehr als 150 Versuche erfolgen, wird die IP-Adresse gedrosselt. Sobald die Quote auf 0 sinkt, wird die gewünschte Aktion (drop, deny oder throttle) durchgeführt. Nach 1 Sekunde (5 Minuten geteilt durch den Wert = 1 Sekunde) ohne weitere POST-Versuche wird die Quote um 1 erhöht. Aktiviere global auf Serverebene¶ Zugreifen Sie auf die WebAdmin-Konsole über https://YOUR_SERVER_IP:7090 Navigieren Sie zu Konfiguration > Server > Sicherheit > reCAPTCHA-Schutz Setze reCAPTCHA auf Ja. Dies ist der Master-Schalter. Er aktiviert die reCAPTCHA-Funktion für das gesamte Web ADC. Dies kann an der virtuellen Host-Ebene überschrieben werden. Für weitere Optionen bewegen Sie den Mauszeiger über das ?-Symbol, um detaillierte Informationen über diese Option anzuzeigen. Zur Demonstrationszwecken werden wir die Verbindungslimitierung und die SSL-Verbindungslimitierung auf 1 und den reCAPTCHA-Typ auf Checkbox festlegen. Sie können diese Werte nach Ihren Bedürfnissen anpassen. Speichern Sie und starten Sie den Web ADC neu. Diese Verbindungslimitierungseinstellung wird an alle virtuellen Hosts geerbt, es sei denn, sie wird an der virtuellen Host-Ebene überschrieben. Wenn ein Besucher die Website aufruft, muss er die reCAPTCHA-Validierung durchlaufen. Diese Validierung schützt den Server gegen HTTP-Flood und andere DDoS-Angriffe. Nach erfolgreicher reCAPTCHA-Validierung wird der Besucher vorübergehend in einer Weißen Liste eingetragen, solange er die Seite weiter durchsucht. Dadurch entsteht ein besseres Benutzererlebnis.

Besucher wird vorübergehend in die Weiße Liste aufgenommen, solange sie die Seite weiter durchsuchen. Dadurch entsteht ein besseres Benutzererlebnis. Sobald der Besucher mehr als 20 Minuten inaktiv ist, wird reCAPTCHA erneut für den nächsten Anfrage des Besuchers aktiviert. Sie können auch reCAPTCHA für einzelne virtuelle Hosts aktivieren, die unter Angriff stehen, während andere Websites deaktiviert bleiben. Übergeben/Deaktivieren auf der Ebene des virtuellen Hosts¶
Veranschaulicht man hat reCAPTCHA auf Serverebene global aktiviert, können die Einstellungen auf der Ebene des virtuellen Hosts überschrieben werden. Verwenden Sie die Web ADC WebAdmin Console, um reCAPTCHA für den VHost zu überschreiben. Navigieren Sie zu Konfiguration > Virtual Hosts > Sicherheit > reCAPTCHA Schutz. Definieren Sie CAPTCHA-Aktionen über Umleitungsregeln¶
Wenn Sie die CAPTCHA-Aktion weiter definieren möchten, wie verweigern oder fallen, oder CAPTCHA aus, können Sie eine der folgenden Umleitungsregel-Direktiven verwenden: [E=verifycaptcha] [E=verifycaptcha:verweigern] [E=verifycaptcha:fallen] [E=verifycaptcha:off] [E=verifycaptcha] wird auf CAPTCHA weiterleiten, bis es verifiziert wurde (außer es ist auf off gesetzt, was CAPTCHA deaktiviert). verweigern wird eine 403 zurückgeben, und fallen wird die Verbindung fallen, wenn Max Tries erreicht ist. Bis Max Tries erreicht ist, wird der Client auf eine CAPTCHA-Herausforderung weitergeleitet. Beispiel UmleitungsBedingung SOME-CONDITIONAL-CHECK UmleitungsRegel .* - [E=verifycaptcha] (SOME-CONDITIONAL-CHECK wäre eine verdächtige UA, IP-Adresse usw.)

Hinweis In den meisten Fällen werden Umleitungsregeln die Standardverhalten des Servers überschreiben.

Wäre eine verdächtige UA, IP-Adresse usw.) Hinweis: In den meisten Fällen überlagern die Umleitungsregeln das Standardverhalten des Servers. Es gibt jedoch Fälle, in denen Besucher direkt auf CAPTCHA geschickt werden können, bevor die Umleitungsregeln verarbeitet werden können, wenn die Sensitivität des Triggers hoch ist. Aktiviere CAPTCHA-Schutz für jede URL¶
Sie können CAPTCHA für eine bestimmte URL aktivieren. Beispielhaft könnte Sie den Bereich der Admin-Area (/administrator/) für alle Joomla-Webseiten auf dem Server schützen. Beispiel: In cPanel erstellt Sie /etc/apache2/conf.d/userdata/joomlaprotection.conf mit dem folgenden Inhalt:

<IfModule LiteSpeed>
RewriteRule /administrator/ - [E=verifycaptcha:deny]
</IfModule>

Gilt für alle cPanel-Virtualhosts und startet LiteSpeed neu: /usr/local/cpanel/scripts/rebuildhttpdconf service lsws restart

Anpassen der guten Bot-Liste¶
Google-Bots werden als gute Bots wegen ihrer Hilfe bei der Indizierung Ihrer Webseite betrachtet. Sie können jedoch nicht richtig arbeiten, ohne die richtige Seite zu erhalten. Die Bot White List-Konfiguration kann verwendet werden, um Bots anzugeben, die Sie für Ihre Webseite benötigen. Hier haben wir Edge in der Bot White List Textfeld konfiguriert. Bot White List ist ein fallender, case-sensitive "enthält"-Match, aber regex kann auch verwendet werden. Nach dem Neustart werden Browser in den User-Agent-Header enthalten, die Edge enthalten, um CAPTCHA umgehen: Die Konfiguration Allowed Robot Hits kann verwendet werden, um zu begrenzen, wie oft ein guter Bot (inklusive Googlebot) eine URL vor dem Umleiten auf CAPTCHA angeklickt werden darf.

Zeitweise sollte ein gutes Bot (zum Beispiel Googlebot) Zugriff auf eine URL haben, bevor er auf CAPTCHA umgeleitet wird. Dies kann nützlich sein, um schleichende Akteure vor dem Umgehen von CAPTCHA mit einem benutzerdefinierten User-Agent zu schützen. Tip: Google und Bing Bots werden automatisch in die Weiße Liste aufgenommen. Sie müssen jedoch weitere Bots, die Sie zulassen möchten, hinzufügen.

Customize the CAPTCHA-Seite¶
Die Standard-CAPTCHA-Seite ist generisch. Wenn Sie die Seite anpassen möchten, können Sie dies durch Erstellen einer Datei an $SERVER_ROOT/lsrecaptcha/_recaptcha_custom.shtml tun. Es gibt zwei Script-Tags, die erforderlich sind, und es wird stark empfohlen, die Form und das recaptchadiv nur zu ändern, wenn Sie sich sicher sind, was Sie tun. Es gibt drei echos innerhalb der Seite selbst. Diese werden vom Webserver verwendet, um den CAPTCHA-Typ und die Schlüssel zu individualisieren und beliebige Abfragezeichen zu spezifizieren. Jenseits dieser erforderlichen Attribute ist alles anders veränderbar. Wie bereits erwähnt, bitte Sie sicher, dass Sie Backups der Standardseite und Ihrer angepassten Seite haben. Bitte beachten Sie, dass die .shtml-Erweiterung erforderlich ist, um die vom LSWS konfigurierten Typ und Schlüssel zu verwenden.

Hinzufügen von Headern zur CAPTCHA-Seite¶
Sie können die Headern auf der CAPTCHA-Seite anpassen. Dazu fügen Sie eine statische Kontext-Konfiguration mit der URL /.lsrecap/ hinzu, dann fügen Sie den gewünschten Antwortheader für diesen Kontext hinzu, wie folgt:

<IfModule LiteSpeed>
<Location "/.lsrecap/">
Header set Access-Control-Allow-Origin "*"
</Location>
</IfModule>

Dieser Snippet kann nicht in .htaccess hinzugefügt werden.

Kontext, wie folgt:
<IfModule LiteSpeed>
<Location "/.lsrecap/">
Header set Access-Control-Allow-Origin "*"
</Location>
</IfModule>
Dieser Satz kann nicht in .htaccess hinzugefügt werden. Er muss entweder in eine Apache Konfigurationsdatei hinzugefügt werden, oder über die WebAdmin Console für einen LSWS Native virtuellen Host.

Beispiel:
Um einen CORS-Header auf der CAPTCHA-Seite in einem WHM/cPanel-Umgebung hinzuzufügen:
Füge einen <Location "/.lsrecap/">-Kontext zu einem globalen Include-File bei /etc/apache2/conf.d/userdata/lsrecaptcha.conf hinzu, um die Anpassung auf alle virtuellen Hosts anzuwenden.
Füge einen <Location "/.lsrecap/">-Kontext zu einem virtuellen Host Include bei /etc/apache2/conf.d/userdata/ssl/2_4/$USER/example.com/lsrecaptcha.conf hinzu, um die Anpassung nur auf den virtuellen Host $USER anzuwenden.

Stelle deine eigene Site-Schlüssel ein¶
Du kannst deinen eigenen reCAPTCHA-Schlüssel einstellen und die Konfiguration anpassen, wie du es möchtest, von der Google developer reCAPTCHA-Seite.

Tipps:
Bei der Anmeldung für deinen eigenen Schlüssel melde dich bei reCAPTCHA v2 an, nicht bei v3. Die Art der Client-Verifikation wird vollständig durch die reCAPTCHA-Dienstseite von Google bestimmt. Wenn du die Wahl zwischen einem Checkbox oder einem unsichtbaren Logo hat, kannst du deine eigene Vorliebe wählen. Beachte, dass das unsichtbare Typ manchmal eine schwierige Rätselaufgabe zeigen kann. Für server-weite Schutz, der viele Domains abdeckt, deaktiviere bitte "Urheber des reCAPTCHA-Lösungsprüfens überprüfen". Andernfalls müssen Sie möglicherweise einen separaten Schlüssel für jedes Domain anwenden. Bitte beziehe dich auf die Google Dokumentation für mehr Information.
