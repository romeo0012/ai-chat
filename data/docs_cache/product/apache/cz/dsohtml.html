Apache HTTP Server je modulární program, kde správce může volit funkce, které chce zahrnout do serveru, vybráním sadu modulů. Moduly se kompilují jako Dynamické Soubory Dílčích Objektů (DSOs), které existují odděleně od hlavního souboru httpd binárního souboru. Moduly DSO mohou být kompilovány při vytváření serveru, nebo mohou být kompilovány a přidány později pomocí nástroje Apache Extension Tool (apxs). Alternativně mohou být moduly staticky kompilovány do souboru httpd, když je server vytvářen. Tento dokument popisuje, jak používat moduly DSO a teorii, která je za jejich použití.

Podpora DSO pro načítání jednotlivých modulů Apache httpd je založena na modulu nazvaném mod_so, který musí být staticky kompilován do jádra Apache httpd. Je to jediný modul, který není možné umístit do DSO sám. Všechny ostatní distribuované moduly Apache httpd se pak umístí do DSO. Po kompilaci modulu do DSO s názvem mod_foo.so můžete použít LoadModule direktivu mod_so v souboru httpd.conf k načtení tohoto modulu při spuštění nebo restartu serveru. Budou-li budoucí moduly DSO zakázány, můžete to provést pomocí možnosti configure --enable-mods-static, jak je popsáno v dokumentaci instalace.

Restartuje. Budou vytvářeny sestavy DSO pro jednotlivé moduly možné zakázat pomocí možnosti --enable-mods-static konfiguračního nástroje, jak je popsáno v dokumentaci k instalaci. Chcete-li jednoduše vytvářet soubory DSO pro Apache httpd moduly (zejména pro třetístranné moduly), je k dispozici podporný program nazvaný apxs (APache eXtenSion). Může se použít k vytváření modulů DSO mimo zdrojový strom Apache httpd. Myšlenka je jednoduchá: Při instalaci Apache HTTP Serveru je procedura make install konfiguračního nástroje instaluje Apache httpd hlavičky C a umístí platformově závislé kompilátorské a linkerské příkazy pro vytváření souborů DSO do programu apxs. Tímto způsobem může uživatel použít apxs k kompilaci svých zdrojů modulu Apache httpd bez Apache httpd distribuce zdrojového stromu a bez nutnosti se zabývat platformově závislými kompilátorskými a linkerskými příkazy pro podporu DSO.

Základ ¶ Na moderních derivátech Unixu existuje mechanismus nazvaný dynamické vytahování/nahrávání Dynamic Shared Objects (DSO), který poskytuje způsob vytvoření kusu programového kódu v určitém formátu pro nahrání do adresního prostoru spustitelného programu v době běhu. Toto nahrání se obvykle provádí buď automaticky systémovým programem nazvaným ld.so při spuštění spustitelného programu nebo ručně z programu běžícího prostřednictvím programového rozhraní systému Unix k nahrání DSO prostřednictvím systémových volání dlopen()/dlsym(). V prvním případě se DSO's obvykle nazývají sdílené knihovny nebo DSO knihovny a jmenují se libfoo.

systémové volání dlopen()/dlsym(). V první metodě se obvykle označují DSO'y za společné knihovny nebo DSO knihovny a nazývají se libfoo.so nebo libfoo.so.1.2. Nacházejí se v systémovém adresáři (obvykle /usr/lib) a odkaz na spustitelný program se vytváří při sestavování pomocí zadání -lfoo do příkazu linkeru. Tímto způsobem se odkazy na knihovnu do spustitelného souboru zahřívají do souboru, takže při spuštění Unix nahrávač může nalézt libfoo.so v /usr/lib, v cestách zahřívaných pomocí linkerových možností jako -R nebo v cestách nakonfigurovaných prostřednictvím prostředíové proměnné LD_LIBRARY_PATH. Poté vyřeší jakékoliv (ještě nevyřešené) symboly v spustitelném souboru, které jsou k dispozici v DSO. Symboly v spustitelném souboru jsou obvykle neodkazovány na DSO (protože jde o obecnou knihovnu kódu, která může být znovu použita), a proto nemusí být provedeno žádné další vyřešování. Spustitelný soubor nemá žádné nutnosti provést samostatně, aby mohl použít symboly z DSO, protože celé vyřešování je provedeno Unix nahrávačem. (Fakticky, kód k volání ld.so je součástí kódu spuštění, který je propojen do každého spustitelného souboru, který byl vytvořen bez statického vazby). Výhodou dynamického načítání společného kódu je patrná: kód potřebuje být uložen pouze jednou, v systémové knihovně jako libc.so, což zachraňuje místo na disku pro každý program. V druhé metodě se obvykle označují DSO'y za společné objekty nebo DSO soubory a mohou být pojmenovány libovolnou rozšířenou cestou (avšak obvyklé jméno je foo.so).

Tento text se nazývá sdílené objekty nebo soubory DSO a mohou být pojmenovány libovolnou rozšířenou (avšak standardní název je foo.so). Tyto soubory se obvykle nacházejí v adresáři určitého programu a není zde automaticky zřízena odkazující na spustitelný program, kde jsou použity. Místo toho se spustitelný program ručně načte DSO do svého prostoru adresy v době běhu pomocí dlopen(). V době načtení se žádné symboly z DSO neodrazují pro spustitelný program. Místo toho se automaticky odrazují symboly z DSO z množiny symbolů exportovaných spustitelným programem a jeho již nahránými knihovnami DSO (zejména všechny symboly z ubiquitous libc.so). Tímto způsobem získává DSO poznání symbolové množiny spustitelného programu jako by bylo staticky spojeno s ním od počátku. Konečně, aby se využilo API DSO, musí spustitelný program odrazit určité symboly z DSO pomocí dlsym() pro pozdější použití v tabulkách rozvržení apod. V podstatě: Spustitelný program musí ručně odrazit každý symbol, který potřebuje, aby ho mohl použít. Výhodou tohoto mechanismu je, že nezbytné části programu se nenacházejí (a tedy nevyžívají paměť) až do chvíle, než je potřeba programu v otázce. Ačkoli tento mechanismus DSO (Dynamic Shared Object) znějí jednoduchý, je zde alespoň jedna obtížná kročka: Resolvování symbolů z exekutáblního programu pro DSO při použití DSO k rozšíření programu (druhý způsob). Proč? Protože "zpětné resolvování" symbolů DSO z množiny symbolů exekutáblního programu je proti návrhu knihovny (kde knihovna nemá žádné znalosti o programech, které používá) a není k dispozici na všech platformách ani standardizováno. V praxi bývají globalní symboly exekutáblního programu často znovuexportovány a tak nedostupné pro použití v DSO. Řešením hlavního problému, který musí být řešen při použití DSO k rozšíření programu v režimu běhu, je nalézt způsob, jak si linker donutit, aby exportoval všechny globální symboly. Přístup knihovny je typický, protože to je to, co bylo DSO mechanismu navrženo, a proto se používá pro většinu typů knihoven, které poskytuje operační systém.

Výhody a nevýhody ¶ Výše uvedené funkce DSO mají následující výhody: Serverový balíček je flexibilnější v režimu běhu, protože serverový proces může být sestaven v režimu běhu pomocí direktiv konfiguračního souboru httpd.conf LoadModule namísto možností konfigurace při sestavování. Například tímto způsobem je možné spustit různé instance serveru (standardní a SSL verze, minimalistická a dynamická verze [mod_perl, mod_php], atd.).

Jedna z možností je možné spustit různé instance serveru (standardní a SSL verze, minimalistická a dynamická verze [mod_perl, mod_php], atd.) s použitím jediné instalace Apache httpd. Balíček serveru lze snadno rozšířit o třetístrané moduly i po instalaci. Tato výhoda je pro výrobce balíčků velkou výhodou, kteří mohou vytvořit Apache httpd jádro balíček a další balíčky obsahující rozšíření jako PHP, mod_perl, mod_security atd. Výhodou je snadnější prototypování Apache httpd modulů, protože pomocí páru DSO/apxs můžete pracovat mimo Apache httpd zdrojový strom a potřebujete pouze apxs -i příkaz následovaný apachectl restartem, aby se do běžícího Apache HTTP Server dostala nová verze vašeho aktuálně vytvářeného modulu. DSO má následující nevýhody: Server je asi o 20% pomalejší při spuštění, protože musí odolat nákladům symbolového rozlišování, které Unix loader musí nyní provádět. Server je asi o 5% pomalejší při běhu na některých platformách, protože position independent code (PIC) někdy potřebuje složité assembler tricks pro relativní adresování, které nejsou nutně tak rychlé jako absolutní adresování. DSO moduly se nemohou vytvářet jako linkované proti jiným DSO-závislým knihovnám (ld -lfoo) na všech platformách (například a.out-základní platformy obvykle neposkytují tuto funkionalitu, zatímco ELF-základní platformy to dělají).

Tedy nelze použít DSO mechanismus pro všechny typy modulů. V jiných slovích, moduly složené jako soubory DSO jsou omezeny pouze na použití symbolů z Apache httpd jádra, z knihovny C (libc) a všech jiných dynamických nebo statických knihoven používaných Apache httpd jádrem, nebo z archivů statických knihoven (libfoo.a) obsahujících position independent code. Jediné šance na použití jiného kódu je buďto zajistit, že httpd jádro už obsahuje odkaz na něj, nebo nahrání kódu samotným dlopen().
