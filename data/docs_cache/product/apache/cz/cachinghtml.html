Třístavový RFC2616 HTTP zacházení Složky: mod_cache a jeho moduly poskytovatele poskytují inteligentní, HTTP-vědomé zacházení. Samotné obsahy jsou uloženy do zacházení, a mod_cache se snaží respektovat všechny různé HTTP hlavičky a možnosti, které ovlivňují zachovávatelnost obsahu, jak je popisováno v RFC 2616. Protokol HTTP obsahuje vlastní podporu pro mechanismus vnitřního zachování RFC 2616, a mod_cache modul může být použit k využití tohoto. Rozdíl mezi jednoduchým dvoustavovým klíč/hodnotovým zachováním, kde obsah vymizí úplně, když již není nový, je v tom, že HTTP zachování zahrnuje mechanismus k uchování starého obsahu, a k tomu, aby požadavek na původní server mohl požádat, zda tento starý obsah se změnil a pokud ne, aby se stal nový znovu. Záznam v HTTP zachování existuje v jednom z tří stavů:

  • Nový Pokud je obsah nový dostatečně (mladší než jeho životnost), je považován za nový. HTTP zachování je volno, aby služba poskytla nový obsah bez žádných volání k původnímu serveru vůbec.

Nový. HTTP kachna může sloužit nové obsah bez provedení žádostí k původnímu serveru vůbec. Zastaralý Pokud je obsah příliš starý (starší než jeho životnost), považuje se za zastaralý. HTTP kachna by měla kontaktovat původní server a zkontrolovat, zda je obsah ještě aktuální, než ho poskytne klientovi. Původní server buď odpoví s náhradním obsahem, pokud není ještě platný, nebo ideálně odpoví s kódem, aby kachna věděla, že obsah je ještě aktuální, bez nutnosti vytvářet nebo posílat obsah znovu. Obsah se stává nový znovu a cyklus pokračuje. HTTP protokol umožňuje kachně sloužit zastaralé data pod určitými okolnostmi, například když pokus o aktualizaci dat s původním serverem selhal s chybovým kódem 5xx, nebo když jiná žádost je již v procesu aktualizace daného vstupu. V těchto případech se přidá hlavička Warning do odpovědi. Neexistující Pokud se kachna naplní, rezervuje si možnost odstranit obsah z kachny, aby vytvořila místo. Obsah může být odstraněn kdykoliv, a může být zastaralý nebo nový. Nástroj htcacheclean může být spuštěn jednou, nebo nasazen jako daemon, aby velikost kachny zůstala v daném rozsahu, nebo daný počet inodů. Nástroj pokusí se odebrat zastaralé obsah před odebráním nového obsahu. Detaily, jak funguje HTTP kachování, mohou být nalezeny v RFC 2616.

Fáze rychlého zpracování
Tato fáze se odehrává velmi brzo během zpracování žádosti, krátce po parsování žádosti. Pokud je obsah nalezen v paměti, je okamžitě poslán a většina zpracování žádosti je obejmována. V tomto scénáři se chová jako by se paměť připojila k přednímu části serveru. Tento režim nabízí nejlepší výkon, protože většina zpracování serveru je obejmována. Tento režim však také obejímá fáze ověřování a autorizace serveru, takže by měl být volen s opatrností, když to je důležité. Žádosti s hlavičkou "Authorization" (například HTTP Basic Authentication) nejsou uložitelné do paměti ani z ní posílány, když mod_cache běží v této fázi.

Běžná fáze zpracování
Tato fáze se odehrává pozdě v zpracování žádosti, po dokončení všech fází žádosti. V tomto scénáři se chová jako by se paměť připojila k zadní části serveru. Tento režim nabízí největší flexibilnost, protože existuje možnost, že se ukládání může stát v přesně určeném bodě v řetězci filtrů, a uložený obsah může být filtrován nebo osobně přizpůsoben před tím, než je odeslán klientovi.

Všimněte si, že technické termíny, kódy, příkazy, cesty k souborům, adresy URL a formátování zůstávají v původní anglické podobě.

Kontrolní bod v řetězci filtrů, a obsah uložený v cache může být filtrován nebo osobnalizován před tím, než bude odeslán na klienta. Pokud URL není v cache nalezena, mod_cache přidá filtr do zásobníku filtrů, aby odpověď uložil do cache, a poté se odpojil, aby se mohla pokračovat v obyčejném zpracování požadavku. Pokud obsah je určen jako uložitelný, obsah se uloží do cache pro budoucí poskytování, jinak se ignoruje. Pokud v cache nalezený obsah je zastaralý, modul mod_cache konvertovat požadavek na podmíněný požadavek. Pokud server původu odpoví normální odpovědí, normální odpověď se uloží do cache, nahrazující obsah již uložený v cache. Pokud server původu odpoví s odpovědí 304 Neupraveno, obsah je označen jako nový znovu, a místo toho, aby se uložil, se služba filtru poskytne zastaralý obsah.

Zlepšení počtu zásahů do cache, když je virtuální host znám pod jedním z mnoha různých serverových aliasů, nastavení UseCanonicalName na On může výrazně zlepšit poměr zásahů do cache. To je proto, že jméno virtuálního hostu sloužícího obsah je používáno v klíči cache. S nastavením na On virtuální hosty s více serverovými jmény nebo aliasy nevytváří různé entity uložené v cache, a místo toho se obsah bude ukládat podle kanonického jména hostitele.

Životnost Platnost obsahu, který je určen k uložení do mezipaměti, by měl být explicitně deklarován pomocí polí Cache-Control hlavičky max-age nebo s-maxage, nebo pomocí vložení hlavičky Expires. Ve stejné době může definovaná životnost obsahu pocházejícího z původního serveru být přepsána klientem, když klient představí vlastní hlavičku Cache-Control v požadavku. V tomto případě vítězí nejmenší životnost platnosti mezi požadavkem a odpovědí. Když je životnost platnosti chybícím z požadavku nebo odpovědi, použije se výchozí životnost platnosti. Výchozí životnost platnosti pro uložené entity je jedna hodina, ale toto může snadno být přepsáno pomocí použití direktivy CacheDefaultExpire. Krátký průvodce podmíněným požadavkem Když obsah vypršuje z mezipaměti a stane se zastaralý, místo toho, aby se přenesl původní požadavek, httpd pozmění požadavek tak, aby byl podmíněný. Když existuje ETag hlavička v původním odpovědi v mezipaměti, mod_cache přidá hlavičku If-None-Match do požadavku na server původu. Když existuje hlavička Last-Modified v původní odpovědi v mezipaměti, mod_cache přidá hlavičku If-Modified-Since do požadavku na server původu. Provedení jednoho z těchto kroků udělá požadavek podmíněný. Když podmíněný požadavek dorazí na server původu, server původu by měl kontrolovat, zda ETag nebo Last-Modified parametr se změnil, v souladu s požadavkem. Pokud ne, server by měl odpovědět terzní "304 Not Modified" odpovědí. Tato signálizuje mezipaměti, že zastaralý obsah je ještě aktuální a by měl být použit pro další požadavky, dokud se nová životnost novosti nedosáhne znovu. Pokud obsah změnil, pak obsah je poskytnut jako by požadavek nebyl podmíněný od počátku. Podmíněné požadavky nabízejí dvě výhody. První, když se takto požadavek odesílá na server původu, pokud obsah z serveru odpovídá obsahu v mezipaměti, to může být snadno určeno a bez nákladu na přenos celého zdroje.

Zapnutí kachování

Kachování k disku modul mod_cache vyžaduje konkrétní implementace back-endového úložiště k řízení kachování, a pro kachování na disk mod_cache_disk je poskytován k tomu. Obvykle bude konfigurován takto;

CacheRoot "/var/cache/apache/"
CacheEnable disk /
CacheDirLevels 2
CacheDirLength 1

Důležité je, že uložené soubory jsou místně uloženy, takže obvykle se aplikuje operační systém v paměti k jejich přístupu také.

Důležité je, že uložené soubory jsou místně uloženy, takže obvykle se při jejich přístupu aplikuje operační systém v paměti. Takže i když soubory jsou uloženy na disk, pokud jsou často přístupována, je pravděpodobné, že operační systém zajistí, aby byly skutečně poskytovány z paměti. Rozumění Cache-Store Pro uložení položek do mezipaměti vytváří mod_cache_disk 22 znakový hash adresy URL, která je požadována. Tento hash zahrnuje hostitele, protokol, port, cestu a jakékoli CGI argumenty URL, stejně jako prvky definované hlavičkou Vary, aby se zajistilo, že se různé URL nezakolísají. Každý znak může být jakýkoli z 64 různých znaků, což znamená, že celkový počet možných hashů je 64^22. Například URL může být hashována na xyTGxSMO2b68mBCykqkp1w. Tento hash se používá jako předpona pro pojmenování souborů specifických pro tuto URL v mezipaměti, ale nejprve je rozdělen do adresářů podle příkazů CacheDirLevels a CacheDirLength. CacheDirLevels určuje, kolik úrovní podadresářů by mělo být, a CacheDirLength určuje, kolik znaků by mělo být v každém adresáři. S uvedenými výchozími nastaveními by se hash stal názvem prefixu souboru jako /var/cache/apache/x/y/TGxSMO2b68mBCykqkp1w. Cílem této techniky je snížit počet podadresářů nebo souborů, které mohou být v určitém adresáři, protože většina soustav souborů se pomalu zpomaluje, když tento počet roste.

Na systémech, kde otevírání souborů je pomalé, existuje možnost otevřít soubor na spuštění a uložit file handle. Tyto možnosti mohou pomoci na systémech, kde je přístup k statickým souborům pomalý. CacheFile Deska uložení souborů nejzákladnějšího typu v httpd je cache file-handle poskytnutá mod_file_cache. Místo toho, aby se ukládaly obsahy souborů, tuto cache udržuje tabulku file descriptors.

Je poskytnut cachování souborových dekriptorů pomocí mod_file_cache. Rozdíl mezi tímto cachováním a cachováním obsahu souborů spočívá v tom, že tento cache udržuje tabulku otevřených souborových dekriptorů. Soubory, které se mají cachovat v tomto způsobu, se určují v konfiguračním souboru pomocí příkazu CacheFile. Příkaz CacheFile instruuje httpd, aby otevřel soubor při spuštění a použil tento souborový dekriptor pro všechny následující přístupy k tomuto souboru.

Příklad: CacheFile /usr/local/apache2/htdocs/index.html

Pokud plánujete cachovat velké množství souborů v tomto způsobu, musíte se ujistit, že je nastavený správný limit počtu otevřených souborů v operačním systému. Použití příkazu CacheFile nezpůsobí, že se obsah souboru skutečně cachuje, ale znamená, že pokud se soubor změní během běhu httpd, tyto změny nebudou zachyceny. Soubor bude služebně konzistentní jako kdyby byl služebně zahájen při spuštění httpd. Pokud se soubor odstraní během běhu httpd, bude stále udržovat otevřený souborový dekriptor a služebně poskytovat soubor jako kdyby byl služebně zahájen při spuštění httpd. To znamená, že i když soubor bude odstraněn a nebude se zobrazovat v systému souborů, nebude se získáno žádné volné místo až do zastavení httpd a zavření souborového dekriptoru.

Pokud požadavky na uživatele mohou být slouženy z cache, samotná cache může být cílem těch, kteří chtějí deface nebo zasahat do obsahu. Důležité je si uvědomit, že cache musí vždy být psatelné uživatelem, který běží httpd. Toto je v rozporu s obvykle doporučenou situací, kdy se všechno obsahuje nepsatelné uživatelem Apache. Pokud je uživatel Apache kompromitován, například prostřednictvím chyby v procesu CGI, je možné, že cache bude cílem. Při použití mod_cache_disk je relativně snadné vložit nebo upravit zachovanou entitu v cache. Tento představuje zvýšený riziko v porovnání s ostatními typy útoků, které je možné provést jako uživatel Apache. Pokud používáte mod_cache_disk, budete si to vědomi - ujistěte se, že aktualizujete httpd při oznámení o zlepšení zabezpečení a spouštíte procesy CGI jako ne-Apache uživatele pomocí suEXEC, pokud to možno. Otrávení cache
Pokud běžíte httpd jako caching proxy server, existuje také možnost tzv. otrávení cache. Otrávení cache je široký termín pro útoky, při kterých útočník způsobí proxy serveru, aby získal neprávě (a obvykle nežádoucí) obsah z původního serveru.

Útoky, při kterých útočník způsobí, aby proxy server získal neprávě (a obvykle nežádoucí) obsah z původního serveru. Například pokud DNS serverů, které používá vaše systémy s httpd, jsou citlivé na útok DNS cache poisoning, útočník může mít možnost ovládat, kam se připojí httpd při požadavku na obsah z původního serveru. Dalším příkladem je takzvané útoky HTTP request-smuggling. Tento dokument není správným místem pro hlubokou diskusi o HTTP request smuggling (místo toho použijte svůj oblíbený vyhledávač), ale je důležité si uvědomit, že je možné vytvořit řadu požadavků a využít chyby na původním webserveru tak, aby útočník mohl celý obsah získat prostřednictvím proxy.

Záměrný záměr / Cachebusting
Mechánismus Vary umožňuje uložit více variant stejného URL do cache po boku. Podle hodnot hlaviček poskytovaných klientem vybere cache správnou variantu k návratu klientovi. Tento mechanismus může být problém, když se pokusíte variovat na hlavičce, která je známá jako obsahuje široký rozsah možných hodnot běžnou použití, například hlavička User-Agent. Podle popularity daného webu mohou být vytvořeny tisíce nebo miliony duplikátů cache vstupů pro stejný URL, které zatěžují ostatní vstupy v cache.

V některých případech může být nutné změnit URL určitého prostředku na každý požadavek, obvykle přidáním řetězce "cachebuster" do URL. Pokud je tento obsah deklarován jako uložitelný serverem pro významnou dobu platnosti, tyto vstupy mohou zatěžovat legitimní vstupy v cache. Ačkoli mod_cache poskytuje direktivu CacheIgnoreURLSessionIdentifiers, tato direktiva by měla být používána s opatrností, aby se nedostaly stejné záměry na proxy nebo na cache prohlížeče.
