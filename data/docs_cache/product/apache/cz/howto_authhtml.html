Letting more than one person in ¶ The directives above only let one person (specifically someone with a username of rbowen) into the directory. In most cases, you'll want to let more than one person in. This is where the AuthGroupFile comes in. If you want to let more than one person in, you'll need to create a group file that associates group names with a list of users in that group. The format of this file is pretty simple, and you can create it with your favorite editor. The contents of the file will look like this: GroupName: rbowen dpitts sungo rshersey That's just a list of the members of the group in a long line separated by spaces. To add a user to your already existing password file, type: htpasswd /usr/local/apache/passwd/passwords dpitts You'll get the same response as before, but it will be appended to the existing file, rather than creating a new file. (It's the -c that makes it create a new password file). Now, you need to modify your .htaccess file to use the AuthGroupFile and Require directives. Here's an example:

AuthType Basic
AuthName "Restricted Area"
AuthUserFile /usr/local/apache/passwd/passwords
AuthGroupFile /usr/local/apache/passwd/groupfile
Require group mygroup

In this example, the "mygroup" group is defined in the group file, and the user "dpitts" is a member of that group. When a user tries to access the restricted area, they will be prompted for a username and password. If they enter a valid username and password that is associated with a member of the "mygroup" group, they will be granted access. If they don't, they will be denied access.

The .htaccess file is a powerful tool for controlling access to your web server. It can be used to restrict access to certain files or directories, as well as to set various other options for your server. In this section, we'll focus on using the .htaccess file to control access to your files and directories.

First, let's talk about the basic syntax of the .htaccess file. The file consists of a series of directives, each of which starts with the name of the directive followed by a space and the options for that directive. For example:

Options FollowSymLinks

This directive tells the server to follow symbolic links in the directory.

The most important directive for controlling access is the "Require" directive. This directive specifies the conditions that must be met for a user to access a file or directory. For example:

Require user rbowen

This directive specifies that only the user "rbowen" can access the file or directory.

You can also use the "Require group" directive to restrict access to a group of users. For example:

Require group mygroup

This directive specifies that only users who are members of the "mygroup" group can access the file or directory.

You can also use the "Require valid-user" directive to require a valid username and password for access. This is useful if you want to restrict access to a file or directory to authenticated users only.

Here's an example of how you might use these directives to restrict access to a directory:

&lt;Directory /path/to/mydirectory&gt;
  Options FollowSymLinks
  Require valid-user
  Require group mygroup
&lt;/Directory&gt;

In this example, the "mydirectory" directory is restricted to authenticated users who are members of the "mygroup" group. If a user tries to access the directory without being authenticated or without being a member of the "mygroup" group, they will be denied access.

You can also use the "Satisfy" directive to specify multiple conditions that must be met for access to be granted. For example:

&lt;Directory /path/to/mydirectory&gt;
  Options FollowSymLinks
  Satisfy All
  Require valid-user
  Require group mygroup
&lt;/Directory&gt;

In this example, access to the "mydirectory" directory is granted only if the user is authenticated and is a member of the "mygroup" group. If either condition is not met, access is denied.

You can also use the "Deny" and "Allow" directives to specify which users or groups are allowed or denied access. For example:

Použití více poskytovatelů ¶
S vstoupením nové architektury poskytovatelů autentizace a autorizace se vám už nedá zablokovat pouze jedna metoda autentizace nebo autorizace. Fakticky můžete libovolný počet poskytovatelů smíchat a kombinovat, aby vám poskytly právě ten schéma, které potřebujete. Následující příklad ukazuje použití obou poskytovatelů autentizace na základě souboru a LDAP.
<Directory "/www/docs/private">
AuthName "Private"
AuthType Basic
AuthBasicProvider file ldap
AuthUserFile "/usr/local/apache/passwd/passwords"
AuthLDAPURL ldap://ldaphost/o=yourorg
Require valid-user
</Directory>
V tomto příkladu se poskytovatel souboru pokusí autentizovat uživatele nejprve. Pokud není schopen autentizovat uživatele, bude volán poskytovatel LDAP. Tímto způsobem se rozšiřuje oblast autentizace, pokud vaše organizace implementuje více než jeden typ úložiště autentizace. Další scénáře autentizace a autorizace mohou zahrnovat smíchání jednoho typu autentizace s jiným typem autorizace. Například autentizaci proti souboru složky, ale autorizaci proti adresáři LDAP. Stejně jako mohou být implementovány více poskytovatelů autentizace, mohou být také použity více metod autorizace.

V Apache 2.2 byl zaveden mechanismus autentizace na základě poskytovatelů, aby se proces autentizace rozdělil od autorizace a podpůrného hardware. Tento stejný mechanismus autentizace byl přenesen i do autorizace. To znamená, že příkaz Require nejen určuje, které metody autorizace by měly být použity, ale také určuje pořadí, v kterém jsou volány. Řízení přístupu zpětně kompatibilní
Řada vedlejších efektů přijetí mechanismu pro autorizaci na základě poskytovatelů je to, že předchozí direktivy pro řízení přístupu Order, Allow, Deny a Satisfy již nejsou potřeba. Pro poskytnutí zpětné kompatibility pro starší konfigurace byly tyto direktivy přesunuty do modulu mod_access_compat. Poznámka Direktivy poskytované mod_access_compat byly deprekovány mod_authz_host. Použití starých direktiv jako Order, Allow nebo Deny se s novými, jako Require, kombinovat je technicky možné, ale není doporučeno. Modul mod_access_compat vznikl k podpoře konfigurací obsahujících pouze staré direktivy k podpoře upgrade na 2.4. Další informace najdete v průvodci upgrade.
