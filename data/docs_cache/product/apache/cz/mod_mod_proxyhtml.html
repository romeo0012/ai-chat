Proxies/Brány ¶ Apache HTTP Server může být konfigurován v obou režimech předávaného a zpětného proxy (nebo brány). Běžný předávaný proxy je intermediární server, který se nachází mezi klientem a původním serverem. Chceme-li získat obsah z původního serveru, odesílá klient požadavek na proxy s uvedením původního serveru jako cíle. Poté požadavek obsahu odesílá proxy na původní server a vrátí ho klientovi. Klient musí být speciálně nakonfigurován, aby mohl přes proxy přistupovat k ostatním stránkám. Typickým použitím předávaného proxy je poskytnutí přístupu k Internetu vnitřním klientům, které jinak bývají omezeny požadavky firewallu. Předávaný proxy může také využívat uchovávání (jako poskytuje mod_cache) k snížení zatížení sítě. Předávaný proxy je aktivován pomocí příkazu ProxyRequests. Protože předávané proxies umožňují klientům přístup k libovolným stránkám prostřednictvím vašeho serveru a skrývat jejich skutečnou identitu, je nutné zajistit, aby byl váš server bezpečný tak, aby mohly přístup k proxy pouze autorizované klienty, než aktivujete předávaný proxy. Zpětný proxy (nebo brána), na rozdíl od toho, se klientovi zobrazí jako běžný webový server. Na klienta není nutné žádné speciální konfigurace. Klient vysílá běžné požadavky na obsah v oblasti zpětného proxy. Zpětný proxy pak rozhodne, kam poslat tyto požadavky, a vrátí obsah jako by se jednalo o vlastní původ.

Překlad:

Zvratný proxy rozhodne, kam poslat tyto požadavky a vrátí obsah jako by se jednalo o původní zdroj. Běžným použitím zvratného proxy je poskytnutí internetovým uživatelům přístupu k serveru, který je za bránou firewall. Zvratné proxies mohou být také použity k rovnoměrnému rozdělení zátěže mezi několika zadními serverem nebo k uložení do mezipaměti pro pomalejší zadní server. Dále mohou být zvratné proxies použity pro připojení několika serverů do stejného URL prostoru. Zvratný proxy je aktivován pomocí příkazu ProxyPass nebo [P] znaku k příkazu RewriteRule. Není nutné zapnout ProxyRequests, aby se konfiguroval zvratný proxy. Základní příklady ¶ Následující příklady představují pouze velmi základní myšlenku, aby vás pomohly začít. ¶ Průchodce spravuje konfiguraci zdrojových serverů a jejich komunikační parametry v objektech zvaných pracovníci. Je zde dvě vbudovaná pracovníci: výchozí pracovníci pro předávací proxy a výchozí pracovníci pro reverzní proxy. Další pracovníci mohou být explicitně konfigurovány. Dva výchozí pracovníci mají pevnou konfiguraci a budou použity, pokud žádný jiný pracovník neodpovídá požadavku. Nejsou používány HTTP Zachovávejte si živou relaci nebo přeužití spojení. TCP spojení s zdrojovým serverem budou otevíráná a zavíráná pro každý požadavek. Explicitně konfigurované pracovníci jsou identifikovány svou URL. Obvykle je vytvořen a konfigurován pomocí ProxyPass nebo ProxyPassMatch, když se používá pro reverzní proxy: ProxyPass "/příklad" "http://zadna.příklad.cz" connectiontimeout=5 timeout=30
Toto vytvoří pracovníka spojený s URL zdrojového serveru http://zadna.příklad.cz, který bude používat dané časové limity. Když se používá v předávacím proxy, pracovníci jsou obvykle definovány prostřednictvím příkazu ProxySet: ProxySet "http://zadna.příklad.cz"
Pracovníci definované prostřednictvím příkazu ProxySet se používají v předávacím proxy.

Přeloženo text:

Následující časové limity. Při použití v předchozích proxy pracovníci obvykle definují pomocí direktivy ProxySet: ProxySet "http://backend.example.com" connectiontimeout=5 timeout=30 nebo alternativně pomocí Proxy a ProxySet:

<Proxy "http://backend.example.com"> ProxySet connectiontimeout=5 timeout=30 </Proxy>

Použití explicitně konfigurovaných pracovníků v režimu předchozího není příliš běžné, protože předchozí proxy obvykle komunikují s mnoha různými původními servery. Vytvoření explicitních pracovníků pro některé z původních serverů může být užitečné, pokud jsou často používány. Explicitně konfigurovaní pracovníci nemají žádný koncept předchozího nebo zpětného proxyování samy o sobě. Zabírají společný koncept komunikace s původními servery. Pracovník vytvořený ProxyPass pro použití v zpětném proxy se použije pro požadavky předchozího proxy, pokud URL k původnímu serveru odpovídá URL pracovníka, a to obráceně. URL identifikující přímo pracovníka je URL jeho původního serveru s jakýkoli součástmi cesty, které byly uděleny:

ProxyPass "/examples" "http://backend.example.com/examples"
ProxyPass "/docs" "http://backend.example.com/docs"

Tento příklad definuje dva různé pracovníky, každý s vlastními připojovacími pooly a konfigurací.

Sdílení pracovníků

Sdílení pracovníků nastane, pokud se URL pracovníků překrývají, což nastane, když URL nějakého pracovníka je předchozí podřetěz URL jiného pracovníka definovaného později v konfiguračním souboru. V následujícím příkladu ProxyPass "/apps" "http://backend.example.com/apps"

V následujícím příkladu se sdílí pracovník pro adresář "/apps", protože URL pracovníka "/apps" je předchozí podřetěz URL pracovníka "/apps/api".

<Location "/apps">
ProxyPass "http://backend.example.com/apps"
</Location>
<Location "/apps/api">
ProxyPass "http://backend.example.com/apps/api"
</Location>

V tomto příkladu se pracovník pro adresář "/apps" sdílí s pracovníkem pro adresář "/apps/api", protože URL pracovníka "/apps" je předchozí podřetěz URL pracovníka "/apps/api".

Část adresy URL jiného pracovníka, definovaného později v konfiguračním souboru. V následujícím příkladu ProxyPass "/apps" "http://backend.example.com/" timeout=60 ProxyPass "/příklady" "http://backend.example.com/příklady" timeout=10 v případě, že se druhý pracovník skutečně nevytvoří, je místo toho použit první pracovník. Výhoda spočívá v tom, že existuje jen jeden pool spojení, takže spojení se častěji opakují. Upozornění, že všechny atributy konfigurace, které jsou pro pozdějšího pracovníka explicitně zadány, budou ignorovány. Toto se zaznamená jako varování. V příkladu výše bude hodnota timeout pro adresu URL /příklady 60 místo 10! Pokud chcete zabránit sdílení pracovníků, řazte definice pracovníků podle délky adresy URL, začínaje nejdelšími adresami URL pracovníků. Pokud chcete maximálně zvýšit sdílení pracovníků, použijte opačnou řazení. Viz také varování související s řazením příkazů ProxyPass. Pracovníci explicitně definované přijímají dva typy: přímo pracující pracovníci a (balancující) pracovníci. Podporují mnoho důležitých atributů konfigurace, které jsou popsány níže v příkazu ProxyPass. Stejné atributy mohou být nastaveny pomocí ProxySet. Množina dostupných možností pro přímo pracujícího pracovníka závisí na protokolu, který je zadán v adrese URL serveru původu. Dostupné protokoly zahrnují ajp, fcgi, ftp, http a scgi. Balancující pracovníci jsou virtuální pracovníci, které používají pracovníky známé jako jejich členové k skutečnému zpracování požadavků. Každý balancující může mít více členů.

Změny protokolu ¶ Pro případy, kdy mod_proxy posílá požadavky na původní server, který neimplikuje správně udržování připojení nebo HTTP/1.1, existují dvě proměnné prostředí, které mohou nutilit požadavek použít HTTP/1.0 bez udržování připojení. </Location>

Při přesměrování těchto požadavků na server původu, mod_proxy_http vždy pokusí se odeslat Content-Length. ProxyVia Direktivu ¶ Popis: Informace poskytované v poli Via HTTP odpovědi pro požadavky na proxy Syntax: ProxyVia On|Off|Full|Block Výchozí hodnota: ProxyVia Off Kontext: Konfigurace serveru, virtuální host Status: Rozšířený Modul: mod_proxy Tento příkaz ovládá použití polí Via: HTTP serverem proxy. Jeho účel je ovládat proud požadavků na proxy přes řetěz proxy serverů. Viz RFC 2616 (HTTP/1.1), část 14.45 pro vysvětlení polí Via: header. Pokud je nastaveno na Off, což je výchozí hodnota, není provedeno žádné zvláštní zpracování. Pokud požadavek nebo odpověď obsahuje polí Via:, je to přenášeno bez změny. Pokud je nastaveno na On, každý požadavek a odpověď dostane polí Via: header novou řádkovou položku pro aktuální host. Pokud je nastaveno na Full, každá generovaná polí Via: headerová položka bude navíc mít ukázanou verzi serveru Apache httpd jako komentářový pole polí Via:.

Pokud je nastaveno na Block, každý požadavek na proxy bude mít všechna polí Via: headerová pole odstraněna. Žádné nové polí Via: nebude vytvořeno.
