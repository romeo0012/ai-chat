Dynamische Shared Object (DSO) Unterstützung Verfügbare Sprachen: en | fr | ja | ko | tr Der Apache HTTP-Server ist ein modularer Programm, bei dem der Administrator die zu integrierende Funktionalität auswählen kann, indem er eine Menge von Modulen auswählt. Modulen werden als Dynamische Shared Objects (DSOs) kompiliert, die getrennt von der Hauptdatei httpd binär existieren. DSO-Module können bei der Erstellung des Servers oder später mithilfe des Apache Extension Tools (apxs) kompiliert und hinzugefügt werden. Als Alternative können die Module statisch in die httpd-Binärdatei kompiliert werden, wenn der Server erstellt wird. Dieses Dokument beschreibt, wie DSO-Module verwendet werden, sowie die Theorie hinter ihrer Verwendung.

Verwandte Module/Verzeichnisse

mod_so

Die Unterstützung für das Laden von einzelnen Apache httpd-Modulen basiert auf einem Modul namens mod_so, das statisch in den Apache httpd-Kern kompiliert werden muss. Es ist das einzige Modul neben core, das nicht in eine DSO selbst gesetzt werden kann. Praktisch alle anderen verteilten Apache httpd-Module werden dann in eine DSO gesetzt. Nachdem ein Modul in eine DSO namens mod_foo.so kompiliert wurde, können Sie die LoadModule-Direktive von mod_so in Ihrer httpd.conf-Datei verwenden, um dieses Modul beim Serverstart oder Neustart zu laden. Die DSO-Builds für einzelne Module können über die --enable-mods-static-Option von configure deaktiviert werden, wie im Installationsdokument erläutert.

Um die Erstellung von DSO-Dateien für Apache httpd-Module (insbesondere für Drittanbieter-Module) zu vereinfachen, steht ein Unterstützungsprogramm namens apxs (APache eXtenSion) zur Verfügung. Es kann verwendet werden, um DSO-basierte Module außerhalb des Apache httpd-Quellcode-Verzeichnisses zu bauen. Die Idee ist einfach: Wenn Apache HTTP Server installiert wird, installiert die make install-Prozedur von configure die Apache httpd-C-Header-Dateien und speichert die plattformabhängigen Compiler- und Linker-Flags für die Erstellung von DSO-Dateien in das apxs-Programm. Dadurch kann der Benutzer apxs verwenden, um seine Apache httpd-Modulquellen zu kompilieren, ohne dass das Apache httpd-Verteilungsquellcode-Verzeichnis und ohne die Anpassung der plattformabhängigen Compiler- und Linker-Flags für DSO-Unterstützung benötigt wird. Zusammenfassung ¶ Um Ihnen einen Überblick über die DSO-Funktionen von Apache HTTP Server 2.x zu geben, hier eine kurze und präzise Zusammenfassung:

Erstellen und installieren Sie ein verteiltes Apache httpd-Modul, z.B. mod_foo.c, in eine eigene DSO-Datei mod_foo.so: 

$ ./configure --prefix=/pfad/zu/install --enable-foo
$ make install

Konfigurieren Sie Apache HTTP Server mit allen Modulen aktiviert. Wird nur ein Basisset aktiviert, wenn der Server gestartet wird. Sie können den Set der geladenen Module durch Aktivieren oder Deaktivieren der LoadModule-Direktiven in httpd.conf ändern. 
$ ./configure --enable-mods-shared=all
$ make install

Es gibt Module, die nur für Entwickler interessant sind und nicht gebaut werden.

in httpd.conf. $ ./configure --enable-mods-shared=all $ make install
Einige Module sind nur für Entwickler von Nutzen und werden nicht gebaut. Wenn man das Module nutzt, kann man alles verwenden. Um alle verfügbaren Module, einschließlich Entwickler-Module, zu bauen, verwendet man stattdessen reallyall. Zusätzlich können die LoadModule-Direktiven für alle gebauten Module über die Konfigurationsoption --enable-load-all-modules von configure aktiviert werden. $ ./configure --enable-mods-shared=reallyall --enable-load-all-modules $ make install

Bauen und installieren Sie einen dritten-party Apache httpd-Modul, z.B. mod_foo.c, in eine eigene DSO mod_foo.so außerhalb des Apache httpd-Quellcode-Baumstamms mithilfe von apxs:
$ cd /path/to/3rdparty
apxs -cia mod_foo.c

In allen Fällen muss die kompilierte shared Module-Datei, nachdem sie erstellt wurde, mit einer LoadModule-Direktive in httpd.conf Apache httpd erzwingen, um das Modul zu aktivieren. Weitere Details finden Sie in der apxs-Dokumentation.

Hintergrund ¶
Auf modernen Unix-Abkömmlingen existiert ein Mechanismus namens dynamische Linkung/Laden von Dynamic Shared Objects (DSO), der eine Möglichkeit bietet, ein Stück Programmcode in einer speziellen Formatierung für die Ladezeit in das Adressraum eines ausführenden Programms zu laden. Dieses Laden kann normalerweise in zwei Weisen erfolgen: automatisch durch ein Systemprogramm namens ld.so, wenn ein ausführendes Programm gestartet wird, oder manuell von innerhalb des ausführenden Programms über eine programmgesteuerte System-Schnittstelle zur Unix-Lader durch die Systemaufrufe dlopen()/dlsym(). Im ersten Fall werden die DSO's normalerweise als geteilte Bibliotheken oder DSO-Bibliotheken bezeichnet und mit dem Namen libfoo benannt.

In allen Fällen muss die shared Module-Datei, nachdem sie erstellt wurde, mit einer LoadModule-Direktive in httpd.conf Apache httpd erzwingen, um das Modul zu aktivieren. Weitere Details finden Sie in der apxs-Dokumentation.

systemaufrufe dlopen()/dlsym(). Im ersten Fall werden die DSO's meistens als geteilte Bibliotheken oder DSO-Bibliotheken bezeichnet und mit dem Namen libfoo.so oder libfoo.so.1.2 benannt. Sie befinden sich in einem Systemverzeichnis (meistens /usr/lib) und die Verbindung zum Exekutable-Programm wird bei der Build-Zeit durch Angabe von -lfoo an den Linker-Befehl hergestellt. Dadurch werden Bibliotheksreferenzen in den Exekutable-Programm-Datei hartkodiert, so dass der Unix-Lader bei Startzeit libfoo.so in /usr/lib finden kann, in Pfaden, die durch Linker-Optionen wie -R oder durch die Umgebungsvariable LD_LIBRARY_PATH konfiguriert wurden. Es wird dann alle (noch ungelösten) Symbole im Exekutable-Programm gelöst, die im DSO verfügbar sind. Symbole im Exekutable-Programm werden meistens nicht von dem DSO referenziert (weil es sich um eine allgemeine Code-Bibliothek handelt, die wiederverwendet werden kann) und daher muss kein weiteres Auflösen vorgenommen werden. Das Exekutable-Programm hat keine Notwendigkeit, etwas selbst zu tun, um die Symbole aus dem DSO zu verwenden, weil das komplette Auflösen durch den Unix-Lader vorgenommen wird. (Tatsächlich ist das Code zum Aufruf von ld.so Teil des Laufzeit-Startup-Codes, der in jedem Exekutable-Programm, das nicht statisch gebunden wurde, eingebunden ist). Der Vorteil der dynamischen Ladeung von allgemeiner Bibliotheks-Code ist offensichtlich: das Bibliotheks-Code muss nur einmal gespeichert werden, in einer Systembibliothek wie libc.so, was jedem Programm Speicherplatz einspart. Im zweiten Fall werden die DSO's meistens als geteilte Objekte oder DSO-Dateien bezeichnet und können mit einem beliebigen Erweiterungsbereich benannt werden (allerdings ist der kanonische Name foo.so).

Diese sogenannten geteilten Objekte oder DSO-Dateien können beliebige Erweiterungen tragen (allerdings ist der kanonische Name foo.so). Diese Dateien befinden sich meist in einem Programm-spezifischen Verzeichnis und es wird kein automatisch eingerichteter Link zum ausführenden Programm hergestellt, in dem sie verwendet werden. Stattdessen lädt das ausführende Programm die DSO manuell zur Laufzeit in seinen Adressraum über dlopen() ein. In diesem Moment werden keine Symbole aus der DSO für das ausführende Programm aufgelöst. Stattdessen erledigt der Unix-Lader automatisch die Aufbereitung von noch ungelösten Symbolen in der DSO aus dem Satz von exportierten Symbolen der ausführenden Programm und der bereits geladenen DSO-Bibliotheken (insbesondere alle Symbole aus der allgegenwärtigen libc.so). Dadurch erhält die DSO Kenntnis der Symboltabelle des ausführenden Programms, als ob sie statisch mit ihm verknüpft worden wäre. Schließlich muss das ausführende Programm, um die API der DSO nutzen zu können, bestimmte Symbole aus der DSO über dlsym() aufzulösen, um sie später in Dispatch-Tabellen usw. zu verwenden. In anderen Worten: Das ausführende Programm muss jeden Symbol, den es verwenden kann, manuell aufgelösen. Der Vorteil solcher Mechanismen ist, dass optionaler Programmbereich nicht geladen (und damit kein Speicher verbraucht) wird, bis er vom Programm benötigt wird. Wenn erforderlich, können diese Programmbereiche dynamisch geladen werden, um die Funktionalität des Basisprogramms zu erweitern.

Durch das betreffende Programm. Wenn erforderlich, können diese Programmbestandteile dynamisch geladen werden, um die Funktionalität der Basis-Software zu erweitern. Obwohl dieses DSO-Mechanismus einfach klingt, gibt es mindestens eine schwierige Schritt: Die Auflösung von Symbolen aus dem ausführbaren Programm für das DSO bei der Erweiterung eines Programms (die zweite Methode). Warum? Weil die rückwärts auflösende Symbole aus dem ausführbaren Programm-Symbolset gegen die Bibliotheksdesign (wo die Bibliothek keinerlei Kenntnis von den Programmen hat, die sie verwendet) ist und nicht unter allen Plattformen verfügbar noch standardisiert ist. In der Praxis werden die globalen Symbole des ausführbaren Programms oft nicht erneut exportiert und somit nicht für die Verwendung in einem DSO verfügbar. Die Lösung, den Linker dazu zu zwingen, alle globalen Symbole zu exportieren, ist das Hauptproblem, das man bei der Verwendung von DSO für die run-time-Erweiterung eines Programms zu lösen hat. Der Ansatz mit der shared library ist der typische, weil er das, was das DSO-Mechanismus entwickelt wurde, ist, daher wird er für nahezu alle Arten von Bibliotheken verwendet, die der Betriebssystem bereitgestellt wird. Vorteile und Nachteile ¶ Die oben beschriebenen DSO-basierten Funktionen haben die folgenden Vorteile: Der Server-Paket ist flexibler bei Laufzeit, weil der Server-Prozess anhand von LoadModule httpd.conf Konfigurationsdirektiven statisch zusammengestellt werden kann, anstatt von Build-Zeit-Optionen. So ist es beispielsweise möglich, verschiedene Server-Instanzen (Standard- und SSL-Version, minimalistische und dynamische Version [mod_perl, mod_php], usw.) auszuführen.

Eine Möglichkeit, mehrere Serverinstanzen (Standard- und SSL-Version, minimalistische und dynamische Version [mod_perl, mod_php], usw.) mit nur einer Apache httpd-Installation auszuführen, ist gegeben. Das Server-Paket kann leicht erweitert werden, indem man Drittanbieter-Module nach der Installation hinzufügt. Dies ist ein großer Vorteil für die Verwalter von Vendor-Paketen, die ein Apache httpd-Kernpaket und weitere Pakete mit Erweiterungen wie PHP, mod_perl, mod_security usw. erstellen können. Es ist leichter, Apache httpd-Modulprototypen zu entwickeln, denn mit dem DSO/apxs-Paar können Sie außerhalb des Apache httpd-Quellbaums arbeiten und nur ein apxs -i-Befehl gefolgt von einem apachectl restart benötigen, um eine neue Version Ihrer derzeit entwickelten Modulversion in den laufenden Apache HTTP-Server zu bringen. DSO hat folgende Nachteile: Der Server ist etwa 20% langsamer bei Startzeit, weil er aufgrund des Symbolauflösungs-Overheads, den der Unix-Loader jetzt ausführen muss, langsamer ist. Der Server ist etwa 5% langsamer bei Ausführungszeit auf bestimmten Plattformen, weil position unabhängiges Code (PIC) manchmal komplizierte Assemblertricks für relative Adressierung benötigt, die nicht notwendigerweise so schnell sind wie absolute Adressierung. DSO-Module können auf allen Plattformen (z.B. a.out-basierte Plattformen bieten dieses Funktionalität oft nicht, während ELF-basierte Plattformen es tun) nicht gegen andere DSO-basierte Bibliotheken (ld -lfoo) verknüpft werden. Daraus resultiert, dass Sie das DSO-Mechanismus für alle Arten von Modulen nicht verwenden können. In anderen Worten, Module, die als DSO-Dateien kompiliert wurden, können nur Symbole aus dem Apache httpd-Kern verwenden, aus der C-Bibliothek (libc) und allen anderen dynamischen oder statischen Bibliotheken, die vom Apache httpd-Kern verwendet werden, oder aus statischen Bibliotheksarchiven (libfoo.a) mit position unabhängigem Code. Es gibt nur wenige Chancen, andere Code zu verwenden, indem Sie entweder sicherstellen, dass der httpd-Kern selbst bereits eine Referenz zu ihm enthält, oder das Code selbst über dlopen() laden.
