Zum Anfang werden wir eine Textpasswortdatei verwenden. Diese Datei sollte an einem Ort gespeichert werden, der nicht über das Web zugänglich ist.

Um zu beginnen, werden wir eine Text-Passwortdatei verwenden. Diese Datei sollte an einer Stelle platziert werden, die nicht über das Web erreichbar ist. Dadurch können die Nutzer die Passwortdatei nicht herunterladen. Zum Beispiel, wenn Ihre Dokumente über /usr/local/apache/htdocs bereitgestellt werden, könnten Sie die Passwortdatei(en) in /usr/local/apache/passwd platzieren. Um die Datei zu erstellen, verwenden Sie die htpasswd-Umgebung, die mit Apache geliefert wurde. Diese befindet sich im bin-Verzeichnis, in dem Sie Apache installiert haben. Wenn Sie Apache von einem Drittanbieter-Paket installiert haben, kann sie in Ihrem Exekutionspfad sein. Um die Datei zu erstellen, geben Sie ein:

htpasswd -c /usr/local/apache/passwd/passwords rbowen

Die htpasswd-Umgebung fragt Sie nach dem Passwort, und dann nach dem Passwort erneut, um es zu bestätigen:

# htpasswd -c /usr/local/apache/passwd/passwords rbowen
Neues Passwort: meinpasswort
Passwort erneut eingeben: meinpasswort
Passwort für den Benutzer rbowen hinzugefügt

Wenn htpasswd nicht in Ihrem Pfad ist, müssen Sie natürlich den vollständigen Pfad zur Datei angeben, um sie auszuführen. Bei einer Standardinstallation befindet sie sich an der Stelle /usr/local/apache2/bin/htpasswd.

Nun benötigen Sie, die Serverkonfiguration zu ändern, um ein Passwort anzufordern und der Server welche Benutzer Zugriff erlauben soll, zu erzwingen. Dies können Sie entweder durch Bearbeiten der httpd.conf-Datei oder durch Verwendung einer .htaccess-Datei tun. Zum Beispiel, wenn Sie den Verzeichnis /usr/local/apache/htdocs/geheim wahren möchten, können Sie die folgenden Direktiven verwenden, entweder in der Datei /usr/local/apache/htdocs/geheim/.htaccess oder in httpd.conf platzieren:

AuthType Basic
AuthName "Geheime Seite"
AuthUserFile /usr/local/apache/passwd/passwords
Require user rbowen

Diese Direktiven sagen dem Server, dass er ein Passwort anfordern soll, dass die Seite "Geheime Seite" heißt und dass nur der Benutzer rbowen Zugriff erhalten soll.

Schützen Sie die Verzeichnis /usr/local/apache/htdocs/geheim, können Sie die folgenden Direktiven verwenden, entweder in der Datei /usr/local/apache/htdocs/geheim/.htaccess, oder in httpd.conf innerhalb einer <Directory "/usr/local/apache/htdocs/geheim">-Sektion. Lass uns jetzt jede der Direktiven einzeln untersuchen. Die AuthType-Direktive wählt den verwendeten Authentifizierungsmethode aus. Der häufigste Methode ist Basic, und dies ist die Methode, die von mod_auth_basic implementiert wird. Es ist wichtig zu beachten, dass Basic-Authentifizierung den Passwort vom Client an den Server unverschlüsselt sendet. Diese Methode sollte daher nur für sehr sensible Daten verwendet werden, wenn sie von mod_ssl begleitet wird. Apache unterstützt eine weitere Authentifizierungsmethode: AuthType Digest. Diese Methode wird von mod_auth_digest implementiert und war ursprünglich als sicherer gedacht. Dies ist nicht mehr der Fall und die Verbindung sollte stattdessen mit mod_ssl verschlüsselt werden. Die AuthName-Direktive setzt das Realm für die Authentifizierung fest. Das Realm dient zwei wichtigen Funktionen. Zunächst präsentiert der Client oft dieses Informationen dem Benutzer als Teil des Passwort-Dialogfelds. Zweitens wird es vom Client verwendet, um festzustellen, welches Passwort für einen bestimmten authentifizierten Bereich gesendet werden soll.

Mögliche Probleme ¶

Wegen der Art und Weise, wie Basic-Authentifizierung angegeben wird, müssen Ihr Benutzername und Passwort jedes Mal überprüft werden, wenn Sie eine Datei vom Server anfordern. Dies gilt auch dann, wenn Sie die gleiche Seite neu laden, und für jedes Bild auf der Seite (wenn sie aus einem geschützten Verzeichnis kommen). Wie Sie denken können, verlangsamt dies etwas.

Auf der Seite (wenn sie aus einem geschützten Verzeichnis kommen). Wie man sich vorstellen kann, verlangsamt das etwas. Der Grad der Verlangsamung ist proportional zur Größe des Passwort-Datei-Pakets, da es dieses Datei-Paket öffnen und die Liste der Benutzer bis zu Ihrem Namen durchgehen muss. Und das muss dies jedes Mal, wenn eine Seite geladen wird. Folge davon ist, dass es eine praktische Grenze gibt, wie viele Benutzer Sie in einem Passwort-Datei-Paket platzieren können. Diese Grenze wird sich je nach Leistung Ihrer speziellen Server-Maschine unterscheiden, aber Sie können erwarten, dass Verlangsamungen auftraten, sobald Sie mehr als einige hundert Einträge haben, und möglicherweise in Betracht ziehen, eine andere Authentifizierungs-Methode in Betracht zu ziehen. Alternative Passwort-Speicherung ¶ Da Passwörter in Text-Dateien die oben genannten Probleme haben, möchten Sie möglicherweise Ihre Passwörter an einem anderen Ort speichern, wie z. B. in einer Datenbank. mod_authn_dbm und mod_authn_dbd sind zwei Module, die dies möglich machen. Mit der Einführung der neuen providerbasierten Authentifizierung und Autorisierung-Architektur sind Sie nicht mehr auf eine einzige Authentifizierungs- oder Autorisierungs-Methode angewiesen. Tatsächlich können Sie beliebig viele der Providers miteinander kombinieren und verbinden, um Ihren Anforderungen genau zu entsprechen. Im folgenden Beispiel werden beide der Datei- und LDAP-basierte Authentifizierungs-Provider verwendet.

<Directory "/www/docs/private">
AuthName "Private"
AuthType Basic
AuthBasicProvider file ldap
AuthUserFile "/usr/local/apache/passwd/passwords"
AuthLDAPURL ldap://ldaphost/o=yourorg
Require valid-user
</Directory>

In diesem Beispiel versucht der Datei-Provider den Benutzer zuerst zu authentifizieren. Wenn er den Benutzer nicht authentifizieren kann, wird der LDAP-Provider aufgerufen. Dadurch kann das Authentifizierungsspektrum erweitert werden, wenn Ihre Organisation mehr als eine Art von Authentifizierungsspeicher implementiert. Andere Authentifizierung- und Autorisierung-Szenarien können beispielsweise darin bestehen, eine Art von Authentifizierung mit einer anderen Art von Autorisierung zu kombinieren. Zum Beispiel authentifizieren Sie sich gegen ein Passwort-File, aber autorisieren Sie sich gegen einen LDAP-Verzeichnis. Wie mehrere Authentifizierungs-Provider implementiert werden können, können auch mehrere Autorisierungs-Methoden verwendet werden.

Autorisierung gegen ein LDAP-Verzeichnis. Genau wie mehrere Authentifizierungsanbieter implementiert werden können, können auch mehrere Autorisierungsmethoden verwendet werden. In diesem Beispiel wird sowohl die Datei-Gruppenautorisierung als auch die LDAP-Gruppenautorisierung verwendet.

<Directory "/www/docs/private">
AuthName "Private"
AuthType Basic
AuthBasicProvider file

AuthLDAPURL ldap://ldaphost/o=yourorg
AuthGroupFile "/usr/local/apache/passwd/groups"
Require group GroupName
Require ldap-group cn=mygroup,o=yourorg
</Directory>

Die Art und Weise, wie Autorisierung angewendet wird, war in der Vergangenheit ein etwas geheimnisvolles Thema. In Apache 2.2 wurde ein provider-basiertes Authentifizierungsmechanismus eingeführt, um das eigentliche Authentifizierungsprozess von Autorisierung und Unterstützungsfunktionalität zu trennen.

In Apache 2.2 wurde ein provider-basiertes Authentifizierungsmechanismus eingeführt, um den eigentlichen Authentifizierungsprozess von Autorisierung und Unterstützungsfunktionalität zu trennen. Ein Vorteil war, dass Authentifizierungsanbieter konfiguriert und aufgerufen werden konnten, in einer bestimmten Reihenfolge, die unabhängig von der Lastfolge des auth-Moduls selbst war. Dieselbe provider-basierte Mechanismus wurde auch in die Autorisierung weitergebracht. Das bedeutet, dass der Require-Direktiv nicht nur angibt, welche Autorisierungsverfahren verwendet werden sollen, sondern auch in welcher Reihenfolge sie aufgerufen werden. Mehrere Autorisierungsverfahren werden in der gleichen Reihenfolge aufgerufen, in der die Require-Direktiven in der Konfiguration auftreten. Mit der Einführung von Autorisierungscontainer-Direktiven wie <RequireAll> und <RequireAny> hat die Konfiguration auch Kontrolle über, wann die Autorisierungsverfahren aufgerufen werden und welche Kriterien bestimmen, wann der Zugriff gewährt wird. Weitere Informationen zu Autorisierungscontainern finden Sie unter Autorisierungscontainern. Beispielhaft werden sie verwendet, um komplexes Autorisierungslogik auszudrücken. Jeder Autorisierungsanbieter gibt eines von drei möglichen Ergebnissen zurück; siehe Autorisierungsresult-Zustände für Details zur Interpretation dieser Ergebnisse. Voreingenommen werden alle Require-Direktiven als ob sie in einem <RequireAny>-Container-Direktiv enthalten wären. Zurückwärtskompatibilität der Zugriffssteuerung
Eines der Nebenwirkungen der Adoption eines Anbieterbasierten Mechanismus für die Autorisierung ist, dass die vorherigen Zugriffssteuerungs-Direktiven Order, Allow, Deny und Satisfy nicht mehr benötigt werden. Um jedoch für ältere Konfigurationen Rückwärtskompatibilität zu gewährleisten, wurden diese Direktiven in den mod_access_compat-Modul verschoben.

Hinweis: Die Direktiven des mod_access_compat-Moduls wurden von mod_authz_host abgelöst. Die Mischung von alten Direktiven wie Order, Allow oder Deny mit neuen Direktiven wie Require ist technisch möglich, aber nicht empfohlen. Das mod_access_compat-Modul wurde geschaffen, um Konfigurationen zu unterstützen, die nur alte Direktiven enthalten, um die 2.4-Upgrade zu erleichtern. Bitte beachten Sie die Upgrading-Anleitung für mehr Informationen.
