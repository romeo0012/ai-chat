Um einen Webserver effektiv zu verwalten, ist es notwendig, um Rückmeldungen über die Aktivität und Leistung des Servers sowie mögliche Fehler zu erhalten. Der Apache HTTP Server bietet sehr umfassende und flexibel anpassbare Logging-Fähigkeiten. Dieses Dokument beschreibt, wie Sie seine Logging-Fähigkeiten konfigurieren und verstehen, was die Logdateien enthalten.

Der Apache HTTP Server bietet eine Vielzahl verschiedener Mechanismen an, um alles, was auf Ihrem Server passiert, zu loggen, von der initialen Anfrage über den URL-Mapping-Prozess bis zur endgültigen Beendigung der Verbindung, einschließlich aller möglicher Fehler. Darüber hinaus können dritte-Partei-Module Logging-Fähigkeiten bieten oder Einträge in die vorhandenen Logdateien einfügen, und Anwendungen wie CGI-Programme, PHP-Skripte oder andere Handler können Nachrichten an den Server-Fehlerprotokoll senden. In diesem Dokument diskutieren wir die Logging-Module, die ein standardteil des http-Servers sind.

Per-Modul-Protokollierung ¶ Das LogLevel-Directive ermöglicht es, auf einer pro-Modul-Basis ein Protokollierungsstufen-Niveau festzulegen. Dadurch können Sie bei der Behebung eines Problems mit nur einem bestimmten Modul dessen Protokollierungsvolumen erhöhen, ohne auch die Details anderer Modul zu erhalten, die Sie nicht interessieren. Dies ist besonders nützlich für Module wie mod_proxy oder mod_rewrite, bei denen Sie Details über, was es versucht, zu tun wissen möchten. Dies erreichen Sie, indem Sie den Namen des Moduls in Ihrem LogLevel-Directive angeben: 
LogLevel info rewrite:trace5

Dies setzt den Haupt-LogLevel auf info, aber es erhöht es auf trace5 für mod_rewrite. Dies ersetzt die pro-Modul-Protokollierungs-Directives, wie RewriteLog, die in früheren Versionen des Servers vorhanden waren. Der Formatzeichenstreng besteht aus Prozent-Richtlinien, jede der dem Server aufträgt, bestimmte Informationen im Protokoll zu vermelden. Bedingte Logdateien Es gibt Zeiten, in denen es praktisch ist, bestimmte Einträge aus den Zugriffslogdateien auszublenden, basierend auf Merkmalen der Clientanfrage. Dies gelingt leicht mit Hilfe von Umgebungsvariablen. Zunächst muss eine Umgebungsvariable festgelegt werden, um anzugeben, dass die Anfrage bestimmte Bedingungen erfüllt. Dies geschieht meistens mit SetEnvIf. Dann wird der env= -Clause der CustomLog-Direktive verwendet, um Einträge ein- oder auszuschließen, bei denen die Umgebungsvariable gesetzt ist.

Inhalt der Datei .htaccess

Sie können auch die Datei .htaccess verwenden, um bestimmte Regeln für Ihre Webseite festzulegen. Hier ist ein Beispiel für eine .htaccess-Datei, die die Erstellung von Zugriffslogdateien und die Ausblendung bestimmter Einträge basierend auf Umgebungsvariablen ermöglicht.

CustomLog logs/access_log common
SetEnvIf User-Agent "MSIE" noaccess
CustomLog logs/noaccess_log env=noaccess

In diesem Beispiel wird eine Zugriffslogdatei erstellt, die die Standard-CLF-Information enthält. Danach wird die Umgebungsvariable "noaccess" festgelegt, wenn der User-Agent "MSIE" ist. Die nächste Zeile erstellt eine weitere Zugriffslogdatei, die nur Einträge enthält, bei denen die Umgebungsvariable "noaccess" gesetzt ist.

Der env=-Clause der CustomLog-Direktive wird verwendet, um Anfragen einzuschließen oder auszuschließen, bei denen die Umgebungsvariable gesetzt ist. Hier sind einige Beispiele:

# Anfragen von der Schleifen-Schnittstelle aus ausschließen
SetEnvIf Remote_Addr "127.0.0.1" dontlog

Anfragen für das robots.txt-Datei ausschließen

SetEnvIf Request_URI "^/robots.txt$" dontlog

Was bleibt protokollieren

CustomLog logs/access_log common env=!dontlog

Als weiteres Beispiel könnte die Protokollierung von Anfragen von englischsprachigen Benutzern in ein Log-Datei und von nicht-englischsprachigen Benutzern in eine andere Log-Datei betrachtet werden.

CustomLog logs/non_english_log common env=!english

Log Rotation ¶ Auf einem moderat stark belasteten Server ist die Menge der in den Log-Dateien gespeicherten Informationen sehr groß. Die Zugriffslog-Datei wächst typischerweise um 1 MB oder mehr pro 10.000 Anfragen. Es wird daher notwendig, die Log-Dateien periodisch zu rotieren, indem man die bestehenden Log-Dateien verschiebt oder löscht. Dies kann während des Servers laufens nicht durchgeführt werden, weil Apache httpd weiterhin in die alten Log-Dateien schreibt, solange diese offen gehalten werden. Stattdessen muss der Server nach den Log-Dateien verschoben oder gelöscht werden, nachdem er neu gestartet wurde, damit er neue Log-Dateien öffnen kann. Durch einen sanften Neustart kann der Server aufgefordert werden, neue Log-Dateien zu öffnen, ohne irgendeine bestehende oder ausstehende Verbindungen von Clients zu verlieren. Um dies zu erreichen, muss der Server jedoch weiterhin in die alten Log-Dateien schreiben, während er alte Anfragen abarbeitet.

Um dieses zu erreichen, muss der Server weiterhin auf die alten Protokolldateien schreiben, während er alte Anfragen abarbeitet. Es ist daher notwendig, einige Zeit nach dem Neustart zu warten, bevor man irgendeine Verarbeitung auf den Protokolldateien durchführt. Ein typischer Vorgang, der die Protokolldateien einfach rotiert und die alten Protokolldateien komprimiert, um Platz zu sparen, lautet wie folgt:

mv access_log access_log.old
mv error_log error_log.old
apachectl graceful
sleep 600
gzip access_log.old error_log.old

Eine andere Möglichkeit zur Protokollrotation ist die Verwendung von gepufferten Protokollen, wie in der nächsten Sektion diskutiert.

Gepuffertes Protokoll ¶
Apache httpd ist fähig, Fehler- und Zugriffsprotokolldateien über eine Pipe an ein anderes Prozess zu schreiben, anstatt direkt in eine Datei. Diese Fähigkeit erhöht die Flexibilität des Protokollierens, ohne zusätzliches Code in den Hauptserver einzubinden. Um Protokolle in eine Pipe zu schreiben, muss man lediglich den Dateinamen durch den Pipe-Zeichenfolgenzeichen "|" ersetzen, gefolgt vom Namen des Executables, das Log-Einträge auf seiner Standard-Eingabe akzeptiert. Der Server startet den gepufferten-Log-Prozess, wenn der Server startet, und startet ihn erneut, wenn er während des Laufens des Servers abstürzt. (Diese letzte Funktion ist der Grund, warum wir dieses Verfahren als "zuverlässiges gepuffertes Protokollieren" bezeichnen können.) Gepuffert-Log-Prozesse werden von der Eltern-Apache-httpd-Prozess gestartet und erben somit die Benutzer-ID dieser Prozess. Dies bedeutet, dass gepuffert-Log-Programme normalerweise als root ausgeführt werden. Es ist daher sehr wichtig, die Programme einfach und sicher zu halten.

Dieser Text handelt von Programmen, die über das Pipen von Logdateien laufen und meistens als Root ausgeführt werden. Es ist daher sehr wichtig, die Programme einfach und sicher zu halten. Eine wichtige Verwendung von Piped Logs ist es, Logrotation ohne Neustart des Servers zu ermöglichen. Der Apache HTTP Server enthält ein einfaches Programm namens rotatelogs für diese Zwecke. Beispielhaft kann man das folgende verwenden, um die Logdateien alle 24 Stunden zu rotieren: CustomLog "|/usr/local/apache/bin/rotatelogs /var/log/access_log 86400" common. Hierbei werden Anführungszeichen verwendet, um das gesamte zu enhalten, das für den Pipe aufgerufen wird. Obwohl diese Beispiele für den Zugriffslog gelten, kann dieselbe Technik für den Fehlerlog verwendet werden. Wie bei bedingtem Logging handelt es sich bei Piped Logs um eine sehr mächtige Werkzeug, aber sie sollten nicht dort verwendet werden, wo ein einfacherer Lösung wie Offline-Nachbearbeitung zur Verfügung steht. Voreingestellt wird der Piped Log-Prozess ohne die Auslösung einer Shell gestartet. Verwende stattdessen "|$" statt "|", um den Prozess mit einer Shell (meistens mit /bin/sh -c) zu starten: # Mit einer Shell aufrufen "rotatelogs" CustomLog "|$/usr/local/apache/bin/rotatelogs /var/log/access_log 86400" common. Dies war die Standardverhalten für Apache 2.2. Abhängig von den Shell-Eigenschaften kann dies zu einem zusätzlichen Shell-Prozess für das Lebensdauer des Logging-Pipe-Programms und Problemen bei Signal-Handling während des Neustarts führen. Aufgrund der Kompatibilität mit Apache 2.2 ist auch die Notation "||" unterstützt und gleichwertig mit dem Verwenden von "|".

Bitte beachten Sie, dass Sie auf Windows möglicherweise Probleme haben, wenn Sie viele gepufferte Logger-Prozesse bei der Ausführung von Apache laufen lassen, insbesondere wenn HTTPD als Dienst gestartet ist. Dieser Fehler entsteht durch Ausnutzung der Desktop-Heap-Speicherplatzreservierung. Die Desktop-Heap-Speicherplatzreservierung für jeden Dienst wird durch den dritten Argumentwert der SharedSection-Parameter in der HKEY_LOCAL_MACHINE\System\CurrentControlSet\Control\SessionManager\SubSystems\Windows-Registry-Wert festgelegt. Ändern Sie diesen Wert mit Vorsicht; die üblichen Vorsichtsmaßnahmen für die Bearbeitung der Windows-Registry gelten, aber Sie könnten auch den Desktop-Heap-Pool erschöpfen, wenn der Wert angepasst wird zu hoch. Virtual Hosts ¶
Bei der Betrieb eines Servers mit vielen Virtual Hosts stehen mehrere Optionen zur Verfügung, um mit den Logdateien umzugehen. Zunächst ist es möglich, die Logdateien genau wie bei einem einzelnen Host-Server zu verwenden. Durch die Platzierung der Logging-Anweisungen außerhalb der <VirtualHost>-Abschnitte im Hauptserverkontext ist es möglich, alle Anfragen in der gleichen Zugriffslog und Fehlerlog zu protokollieren. Diese Technik ermöglicht es nicht, leicht Statistiken zu einzelnen Virtual Hosts zu sammeln. Wenn CustomLog oder ErrorLog-Anweisungen innerhalb eines <VirtualHost>-Abschnitts platziert werden, werden nur Anfragen oder Fehler für den Virtual Host in das angegebene Datei angezeigt. Jeder Virtual Host, der keine Logging-Anweisungen hat, wird seine Anfragen weiter an die Hauptserver-Logs senden.

Jede virtuelle Host, die keine Logging-Anweisungen hat, wird weiterhin ihre Anfragen an die Hauptserver-Logs senden. Diese Technik ist sehr nützlich für eine kleine Anzahl von virtuellen Hosts, aber wenn die Anzahl der Hosts sehr groß ist, kann es kompliziert werden, sie zu verwalten. Zusätzlich kann es häufig Probleme mit zu wenigen freien Datei-Deskriptoren verursachen. Für den Zugriffslog gibt es eine sehr gute Kompromisslösung. Durch Hinzufügen von Informationen über den virtuellen Host zur Log-Format-Zeichenfolge ist es möglich, alle Hosts in das gleiche Log zu schreiben, und später in einzelne Dateien zu trennen. Beispielhaft sehen Sie sich die folgenden Anweisungen an.

LogFormat "%v %p %h %l %u %t \"%r\" %>s %b" commonvhost
CustomLog logs/access_log commonvhost

Das %v wird verwendet, um den Namen des virtuellen Hosts zu protokollieren, der die Anfrage verarbeitet. Dann kann ein Programm wie split-logfile verwendet werden, um die Zugriffsprotokollierung nachbearbeiten zu können, um sie in eine Datei pro virtuellem Host zu trennen.

Logging der tatsächlich übertragenen Bytes sendet und empfängt mod_logio fügt zwei zusätzliche LogFormat-Felder (%I und %O) hinzu, die die tatsächliche Anzahl der übertragenen Bytes auf dem Netzwerk protokollieren.

Forensische Protokollierung mod_log_forensic ermöglicht die forensische Protokollierung von Client-Anfragen. Die Protokollierung erfolgt vor und nach der Verarbeitung einer Anfrage, so enthält der forensische Log zwei Log-Einträge pro Anfrage.

Die Protokollierung erfolgt vor und nach der Verarbeitung einer Anfrage, sodass der forensische Protokollierer zwei Protokollzeilen für jede Anfrage enthält. Der forensische Protokollierer ist sehr strikt und bietet keine Anpassungen. Er kann ein unschätzbares Debugging- und Sicherheitswerkzeug sein. PID-Datei Beim Startup speichert Apache httpd die Prozess-ID des Elternprozesses httpd in der Datei logs/httpd.pid. Dieser Dateiname kann mit der PidFile-Richtlinie geändert werden. Der Prozess-ID dient dem Administrator zur Wiederaufnahme und Beendigung des Dämonen durch Senden von Signalen an den Elternprozess; auf Windows verwenden Sie stattdessen das -k Befehlszeilenoption. Weitere Informationen finden Sie auf der Seite zur Beendigung und Wiederaufnahme. Script-Protokoll, um bei der Debugging-Unterstützung zu helfen, ermöglicht die ScriptLog-Richtlinie, die Eingabe und Ausgabe von CGI-Skripten aufzuzeichnen. Dies sollte nur in der Testphase verwendet werden - nicht für lebende Server. Weitere Informationen finden Sie in der mod_cgi-Dokumentation.
