Das HTTP/2-Protokoll ¶

HTTP/2 ist die Weiterentwicklung des erfolgreichsten Anwendungsschichtprotokolls der Welt, HTTP. Es konzentriert sich auf die effiziente Nutzung von Netzwerkressourcen. Es ändert die Grundlagen von HTTP, die Semantik nicht. Es gibt immer noch Anfragen und Antworten und Header und all das. Also, wenn Sie bereits HTTP/1 kennen, kennen Sie 95% von HTTP/2 auch. Das Protokoll ist in RFC 9113 (das den ursprünglichen RFC 7540 ablöst) definiert. Für eine ansprechende Einführung siehe HTTP/2 erklärt von Daniel Stenberg, dem Autor von curl. Es behandelt die Motivation und Design von HTTP/2 ohne, dass Sie zuerst die RFC-Notation parsen müssen. In Kürze: es gibt einige neue Begriffe und Falle, die beim Lesen dieses Dokuments beachtet werden müssen: HTTP/2 ist ein binäres Protokoll, im Gegensatz zu HTTP 1.1, das einfach Text ist. Letzteres ist für den menschlichen Leser (zum Beispiel das Überwachen von Netzwerkverkehr) gedacht, während das letztere nicht ist. Mehr Informationen in der offiziellen FAQ. h2 ist HTTP/2 über TLS (Protokollverhandlung über ALPN). h2c ist HTTP/2 über klaren TCP (ohne TLS).

offizieller FAQ-Frage. h2 ist HTTP/2 über TLS (Protokollverhandlung über ALPN). h2c ist HTTP/2 über reine TCP ohne TLS (TLS fehlt). Bemerkung: h2c wurde aus der aktuellen Spezifikation entfernt, aber httpd unterstützt es weiterhin. Ein Frame ist die kleinste Einheit der Kommunikation innerhalb einer HTTP/2-Verbindung, bestehend aus einem Kopfteil und einer variablen Reihe von Oktet-Sequenzen, strukturiert nach dem Typ des Frames. Weitere Informationen finden Sie in der offiziellen Dokumentation RFC 9113. Ein Stream ist eine zweidimensionale Datenströmung innerhalb der HTTP/2-Verbindung. Das entsprechende Konzept in HTTP 1.1 ist eine Anforderung/Antwort-Nachrichtenauswechslung. Weitere Informationen finden Sie in der offiziellen Dokumentation RFC 9113. HTTP/2 ist in der Lage, mehrere Datenstroms über die gleiche TCP-Verbindung laufen zu lassen, was das klassische HTTP 1.1-Head-of-Line-Blocking von langsamen Anforderungen und die Notwendigkeit, TCP-Verbindungen für jede Anforderung/Antwort (KeepAlive) neu zu instanzieren, vermeidet. HTTP/2 in Apache httpd ¶ Das HTTP/2-Protokoll wird von seinem eigenen httpd-Modul implementiert, genau genommen mod_http2. Es implementiert die komplette Funktionspalette, wie sie in RFC 9113 beschrieben ist, und unterstützt HTTP/2 über reine (http:), sowie sichere (https:) Verbindungen. Der reine Textvariante wird der Name 'h2c' gegeben, der sichere 'h2'. Für h2c ermöglicht es die direkte Modusausführung und die Upgrade-Methode über eine initiale HTTP/1-Anforderung. Eine Funktion von HTTP/2, die früher neue Möglichkeiten für Webentwickler bot, war Server Push, allerdings ist sie mittlerweile veraltet.

Ein Merkmal von HTTP/2, das früher neue Fähigkeiten für Webentwickler bot, ist Server Push, allerdings ist es nun abgelöst. Siehe den Abschnitt Early Hints für die empfohlene Alternative. Bauen Sie httpd mit Unterstützung für HTTP/2 ¶ mod_http2 nutzt die Bibliothek von nghttp2 als Basis für seine Implementierung. Die Erstellung von mod_http2 erfordert mindestens die Version 1.2.1 von libnghttp2 auf Ihrem System. Wenn Sie Ihre Apache httpd Quellquellbaum konfigurieren, müssen Sie ihm '--enable-http2' als zusätzlicher Argument geben, um die Erstellung des Moduls auszulösen. Wenn Ihre libnghttp2 in einem ungewöhnlichen Ort (was auf Ihrem Betriebssystem bedeutet) liegt, können Sie Ihre Position mit '--with-nghttp2=<pfad>' angeben, um zu konfigurieren. Wahrscheinlich reicht das für die meisten, es gibt jedoch Menschen, die einen statisch verknüpften nghttp2 in diesem Modul vorziehen. Für diese gibt es die Option --enable-nghttp2-staticlib-deps. Sie funktioniert ähnlich wie die statische Verknüpfung von openssl zu mod_ssl. Rede mal von SSL, Sie müssen wissen, dass die meisten Browser HTTP/2 nur auf https: URLs sprechen werden, also benötigen Sie einen Server mit SSL-Unterstützung. Aber nicht nur das, Sie benötigen auch eine SSL-Bibliothek, die die ALPN-Erweiterung unterstützt. Wenn Sie OpenSSL als Bibliothek verwenden, benötigen Sie mindestens die Version 1.0.2. Zunächst ist es, wie bei jedem httpd-Modul, notwendig, dass Sie es laden: LoadModule http2_module modules/mod_http2.

Die zweite Direktive, die Sie Ihrer Serverkonfiguration hinzufügen müssen, ist Protocols h2 http/1.1 Dadurch wird h2, die sichere Variante, als bevorzugter Protokolltyp auf Ihren Serververbindungen zugelassen. Wenn Sie alle HTTP/2-Varianten aktivieren möchten, schreiben Sie: Protocols h2 h2c http/1.1

Abhängig von der Position dieser Direktive, betrifft sie alle Verbindungen oder nur solche zu einem bestimmten virtuellen Host. Sie können sie auch ineinander verschieben, wie folgt:
Protocols http/1.1
<VirtualHost ...>
ServerName test.example.org
Protocols h2 http/1.1
</VirtualHost>

Dies erlaubt nur HTTP/1 auf Verbindungen, außer SSL-Verbindungen zu test.example.org, die HTTP/2 anbieten.

Wählen Sie eine starke SSLCipherSuite
Die SSLCipherSuite muss mit einer starken TLS-Verschlüsselungssuite konfiguriert werden. Die aktuelle Version von mod_http2 erzwingt keine Verschlüsselung, aber die meisten Clients tun dies. Wenn Sie eine h2 aktivierte Serveradresse in einem Browser zeigen, der mit einer unpassenden Verschlüsselungssuite arbeitet, wird dieser zurückfallen auf HTTP 1.1. Dies ist ein häufiger Fehler, der beim Erstmaligen der Konfiguration von httpd für HTTP/2 gemacht wird, um langwierige Debugging-Sitzungen zu vermeiden! Wenn Sie sicher sein möchten, welche Verschlüsselungssuite Sie wählen sollten, bitte vermeiden Sie diejenigen, die in der HTTP/2 TLS-Ablehnbelistung (RFC 9113) aufgeführt sind.

MPM-Konfiguration ¶ HTTP/2 ist in allen multi-processing-Modulen verfügbar, die mit httpd geliefert werden. Wenn Sie jedoch das prefork-MPM verwenden, werden es schwere Einschränkungen geben. In prefork wird mod_http2 nur ein Anforderung pro Verbindung pro Zeiteinheit verarbeiten. Aber Clients, wie z.B. Browser, werden viele Anforderungen gleichzeitig senden. Wenn eines dieser langsam verarbeitet (oder ein langsames Polling ist), werden die anderen Anforderungen stehenbleiben.

Zeit. Wenn einer dieser Vorgänge lang ausführen (oder ein langsam pollendes ist), werden die anderen Anforderungen blockieren. mod_http2 wird diesen Grenzwert standardmäßig nicht umgehen. Der Grund dafür ist, dass prefork heute nur gewählt wird, wenn Sie Verarbeitungsmotoren verwenden, die nicht für Mehrfach-Threadung bereit sind, z.B. mit mehr als einer Anforderung abstürzen. Wenn Ihre Umgebung das ausstehen kann, ist die aktuell beste Konfiguration (wenn sie auf Ihrer Plattform unterstützt wird) das event mpm. Wenn Sie sich wirklich an der Stelle befinden, in der Sie nur mit prefork arbeiten möchten und mehrere Anforderungen haben, können Sie das H2MinWorkers-Parameter anpassen, um das möglich zu machen. Wenn es jedoch funktionsunfähig wird, sind Sie für beide Teile verantwortlich. Clients ¶ Alle modernen Browser unterstützen HTTP/2 über TLS-Verbindungen (Quelle). Während mod_http2 noch Push implementiert, sollten neue Bereitstellungen stattdessen die 103 Early Hints verwenden, da dies ein zuverlässigerer Weg ist, um Clients über benötigte Ressourcen zu informieren. Das HTTP/2-Protokoll erlaubt dem Server, Antworten auf einen Client zu schieben, den er nie angefordert hat. Der Ton der Konversation ist: "hier ist eine Anfrage, die Sie nicht gesendet haben und die Antwort dazu wird bald eintreffen..." Aber es gibt Einschränkungen: der Client kann diese Funktion deaktivieren und der Server kann nur immer auf eine Anfrage schieben, die vom Client kommt.

Der Client kann diese Funktion deaktivieren und der Server kann nur immer auf eine Anforderung des Clients PUSH, wenn diese vorliegt. Der Zweck ist es zu ermöglichen, dem Server zu senden, was der Client wahrscheinlich benötigt: ein CSS- oder JavaScript-Ressource, die einer angeforderten HTML-Seite angehören, eine Menge von Bildern, die in einem CSS verlinkt sind usw. Der Vorteil für den Client ist, dass die Zeit gespart wird, um die Anforderung zu senden, die sich von einigen Millisekunden bis zu einer halben Sekunde erstrecken kann, je weiter sie auf der Erde voneinander entfernt sind. Der Nachteil ist, dass der Client möglicherweise Dinge erhalten kann, die er bereits in seinem Cache hat. Ja, HTTP/2 erlaubt die frühzeitige Abbruch von solchen Anforderungen, aber dennoch werden Ressourcen verschwendet. Zusammenfassend: es gibt keine einzige gute Strategie, um dieses Feature von HTTP/2 optimal zu nutzen und jeder versucht noch immer aus. Die Anfrage-Header kommen von wo? Beispielhaft wird ein PUSH-Anfrage den accept-language Header anfordern und wenn ja mit welchem Wert? httpd wird sich an die originale Anfrage (die, die das PUSH ausgelöst hat) orientieren und die folgenden Headers auf PUSH-Anfragen kopieren: user-agent, accept, accept-encoding, accept-language, cache-control. Alle anderen Headers werden ignoriert. Cookies werden auch nicht kopiert. PUSHing Ressourcen, die einen Cookie voraussetzen, funktionieren nicht. Dies kann ein Streitpunkt sein. Aber solange dies nicht mehr klar mit Browsern diskutiert wird, sollte man vorsichtshalber auf Seite des Vorsichts bleiben und Cookies nicht dort aussetzen, wo sie sonst nicht sichtbar wären. Early Hints ¶ Ein Alternative zu PUSHing Ressourcen ist, dem Client vor der Antwort gar noch Link-Header zu senden. Dies nutzt die HTTP-Funktion Early Hints und ist in RFC 8297 beschrieben. Um dies zu nutzen, muss die Funktion auf dem Server explizit aktiviert werden, indem man H2EarlyHints auf setzt (Die Funktion ist nicht standardmäßig aktiviert, da einige alte Browser sich an solchen Antworten verfingen konnten.) Wenn diese Funktion aktiviert ist, kann man die Anweisung H2PushResource verwenden, um Early Hints und Ressourcen-PUSHs auszulösen:

<Location /xxx.html>
H2PushResource /xxx.css
H2PushResource /xxx.js
</Location>

Dies wird dem Client eine "103 Early Hints" Antwort aussetzen, sobald der Server die Anfrage beginnt zu verarbeiten. Dies kann viel früher sein als die Zeit, in der die ersten Antwort-Header bestimmt wurden, je nachdem, wie deine Web-Anwendung aufgebaut ist.

Wenn H2Push aktiviert ist, wird auch der PUSH sofort nach der 103-Antwort gestartet. Wenn H2Push jedoch deaktiviert ist, wird die 103-Antwort dennoch dem Client gesendet.
