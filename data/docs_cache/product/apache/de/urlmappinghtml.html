DocumentRoot ¶
Beim Entscheiden, welches Datei für eine gegebene Anfrage gesendet werden soll, ist das Standardverhalten von httpd, den URL-Pfad der Anfrage dem Ende des in Ihren Konfigurationsdateien angegebenen DocumentRoot hinzuzufügen. Somit besteht die Grunddokumentbaum, der vom Web sichtbar ist, aus den Dateien und Verzeichnissen unter dem DocumentRoot. Beispielhaft würde dies bedeuten, dass eine Anfrage nach http://www.beispiel.com/fisch/guppies.html zum Senden des Dateis /var/www/html/fisch/guppies.html an den anfragenden Client führen. Wenn ein Verzeichnis angefordert wird (z.B.), würde dies zu einem Verzeichnis /var/www/html/fisch/guppies.html führen.
Wenn ein Verzeichnis angefordert wird (z.B. http://www.beispiel.com/fisch/), würde dies zu einem Verzeichnis /var/www/html/fisch/ erfolgen, das die Dateien und Unterverzeichnisse enthält, die in diesem Verzeichnis gespeichert sind.
Wenn ein Datei nicht gefunden wird, kann die Anfrage mit einer Fehlermeldung beantwortet werden, oder die Anfrage kann umgeleitet werden, indem die URL umgeleitet wird.

Für die Adresse <http://www.example.com/fish/guppies.html> würde das Dateisystem der anfragenden Client-Anwendung das Datei-Objekt /var/www/html/fish/guppies.html liefern. Wenn eine Verzeichnisanforderung (also ein Pfad, der mit einem Schrägstrich endet) gestellt wird, wird aus diesem Verzeichnis das Datei-Objekt definiert, das über die Direktive DirectoryIndex angegeben ist. Beispielhaft wäre dies so, wenn DocumentRoot wie oben festgelegt und folgendes gesetzt wäre:

DirectoryIndex index.html index.php

Eine Anfrage nach <http://www.example.com/fish/> würde darauf hin, dass httpd versucht, das Datei-Objekt /var/www/html/fish/index.html zu liefern. Im Fall, dass dieses Datei-Objekt nicht vorhanden ist, versucht httpd anschließend das Datei-Objekt /var/www/html/fish/index.php zu liefern. Wenn beide Dateien nicht vorhanden sind, versucht httpd anschließend eine Verzeichnisindex anzuzeigen, wenn mod_autoindex geladen und konfiguriert ist, um das zu ermöglichen.

httpd ist auch für das Virtual Hosting befähigt, bei dem der Server Anfragen für mehrere Hosts erhält. In diesem Fall kann für jeden virtuellen Host ein anderer DocumentRoot angegeben werden, oder alternativ die Direktiven der Modul-Erweiterung mod_vhost_alias verwenden, um die richtige Stelle auszuwählen, von der aus Inhalte bereitgestellt werden sollen, basierend auf der angeforderten IP-Adresse oder Hostnamen.

Die Direktive DocumentRoot wird in Ihrer Hauptserver-Konfigurationsdatei (httpd.conf) festgelegt und, möglicherweise, einmal pro zusätzlichen Virtual Host, den Sie erstellen.

Dateien außerhalb des DocumentRoot ¶ Es gibt häufig Situationen, in denen es erforderlich ist, Webzugriff auf Teile des Dateisystems zu ermöglichen, die nicht genau unter dem DocumentRoot liegen.

Hier ist es notwendig, Webzugriff auf Teile des Dateisystems zu ermöglichen, die nicht strikt unter dem DocumentRoot liegen. httpd bietet mehrere verschiedene Möglichkeiten, dies zu erreichen. Auf Unix-Systemen können symbolische Links andere Teile des Dateisystems unter den DocumentRoot bringen. Auf Sicherheitsgründen folgt httpd symbolische Links nur dann, wenn die Optionseinstellung für das entsprechende Verzeichnis die Einstellung FollowSymLinks oder SymLinksIfOwnerMatch enthält. Als Alternative bietet die Alias-Anweisung an, jede beliebige Teilmenge des Dateisystems in den Webraum zu kopieren. Beispielhaft würde dies mit Alias "/docs" "/var/web" lauten. Dadurch wird die URL http://www.beispiel.de/docs/dir/file.html von /var/web/dir/file.html serviert. Die ScriptAlias-Anweisung funktioniert ähnlich, mit der zusätzlichen Wirkung, dass alle Inhalte an der Zieladresse als CGI-Skripte behandelt werden. Für Situationen, in denen Sie zusätzliche Flexibilität benötigen, können Sie die AliasMatch und ScriptAliasMatch-Anweisungen verwenden, um mächtige reguläre Ausdrücke basierte Matching und Substitution durchzuführen. Beispielhaft würde dies ScriptAliasMatch "^/~([a-zA-Z0-9]+)/cgi-bin/(.+)" "/home/$1/cgi-bin/$2" lauten. Dadurch wird eine Anfrage an http://beispiel.de/~user/cgi-bin/script.cgi auf den Pfad /home/user/cgi-bin/script.cgi und behandelt das Ergebnis als CGI-Skript.

Benutzerverzeichnisse ¶
Traditionell auf Unix-Systemen kann das Heimverzeichnis eines bestimmten Benutzers als ~user/ bezeichnet werden.

Benutzerverzeichnisse ¶ Traditionell auf Unix-Systemen kann das Heimverzeichnis eines bestimmten Benutzers mit ~user/ angegeben werden. Das Modul mod_userdir erweitert diese Idee auf das Web, indem es es ermöglicht, Dateien unter jedem Benutzer-Heimverzeichnis über URLs wie folgt zuzugreifen: http://www.beispiel.com/~user/file.html Für Sicherheitsgründe ist es unangemessen, direkten Zugriff auf ein Benutzer-Heimverzeichnis über das Web zu ermöglichen. Daher gibt es die UserDir-Direktive, um anzugeben, in welchem Verzeichnis unter dem Benutzer-Heimverzeichnis Web-Dateien gespeichert sind. Mit der Standard-Einstellung Userdir public_html korrespondiert die obige URL mit einem Datei-Pfad wie /home/user/public_html/file.html, wo /home/user/ das Benutzer-Heimverzeichnis ist, wie es in /etc/passwd angegeben ist. Es gibt auch mehrere andere Formen der Userdir-Direktive, die Sie auf Systemen verwenden können, auf denen /etc/passwd die Lage des Heimverzeichnisses nicht enthält. Einige Menschen finden das "~"-Symbol (das auf dem Web oft als %7e kodiert wird) unangenehm und bevorzugen stattdessen eine alternative Zeichenkette, um Benutzerverzeichnisse darzustellen. Diese Funktionalität wird von mod_userdir nicht unterstützt. Allerdings ist es möglich, wenn die Heimverzeichnisse der Benutzer in einer regelmäßigen Weise strukturiert sind, die gewünschte Wirkung mit der AliasMatch-Direktive zu erreichen. Beispielhaft, um http://www.beispiel.com/upages/user/file.html auf /home/user/public_html/file.html zu zeigen, verwenden Sie die folgende AliasMatch-Direktive: AliasMatch "^/upages/([a-zA-Z0-9]+)(/(.*))?"

Um das gewünschte Ergebnis zu erzielen. Beispielhaft, um http://www.beispiel.com/upages/user/file.html auf /home/user/public_html/file.html zu zeigen, verwende die folgende AliasMatch-Anweisung: AliasMatch "^/upages/([a-zA-Z0-9]+)(/(.*))?$" "/home/$1/public_html/$3" URL Umleitung ¶ Die in den oben genannten Abschnitten erwähnten Konfigurationsanweisungen erzwingen httpd, dass das Inhalt aus einem bestimmten Speicherort des Dateisystems an den Client zurückgegeben wird. Manchmal ist es jedoch beabsichtigt, dem Client mitzuteilen, dass das angeforderte Inhalt an einer anderen URL zu finden ist, und den Client dazu anzuweisen, einen neuen Anforderungswert mit der neuen URL zu senden. Dies wird als Umleitung bezeichnet und wird durch die Redirect-Anweisung implementiert. Beispielhaft, wenn die Inhalte des Verzeichnisses /foo/ unter dem DocumentRoot auf das neue Verzeichnis /bar/ verschoben werden, können Sie den Clients auf die neue Lage anfordern, wie folgt: Redirect permanent "/foo/" "http://www.beispiel.com/bar/" Dies wird jede URL-Pfad, der mit /foo/ beginnt, auf den gleichen URL-Pfad auf dem www.beispiel.com-Server mit /bar/ statt /foo/ umleiten. Sie können Clients auf jeden Server umleiten, nicht nur auf den Ursprungserver. httpd bietet zudem eine RedirectMatch-Anweisung für komplexere Umleitungssituationen. Beispielhaft, um Anfragen für die Startseite auf eine andere Seite umzuleiten, aber alle anderen Anfragen unverändert zu lassen, verwende die folgende Konfiguration: RedirectMatch permanent "^/$" "http://www.beispiel.com/startpage.html"

Heimseite zu einer anderen Seite, aber alle anderen Anforderungen unberührt lassen, verwenden Sie die folgende Konfiguration: RedirectMatch permanent "^/$" "http://www.example.com/startpage.html" Alternativ, um alle Seiten einer bestimmten Seite auf eine bestimmte Seite einer anderen Seite zu temporär umleiten, verwenden Sie die folgende: RedirectMatch temp ".*" "http://othersite.example.com/startpage.html" Umgekehrter Proxy ¶ httpd ermöglicht es auch, remote Dokumente in den URL-Raum des lokalen Servers einzubringen. Diese Technik heißt umgekehrter Proxying, weil der Webserver wie ein Proxy-Server agiert, indem er Dokumente von einer entfernten Server abruft und sie dem Client zurückgibt. Es unterscheidet sich von normalem (vorwärts) Proxying, weil es dem Client so erscheint, als ob die Dokumente auf dem umgekehrten Proxy-Server entstammen. Im folgenden Beispiel werden Clients, die Dokumente unter dem /foo/-Verzeichnis anfordern, werden diese Dokumente vom /bar/-Verzeichnis auf internal.example.com abrufen und dem Client als ob sie von der lokalen Server stammten zurückgegeben. ProxyPass "/foo/" "http://internal.example.com/bar/" ProxyPassReverse "/foo/" "http://internal.example.com/bar/" ProxyPassReverseCookieDomain internal.example.com public.example.com ProxyPassReverseCookiePath "/foo/" "/bar/" Die ProxyPass-Konfiguration konfiguriert den Server, um die passenden Dokumente abzurufen, während die ProxyPassReverse-Richtlinie Umleitungen erstellt, die auf internal.example.com entstehen, so dass sie auf das passende Verzeichnis auf dem lokalen Server zielen.

Während der ProxyPassReverse-Direktive die Umleitungen ursprünglich von internal.example.com hergestellt werden, werden sie so umgeschrieben, dass sie auf den entsprechenden Ordner des lokalen Servers zielen. Ähnlich wie ProxyPassReverseCookieDomain und ProxyPassReverseCookiePath umschreiben Sie Cookies, die vom Backend-Server gesetzt werden. Es ist jedoch wichtig zu beachten, dass Links innerhalb der Dokumente nicht umgeschrieben werden. Daher ergeben sich absolute Links auf internal.example.com, dass der Client aus dem Proxy-Server ausbricht und direkt von internal.example.com anfragt. Sie können diese Links (und andere Inhalte) in einer Seite während der Ausgabe an den Client mithilfe von mod_substitute ändern. Verwenden Sie "s/internal\.example\.com/www.example.com/i" für eine umfassendere Umleitung von Links in HTML und XHTML. Für mehr komplexes Umleiten von Links in HTML und XHTML steht auch das mod_proxy_html-Modul zur Verfügung. Es ermöglicht es Ihnen, Maps von URLs zu erstellen, die umgeschrieben werden müssen, so dass komplexe Proxyszenarien bearbeitet werden können. Umschreibengine ¶ Wenn noch stärkere Substitution erforderlich ist, kann die Umschreibengine von mod_rewrite hilfreich sein. Die Direktiven dieses Moduls können Merkmale der Anfrage wie Browsertyp oder Quell-IP-Adresse in der Entscheidung verwenden, von wo aus Inhalte gesendet werden sollen. Zusätzlich kann mod_rewrite auf externen Datenbankdateien oder Programmen verweisen, um eine Anfrage zu bearbeiten. Die Umschreibengine ist in der Lage, alle drei Arten von Abbildungen durchzuführen, die hier diskutiert wurden: interne Umleitungen (Aliase), externe Umleitungen und Proxying.

Umschreibungsmotor ist in der Lage, alle drei Typen von Abbildungen aus oben erwähnt zu durchführen: interne Umleitungen (Aliase), externe Umleitungen und Proxying. Datei nicht gefunden ¶ Es ist unvermeidlich, dass URLs angefordert werden, für die kein entsprechender Datei im Dateisystem gefunden werden kann. Das kann für mehrere Gründe der Fall sein. In manchen Fällen kann es sich um das Verschieben von Dokumenten von einer Stelle auf eine andere handeln. In diesem Fall ist es am besten, URL-Umleitungen zu verwenden, um den Clients über den neuen Standort der Ressource zu informieren. Dadurch kann sichergestellt werden, dass alte Bookmarks und Links weiterhin funktionieren, selbst wenn die Ressource an einem neuen Ort ist. Eine weitere häufige Ursache für "Datei nicht gefunden"-Fehler ist unbeabsichtigte Tastfehler bei der URL-Eingabe, entweder direkt im Browser oder in HTML-Links. httpd bietet das Modul mod_speling (sic) an, um dieses Problem zu helfen. Wenn dieses Modul aktiviert ist, wird es "Datei nicht gefunden"-Fehler intercepten und nach einem Ressource mit ähnlichem Dateinamen suchen. Wenn solche Datei gefunden wird, wird mod_speling einen HTTP-Umleitung an den Client senden, um ihn über den richtigen Standort zu informieren. Wenn mehrere "nahe" Dateien gefunden werden, wird eine Liste der verfügbaren Alternativen dem Client präsentiert. Eine besonders nützliche Funktion von mod_speling ist, dass es Dateinamen ohne Rücksicht auf den Fall vergleicht. Dies kann Systems helfen, bei denen Benutzer unbewusst von der case-sensitive Natur von URLs und dem unix-Dateisystem sind.

Zu Fallcase. Dies kann Systems helfen, bei denen die Benutzer unbewusst der Fallunterscheidung der URLs und des unix-Dateisystems nicht bewusst sind. Allerdings kann die Verwendung von mod_speling für etwas mehr als die gelegentliche URL-Korrektur zusätzlichen Last auf den Server legen, da jede "falsche" Anfrage von einem URL-Weiterleitung und einem neuen Anfrage vom Client folgte. mod_dir bietet FallbackResource, das verwendet werden kann, um virtuelle URIs auf ein wirkliches Ressource zu mappen, das sie dann dient. Dies ist eine sehr nützliche Ersatz für mod_rewrite bei der Implementierung eines 'front controller', falls alle Versuche, das Inhalt zu finden, fehlschlagen, httpd gibt eine Fehlerseite mit HTTP-Statuscode 404 (Datei nicht gefunden) zurück. Die Aussehen dieser Seite wird mit dem ErrorDocument-Direktiv gesteuert und kann in einer flexiblen Weise individualisiert werden, wie in dem Dokument Custom error responses diskutiert. Andere URL-Mapping-Module ¶ Andere Modul verfügbar für URL-Mapping sind:

  • mod_actions - Maps eine Anfrage an einen CGI-Skript basierend auf der Anfrage-Methode oder Ressourcen-MIME-Typ.
  • mod_dir - Bietet eine Basismapping einer Trailing-Schrägstrich in eine Index-Datei wie index.html.
  • mod_imagemap - Maps eine Anfrage an eine URL basierend auf dem Ort, an dem der Benutzer auf ein Bild in einem HTML-Dokument klickt.

* mod_negotiation - Wählt ein passendes Dokument aus, basierend auf den Vorlieben des Clients wie Sprache oder Inhaltskompression.
