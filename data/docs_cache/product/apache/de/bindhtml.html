Beim Starten von httpd bindet es sich an eine bestimmte Port- und Adresse auf der lokalen Maschine und wartet auf kommende Anfragen. Standardmäßig hört es auf alle Adressen der Maschine. Es kann jedoch angegeben werden, dass es nur auf bestimmte Ports, oder nur auf ausgewählte Adressen, oder eine Kombination von beiden hören soll. Dies wird oft mit der Virtual Host-Funktion kombiniert, die bestimmt, wie httpd auf verschiedene IP-Adressen, Hostnamen und Ports reagiert. Die Listen-Direktive tellt dem Server, nur auf die angegebenen Port(s) oder Adressen-und-Port-Kombinationen eingehende Anfragen anzunehmen. Wenn in der Listen-Direktive nur ein Portnummer angegeben wird, hört der Server auf den angegebenen Port auf allen Interfaces. Wenn eine IP-Adresse neben einem Port angegeben wird, hört der Server auf den angegebenen Port und Interface. Mehrere Listen-Direktiven können verwendet werden, um eine Anzahl von Adressen und Ports anzugeben, auf die der Server hören soll. Der Server reagiert auf Anfragen von jedem der angegebenen Adressen und Ports.

Änderungen der Listen-Konfiguration bei Neustart ¶ Wenn httpd neu gestartet wird, müssen besondere Maßnahmen getroffen werden, wenn Änderungen an den Listen-Direktiven vorgenommen werden. Beim Neustart hält httpd Ports fest (wie in der Originalkonfiguration) um "Connection refused"-Fehler für jede neue Versuch, eine Verbindung mit dem Server herzustellen, zu vermeiden. Wenn Änderungen an der Menge der Listen-Direktiven vorgenommen werden, die mit der alten Konfiguration in Widerspruch stehen, wird die Konfiguration fehlschlagen und der Server wird beendet. Spezielle IPv6 Überlegungen ¶ Ein wachsendes Angebot an Plattformen implementiert IPv6, und APR unterstützt IPv6 auf den meisten dieser Plattformen, sodass httpd IPv6-Sockets zuweisen und Anfragen über IPv6 verarbeiten kann. Ein komplizierender Faktor für httpd-Administratoren ist, ob ein IPv6-Socket sowohl IPv4-Verbindungen als auch IPv6-Verbindungen behandeln kann. Die Verarbeitung von IPv4-Verbindungen mit einem IPv6-Socket erfolgt über IPv4-gemappte IPv6-Adressen, die auf den meisten Plattformen standardmäßig erlaubt sind, aber auf FreeBSD, NetBSD und OpenBSD standardmäßig verboten sind, um die systemweite Politik auf diesen Plattformen zu entsprechen. Auf Systemen, auf denen dies standardmäßig verboten ist, kann ein spezieller configure-Parameter das Verhalten von httpd für diese Plattform ändern. Andererseits können auf einigen Plattformen, wie Linux und Tru64, die einzige Möglichkeit, sowohl IPv6 als auch IPv4 zu verarbeiten, die Verwendung von gemappten Adressen sein. Wenn Sie httpd, um IPv4 und IPv6-Verbindungen mit einem Minimum an Sockets zu verarbeiten, was die Verwendung von IPv4-gemappten IPv6-Adressen erfordert, geben Sie den --enable-v4-mapped configure-Option an. --enable-v4-mapped ist das Standardverhalten auf allen Plattformen außer FreeBSD, NetBSD und OpenBSD, also ist dies wahrscheinlich, wie Ihr httpd aufgebaut wurde.

Hier ist der Standard auf allen Plattformen außer FreeBSD, NetBSD und OpenBSD, sodass dies wahrscheinlich so Ihr httpd erstellt wurde. Wenn Sie httpd nur IPv4-Verbindungen bearbeiten möchten, unabhängig von was Ihre Plattform und APR unterstützen, spezifizieren Sie in allen Listen-Anweisungen eine IPv4-Adresse, wie in den folgenden Beispielen: Listen 0.0.0.0:80 Listen 192.0.2.1:80

Wenn Ihre Plattform es unterstützt und Sie httpd IPv4 und IPv6-Verbindungen auf separate Sockets (also IPv4-mapped Adressen deaktivieren möchten), geben Sie die --disable-v4-mapped Konfigurationsoption an. --disable-v4-mapped ist der Standard auf FreeBSD, NetBSD und OpenBSD. Wenn Sie die Protokolloption mit Listen angeben, kann der optional zweite Protokollargument des Listen nicht für die meisten Konfigurationen erforderlich sein. Wenn nicht angegeben, ist https der Standard für Port 443 und http der Standard für alle anderen Ports. Das Protokoll dient dazu zu bestimmen, welcher Modul die Anfrage bearbeiten soll, und um mit der AcceptFilter-Anweisung protokollspezifische Optimierungen anzuwenden. Sie müssen das Protokoll nur dann setzen, wenn Sie auf nicht-standard Ports laufen. Beispiel: Eine https-Seite auf Port 8443 laufen lassen: Listen 192.170.2.1:8443 https

Wie dies mit Virtual Hosts funktioniert ¶

Der Listen-Befehl implementiert Virtual Hosts nicht - er gibt nur an, welche Adressen und Ports der Hauptserver hören soll. Wenn keine <VirtualHost>-Anweisungen verwendet werden, verhält sich der Server gleich für alle angenommenen Anfragen.

Wenn keine <VirtualHost>-Anweisungen verwendet werden, verhält sich der Server gleich für alle angenommenen Anfragen. Es kann jedoch mit <VirtualHost> eine andere Verhalten für eine oder mehrere der Adressen oder Ports angegeben werden. Um eine VirtualHost zu implementieren, muss der Server zunächst auf die zu verwendende Adresse und Port angehalten werden. Dann sollte eine <VirtualHost>-Sektion erstellt werden, um das Verhalten dieser virtuellen Host zu setzen. Achtung: Wenn die <VirtualHost> für eine Adresse und Port gesetzt wird, die der Server nicht hören kann, kann sie nicht zugreifen.
