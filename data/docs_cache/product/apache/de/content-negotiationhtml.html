Multiviews
Multiviews ist eine Option pro-Verzeichnis, was bedeutet, dass sie mit einem Options-Befehl innerhalb einer <Directory>, <Location> oder <Files>-Sektion in httpd.conf, oder (wenn AllowOverride richtig eingestellt ist) in .htaccess-Dateien gesetzt werden kann. Bemerkenswert ist, dass Options All MultiViews nicht setzt; Sie müssen es ausdrücklich anfordern. Die Wirkung von Multiviews ist wie folgt: Wenn der Server eine Anfrage für /some/dir/foo erhält, wenn /some/dir MultiViews aktiviert ist und /some/dir/foo nicht existiert, dann liest der Server das Verzeichnis nach Dateien mit dem Namen foo.* durch und erstellt sozusagen eine Typemap, die alle diese Dateien nennt und ihnen die gleichen Medientypen und Inhalts-Encodings zuweist, die der Client, wenn er eine von ihnen nach Name gefragt hätte, erhalten würde. Danach wählt er den besten Anpassung an die Anforderungen des Clients.

Der Kunde hat nach einem von ihnen per Name gefragt. Es wählt dann den besten Anpassung an die Anforderungen des Kunden. MultiViews können auch auf Suchvorgänge für den Dateinamen durch die DirectoryIndex-Direktive angewendet werden, wenn der Server versucht, eine Verzeichnisindexierung durchzuführen. Wenn die Konfigurationsdateien auf DirectoryIndex index festlegen, so entscheidet der Server zwischen index.html und index.html3, wenn beide vorhanden sind. Wenn beide fehlen und index.cgi vorhanden ist, wird dieser ausgeführt. Wenn bei der Lesung des Verzeichnisses einer der Dateien keine Erweiterung erkannt wird, die von mod_mime zur Designierung des Charsets, Content-Type, Sprache oder Codierung verwendet wird, so hängt das Ergebnis von der Einstellung der MultiViewsMatch-Direktive ab. Diese Direktive bestimmt, ob Handler, Filter und andere Erweiterungstypen an der MultiViews-Verhandlung teilnehmen können. Fiddling mit Qualitätswerten ¶ httpd kann die Qualitätswerte manchmal ändern, was von einer strikten Interpretation des httpd-Verhandlungsalgorithmus oben erwartet wäre. Das ist, um einen besseren Ergebnis vom Algorithmus für Browser zu erhalten, die kein vollständiges oder genaues Information senden. Einige der beliebtesten Browser senden Accept-Header-Information, die sonst in vielen Fällen die Auswahl der falschen Variant erfordern würde. Wenn ein Browser vollständige und korrekte Information sendet, werden diese Fiddles nicht angewendet. Media Types und Wildcards Der Accept: Anforderungskopf gibt Vorlieben für Media-Typen an. Er kann auch 'wildcard' Media-Typen enthalten, wie z. B. "image/*" oder "*/*" wo das * beliebige Zeichenzeichen darstellt. Somit bedeutet eine Anforderung, die: Accept: image/*, */* angezeigt wird, dass jeder Typ, der mit "image/" beginnt, akzeptabel ist, sowie jeder andere Typ. Einige Browser senden wildcards regelmäßig hinzu, neben expliziten Typen, die sie verarbeiten können.

Akzeptabel ist auch jede andere Art. Einige Browser senden wildcards zusätzlich zu den explizit angegebenen Typen, die sie verarbeiten können. Beispiel: Accept: text/html, text/plain, image/gif, image/jpeg, */*
Die Absicht dieses ist, die explizit aufgelisteten Typen als bevorzugt anzugeben, aber wenn eine andere Darstellung verfügbar ist, ist das auch in Ordnung. Mit expliziten Qualitätswerten, was der Browser eigentlich will, ist etwas wie: Accept: text/html, text/plain, image/gif, image/jpeg, */*; q=0,01
Die expliziten Typen haben keinen Qualitätsfaktor, also sind sie mit einem Vorzugswert von 1,0 (der höchste) vorgesehen. Das Wildcard */* wird einen niedrigen Vorzugswert von 0,01 zugewiesen, so dass andere Typen nur zurückgegeben werden, wenn kein Variant einem explizit aufgelisteten Typ entspricht. Wenn der Accept-Header keine q-Faktoren enthält, setzt httpd den Vorzugswert von "*/*" auf 0,01, um das gewünschte Verhalten zu emulieren. Es setzt auch den Vorzugswert von Wildcards des Typs "type/*" auf 0,02 (also sind diese bevorzugt gegenüber Matches gegenüber "*/*"). Wenn irgendeine Medientypen im Accept-Header einen q-Faktor enthält, werden diese speziellen Werte nicht angewendet, so dass Anfragen von Browsern, die die explizite Information von vornherein mitbringen, wie erwartet funktionieren.

In order to support advanced techniques (such as cookies or special URL-paths) to determine the user's preferred language, since httpd 2.0.47 mod_negotiation recognizes the environment variable prefer-language. If it exists and contains an appropriate language tag, mod_negotiation will try to select a matching variant. If there's no such variant, the normal negotiation process applies. Example:

Hinweis zu Hyperlinks und Namenskonventionen ¶ Wenn Sie Sprachverhandlung verwenden können, wählen Sie zwischen verschiedenen Namenskonventionen, da Dateien mehrere Erweiterungen haben können und die Reihenfolge der Erweiterungen normalerweise irrelevant ist (siehe die mod_mime-Dokumentation für Details). In der Tabelle oben wird deutlich, dass es immer möglich ist, den Namen ohne jede Erweiterung in einem Hyperlink zu verwenden (z.B. foo). Der Vorteil liegt darin, dass man den tatsächlichen Dokumententyp bzw. Dateityp einer Datei verbergen und später ändern kann, z.B. von html zu shtml oder cgi ohne irgendwelche Verweise auf Hyperlinks zu ändern. Wenn man jedoch weiterhin einen MIME-Typ in seinen Hyperlinks verwenden möchte (z.B. foo.html), muss die Spracherweiterung (einschließlich einer Codierungs-Erweiterung, falls vorhanden) rechts neben der MIME-Erweiterung stehen (z.B. foo.html.en).

Hinweis zur Caching ¶
Wenn ein Cache eine Darstellung speichert, verknüpft er sie mit der Anfrage-URL. Wenn diese URL erneut angefordert wird, kann der Cache die gespeicherte Darstellung verwenden. Allerdings kann dies passieren, dass nur der erste angeforderte Variant des negotiable-Ressourcen im Cache gespeichert wird und anschließende Cache-Treffer falsche Antworten liefern. Um dies zu verhindern, markiert httpd normalerweise alle Antworten, die nach Inhaltserneuerung zurückgegeben werden, als nicht-zachbar für HTTP/1.0-Cliente. httpd unterstützt auch die HTTP/1.1-Protokoll-Funktionen, um verhandelte Antworten im Cache zu speichern. Für Anfragen, die von einem HTTP/1.1-Client kommen, kann httpd verhandelte Antworten im Cache speichern.

httpd unterstützt auch die HTTP/1.1-Protokollmerkmale, um die Caching von verhandelten Antworten zu erlauben. Für Anforderungen, die von einem HTTP/1.0-kompatiblen Client (entweder einem Browser oder einem Cache) stammen, kann die Direktive CacheNegotiatedDocs verwendet werden, um die Caching von Antworten zu ermöglichen, die durch Verhandlung betroffen waren. Diese Direktive kann in der Serverkonfiguration oder in der virtuellen Hostkonfiguration gegeben werden und nimmt keine Argumente an. Sie hat keinen Einfluss auf Anforderungen von HTTP/1.1-Clients. Für HTTP/1.1-Clients sendet httpd einen Vary-HTTP-Antwortkopf, um die Verhandlungsdimensionen für die Antwort anzugeben. Caches können diese Information verwenden, um zu bestimmen, ob eine nachfolgende Anforderung aus dem lokalen Kopie gespeichert werden kann. Um einen Cache dazu zu bewegen, den lokalen Kopie unabhängig von den Verhandlungsdimensionen zu verwenden, kann die force-no-vary Umgebungsvariable gesetzt werden.
