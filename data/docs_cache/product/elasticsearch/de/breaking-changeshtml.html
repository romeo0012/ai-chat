9.4.0 ILM: In früheren Versionen von Elasticsearch wurde die downsampling-API durch Zwangsmerging der downsampled-Index bearbeitet. In Elasticsearch 9.3.0 und später haben wir dieses Verhalten von der downsampling-API auf die ILM-downsampling-Aktion verschoben und aktiviert. Dadurch konnten Benutzer es deaktivieren, wenn sie es wünschten. Da der Zwangsmerge nicht notwendigerweise für die downsampling-Operation erforderlich ist, haben wir in Elasticsearch 9.4.0 entschieden, es standardmäßig auszuschalten.

Quelle: [https://www.elastic.co/de/support/releases/elasticsearch-9-4-0](https://www.elastic.co/de/support/releases/elasticsearch-9-4-0)

Benutzer können es, falls sie es wünschen, deaktivieren. Da die Zwangsmerge nicht von der Downsampling-Operation erforderlich ist, wählen wir in Elasticsearch 9.4.0 die Zwangsmerge standardmäßig aus. Diese Änderung betrifft nur die Downsampling-ILM-Aktionen; andere Aktionen, die eine Index-Zwangsmerge standardmäßig durchführen, wie z.B. die suchbare Snapshot-Aktion, bleiben unverändert. Wenn ein Benutzer auf dieses Verhalten angewiesen war, muss er seine ILM-Politik aktualisieren, indem er entweder eine Zwangsmerge-Aktion in derselben oder einer nachfolgenden Phase der Politik hinzufügt oder indem er den Parameter force_merge_index des Downsample-Auftrags auf true setzt. #145400 (Issue: #140811) Abbildung: OTLP-Endpunkt: Verwende exponential_histograms standardmäßig #145065 TSDB: Sequenznummern haben einen bedeutenden Speicherfußabdruck in Metrikenanwendungen (bis zu 30% für OTLP). Um dies zu reduzieren, deaktivieren wir Sequenznummern für Indizes im Zeitreihenmodus, was bedeutet, dass sie abgeschnitten werden, sobald sie nicht mehr für die Replikation benötigt werden. Dadurch wird die Speichereffizienz verbessert, und es wird auch die Belastung für Segment-Zusammenfassung reduziert. Der Nachteil ist, dass Optimistische Konkurrenzsteuerung für diese Indizes nicht mehr anwendbar ist. Index, Aktualisierung und Löschvorgänge, die mit if_seq_no Fehler auslösen, und Suchaufrufe mit seq_no_primary_term festgelegt werden, liefern Sentinelwerte für Sequenznummern zurück.

Aktualisierungs- und Löschvorgänge mit Hilfe von if_seq_no, Fehlerausgabe und Suchaufrufen mit seq_no_primary_term gesetzt, die Sentinelwerte für die Sequenznummern zurückgeben sollten. Zusätzlich laufen update_by_query und delete_by_query Vorgänge ohne Konfliktkontrolle ab, sodass sich parallel ausführte Änderungen ohne Auslösung von Versionkonflikterfehlern stumm über die betroffenen Dokumente schreiben können. Dies ist in der Regel ein günstiger Handelssatz, da parallel ausführende Änderungen eher selten in Metrikenanwendungen auftreten und die Speicher-Einsparungen beträchtlich sind. Dennoch können Nutzer, die OCC-Unterstützung benötigen, die alte Verhalten wiederherstellen, indem sie index.disable_sequence_numbers in ihren Zeitreihenindex-Vorlagen auf false setzen. #145737 (Issue: #136305)

9.1.0 Discovery-Plugins: Migrates discovery-ec2 Plugin zur AWS SDK v2
Der discovery-ec2 Plugin nutzt jetzt AWS SDK v2 anstelle von v1, da AWS SDK v1 vor dem Ende der Unterstützung für Elasticsearch 8.19 abgelöst wird. AWS SDK v2 führt mehrere Verhaltensänderungen ein, die die Konfiguration betreffen. Auswirkung: Wenn Sie den discovery-ec2 Plugin verwenden, können Ihre aktuellen Einstellungen nicht mehr kompatibel sein. Bemerkenswerte Änderungen umfassen, aber sind nicht auf alle beschränkt: AWS SDK v2 unterstützt nicht den EC2 IMDSv1-Protokoll. AWS SDK v2 unterstützt nicht die Systemvariablen aws.secretKey oder com.amazonaws.sdk.ec2MetadataServiceEndpointOverride. AWS SDK v2 erlaubt es nicht, zwischen HTTP und HTTPS auszuwählen, sodass die Einstellung discovery.ec2.protocol nicht mehr wirksam ist. AWS SDK v2 akzeptiert kein Zugriffsschlüssel ohne Geheimschlüssel oder umgekehrt. Maßnahme: Testen Sie die Upgrade in einer nicht-Produktionsumgebung. Adaptieren Sie Ihre Konfiguration an die neuen SDK-Funktionalitäten. Dies umfasst, aber ist nicht auf alle beschränkt, folgende Punkte: Wenn Sie IMDS verwenden, um den Verfügbarkeitsbereich eines Knotens zu bestimmen oder um Zugangsdaten für den Zugriff auf die EC2-API zu erhalten, stellen Sie sicher, dass sie das IMDSv2-Protokoll unterstützen. Wenn zutreffend, sollten Sie die Verwendung von aws.secretKey und com.amazonaws.sdk.ec2MetadataServiceEndpointOverride einstellen.

Verfügbarkeitszone eines Knotens oder um Zugangsdaten für die Verwendung der EC2-API zu erhalten, stellen Sie sicher, dass sie das IMDSv2-Protokoll unterstützt. Falls angewendbar, sollte die Nutzung der aws.secretKey und com.amazonaws.sdk.ec2MetadataServiceEndpointOverride Systemvariablen eingestellt werden. Falls angewendbar, sollte angegeben werden, dass Sie das unverschlüsselte HTTP-Protokoll zur Verwendung der EC2-API verwenden möchten, indem Sie discovery.ec2.endpoint auf eine URL festlegen, die mit http:// beginnt. Entweder sollten beide ein Zugangsschlüssel und ein Geheimnis-Schlüssel mittels der discovery.ec2.access_key und discovery.ec2.secret_key Keystore-Einstellungen bereitgestellt werden, oder keine dieser Einstellungen konfiguriert werden. Weitere Informationen finden Sie unter #122062.

ES|QL: ES|QL gibt nun standardmäßig teilweise Ergebnisse zurück
In früheren Versionen scheiterten ES|QL-Abfragen vollständig, wenn ein Fehler auftrat. Ab der Version 8.19.0 gibt ES|QL stattdessen teilweise Ergebnisse zurück. Auswirkung: Aufrufer müssen den Flag is_partial im Antworten überprüfen, um festzustellen, ob das Ergebnis vollständig ist. Vertrauen auf vollständige Ergebnisse ohne diesen Flag überprüfen zu lassen, kann falsche Annahmen über die Antwort zur Folge haben. Maßnahme: Wenn teilweise Ergebnisse für Ihr Szenario nicht akzeptabel sind, können Sie dieses Verhalten wie folgt deaktivieren:

  • Setzen Sie allow_partial_results=false in der Abfrage-URL pro Anfrage fest, oder
  • Setzen Sie das esql.query.allow_partial_results Cluster-Setting auf false.
    Weitere Informationen finden Sie unter #127351 (Issue: #122802)

Verhindert die Verwendung von Klammern in unzitierten Index-Muster in ES|QL, um Verwirrung mit der Syntax von Subabfragen zu vermeiden, kann ES|QL ab jetzt nicht mehr die Verwendung von ( und ) in unzitierten Index-Muster zulassen.

(Issue: #122802) ES|QL verbietet es, Klammern in unzitierten Indexmustern zu verwenden, um Verwirrung mit der Syntax von Subabfragen zu vermeiden, wird die Verwendung von ( und ) in unzitierten Indexmustern nicht mehr unterstützt. Auswirkung: Abfragen, die Klammern in unzitierten Indexnamen enthalten, werden jetzt eine Parsing-Ausnahme erzeugen. Maßnahme: Aktualisieren Sie betroffene Abfragen, um Indexnamen, die Klammern enthalten, zu zitieren. Beispiel: Verwenden Sie stattdessen FROM "("foo")" anstatt FROM (foo). Weitere Informationen finden Sie unter #130427 (Issue: #130378) ES|QL verbietet es, zitierte und unzitierte Komponenten in FROM Indexmustern zu mischen. ES|QL unterstützt es nicht mehr, zitierte und unzitierte Teile in FROM Indexmustern zu mischen (z.B. FROM remote:"index"). Bisher wurden solche Mustern unkonsistent interpretiert und konnten zu täuschenden Laufzeitfehlern führen. Auswirkung: Abfragen, die teilweise zitierte Indexmuster verwenden – z.B. nur den Index oder nur den entfernten Cluster zitieren – werden jetzt bei der Parsingzeit abgelehnt. Diese Änderung vereinfacht die Grammatikverarbeitung und vermeidet verwickelte Validierungsfehler. Maßnahme: Stellen Sie sicher, dass Indexmuster entweder vollständig zitiert oder vollständig unzitiert sind. Beispiel: Gültig: FROM "remote:index" oder FROM remote:index Ungültig: FROM remote:"index", FROM "remote":index Weitere Informationen finden Sie unter #127636 (Issue: #122651) skip_unavailable erfasst jetzt alle Laufzeitfehler des entfernten Clusters in ES|QL Wenn skip_unavailable auf true festgelegt ist, wird ES|QL jetzt alle Laufzeitfehler des Clusters als nicht-fatal behandeln. Bisher galt diese Einstellung nur für Verbindungsprobleme (d.h. Verbindungsprobleme). Auswirkung: Wenn skip_unavailable auf true festgelegt ist, werden jetzt alle Laufzeitfehler des Clusters als nicht-fatal behandelt.

Wenn skip_unavailable auf wahr gesetzt ist, behandelt ES|QL jetzt alle Laufzeitfehler aus diesem Cluster nicht mehr als tödlich. Bislang galt diese Einstellung nur für Verbindungsprobleme (also wenn ein Cluster unverfügbar war). Maßnahme: Wenn Ihre Workflows auf die Erkennung von Fehlern auf einem entfernten Cluster angewiesen sind, überprüfen Sie Ihre Verwendung von skip_unavailable und korrigieren Sie die Fehlerbehandlung, falls nötig. Der repository-s3 Plugin nutzt jetzt AWS SDK v2 anstatt v1, da AWS SDK v1 vor dem Ende der Unterstützung für Elasticsearch 8.19 abgelöst wird. Die beiden SDKs unterscheiden sich im Verhalten, was möglicherweise Konfigurationsänderungen erfordern. Auswirkung: Existierende repository-s3 Konfigurationen könnten nicht mehr kompatibel sein. Bemerkenswerte Unterschiede in AWS SDK v2 umfassen, aber sind nicht auf die folgenden Punkte beschränkt: AWS SDK v2 erfordert es, dass Benutzer die Region angeben, die für die Signaturanforderungen verwendet werden soll, oder dass sie in einem Umgebung, in der es automatisch die richtige Region ermitteln kann, laufen. Das ältere SDK ermittelte die Region anhand des Endpoint-URLs, wie es mit dem s3.client.${CLIENT_NAME}.endpoint-Setting angegeben wurde, zusammen mit anderen Daten aus der Umgebung, und fiel zurück auf us-east-1, wenn kein besseres Wert gefunden wurde. AWS SDK v2 unterstützt nicht mehr den EC2 IMDSv1-Protokoll.

Zusammen mit anderen Daten aus dem Betriebsumfeld, fiel der SDK v2 zurück auf us-east-1, wenn kein besseres Wert gefunden wurde. AWS SDK v2 unterstützt nicht den EC2-IMDSv1-Protokoll. AWS SDK v2 unterstützt nicht die com.amazonaws.sdk.ec2MetadataServiceEndpointOverride-Systemvariable. AWS SDK v2 erlaubt es nicht, zwischen HTTP und HTTPS auszuwählen, sodass die s3.client.${CLIENT_NAME}.protocol-Einstellung veraltet ist und keinen Einfluss mehr hat. AWS SDK v2 erlaubt es nicht, die Wiederholungsverzögerung zu steuern, sodass die s3.client.${CLIENT_NAME}.use_throttle_retries-Einstellung veraltet ist und keinen Einfluss mehr hat. AWS SDK v2 erfordert die Verwendung des V4-Signaturalgorithms, sodass die s3.client.${CLIENT_NAME}.signer_override-Einstellung veraltet ist und keinen Einfluss mehr hat. AWS SDK v2 unterstützt nicht den log-delivery-write canned ACL. AWS SDK v2 zählt 4xx-Antworten anders in seiner Metrikenberichterstattung. AWS SDK v2 nutzt immer den regionalen STS-Endpunkt, während AWS SDK v2 entweder einen regionalen Endpunkt oder den globalen https://sts.amazonaws.com-Endpunkt verwenden könnte. Maßnahme: Testen Sie die Upgrade in einer nicht-produktionsumgebung. Adaptieren Sie Ihre Konfiguration an die neuen SDK-Funktionalitäten. Dies umfasst, aber ist nicht auf die folgenden Punkte beschränkt: Spezifizieren Sie die richtige Signaturregion mithilfe der s3.client.${CLIENT_NAME}.region-Einstellung auf jedem Knoten.

Folgende Punkte können nicht auf eine Beschränkung beschränkt sein:

  1. Verwende die richtige Signaturregion mithilfe der Einstellung s3.client.${CLIENT_NAME}.region auf jedem Knoten. {es} versucht, die richtige Region aufgrund des Endpunkt-URLs und anderen Umweltdaten zu bestimmen, kann dies jedoch in allen Fällen nicht korrekt ausführen. Wenn Sie IMDS verwenden, um die Verfügbarkeitszone eines Knotens zu bestimmen oder um Zugriffscredentials für den Zugriff auf die EC2-API zu erhalten, stellen Sie sicher, dass es den IMDSv2-Protokoll unterstützt. Wenn zutreffend, beenden Sie die Verwendung der com.amazonaws.sdk.ec2MetadataServiceEndpointOverride-Systemeigenschaft. Wenn zutreffend, legen Sie fest, dass Sie das ungesicherte HTTP-Protokoll zum Zugriff auf die S3-API verwenden möchten, indem Sie s3.client.${CLIENT_NAME}.endpoint auf eine URL festlegen, die mit http:// beginnt. Wenn zutreffend, beenden Sie die Verwendung der log-delivery-write canned ACL. Weitere Informationen finden Sie unter #126843 (Issue: #120993).
