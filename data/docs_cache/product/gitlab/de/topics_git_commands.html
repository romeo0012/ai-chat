Git-Befehle Git-Befehle sparen Ihnen Zeit während Ihrer Entwicklungsarbeitsfluss. Diese Referenzseite enthält häufig verwendete Befehle für alltägliche Aufgaben wie Codeänderungen, Branch-Management und Historie-Überprüfung. Jeder Befehlsteil bietet die genaue Syntax, praktische Beispiele und Links zu zusätzlicher Dokumentation.

git add Verwenden Sie git add um Dateien in den Staging-Bereich zu bringen. 

git add &lt;file_path&gt;

Sie können die Änderungen aus dem aktuellen Arbeitsverzeichnis rekursiv in den Staging-Bereich übernehmen, indem Sie git add . verwenden, oder alle Änderungen in der Git-Repository mit git add --all übernehmen. Weitere Informationen finden Sie unter [Dateien Ihrer Branch hinzufügen](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository).

git blame Verwenden Sie git blame um zu berichten, welche Benutzer welche Teile einer Datei geändert haben. 

git blame &lt;file_name&gt;

Sie können git blame -L <line_start>,<line_end> verwenden, um einen bestimmten Bereich von Zeilen zu überprüfen. Weitere Informationen finden Sie unter [Git-Datei-Blame](https://git-scm.com/docs/git-blame).

Beispiel: Um zu überprüfen, welcher Benutzer die letzte Änderung an Zeile fünf von example.txt vorgenommen hat: 

$ git blame -L 5,5 example.txt
123abc (Zhang Wei 2021-07-04 12:23:04 +0000 5)
git bisect Verwenden Sie git bisect um binäre Suche zu verwenden, um den Commit zu finden, der den Fehler eingeführt hat. Starten Sie mit der Identifizierung eines Commit, der als "schlecht" (der Fehler enthält) und eines Commit, der als "gut" (der Fehler enthält nicht) bezeichnet wird. 
git bisect start
git bisect bad # Aktuelle Version ist schlecht
git bisect good v2.6.13-rc2 # v2.6.13-rc2 ist bekannt, dass es gut ist
git bisect wählt dann einen Commit zwischen den beiden Punkten aus und fragt Sie, ob der Commit "schlecht" oder "gut" ist, indem Sie git bisect good oder git bisect bad verwenden. Wiederholen Sie den Prozess, bis der Commit gefunden ist.

Zwischen den zwei Punkten und fragt Sie, ob der Commit "gut" oder "schlecht" ist, mit git bisect good oder git bisect bad. Wiederholen Sie den Vorgang, bis der Commit gefunden ist. git checkout Verwenden Sie git checkout, um auf eine spezifische Branch zu wechseln. git checkout <branch_name> Um eine neue Branch zu erstellen und auf sie zu wechseln, verwenden Sie git checkout -b <branch_name>. Weitere Informationen finden Sie hier: [Erstellen Sie eine Git-Branch für Ihre Änderungen](https://docs.github.com/de/github/using-git/creating-a-new-branch-for-your-work). git clone Verwenden Sie git clone, um ein vorhandenes Git-Repository zu kopieren. git clone <repository> Weitere Informationen finden Sie hier: [Ein Git-Repository auf Ihren lokalen Computer klonen](https://docs.github.com/de/github/using-git/cloning-a-repository). git commit Verwenden Sie git commit, um geplante Änderungen an dem Repository zu committen. git commit -m "<commit_message>" Wenn der Commit-Nachricht ein Leerzeile enthält, wird die erste Zeile der Commit-Nachricht der Commit-Betreff, während der Rest der Nachricht die Commit-Nachricht wird. Verwenden Sie den Betreff, um einen Änderungszusammenfassung kurz zu beschreiben, und die Commit-Nachricht, um weitere Details zu geben. Weitere Informationen finden Sie hier: [Staging, Committen und Pushen von Änderungen](https://docs.github.com/de/github/using-git/committing-changes-to-your-repository). git commit --amend Verwenden Sie git commit --amend, um die letzte Commit-Änderung zu modifizieren. git diff Verwenden Sie git diff, um die Unterschiede zwischen Ihren lokalen ungestaged Änderungen und der letzten Version zu sehen, die Sie geklont oder gezogen haben. git diff Sie können den Unterschied (oder diff) zwischen Ihren lokalen Änderungen und der letzten Version einer Branch anzeigen. Verwenden Sie den diff, um Ihre lokalen Änderungen vor dem Committen auf der Branch zu verstehen.

Differenz (oder diff) zwischen Ihren lokalen Änderungen und der aktuellsten Version einer Branch. Um eine Differenz anzeigen zu lassen, um Ihre lokalen Änderungen vor dem Kommen in die Branch zu verstehen, führen Sie folgendes aus: git diff <branch>
In der Ausgabe: Zeilen mit Hinzufügungen beginnen mit einem Plus (+) und werden in Grün angezeigt. Zeilen mit Löschungen oder Änderungen beginnen mit einem Minus (-) und werden in Rot angezeigt.

git init
Verwenden Sie git init, um eine Verzeichnis zu initialisieren, damit Git es als Repository verfolgt. Bei der Verwendung von git init wird in der Verzeichnis ein .git-File mit Konfigurations- und Log-Dateien hinzugefügt. Das .git-File sollte nicht direkt bearbeitet werden. Die Standard-Branch ist auf "main" festgelegt. Sie können den Namen der Standard-Branch mit git branch -m <branch_name> ändern oder mit git init -b <branch_name> initialisieren.

git pull
Verwenden Sie git pull, um alle Änderungen von Benutzern nach dem letzten Mal, dass Sie das Projekt geklont oder gezogen haben, zu erhalten. git pull <optional_remote> <branch_name>

git push
Verwenden Sie git push, um die lokalen Änderungen an den Remotebranches zu senden. Weitere Informationen finden Sie unter stage, commit und push Änderungen.

git reflog
Verwenden Sie git reflog, um eine Liste der Änderungen an den Git Referenzprotokollen anzuzeigen. git reflog zeigt standardmäßig eine Liste der Änderungen an HEAD an. Weitere Informationen finden Sie unter rückgängig machen.

git remote add
Verwenden Sie git remote add, um Git mitzuteilen, welche Remote-Repository in GitLab mit einer lokalen Verzeichnis verknüpft ist. git remote add <remote_name> <repository_url>

Beim Klonen eines Repositorys wird standardmäßig die Quell-Repository mit dem Remote-Namen origin verbunden.

Im GitLab ist eine lokale Verzeichnisverbindung. Um eine Remoteverbindung hinzuzufügen, verwenden Sie git remote add <remote_name> <repository_url>. Wenn Sie eine Repository klonen, ist die Quellrepository standardmäßig mit dem Remote-Namen origin verknüpft. Weitere Informationen zum Konfigurieren zusätzlicher Remotes finden Sie hier: [Forks](https://docs.gitlab.com/ee/gitlab-basics/forking_workflow.html). Verwenden Sie git log, um eine Liste der Commits in chronologischer Reihenfolge anzuzeigen. Verwenden Sie git log und git show, um Informationen über ein Objekt in Git anzuzeigen. Beispiel: Um zu sehen, welchen Commit HEAD zeigt: 

$ git show HEAD
commit ab123c (HEAD -&gt; main, origin/main, origin/HEAD)

Verwenden Sie git merge, um die Änderungen von einer Branch mit einer anderen zu kombinieren. Weitere Informationen zu einer Alternative zu git merge finden Sie hier: [rebase](https://docs.gitlab.com/ee/topics/git/rebase.html) zum Adressieren von Mergekonflikten. Beispiel: Um die Änderungen in feature_branch auf target_branch anzuwenden: 
git checkout target_branch
git merge feature_branch

Verwenden Sie git rebase, um die Commitgeschichte einer Branch zu überarbeiten. git rebase <branch_name> Sie können git rebase verwenden, um Mergekonflikte zu lösen. In den meisten Fällen möchten Sie auf die Standardbranch rebase-n. Verwenden Sie git reset, um einen Commit rückgängig zu machen und die Commitgeschichte zurückzurollen und von einem früheren Commit aus fortzufahren. Weitere Informationen finden Sie hier: [undo changes](https://docs.gitlab.com/ee/topics/git/undo_changes.html). Verwenden Sie git status, um den Status des Arbeitsverzeichnisses und der staged Files anzuzeigen. git status Wenn Sie Dateien hinzufügen, ändern oder löschen, kann Git Ihnen die Änderungen anzeigen.
