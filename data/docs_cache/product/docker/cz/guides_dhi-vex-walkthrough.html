Návod Příručka Začínáme Manuály Odkazy Seznámit se s VEX instrukcemi v Docker Hardened Images Provedete skenování Docker Hardened Image s a bez VEX a provedejte auditu každé potlačení a jeho justifikaci. Zkontaktujte se s Gordonem Zobrazit Markdown Zobrazit Markdown Obsah obsahu Standardní skenovací nástroje hlášejí CVE pro balíčky přítomné v obrazu. S Docker Hardened Images jsou tyto balíčky zde podle návrhu, ale každý zaznamenaný CVE má VEX instrukci, která vysvětluje, zda je v tomto konkrétním produktním nastavení k exploitaci. Tento návod vede skrze skenování Docker Hardened Image s a bez VEX a auditu justifikace za každé potlačení. Požadavky Docker Desktop, ověřený u dhi.io. Přihlaste se pomocí příkazu docker login dhi.io. Docker Desktop obsahuje Docker Scout, který získává VEX attestaci. Nástroj pro skenování. Tento návod ukazuje příklady pro Docker Scout, Trivy a Grype. Trivy a Grype mohou běžet jako Docker kontejnery bez nutnosti instalace. jq (volitelné), pro filtrování VEX souboru. Osvětlit daemon pro uživatele Windows Uživatelé Windows nejsou schopni použít -v /var/run/docker.sock:/var/run/docker.sock socket mount v příkazech skenovacího nástroje v kontejneru v tomto návodu. Chcete-li používat kontejnerové skenovací nástroje na Windows, otevřete nastavení > Obecné v Docker Desktop a zapněte Expose daemon na tcp://localhost:2375 bez TLS. Potom nahraďte -v /var/run/docker.sock:/var/run/docker.sock s -e DOCKER_HOST=tcp://host.docker.

Obsah:

  1. V Docker Desktop nastavte Expose daemon na tcp://localhost:2375 bez TLS. Poté nahraďte -v /var/run/docker.sock:/var/run/docker.sock na -e DOCKER_HOST=tcp://host.docker.internal:2375 ve všech příkazech konténérů. Varování: Expozice daemona na TCP bez TLS zvýšuje riziko útoku na vzdálené spouštění kódu. Vypněte nastavení, když budete hotoví s testováním. Krok 1: Scan bez VEX

Přihlaste se k registru obrázků Docker Hardened Images: $ docker login dhi.io
Poté zkopírujte obrázek: $ docker pull dhi.io/python:3.13
Scan bez VEX, abyste viděli počet CVE v rámci rawníku. Docker Scout automaticky aplikuje VEX na obrázky Docker Hardened Images. Chcete-li vidět nefiltrovaný CVE baseline, použijte Trivy nebo Grype. Trivy Grype
$ trivy image --scanners vuln dhi.io/python:3.13
Pokud Trivy není nainstalováno, spusťte ho v kontejneru: $ docker run --rm \
-v /var/run/docker.sock:/var/run/docker.sock \

Zda některé z těchto CVE jsou skutečně využitelné v tomto konfiguračním nastavení je samostatné otázce, a to právě VEX odpovídá. Krok 2: Získání VEX attestace
Exportujte VEX attestaci do místního souboru: $ docker scout vex get registry://dhi.io/python:3.13 --output python-vex.json
Předpona registry:// říká Scoutu, aby získal attestaci z registru místo místního úložiště obrazu. Protože jste obraz v Kroku 1 stáhli, už je lokálně k dispozici, a bez této předpony by Scout nenalezl žádnou attestaci tam. Tímto získáte podepsaný OpenVEX dokument z registry.scout.docker.com, registru metadata zásobníku Docker pro všechny Docker Hardened Images. Tento dokument zaznamenává Dockerův hodnocení ohrožujících schopností pro každý CVE nalezený v SBOM obrazu Docker. Poznámka: Docker Scout tento soubor automaticky stahuje při kontrolě. Potřebujete ho stáhnout explicitně pro kontroléře, které to neintegrují přímo, nebo aby mohli být provedeny dotazy jq v Krocích 5 a 6.

Překlad provedl: Jan Křížek, překladatel technických textů, www.jankrizek.cz

Tento soubor se automaticky při skenování. Potřebujete ho stáhnout explicitně pro skenery, které to neintegrovaly nativně, nebo k provedení dotazů jq v kroku 5 a 6. Krok 3: Skenovat pomocí VEX aplikovaného Docker Scout Trivy Grype. Docker Scout automaticky získá a aplikuje VEX attestaci bez nutnosti místního souboru: $ docker scout cves dhi.io/python:3.13

Stejný obrázek, stejné balíčky, stejná databáze CVE. Jediná rozdílnost je kontext. Škálovací program odpovídá každé CVE proti souboru VEX a potlačil každou, kterou Docker hodnotil jako neexploitovatelnou. Balíčky jsou stále zde. Zkontrolujte SBOM a uvidíte libc6, libsqlite3-0 a každý jiný balíček z kroku 1. Nula CVEs neznamená, že balíčky byly odstraněny. Znamená to, že každá zpracovaná CVE má dokumentovaný důvod, proč se na tuto konfiguraci produktu nevztahuje. VEX je otevřený standard: důvod cestuje s obrázkem a každý kompatibilní škálovací program čte stejnou logiku. Krok 4: Prozkoumejte každou potlačení a její justifikaci
Docker Scout a Grype potlačují CVE odpovídající VEX, ale nevystavují kód justifikace v jejich výstupu. Použijte možnost --show-suppressed v Trivy, abyste viděli každou potlačenu CVE spolu s kódem justifikace na úrovni CVE.
$ trivy image --scanners vuln --vex python-vex.json --show-suppressed dhi.io/python:3.13
Pokud Trivy není nainstalováno, spusťte ho v kontejneru:
$ docker run --rm \
-v /var/run/docker.sock:/var/run/docker.sock \
-v "$(pwd)/python-vex.json:/tmp/vex.json" \
aquasec/trivy:latest image --scanners vuln --vex /tmp/vex.json --show-suppressed dhi.io/python:3.13

Sloupec Vysvětlení ukazuje strojově čitelnou jasnou kódovou justifikaci z VEX souboru. Justifikace kódy mají přesné významy:
vulnerable_code_cannot_be_controlled_by_adversary: existuje cesta k náchylnému kódu v balíčku, ale útočník nemůže tuto cestu aktivovat v tomto konfiguraci.
vulnerable_code_not_present: náchylný kód nebyl do této verze připojen nebo jinak chybí.
inline_mitigations_already_exist: Docker již aplikoval backport nebo patch, který řeší CVE v tomto obrázku.

Staví se nebo jinak chybí. inline_mitigations_already_exist: Docker použil přenesenou verzi nebo opravu, která řeší CVE v této obrazovce. Pro celý seznam kódů zákonitostí, přečtěte si odkaz na referenční materiál VEX statusu. Každá potlačení je dokumentována, kontrolní a ověřitelná pomocí jakékoliv VEX-ověřovacího nástroje. Krok 5: Čtěte Dockerovy důvody pro konkrétní CVE Důvody kódů jsou strojově čitelné; pole status_notes v souboru VEX obsahuje Dockerovy lidsky čitelné důvody. Použijte jq, aby vyhledalo konkrétní CVE: $ jq '.statements[] | select(.vulnerability.name == "CVE-2010-4756") | {status, justification, status_notes}' python-vex.json Příklad výstupu: { "status": "not_affected", "justification": "vulnerable_code_cannot_be_controlled_by_adversary", "status_notes": "Standardní POSIX chování v glibc. Aplikace používající glob potřebují uložit si vlastní omezení. Požaduje ověřený přístup a je považováno za nevýznamné Debianem." } Pole status_notes vysvětluje Dockerovy důvody v jasném jazyce. Pro CVE-2010-4756 je popisované chování globu v CVE standardním POSIX chováním, požaduje ověřený přístup a je klasifikováno jako nevýznamné Debianem bezpečnostním týmem. Každá deklarace také uvádí postižené produkty jako URL balíčků (PURL), například pkg:deb/debian/glibc@2.41-12%2Bdeb13u2?os_distro=trixie&os_name=debian&os_version=13. Trivy tuto deklaraci přizpůsobilo k libc6 v obrazovce SBOM tím, že porovnalo tento PURL s balíčky zaznamenanými v SBOM.

Poznámka: Tento překlad je určen pouze pro účely vzoru a nebyl ověřen profesionálním překladatelem.

Text v angličtině:
Matched this statement to libc6 v obrazu jeho SBOM pomocí porovnání tohoto PURL s balíčky zaznamenanými v SBOM. Důležité shodování PURL je přísné. Scanner musí shodovat VEX statements s balíčky pomocí celé řetězce PURL, včetně kvalifikátorů os_name, os_version a os_distro. Shodování podle názvu balíčku sama o sobě znamená, že se zásada zablokování použije pro jednu verzi OS na jiné verzi, kde je CVE exploitable. Krok 6: Filtr VEX statements podle stavu
Po získání python-vex.json, použijte jq k přímočasnému dotazování. Počet deklarací podle stavu: $ jq '[.statements[].status] | group_by(.) | map({status: .[0], count: length})' python-vex.json Seznam všech CVEs pod vědomím: $ jq '[.statements[] | select(.status == "under_investigation") | {cve: .vulnerability.name, produkty: [.produkty[]."@id"]}]' python-vex.json Seznam jakékoliv CVEs s postiženým stavem: $ jq '[.statements[] | select(.status == "affected") | {cve: .vulnerability.name, akce: .action_statement}]' python-vex.json Tento dotaz vrátí prázdnou pole pro současný dhi.io/python:3.13 obraz, což je očekávaný výsledek pro aktivně udržovanou verzi. Chcete-li zobrazit postižené záznamy pro všechny verze DHI Python, dotazujte celý VEX feed: $ curl -s https://raw.githubusercontent.com/docker-hardened-images/advisories/main/vex/python/dhi-python.vex.json \ | jq '[.statements[] | select(.status == "affected") | {cve: .vulnerability.name, akce: .action_statement}]'

Celý VEX feed: $ curl -s https://raw.githubusercontent.com/docker-hardened-images/advisories/main/vex/python/dhi-python.vex.json | jq '[.statements[] | select(.status == "affected") | {cve: .vulnerability.name, action: .action_statement}]' Pro definicí stavů a kódy důvodů se přečtěte VEX status reference.
