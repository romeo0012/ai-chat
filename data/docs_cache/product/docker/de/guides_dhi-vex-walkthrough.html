Markdown Ansicht Markdown Tabelle der Inhaltsverzeichnis
Standard-Sicherheitsanzeigen melden CVEs gegen Pakete in einem Bild. Mit Docker-harten Bildern sind diese Pakete vorgegeben, aber jede gemeldete CVE hat einen VEX-Aussage, der erklärt, ob sie in dieser spezifischen Produktkonfiguration ausnutzbar ist. Diese Anleitung führt durch das Scannen eines Docker-harten Bildes mit und ohne VEX und die Prüfung der Begründung hinter jeder Suppression.

Voraussetzungen
Docker Desktop, authentifiziert bei dhi.io. Melden Sie sich mit docker login dhi.io an.
Docker Desktop enthält Docker Scout, der die VEX-Attestation abruft. Ein Sicherheitsanzeiger. Diese Anleitung zeigt Beispiele für Docker Scout, Trivy und Grype. Trivy und Grype können auch als Docker-Container ausgeführt werden, ohne dass eine Installation erforderlich ist. jq (optional), um das VEX-Datei zu filtern.

Windows-Nutzer: Offenlegen des Daemons
Das -v /var/run/docker.sock:/var/run/docker.sock-Socket-Mount, das in den containerisierten Scanner-Befehlen dieser Anleitung verwendet wird, funktioniert nicht auf Docker Desktop für Windows. Um containerisierte Scanner auf Windows zu verwenden, gehen Sie zu Einstellungen > Allgemein in Docker Desktop und aktivieren Sie Expose daemon auf tcp://localhost:2375 ohne TLS. Dann ersetzen Sie -v /var/run/docker.sock:/var/run/docker.sock durch -e DOCKER_HOST=tcp://host.docker.

Allgemein in Docker Desktop und aktiviere Expose daemon auf tcp://localhost:2375 ohne TLS. Dann ersetze -v /var/run/docker.sock:/var/run/docker.sock mit -e DOCKER_HOST=tcp://host.docker.internal:2375 in jedem Befehl, der ein containerisiertes Scanner ist. Achtung: Die Exposition des Daemons auf TCP ohne TLS macht Ihren System anfällig für Angriffe mit fremdem Code. Deaktiviere die Einstellung, wenn Sie fertig mit der Testung sind. Schritt 1: Scan ohne VEX

Meldet dich bei der Docker Hardened Images registry an: $ docker login dhi.io
Dann ziehe das Bild ab: $ docker pull dhi.io/python:3.13

Ein Ergebnis wie dieses bedeutet nicht, dass jede berichtete CVE behoben werden muss. Es bedeutet nur, dass diese CVEs gegen Pakete im Bild gemeldet wurden. Ob jede dieser CVEs in dieser Konfiguration tatsächlich ausgenutzt werden kann, ist eine separate Frage, und das ist genau, was VEX antwortet. Schritt 2: Herunterladen der VEX-Attestation
Exportiere die VEX-Attestation in einen lokalen Datei: $ docker scout vex get registry://dhi.io/python:3.13 --output python-vex.json
Der registry://-Prefix erzwingt Scout, die Attestation von der Registry-Stelle zu holen, anstatt von der lokalen Bildspeicherung. Da Sie das Bild in Schritt 1 gezogen haben, existiert es bereits lokal, und ohne diesen Prefix würde Scout keine Attestation finden. Dies holt eine signierte OpenVEX-Dokumentation von registry.scout.docker.com, dem Metadaten-Registry für alle Docker Hardened Images von Docker. Das Dokument enthält Docker's Exploitability-Bewertung für jede CVE im SBOM des Bildes. Bemerkung: Docker Scout holt dieses Datei automatisch während der Scanung. Sie müssen es nur explizit herunterladen, wenn die Scanner nicht nativ integriert sind, oder um die jq-Abfragen in Schritten 5 und 6 auszuführen.

Dieselbe Bilder, dieselbe Pakete, dieselbe CVE-Datenbank. Der einzige Unterschied ist Kontext. Der Scanner hat jede CVE gegenüber dem VEX-Datei gepasst und hat jede ausgewertet, die Docker als nicht ausnutzbar einschätzte. Die Pakete sind noch da. Überprüfe die SBOM und du wirst libc6, libsqlite3-0 und jedes andere Paket aus Schritt 1 finden. Null CVEs bedeutet nicht, dass die Pakete entfernt wurden. Es bedeutet, dass jeder gemeldete CVE einen dokumentierten Grund hat, warum er sich nicht auf diese Produktkonfiguration bezieht. VEX ist eine offene Standard: die Attestation reist mit dem Bild und jeder kompatible Scanner liest dieselbe Begründung. Schritt 4: Prüfe jede Unterdrückung und ihre Begründung
Docker Scout und Grype unterdrücken VEX-gematchte CVEs, aber bringen nicht das Justifizierungs-Code in ihre Ausgabe. Verwende Trivys --show-suppressed-Flag, um jede unterdrückte CVE zusammen mit ihrer jeweiligen per-CVE-Justifizierungs-Code anzuzeigen.
$ trivy image --scanners vuln --vex python-vex.json --show-suppressed dhi.io/python:3.13
Wenn Trivy nicht installiert ist, führe es in einem Container aus:
$ docker run --rm \
-v /var/run/docker.sock:/var/run/docker.sock \
-v "$(pwd)/python-vex.json:/tmp/vex.json" \
aquasec/trivy:latest image --scanners vuln --vex /tmp/vex.json --show-suppressed dhi.io/python:3.13

Schritt 5: Lesen Sie Docker's Begründung für ein spezifisches CVE
Die Begründungscodes sind maschinenlesbar; das status_notes-Feld im VEX-Datei enthält Docker's menschlich lesbare Begründung. Verwenden Sie jq, um nach einem spezifischen CVE zu suchen: $ jq '.statements[] | select(.vulnerability.name == "CVE-2010-4756") | {status, justification, status_notes}' python-vex.json Beispielausgabe: { "status": "not_affected", "justification": "vulnerable_code_cannot_be_controlled_by_adversary", "status_notes": "Standard POSIX Verhalten in glibc. Anwendungen, die glob verwenden, müssen selbst Schränken einrichten. Erfordert authentifizierte Zugriff und wird von der Debian-Sicherheits-Mannschaft als unbedeutend eingestuft." } Das status_notes-Feld erklärt Docker's Begründung in einfacher Sprache. Für CVE-2010-4756 wird das beschriebene glob-Verhalten durch das CVE als standard POSIX-Verhalten, erfordert authentifiziertes Zugriff und wird von der Debian-Sicherheits-Mannschaft als unbedeutend eingestuft. Jede Aussage listet auch die betroffenen Produkte als Paket-URLs (PURLs) auf, z.B. pkg:deb/debian/glibc@2.41-12%2Bdeb13u2?os_distro=trixie&os_name=debian&os_version=13. Trivy hat diese Aussage mit libc6 in der Image-SBOM gematcht, indem es diesen PURL gegen die in der SBOM aufgezeichneten Pakete verglichen hat.

Hier ist die deutsche Übersetzung des Textes:

Matched this statement dem libc6 in der Abbildungs-BOM durch Vergleich des PURLs mit den Paketen, die in der BOM aufgezeichnet sind. Es ist wichtig, dass PURL-Übereinstimmungen streng sind. Scanner müssen VEX-Anweisungen mit Paketen verknüpfen, indem sie den vollständigen PURL-Zeichenfolgen-String verwenden, einschließlich der os_name, os_version und os_distro-Qualifizierer. Eine Übereinstimmung nach Paketname allein kann es riskant machen, eine Suppression von einer OS-Version auf eine andere anzuwenden, wo das CVE ausnutzbare ist. Schritt 6: Filterung von VEX-Anweisungen nach Status
Nachdem Sie python-vex.json haben, können Sie es direkt mit jq abfragen. Zählen Sie Anweisungen nach Status: $ jq '[.statements[].status] | group_by(.) | map({status: .[0], count: length})' python-vex.json Liste alle CVEs, die unter Untersuchung stehen: $ jq '[.statements[] | select(.status == "under_investigation") | {cve: .vulnerability.name, products: [.products[]."@id"]}]' python-vex.json Liste alle CVEs mit betroffenen Status: $ jq '[.statements[] | select(.status == "affected") | {cve: .vulnerability.name, action: .action_statement}]' python-vex.json Die betroffene Abfrage gibt für das derzeitige dhi.io/python:3.13-Bild leer zurück, was der erwartete Ergebnis für ein aktiv gepflegtes Tag ist. Um betroffene Einträge für alle DHI Python-Versionen zu sehen, fragen Sie den VEX-Feed ab: $ curl -s https://raw.githubusercontent.com/docker-hardened-images/advisories/main/vex/python/dhi-python.vex.json \ | jq '[.statements[] | select(.status == "affected") | {cve: .vulnerability.name, action: .action_statement}]'

Voller VEX-Feed: $ curl -s https://raw.githubusercontent.com/docker-hardened-images/advisories/main/vex/python/dhi-python.vex.json | jq '[.statements[] | select(.status == "affected") | {cve: .vulnerability.name, action: .action_statement}]' Für Statusdefinitionen und Begründungscodes siehe den VEX-Status-Referenz. VEX-Status-Referenz: Für Statusdefinitionen, Begründungscodes und warum DHI nicht fixe verwendet, siehe Vulnerability Exploitability eXchange (VEX).
