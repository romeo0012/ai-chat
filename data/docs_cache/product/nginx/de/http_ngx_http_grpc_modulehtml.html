Module ngx_http_grpc_module

← Chat

Modul ngx_http_grpc_module erlaubt es, Anfragen an einen gRPC-Server (1.13.10) zu senden. Der Modul benötigt den Modul ngx_http_v2_module.

Beispielkonfiguration: 

server {
    listen 9000;
    http2 on;
    location / {
        grpc_pass 127.0.0.1:9000;
    }
}

Syntax: grpc_allow_upstream address;
Standard: —
Kontext: http, server, location
Diese Direktive erschien in Version 1.29.3.
Definiert die Bedingungen, unter denen der Zugriff auf einen gRPC-Server erlaubt oder verweigert wird. Wenn alle Zeichenfolgenparameter nicht leer und nicht mit „0“ gleich sind, wird der Zugriff erlaubt. Die Bedingungen werden jedes Mal vor dem Herstellen einer Verbindung zu einem gRPC-Server bewertet. Die Parameterwerte können Variablen enthalten: 
geo $upstream_last_addr $allow { volatile; 10.10.0.0/24 1; }

server {
listen 127.0.0.1;
}

Senden Sie ausgehende Verbindungen zu einem gRPC-Server von der angegebenen lokalen IP-Adresse mit einer optionalen Portnummer. Parameterwert kann Variablen enthalten. Um diese Parameterfunktion zu aktivieren, ist es in der Regel erforderlich, nginx-Workerprozesse mit Superbenutzerrechten auszuführen. Auf Linux ist dies nicht erforderlich, da der transparent-Parameter Workerprozessen die CAP_NET_RAW-Berechtigung vom Masterprozess erbt, wenn er angegeben wird. Es ist auch erforderlich, die Kernel-Routingtabelle für das Netzwerkverkehr des gRPC-Servers zu konfigurieren.

Syntax: grpc_buffer_size size; Standard: grpc_buffer_size 4k|8k; Kontext: http, server, location
Legt die Größe des Buffers fest, der für die Lesung der vom gRPC-Server empfangenen Antwort verwendet wird. Der erste Teil der Antwort enthält meistens einen kleinen Header; wenn er die Buffergröße überschreitet, wird die Antwort als ungültig betrachtet. Die Antwort wird dem Client synchron übermittelt, sobald sie empfangen wird. Standardmäßig ist die Buffergröße gleich einer Speicherseite. Das ist entweder 4K oder 8K, je nach Plattform. Es kann jedoch kleiner gemacht werden.

Syntax: grpc_connect_timeout time; Standard: grpc_connect_timeout 60s; Kontext: http, server, location
Legt eine Verbindungszeitlimit fest, um eine Verbindung mit einem gRPC-Server herzustellen. Es sollte beachtet werden, dass dieses Timeout normalerweise nicht mehr als 75 Sekunden betragen kann.

Syntax: grpc_hide_header field; Standard: — Kontext: http, server, location
Standardmäßig übermittelt nginx nicht die Headerfelder "Date", "Server", und "X-Accel-..." der Antwort eines gRPC-Servers an den Client. Die grpc_hide_header-Direktive legt zusätzliche Felder fest, die nicht übertragen werden. Deaktiviert die Verarbeitung bestimmter Antwortheaderfelder vom gRPC-Server. Die folgenden Felder können ignoriert werden: “X-Accel-Redirect” und “X-Accel-Charset”. Wenn nicht deaktiviert, hat die Verarbeitung dieser Headerfelder folgenden Effekt: “X-Accel-Redirect” führt zu einer internen Umleitung auf die angegebene URI; “X-Accel-Charset” setzt die gewünschte Zeichenkodierung einer Antwort. Bestimmt, ob gRPC-Serverantworten mit Codes größer oder gleich 300 an den Client weitergegeben oder von nginx intercepted und mit der error_page-Direktive verarbeitet werden sollen. Syntax: grpc_next_upstream error | timeout | denied | invalid_header | http_500 | http_502 | http_503 | http_504 | http_403 | http_404 | http_429 | non_idempotent | off ...

Die folgenden Beispiele zeigen, wie die Direktiven in einer Nginx-Konfigurationsdatei angegeben werden können:

server {
    listen 80;
    location / {
        grpc_pass_header X-Accel-Redirect;
        grpc_pass_header X-Accel-Charset;
        grpc_intercept_errors off;
        grpc_next_upstream error;
    }
}

In diesem Beispiel werden die Headerfelder “X-Accel-Redirect” und “X-Accel-Charset” an den gRPC-Server weitergegeben, während die gRPC-Antworten mit Codes größer oder gleich 300 an den Client weitergegeben werden.

Man sollte daran denken, dass die Übertragung einer Anfrage an den nächsten Server nur möglich ist, wenn nichts an einen Client gesendet wurde. Das heißt, wenn ein Fehler oder Timeout im Mittel der Übertragung einer Antwort auftritt, kann dies nicht korrigiert werden. Die Direktive definiert auch, was als unerfolgtes Kommunikationsversuch mit einem Server betrachtet wird. Die Fälle von Error, Timeout, denied und invalid_header werden immer als unerfolgte Versuche betrachtet, unabhängig davon, ob sie in der Direktive spezifiziert sind. Die Fälle von http_500, http_502, http_503, http_504 und http_429 werden als unerfolgte Versuche nur dann betrachtet, wenn sie in der Direktive spezifiziert sind. Die Fälle von http_403 und http_404 werden nie als unerfolgte Versuche betrachtet. Syntax: grpc_ssl_verify on | off; Standard: grpc_ssl_verify off; Kontext: http, server, location Aktiviert oder deaktiviert die Verifikation des Zertifikats des gRPC SSL-Servers. Syntax: grpc_ssl_verify_depth number; Standard: grpc_ssl_verify_depth 1; Kontext: http, server, location Setzt die Verifikationstiefe in der Zertifikatskette des gRPC SSL-Servers.
