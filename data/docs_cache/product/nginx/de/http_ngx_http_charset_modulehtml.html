Modul ngx_http_charset_module
Beispiel-Konfigurationsdirektiven: charset, charset_map, charset_types, override_charset, source_charset

Der Modul ngx_http_charset_module fügt den angegebenen Charset dem "Content-Type" Antwort-Headerfeld hinzu. Zusätzlich kann das Modul Daten von einem Charset in ein anderes umwandeln, allerdings mit einigen Einschränkungen: die Umwandlung erfolgt nur in einer Richtung – von Server zu Client, einzelzeichenbasierte Charsets können umgewandelt oder einzelzeichenbasierte Charsets zu/von UTF-8 umgewandelt werden.

Beispiel-Konfiguration: include conf/koi-win; charset windows-1251; source_charset koi8-r;

Syntax der Direktiven: charset charset | off;
Standard: charset off;
Kontext: http, server, location, if in location

Fügt den angegebenen Charset dem "Content-Type" Antwort-Headerfeld hinzu. Wenn dieses Charset anders ist als das Charset, das in der source_charset-Direktive angegeben ist, wird eine Umwandlung durchgeführt. Der Parameter off storniert die Hinzufügung des Charsets zum "Content-Type" Antwort-Headerfeld. Ein Charset kann mit einer Variable definiert werden: charset $charset;

In solchen Fällen müssen alle möglichen Werte der Variable in der Konfiguration mindestens einmal vorhanden sein, in der Form der charset_map, charset, oder source_charset-Direktiven. Für die Charsets utf-8, windows-1251, und koi8-r reicht es, die Dateien conf/koi-win, conf/koi-utf, und conf/win-utf in die Konfiguration einzubeziehen.

Direktiven. Für die Zeichenkodierungen utf-8, windows-1251 und koi8-r ist es ausreichend, die Dateien conf/koi-win, conf/koi-utf und conf/win-utf in die Konfiguration einzuschließen. Für andere Zeichenkodierungen funktioniert es, eine fiktive Umwandlungstabelle einzurichten, z.B.: charset_map iso-8859-5 _ { } Weitere Möglichkeiten bietet es, die Zeichenkodierung in der Antwort-Header-Feldzeile "X-Accel-Charset" zu setzen. Diese Funktionalität kann deaktiviert werden, indem die Direktiven proxy_ignore_headers, fastcgi_ignore_headers, uwsgi_ignore_headers, scgi_ignore_headers und grpc_ignore_headers verwendet werden. Syntax: charset_map charset1 charset2 { ... } Standard: — Kontext: http Beschreibt die Umwandlungstabelle von einer Zeichenkodierung in eine andere. Für die Umkehrung wird mit demselben Datenmaterial eine Tabelle aufgebaut. Die Zeichencodes werden in hexadezimal angegeben. Fehlende Zeichen im Bereich 80-FF werden mit “?” ersetzt. Wenn von UTF-8 umgewandelt wird, werden fehlende Zeichen in einem einzeiligen Zeichenkodierungssystem mit “&#XXXX;” ersetzt. Beispiel: charset_map koi8-r windows-1251 { C0 FE ; # kleines yu C1 E0 ; # kleines a C2 E1 ; # kleines b C3 F6 ; # kleines ts ... } Wenn eine Umwandlungstabelle zu UTF-8 beschrieben wird, sollten die Zeichencodes für den Zeichenkodierungssatz UTF-8 in der zweiten Spalte angegeben werden, z.B.: charset_map koi8-r utf-8 { C0 D18E ; # kleines yu C1 D0B0 ; # kleines a C2 D0B1 ; # kleines b C3 D186 ; # kleines ts ... } Vollständige Umwandlungstabellen von koi8-r zu windows-1251 und von koi8-r und windows-1251 zu utf-8 sind in den Verteilungsdateien conf/koi-win, conf/koi-utf und conf/win-utf enthalten. Syntax: charset_types mime-type ...

Die Syntax und die Beschreibung der Umwandlungstabellen sind genau so wie im Originaltext.

Von koi8-r und windows-1251 zu utf-8 sind in den Verteilungsdokumenten conf/koi-win, conf/koi-utf, und conf/win-utf bereitgestellt. Syntax: charset_types mime-type ...; Standard: charset_types text/html text/xml text/plain text/vnd.wap.wml application/javascript application/rss+xml; Kontext: http, server, location
Diese Direktive erschien in der Version 0.7.9. Aktiviert die Modulverarbeitung in Antworten mit den angegebenen MIME-Typen zusätzlich zu “text/html”. Der Sonderwert “*” passt sich jeder MIME-Typ an (0.8.29). Bis zur Version 1.5.4 wurde anstelle von “application/javascript” “application/x-javascript” als Standard-MIME-Typ verwendet.
Syntax: override_charset on | off; Standard: override_charset off; Kontext: http, server, location, wenn in location
Bestimmt, ob eine Konversion durchgeführt werden soll für Antworten, die von einem proxied oder einem FastCGI/uwsgi/SCGI/gRPC-Server empfangen wurden, wenn die Antworten bereits einen Charset in der “Content-Type”-Antwort-Header-Feld tragen. Wenn die Konversion aktiviert ist, wird der Charset, der in der empfangenen Antwort enthalten ist, als Quellcharset verwendet. Es sollte beachtet werden, dass wenn eine Antwort in einer Unteranfrage empfangen wird, dann die Konversion von der Antwortcharset auf das Charset der Hauptanfrage immer durchgeführt wird, unabhängig von der Einstellung des override_charset-Directives.
Syntax: source_charset charset; Standard: — Kontext: http, server, location, wenn in location
Definiert den Quellcharset einer Antwort. Wenn dieses Charset von dem Charset unterscheidet, das in der charset-Direktive angegeben ist, wird eine Konversion durchgeführt.
