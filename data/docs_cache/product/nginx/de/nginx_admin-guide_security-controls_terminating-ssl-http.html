NGINX SSL-Terminierung
In diesem Abschnitt wird erläutert, wie man auf NGINX und F5 NGINX Plus ein HTTPS-Server konfiguriert. Um einen HTTPS-Server einzurichten, fügt man im nginx.conf-Datei-Abschnitt den Parameter ssl zur listen-Direktive in einem server-Block hinzu und gibt die Pfade zu den Serverzertifikat- und privaten Schlüsselfiles an:

nginx
server {
 listen 443 ssl;
 server_name www.beispiel.de;
 ssl_certificate www.beispiel.de.crt;
 ssl_certificate_key www.beispiel.de.key;
 ssl_protocols TLSv1.2 TLSv1.3;
 ssl_ciphers HIGH:!aNULL:!MD5;
 #...
}

Das Serverzertifikat ist eine öffentliche Entität. Es wird an jeden Client gesendet, der sich mit dem NGINX- oder NGINX Plus-Server verbindet. Der private Schlüssel ist eine sichere Entität und sollte in einem Datei mit beschränkten Zugriffsrechten gespeichert werden. Allerdings muss der NGINX-Master-Prozess diesen Datei zugreifen können. Als Alternative kann der private Schlüssel in derselben Datei wie das Zertifikat gespeichert werden:

nginx
server {
 listen 443 ssl;
 server_name www.beispiel.de;
 ssl_certificate www.beispiel.de.cert;
 ssl_certificate_key www.beispiel.de.cert;
 ssl_protocols TLSv1.2 TLSv1.3;
 ssl_ciphers HIGH:!aNULL:!MD5;
}

In diesem Fall ist es wichtig, den Zugriff auf das Datei zu beschränken. Merke dir bitte, dass obwohl das Zertifikat und der Schlüssel in einer Datei gespeichert werden, nur das Zertifikat an die Clients gesendet wird. Die ssl_protocols und ssl_ciphers-Direktiven können verwendet werden, um zu verlangen, dass Clients nur die starken Versionen und Verschlüsselungsmethoden von SSL/TLS bei der Herstellung von Verbindungen verwenden. Seit der Version 1.23.4 verwendet NGINX diese Standardeinstellungen:

nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers HIGH:!aNULL:!MD5;

SSL/TLS-Verschlüsselungen bei der Herstellung von Verbindungen. Seit Version 1.23.4 verwendet NGINX diese Standardeinstellungen:

nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers HIGH:!aNULL:!MD5;

Es werden gelegentlich Sicherheitslücken in den Algorithmus von älteren Verschlüsselungen gefunden, und wir empfehlen, sie in einer modernen NGINX-Konfiguration auszuschalten (leider kann die Standardkonfiguration leicht nicht leicht geändert werden, weil es wegen der Rückwärtskompatibilität für bestehende NGINX-Implementierungen ist). Bitte beachten Sie, dass CBC-modus-Verschlüsselungen möglicherweise anfällig für eine Reihe von Angriffen sind (insbesondere der BEAST-Angriff, wie er in CVE-2011-3389 beschrieben ist), und wir empfehlen, SSLv3 nicht zu verwenden, aufgrund des POODLE-Angriffes, außer Sie müssen Legacy-Clients unterstützen.

OCSP-Validierung von Client-Zertifikaten
NGINX kann konfiguriert werden, um Online Certificate Status Protocol (OCSP) zu verwenden, um die Gültigkeit von X.509-Client-Zertifikaten zu überprüfen, die sie vorliegen lassen. Ein OCSP-Anfrage für den Status des Client-Zertifikats wird an einen OCSP-Antwortgeber gesendet, der die Zertifikatgültigkeit überprüft und die Antwort mit dem Zertifikatstatus zurückgibt: Gültig - das Zertifikat ist nicht entzogen Entzogen - das Zertifikat ist entzogen Unbekannt - keine Informationen über das Client-Zertifikat sind verfügbar

Um die OCSP-Validierung von SSL-Client-Zertifikaten zu aktivieren, müssen Sie den ssl_ocsp-Directive zusammen mit dem ssl_verify_client-Directive angeben, der die Zertifikatüberprüfung aktiviert:

nginx
server {
    listen 443 ssl;
    ssl_certificate /etc/ssl/foo.example.com.crt;
    ssl_certificate_key /etc/ssl/foo.example.com.key;
    ssl_verify_client on;
    ssl_ocsp on;
}

Zusammen mit dem Directive ssl_verify_client, das die Zertifikatsüberprüfung aktiviert:

server {
    listen 443 ssl;
    ssl_certificate /etc/ssl/foo.example.com.crt;
    ssl_certificate_key /etc/ssl/foo.example.com.key;
    ssl_verify_client on;
    ssl_trusted_certificate /etc/ssl/cachain.pem;
    ssl_ocsp on;
    # Enable OCSP validation
    #...
}

NGINX sendet die OCSP-Anfrage an den OCSP-URI im Clientzertifikat, es sei denn, ein anderer URI wird mit dem Directive ssl_ocsp_responder definiert. Nur OCSP-Responder mit der URL http:// werden unterstützt:

#...
ssl_ocsp_responder http://ocsp.example.com/;
#...

Um OCSP-Antworten in einem einzigen Speicherbereich zu cache, der von allen Arbeiterprozessen geteilt wird, muss der Directive ssl_ocsp_cache verwendet werden, um den Namen und die Größe des Bereichs zu definieren. Antworten werden für 1 Stunde gecachet, es sei denn, der Wert nextUpdate in der OCSP-Antwort gibt einen anderen Wert an:

#...
ssl_ocsp_cache shared:one:10m;
#...

Der Ergebnis der Clientzertifikatsvalidierung ist im Variablen $ssl_client_verify verfügbar, einschließlich des Grundes für die OCSP-Fehlermeldung.

Optimierung von HTTPS-Servern SSL-Operationen verbrauchen zusätzliche CPU-Ressourcen. Die aufwändigste CPU-intensive Operation ist die SSL-Handshake.

Für OCSP-Fehler. HTTPS-Server Optimierung SSL-Vorgänge verbrauchen zusätzliche CPU-Ressourcen. Die aufwändigste CPU-intensive Operation ist die SSL-Handshake. Es gibt zwei Möglichkeiten, die Anzahl dieser Operationen pro Client zu minimieren: Aktivieren Sie keepalive-Verbindungen, um mehr Anfragen über eine Verbindung zu senden
Reutilisieren Sie SSL-Session-Parameter, um SSL-Handshakes für parallele und nachfolgende Verbindungen zu vermeiden
Sessions werden im SSL-Session-Cache zwischen den Arbeitsprozessen gespeichert und konfiguriert durch die ssl_session_cache-Direktive. Ein Megabyte des Caches enthält etwa 4000 Sessions. Der Standard-Timeout beträgt 5 Minuten. Diesen Timeout kann man über die ssl_session_timeout-Direktive erhöhen. Hier ist ein Beispielkonfiguration optimiert für ein Mehrkernsystem mit 10 Megabyte gemeinsamem Session-Cache:

nginx 

worker_processes auto;
http {
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 10m;
    server {
        listen 443 ssl;
        server_name www.example.com;
        keepalive_timeout 70;
        ssl_certificate www.example.com.crt;
        ssl_certificate_key www.example.com.key;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_ciphers HIGH:!aNULL:!MD5;
        #...
    }
}

SSL-Zertifikat-Ketten

Einige Browser können über eine von einem bekannten Zertifizierungsstelle unterzeichnetes Zertifikat warnen, während andere Browser das Zertifikat ohne Probleme akzeptieren.

Dein Browser kann möglicherweise über eine Zertifikat-Unterschrift einer bekannten Zertifizierungsstelle beschweren, während andere Browser das Zertifikat ohne Probleme akzeptieren. Dies geschieht, weil die Ausstellungsstelle das Server-Zertifikat mit einem Intermediate-Zertifikat unterzeichnet hat, das in der Basis der bekannten vertrauenswürdigen Zertifikatsstellen, die in einem bestimmten Browser verteilt werden, nicht enthalten ist. In diesem Fall bietet die Autorität ein Bundle von kaskadierten Zertifikaten an, das mit dem signierten Server-Zertifikat konkateniert werden sollte. Das Server-Zertifikat muss vor den kaskadierten Zertifikaten in der kombinierten Datei auftreten:

cat www.example.com.crt bundle.crt &gt; www.example.com.chained.crt

Das erzeugte Datei sollte in der ssl_certificate-Direktive verwendet werden:

nginx
server {
    listen 443 ssl;
    server_name www.example.com;
    ssl_certificate www.example.com.chained.crt;
    ssl_certificate_key www.example.com.key;
    #...
}

Wenn das Server-Zertifikat und das Bundle in falscher Reihenfolge konkateniert wurden, startet NGINX nicht und zeigt folgenden Fehleranzeige:

SSL_CTX_use_PrivateKey_file(" ... /www.example.com.key") failed (SSL: error:0B080074:x509 certificate routines: X509_check_private_key:key values mismatch)

Dieser Fehler tritt auf, weil NGINX versucht, das Private-Key mit dem Bundle’s erstem Zertifikat anstelle des Server-Zertifikats zu verwenden. Browser speichern meistens Intermediate-Zertifikate, die sie von vertrauenswürdigen Stellen erhalten haben.

Zertifikat anstelle des Serverzertifikats. Browser halten meistens intermediäre Zertifikate, die sie empfangen und von vertrauenswürdigen Stellen signiert bekommen. Aktiv genutzte Browser können daher bereits die erforderlichen intermediären Zertifikate haben und sich nicht über ein gesendetes Zertifikat ohne verknüpftes Paket beschweren. Um sicherzustellen, dass der Server das komplette Zertifikat-Paket sendet, kann die openssl-Befehlszeilenschnittstelle verwendet werden:

openssl s_client -connect www.godaddy.com:443

In NGINX-Version 0.7.13 und früher kann SSL nicht selectiv für einzelne Zuhörer-Sockets aktiviert werden, wie oben gezeigt. SSL kann nur für das gesamte Server mithilfe des ssl-Directives aktiviert werden, was es unmöglich macht, ein einzelnes HTTP/HTTPS-Server einzurichten. Das ssl-Parameter zum listen-Directive wurde hinzugefügt, um dieses Problem zu lösen. Das ssl-Directive ist daher ab der Version 0.7.14 und später veraltet.

Der Direktiv listen wurde hinzugefügt, um dieses Problem zu lösen. Das Direktiv ssl ist daher ab Version 0.7.14 und später veraltet. Name-basierte HTTPS-Server
Ein häufiges Problem entsteht, wenn zwei oder mehr HTTPS-Server auf einer einzigen IP-Adresse konfiguriert werden:

server {
    listen 443 ssl;
    server_name www.beispiel.com;
    ssl_certificate www.beispiel.com.crt;
    #...
}
server {
    listen 443 ssl;
    server_name www.beispiel.org;
    ssl_certificate www.beispiel.org.crt;
    #...
}

Mit dieser Konfiguration erhält der Browser die Standard-Server-Zertifikat. In diesem Fall ist es www.beispiel.com, unabhängig von der angeforderten Server-Namen. Dies ist durch das Verhalten des SSL-Protokolls selbst verursacht. Der SSL-Verbindung wird vor dem Senden eines HTTP-Anfrage durch den Browser hergestellt und NGINX kennt nicht den Namen der angeforderten Server. Daher kann es nur das Standard-Server-Zertifikat anbieten. Das beste Lösung für dieses Problem ist, einer jedem HTTPS-Server eine separate IP-Adresse zuzuweisen:

server {
    listen 192.168.1.1:443 ssl;
    server_name www.beispiel.com;
    ssl_certificate www.beispiel.com.crt;
    #...
}
server {
    listen 192.168.1.2:443 ssl;
    server_name www.beispiel.org;
    ssl_certificate www.beispiel.org.crt;
    #...
}

Es ist zu beachten, dass es auch spezifische Proxy-Einstellungen für HTTPS-Upstreams (proxy_ssl_ciphers, proxy_ssl_protocols, und proxy_ssl_session_reuse) gibt, die für die Feinabstimmung des SSL zwischen NGINX und den Upstream-Servern verwendet werden können. Weitere Informationen hierzu finden Sie in der Dokumentation des HTTP-Proxy-Moduls.

Für die Feinjustierung von SSL zwischen NGINX und den upstream-Servern kannst du mehr darüber lesen, indem du dich in der HTTP-Proxy-Modul-Dokumentation informierst. Ein SSL-Zertifikat Mit Vielen Namen Es gibt weitere Möglichkeiten, eine einzelne IP-Adresse unter verschiedenen HTTPS-Servern aufzuteilen. Allerdings haben sie alle Nachteile. Eine Möglichkeit ist, ein Zertifikat mit vielen Namen in dem SubjectAltName-Feld der Zertifikatsdatei zu verwenden, beispielsweise www.beispiel.com und www.beispiel.org. Allerdings ist die Länge des SubjectAltName-Felds begrenzt. Eine weitere Möglichkeit ist, ein Zertifikat mit einem Wildcard-Namen zu verwenden, beispielsweise \*.beispiel.org. Ein Wildcard-Zertifikat sichert alle Unterdomänen der angegebenen Domäne, aber nur auf einer Ebene. Dieses Zertifikat passt zu www.beispiel.org, aber nicht zu beispiel.org oder www.sub.beispiel.org. Diese beiden Methoden können auch kombiniert werden. Ein Zertifikat kann genau und Wildcard-Namen in dem SubjectAltName-Feld enthalten. Beispiel: beispiel.org und \*.beispiel.org. Es ist besser, den Zertifikatsfile mit mehreren Namen und seinen privaten Schlüsselfile auf der http-Ebene deiner Konfiguration zu platzieren, damit sie die einzige Speicher-Kopie über alle Server erben:

nginx

ssl_certificate common.crt;
ssl_certificate_key common.key;
server {
 listen 443 ssl;
 server_name www.beispiel.com;
 #...
}
server {
 listen 443 ssl;
 server_name www.beispiel.org;
 #...
}

common.crt; ssl_certificate_key common.key; server {
listen 443 ssl;
server_name www.example.com;
#...
}
server {
listen 443 ssl;
server_name www.example.org;
#...
}

TLS Server Name Indication (SNI) ist eine allgemeinere Lösung für den Betrieb mehrerer HTTPS-Server auf einer einzigen IP-Adresse. Die Erweiterung TLS Server Name Indication (SNI, RFC 6066) ermöglicht es einem Browser, einen angeforderten Servernamen während des SSL-Handshakes zu übermitteln. Dadurch weiß der Server, welche Zertifikat er für die Verbindung verwenden soll. Obwohl SNI von modernen Browsern weitgehend unterstützt wird, können noch alte Browser kein Support für es bieten. Die folgenden Versionen unterstützen SNI:

  • Chrome 105 (Unterstützung für Windows-Versionen ab Vista)
  • Firefox 2.0 und andere Browser, die auf der Mozilla-Plattform basieren und ab rv:1.8.1
  • Microsoft Internet Explorer 7.0 (nur ab Windows Vista)
  • Opera 8.0
  • Safari 3.2.1 (Unterstützung für Windows-Versionen ab Vista)

Nur Domainnamen können in SNI übermittelt werden. Allerdings können einige Browser den Server-IP-Adresse als Namen übermitteln, wenn eine Anfrage eine literale IP-Adresse enthält. Es ist besser darauf zu verzichten. Um SNI in NGINX zu verwenden, muss es in beiden verwendeten OpenSSL-Bibliotheken unterstützt sein, mit der die NGINX-Binäre erstellt wurden, sowie der Bibliothek, mit der sie dynamisch gelinkt wird. OpenSSL unterstützt SNI ab der Version 0.9.8f, wenn es mit der Konfigurationsoption --enable-tlsext erstellt wurde.

runtime. OpenSSL unterstützt SNI ab der Version 0.9.8f, wenn es mit der Konfigurationsoption --enable-tlsext gebaut wurde. Seit OpenSSL Version 0.9.8j ist diese Option standardmäßig aktiviert. Wenn NGINX mit SNI-Unterstützung gebaut wurde, zeigt es das folgende, wenn es mit dem -V-Schalter gestartet wird:

NGINX wurde mit SNI-Unterstützung gebaut, jedoch ist es jetzt dynamisch mit einer OpenSSL-Bibliothek verknüpft, die keine tlsext-Unterstützung bietet, sodass SNI nicht verfügbar ist
