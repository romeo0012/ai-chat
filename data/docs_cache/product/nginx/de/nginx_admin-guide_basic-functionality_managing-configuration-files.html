Create NGINX Plus and NGINX Configuration Files

← Chat

Erstellt werden die NGINX Plus und NGINX Konfigurationsdateien. NGINX und NGINX Plus verwenden eine textbasierte Konfigurationsdatei, die standardmäßig den Namen nginx.conf hat. NGINX Plus: Standardort ist /etc/nginx für Linux oder /usr/local/etc/nginx für FreeBSD. NGINX Open Source: Der Ort hängt von dem Paketmanagementsystem ab, das verwendet wird, um NGINX zu installieren, und dem Betriebssystem. Es ist typischerweise einer von /usr/local/nginx/conf, /etc/nginx oder /usr/local/etc/nginx. Sie können die genauen Konfigurationsdateipfad mit dem --conf-path= Parameter im Ausgabe von dem nginx -V Befehl überprüfen:

nginx -V 2&gt;&amp;1 | awk -F: '/configure arguments/ {print $2}' | xargs -n1

Beispielausgabe:

--prefix=/etc/nginx --sbin-path=/usr/sbin/nginx --modules-path=/usr/lib64/nginx/modules --conf-path=/etc/nginx/nginx.conf # Der Pfad zu Ihrer Konfigurationsdatei
--error-log-path=/var/log/nginx/error.log --http-log-path=/var/log/nginx/access.log --pid-path=/var/run/nginx.pid --...&lt;mehr Parameter&gt;

Anweisungen
Die Konfigurationsdatei besteht aus Anweisungen und ihren Parametern. Einfache (einzeilige) Anweisungen enden mit einem Semikolon ( ; ). Andere Anweisungen dienen als „Container“, die verwandte Anweisungen zusammenfassen. Container werden in geschweiften Klammern ( {} ) eingeschlossen und werden oft als Blöcke bezeichnet. Hier sind einige Beispiele für einfache Anweisungen. nginx

user nobody;
error_log logs/error.

Hier sind einige Beispiele für einfache Direktiven. nginx 

user nobody;
error_log logs/error.log notice;
worker_processes 1;

Feature-spezifische Konfigurationsdateien
Um die Konfiguration leichter warten zu können, kann sie in eine Menge von feature-spezifischen Dateien aufgeteilt werden, die im Verzeichnis /etc/nginx/conf.d gespeichert werden. Mit dem include-Direktiv im Haupt-nginx.conf-Datei kann man auf die Inhalte der feature-spezifischen Dateien verweisen. 
include conf.d/http;
include conf.d/stream;
include conf.d/exchange-enhanced;

Kontexte
Einige oberstes-Niveau-Direktiven, die als Kontexte bezeichnet werden, gruppieren die Direktiven, die für verschiedene Verkehrstypen gelten: events – Allgemeine Verbindungsverarbeitung http – HTTP-Verkehr mail – Postverkehr stream – TCP und UDP-Verkehr
Direktiven, die außerhalb dieser Kontexte stehen, werden als im Hauptkontext bezeichnet.

Virtual Server
In jedem Verkehrsverarbeitungskontext werden eine oder mehrere Server-Blocks eingeschlossen, um virtuelle Server zu definieren, die die Verarbeitung von Anfragen steuern. Die Direktiven, die innerhalb eines Server-Kontextes eingeschlossen werden können, variieren je nach Verkehrstyp. Für HTTP-Verkehr (der http-Kontext) steuert jede Server-Direktive die Verarbeitung von Anfragen für Ressourcen an bestimmten Domains oder IP-Adressen. Eine oder mehrere Location-Kontexte innerhalb eines Server-Kontextes definieren, wie bestimmte Mengen von URIs verarbeitet werden sollen.

Hier ist ein Beispiel für eine Konfigurationsdatei mit mehreren Kontexten:

Die folgende Konfiguration zeigt die Verwendung von Kontexten.
nginx

User nobody; # eine Direktive im 'main'-Kontext
events { # Konfiguration der Verarbeitung von Verbindungen
}
http { # Konfiguration, die spezifisch für HTTP ist und alle virtuellen Server betrifft
server { # Konfiguration der HTTP-virtuellen Server 1
location /one { # Konfiguration für die Verarbeitung von URIs, die mit '/one' beginnen
}
location /two { # Konfiguration für die Verarbeitung von URIs, die mit '/two' beginnen
}
}
server { # Konfiguration der HTTP-virtuellen Server 2
}
}
stream { # Konfiguration, die spezifisch für TCP/UDP ist und alle virtuellen Server betrifft
server { # Konfiguration der TCP-virtuellen Server 1
}
}

Erbschaft
Allgemein erbt ein Kind-Kontext – also ein Kontext, der innerhalb eines anderen Kontextes (seinem Elternkontext) enthalten ist – die Einstellungen der Direktiven, die auf Ebene des Elternkontexts definiert sind. Einige Direktiven können in mehreren Kontexten auftreten, in dem Fall können Sie die Einstellung, die vom Elternkontext geerbt wird, durch die Direktive im Kind-Kontext überschreiben. Als Beispiel siehe die proxy_set_header-Direktive.

Neu laden Konfigurationsdatei
Um Änderungen an der Konfigurationsdatei in Kraft zu setzen, muss diese neu geladen werden.

Siehe die proxy_set_header-Direktive. Um Änderungen an der Konfigurationsdatei in Kraft zu setzen, muss diese neu geladen werden. Sie können entweder den nginx-Prozess neu starten oder dem Signal "reload" senden, um die Konfiguration aufzufrischen, ohne die Verarbeitung der aktuellen Anfragen zu unterbrechen. Weitere Informationen finden Sie unter Kontrollieren von nginx-Prozessen während der Laufzeit. Mit NGINX Plus können Sie die Lastverteilung dynamisch über die Server einer upstream-Gruppe anpassen, ohne die Konfiguration zu reloaden. Sie können auch die NGINX Plus API und den Schlüssel-Wert-Speicher verwenden, um dynamisch den Zugriff zu steuern, beispielsweise basierend auf der IP-Adresse des Clients.
