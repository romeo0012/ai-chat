HTTP-Last-Schaltung-Übersicht

Die Lastverteilung über mehrere Anwendungsinstanzen ist eine häufige Technik, um Ressourcenverbrauch zu optimieren, Durchsatz zu maximieren, Latenz zu reduzieren und Fault-Toleranz zu verbessern. NGINX und NGINX Plus bieten Layer 7 (Anwendungsschicht) Lastverteilung für HTTP und HTTPS-Verkehr. Sie können sich von mehreren Lastverteilungsalgorithmen auswählen, die sich von einfachen Round Robin bis zu anspruchsvollen Methoden wie Least Connections, Least Time und hashing-basierten Methoden erstrecken. NGINX Plus bietet zusätzliche Funktionen wie slow-start, das sanft die wiederhergestellten Server wieder einführt, und Session Persistenz (“sticky” Sessions), die die Anfragen des Clients an den gleichen Backend-Server weiterleitet. Für Layer 4 oder Transportschicht Lastverteilung siehe TCP und UDP Lastverteilung.

Proxy HTTP-Verkehr an eine Gruppe von Servern

Verwenden Sie NGINX oder NGINX Plus, um Lastverteilung über eine Gruppe von Servern durchzuführen. Zunächst definieren Sie die Gruppe von Servern mit dem upstream-Direktiv. Platzieren Sie das Direktiv in der http Kontext. Die Server in der Gruppe werden mithilfe des server-Direktivs konfiguriert (nicht zu verwechseln mit dem server block, der eine virtuelle Server-Instanz auf NGINX definiert). Beispielhaft wird die folgende Konfiguration eine Gruppe namens backend und besteht aus drei Serverkonfigurationen definieren:

nginx

http {
upstream backend {
server backend1.example.com weight=5;
server backend2.example.com;
server 192.0.0.0;
}
}

Dies kann mehr als drei tatsächliche Server ergeben:

Um mehr als drei tatsächlichen Servern:

http {
    upstream backend {
        server backend1.example.com weight=5;
        server backend2.example.com;
        server 192.0.0.1 backup;
    }
}

Um Anfragen an eine Servergruppe weiterzuleiten, wird der Name der Gruppe in der Direktive proxy_pass angegeben. Wenn ein alternativer Protokolltyp wie fastcgi verwendet wird, verwende stattdessen die entsprechende pass-Direktive. Die Liste der alternativen pass-Direktiven ist: fastcgi_pass, memcached_pass, scgi_pass, uwsgi_pass. Im folgenden Beispiel lädt ein virtuelles Server auf NGINX alle Anfragen an die backend-upstream-Gruppe, die in dem oben angegebenen Beispiel definiert wurde:

server {
    location / {
        proxy_pass http://backend;
    }
}

Das folgende Beispiel kombiniert die beiden oben angegebenen Snippets und zeigt, wie HTTP-Anfragen an die backend-Servergruppe weitergeleitet werden können. Die Gruppe besteht aus drei Servern, zwei von ihnen führen Instanzen desselben Anwendungsprogramms aus, während der dritte ein Backup-Server ist.

http {
    upstream backend {
        server backend1.example.com;
        server backend2.example.com;
        server 192.0.0.1 backup;
    }
    server {
        location / {
            proxy_pass http://backend;
        }
    }
}

Wähle eine Lastverteilungsmethode

NGINX Open Source unterstützt fünf Lastverteilungsmethoden: Round Robin, Least Connections, Least Time, IP Hash und Generic Hash. NGINX Plus unterstützt sechs Lastverteilungsmethoden: alle oben genannten, plus Random.

Mindestes Zeit, IP Hash, und Allgemeiner Hash. NGINX Plus unterstützt sechs Verteilungsverfahren für Lastenausgleich: alle oben genannten, plus Zufall. Hinweis: Wenn für jedes Verfahren außer Round Robin eine Konfiguration vorgenommen wird, muss die entsprechende Direktive (hash, ip_hash, least_conn, least_time, oder random) oberhalb der Liste der Serverdirektiven im upstream {} Block stehen. Round Robin – Anfragen werden gleichmäßig auf die Server verteilt, wobei die Servergewichte berücksichtigt werden. Dieses Verfahren wird standardmäßig verwendet; es gibt keinen Directive für die Aktivierung.

nginx

upstream backend {
  # keine Lastenausgleichsmethode ist für Round Robin Server backend1.example.com angegeben
  server backend1.example.com;
  server backend2.example.com;
}

Mindest Verbindungen – Eine Anfrage wird an den Server mit dem geringsten Anzahl aktiver Verbindungen gesendet. Dieses Verfahren berücksichtigt auch die Servergewichte.

nginx

upstream backend {
  least_conn;
  server backend1.example.com;
  server backend2.example.com;
}

IP Hash – Der Server, an den eine Anfrage gesendet wird, wird aus der IP-Adresse des Clients bestimmt. In diesem Fall wird entweder die erste drei Oktet der IPv4-Adresse oder die gesamte IPv6-Adresse verwendet, um den Hashwert zu berechnen. Das Verfahren garantiert, dass Anfragen von der gleichen Adresse auf den gleichen Server gelangen, solange dieser verfügbar ist.

nginx

upstream backend {
  ip_hash;
  server backend1.example.com;
  server backend2.example.com;
}
``
Wenn eines der Servers vorübergehend aus der Lastenausgleichsdrehung ausfallen muss, kann es mit dem down-Parameter markiert werden.
 Um die Servers temporär aus der Lastverteilung zu entfernen, kann der down-Parameter verwendet werden. Dadurch wird die aktuelle Hashung der Client-IP-Adressen erhalten. Anstatt von diesem Server zu verarbeiten, werden Anfragen automatisch an den nächsten Server in der Gruppe gesendet.
nginx

Copy upstream backend {
  server backend1.example.com;
  server backend2.example.com;
  server backend3.example.com down;
}
Generische Hash – Der Server, an den eine Anfrage gesendet wird, wird aus einer vom Nutzer definierten Schlüssel bestimmt. Der Schlüssel kann ein Textzeichenfolge, eine Variable oder eine Kombination sein. Beispielhaft könnte der Schlüssel eine verknüpfte Quell-IP-Adresse und Port sein. Dieses Beispiel verwendet eine URI:
nginx

Copy upstream backend {
  hash $request_uri consistent;
  server backend1.example.com;
  server backend2.example.com;
}
Die optionalen consistent-Parameter zum hash-Directive ermöglichen ketama-konsequente Lastverteilung. Anfragen werden gleichmäßig auf alle upstream-Server verteilt, basierend auf dem vom Nutzer definierten hashed Schlüsselwert. Wenn ein upstream-Server zu oder von einer upstream-Gruppe hinzugefügt oder entfernt wird, werden nur wenige Schlüssel umgezeichnet, was Cache-Fehler minimiert. Dies ist nützlich für die Lastverteilung von Cache-Servern oder anderen Anwendungen, die Zustand anhäufen.
Wenigste Zeit – Für jede Anfrage wählt NGINX den Server mit dem geringsten durchschnittlichen Latenz und den geringsten Anzahl aktiver Verbindungen aus. Der geringste durchschnittliche Latenz wird aufgrund des mit dem least_time-Directive enthaltenen Parameters berechnet.
Least Time – Für jede Anfrage wählt NGINX den Server mit dem geringsten durchschnittlichen Latenz und den geringsten Anzahl aktiver Verbindungen aus. Der geringste durchschnittliche Latenz wird aufgrund des mit dem least_time-Directive enthaltenen Parameters berechnet.
 Die geringste Anzahl aktiver Verbindungen. Die durchschnittliche Verzögerung wird anhand des mit dem least_time-Parameter berechnet, der mit der geringsten Zeit verbunden ist. Dieser Parameter kann einer der folgenden sein: header – Zeit, um das erste Byte vom Server zu empfangen, last_byte – Zeit, um die gesamte Antwort vom Server zu empfangen, last_byte inflight – Zeit, um die gesamte Antwort vom Server zu empfangen, berücksichtigend unvollständige Anfragen.
Beispiel:

nginx Copy upstream backend { least_time header; server backend1.example.com; server backend2.example.com; } 

Zufällig (NGINX Plus nur) – Jede Anfrage wird an einen zufällig ausgewählten Server weitergeleitet. Diese Methode berücksichtigt die Servergewichte. Wenn zwei Parameter angegeben sind, wählt NGINX zunächst zwei Server zufällig aus, und wählt dann zwischen diesen Servern anhand eines der folgenden angegebenen Methoden: least_conn – Die geringste Anzahl aktiver Verbindungen least_time=header (NGINX Plus) – Die geringste durchschnittliche Zeit zum Empfang der Antwort-Header vom Server ($upstream_header_time) least_time=last_byte (NGINX Plus) – Die geringste durchschnittliche Zeit zum Empfang der gesamten Antwort vom Server ($upstream_response_time)
Beispiel:

nginx Copy upstream backend { random two least_time=last_byte; server backend1.example.com; server backend2.example.com; server backend3.example.com; server backend4.example.com; } 

Die Zufalls-Ladeverteilungsmethode sollte für verteilte Umgebungen verwendet werden, in denen mehrere Lastenausgleichsanlagen Anfragen an die gleiche Gruppe von Backends weiterleiten.
 Methode sollte in umgebungen verwendet werden, in denen mehrere Load Balancer Anfragen an die gleiche Gruppe von Backends weiterleiten. Für Umgebungen, in denen der Load Balancer eine vollständige Sicht aller Anfragen hat, sollten andere Load Balancing Methoden verwendet werden. Servergewichte Einige Load Balancing Methoden, einschließlich Round Robin, Least Connections und Random, verteilen Anfragen gemäß ihren Servergewichten. Der Parameter weight zur Server-Direktive setzt den Gewichtswert eines Servers. Wenn kein Gewicht gesetzt wird, hat er den Standardwert 1: nginx

upstream backend {
server backend1.example.com weight=5;
server backend2.example.com;
server 192.0.0.1 backup;
} 

Im obigen Beispiel hat backend1.example.com Gewicht 5, während die anderen beiden Server den Standardwert (1) haben. Allerdings ist der Server mit der IP-Adresse 192.0.0.1 als Reserve-Server markiert und erhält Anfragen nur dann, wenn beide anderen Server nicht verfügbar sind. Mit dieser Konfiguration von Gewichten werden aus jeden 6 Anfragen 5 an backend1.example.com und 1 an backend2.example.com gesendet.
Server slow-start
Die Server-slow-start-Funktion verhindert, dass ein neuerlich wiederhergestellter Server überlastet wird, was möglicherweise zu Verzögerungen und der Markierung des Servers als fehlgeschlagen führt. Diese Funktion ist nur in NGINX Plus verfügbar. Slow-start erlaubt es, dass ein upstream-Server seinen Gewichtswert von 0 auf seinen nominalen Wert allmählich zurückerlangt, nachdem er wiederhergestellt oder verfügbar geworden ist.
 upstream-Server soll langsam seinen Wert von 0 auf seinen nominalen Wert erhöhen, nachdem er wiederverfügbar oder wiederhergestellt ist. Dies kann mit dem Parameter slow_start zur Server-Direktive bei Nginx durchgeführt werden:

nginx

upstream backend {
server backend1.example.com slow_start=30s;
server backend2.example.com;
server 192.0.0.1 backup;
}

Die angegebene Zeit (hier 30 Sekunden) legt die Zeit fest, während NGINX Plus die Anzahl der Verbindungen zum Server auf den vollen Wert erhöht. Wenn kein Wert angegeben wird, wird der slow-start-Modus deaktiviert (0). Hinweis: Wenn in einer Gruppe nur ein Server vorhanden ist, werden die Parameter max_fails, fail_timeout und slow_start zur Server-Direktive ignoriert und der Server wird nie als unverfügbar betrachtet.

Session-Persistenz

Session-Persistenz bedeutet, dass NGINX Plus die Benutzer-Sitzungen identifiziert und alle Anfragen einer Sitzung an den gleichen upstream-Server weiterleitet. NGINX Plus unterstützt drei Session-Persistenz-Methoden. Die Methoden werden mit dem Directive sticky festgelegt. (Für Session-Persistenz mit NGINX Open Source verwenden Sie die Directive hash oder ip_hash, wie oben beschrieben.)

Sticky Cookie – NGINX Plus fügt einer Session-Cookie beim ersten Antworten des upstream-Gruppen-Servers eine Session-Cookie hinzu und identifiziert den Server, der die Antwort gesendet hat. Der Wert der Cookie-Kopfzeile des Clients wird für den nächsten Anfrage verwendet und NGINX Plus leitet die Anfrage an den upstream-Server, der die erste Antwort gesendet hat, weiter. Dies ist die einfachste Session-Persistenz-Methode.


nginx
upstream backend {
    server backend1.example.com;
}
server {
    listen 80;
    location / {
        sticky cookie example_cookie;
        proxy_pass http://backend;
    }
}

Dieses ist die einfachste Methode zur Session-Persistenz. nginx

upstream backend {
    server backend1.example.com;
    server backend2.example.com;
    sticky cookie srv_id expires=1h domain=.example.com path=/;
}

Im Beispiel oben wird der srv_id-Parameter zum Festlegen des Cookienamens verwendet. Der optionalen expires-Parameter legt die Zeit fest, die der Browser den Cookie speichern soll (hier: 1 Stunde). Der optionalen domain-Parameter definiert die Domain, für die das Cookie gesetzt wird, und der optionalen path-Parameter definiert den Pfad, für den das Cookie gesetzt wird. Sticky route – Verwende den Route-Parameter zur Server-Anweisung, um einer Server-Instanz eine Route-Identifikator zuzuweisen. NGINX Plus gibt einer der Route-Identifikatoren dem Client zu, wenn es den ersten Anforderung des Clients empfängt. Anschließende Anforderungen vergleichen dann diese Route-Identifikatoren, die entweder in einem Cookie gespeichert oder im Anforderungs-URI enthalten sind.

upstream backend {
    server backend1.example.com route=a;
    server backend2.example.com route=b;
    sticky route $route_cookie $route_uri;
}

Im Beispiel oben wird zuerst der Session-Cookie auf den Route-Identifier überprüft. Wenn keiner vorhanden ist, wird der URI überprüft. Sticky learn – NGINX Plus findet zunächst Session-Identifikatoren durch die Überprüfung von Anforderungen und Antworten. Danach lernt NGINX Plus, welcher Backend-Server mit welcher Session-Identifikator assoziiert ist. Allgemein werden diese Identifikatoren in einem HTTP-Cookie übertragen.

NGINX Plus erkennt, welcher Backend-Server mit welcher Session-Identifikator assoziiert ist. Generell werden diese Identifikatoren über eine HTTP-Cookie übertragen. Wenn eine Anforderung einen bereits gelernten Session-Identifikator enthält, leitet NGINX Plus die Anforderung an den entsprechenden Server weiter:

nginx
upstream backend {
    server backend1.example.com;
    server backend2.example.com;
    sticky learn create=$upstream_cookie_examplecookie lookup=$cookie_examplecookie zone=client_sessions:1m timeout=1h;
}

In diesem Beispiel erstellt einer der Backend-Server eine Session, indem er den Cookie EXAMPLECOOKIE in der Antwort setzt. Der erforderliche create-Parameter gibt an, wie eine neue Session erstellt wird. Im Beispiel werden neue Sessions aus dem von dem Backend-Server gesendeten Cookie EXAMPLECOOKIE erstellt. Der erforderliche lookup-Parameter gibt an, wie nach vorhandenen Sessions gesucht wird. In unserem Beispiel werden vorhandene Sessions in dem von dem Client gesendeten Cookie EXAMPLECOOKIE gesucht. Der erforderliche zone-Parameter gibt an, in welchem shared memory Bereich alle Informationen über die sticky Sessions gespeichert werden. In unserem Beispiel heißt der Bereich client_sessions und ist 1 Megabyte groß. Dies ist eine anspruchsvollere Session-Persistenzmethode als die beiden vorherigen, da keine Cookies auf der Client-Seite gespeichert werden müssen: alle Informationen werden server-seitig in dem shared memory Bereich gespeichert.

Dieser Text benötigt keine Speicherung von Cookies auf der Client-Seite: Alle Informationen werden server-seitig in der gemeinsamen Speicherzone gespeichert. Wenn es mehrere NGINX-Instanzen in einem Cluster gibt, die das "sticky learn"-Verfahren verwenden, ist es möglich, die Inhalte ihrer gemeinsamen Speicherzonen zu synchronisieren, wenn die folgenden Bedingungen erfüllt sind: die Zonen haben den gleichen Namen, die Funktionalität "zone_sync" ist auf jedem Instanz konfiguriert, und der Sync-Parameter ist auf jeder Instanz angegeben.

nginx Copy

sticky learn erzeugen = $upstream_cookie_examplecookie suche = $cookie_examplecookie zone = client_sessions:1m timeout = 1h sync; }

Limitiere die Anzahl der Verbindungen

Mit NGINX Plus ist es möglich, die Anzahl der aktiven Verbindungen zu einem upstream-Server zu begrenzen. Der max_conns-Parameter setzt die maximale Anzahl von Verbindungen zu dem upstream-Server. Der queue-Befehl erlaubt es, überschüssige Verbindungen in eine Warteschlange zu halten. Er erfordert eine maximale Anzahl für die Warteschlange und einen Timeout. Wenn die max_conns-Grenze erreicht ist, wird die Anfrage in eine Warteschlange für weitere Verarbeitung gelegt. Wenn die Warteschlange erreicht ist, wenn kein queue-Befehl angegeben ist, oder wenn ein Client die Timeout-Zeit in der Warteschlange erreicht hat, wird der Client eine Fehlermeldung erhalten.

nginx Copy

upstream backend
{
server backend1.example.com max_conns=3;
server backend2.example.com;
queue 100 timeout=70;
}

Hinweis: Der max_conns-Limit wird ignoriert, wenn es in anderen Worker-Prozessen offene Idle-Keepalive-Verbindungen gibt.

Daten mit mehreren Arbeiterprozessen teilen
Wenn in einem upstream-Block der zone-Direktiv fehlt, behält jeder Arbeiterprozess seine eigene Kopie der Servergruppe-Konfiguration bei und pflegt seine eigene Menge an verwandten Zählern. Die Zähler umfassen die aktuelle Anzahl der Verbindungen zu jedem Server in der Gruppe und die Anzahl der gescheiterten Versuche, eine Anfrage an einen Server zu übermitteln. Folglich kann die Servergruppe-Konfiguration nicht dynamisch modifiziert werden.
Wenn die zone-Direktiv in einem upstream-Block enthalten ist, wird die Konfiguration der upstream-Gruppe in einem Speicherbereich gespeichert, der von allen Arbeiterprozessen geteilt wird. Dieser Szenario ist dynamisch konfigurierbar, weil die Arbeiterprozesse auf die gleiche Kopie der Gruppenkonfiguration zugreifen und die gleichen verwandten Zähler verwenden. Die zone-Direktiv ist vorgeschrieben für aktive Gesundheitsprüfungen und die dynamische Konfiguration der upstream-Gruppe.

Die folgenden verwandten Counters. Die Zone-Anweisung ist vorgeschrieben für aktive Gesundheitsprüfungen und die dynamische Konfiguration der upstream-Gruppe. Allerdings können sich auch andere Funktionen von upstream-Gruppen von der Verwendung dieser Anweisung profitieren. Beispielsweise, wenn die Konfiguration einer Gruppe nicht geteilt wird, führt jedes Arbeiterprozess sein eigenes Counter für die fehlgeschlagenen Versuche, eine Anfrage an einen Server zu übertragen (durch den Parameter max_fails festgelegt). In diesem Fall erhält jede Anfrage nur einen Arbeiterprozess. Wenn der Arbeiterprozess ausgewählt, um eine Anfrage zu verarbeiten, versagt, die Anfrage an einen Server zu übertragen, wissen die anderen Arbeiterprozesse nichts darüber. Während einige Arbeiterprozesse einen Server als nicht verfügbar betrachten können, können andere noch Anfragen an diesen Server senden. Um einen Server definitiv als nicht verfügbar zu betrachten, muss die Anzahl der fehlgeschlagenen Versuche innerhalb des Zeitraums, der durch den Parameter fail_timeout festgelegt ist, gleich der Anzahl der Arbeiterprozesse multipliziert mit max_fails sein. Andererseits garantiert die Zone-Anweisung das erwartete Verhalten. Ähnlich funktioniert die Least Connections-Lastenausgleichsmethode möglicherweise nicht wie erwartet ohne die Zone-Anweisung, mindestens unter niedriger Belastung. Diese Methode überträgt eine Anfrage an den Server mit dem geringsten Anzahl an aktiven Verbindungen. Wenn die Konfiguration der Gruppe nicht geteilt wird, verwendet jedes Arbeiterprozess sein eigenes Counter für die Anzahl der Verbindungen und kann eine Anfrage an denselben Server senden, den ein anderer Arbeiterprozess gerade eine Anfrage gesendet hat.

In den folgenden Beispielen wird gezeigt, wie die Zone-Anweisung verwendet werden kann, um das erwartete Verhalten zu gewährleisten:

upstream backend {
    zone backend 10m;
    server server1 192.168.1.1:80;
    server server2 192.168.1.2:80;
}

In diesem Beispiel wird die Zone-Anweisung verwendet, um die Anzahl der Verbindungen zu einem Server innerhalb einer bestimmten Zeitspanne (10 Minuten) zu begrenzen.

upstream backend {
    zone backend 10m with {
        fail_timeout = 5s;
        max_fails = 3;
    }
    server server1 192.168.1.1:80;
    server server2 192.168.1.2:80;
}

In diesem Beispiel wird die Zone-Anweisung verwendet, um die Anzahl der fehlgeschlagenen Versuche, eine Anfrage an einen Server zu übertragen, innerhalb einer bestimmten Zeitspanne (5 Sekunden) und die maximale Anzahl der fehlgeschlagenen Versuche (3) zu begrenzen.

In diesem Beispiel gibt der resolve-Parameter zum Server-Direktiv NGINX Plus an, periodisch die Domainnamen backend1.example.com und backend2.example.com neu aufzulösen in IP-Adressen. Wenn eine Domainname mehrere IP-Adressen aufweist, werden diese in die upstream-Konfiguration gespeichert und geladen. Vertragsnotiz

Die least_time-Lastverteilungsmethode wird in NGINX Plus ab der Version 6 und in NGINX Open Source ab der Version 1.31.0 unterstützt.

Dynamische Konfiguration mit der NGINX Plus-API

Mit NGINX Plus kann die Konfiguration einer upstream-Servergruppe dynamisch über die NGINX Plus-API geändert werden. Eine Konfigurationsbefehl kann verwendet werden, um alle Server oder einen bestimmten Server in einer Gruppe anzuzeigen, einen Parameter für einen bestimmten Server zu ändern und Server hinzuzufügen oder zu entfernen.
