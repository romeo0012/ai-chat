Um das Reloaden zu unterstützen, konfiguriert der NGINX Ingress Controller einen Server, der auf dem Unix-Socket unix:/var/lib/nginx/nginx-config-version.sock lauscht und für die /configVersion-URI eine Antwort mit der Konfigurationsversion liefert. Der NGINX Ingress Controller schreibt die Konfiguration in /etc/nginx/config-version.conf. Die Reloads erfolgen mit dieser Reihenfolge von Schritten: Der NGINX Ingress Controller aktualisiert die erzeugten Konfigurationsdateien, einschließlich aller Geheimnisse. Der NGINX Ingress Controller aktualisiert die Konfigurationsversion in /etc/nginx/config-version.conf. Der NGINX Ingress Controller startet nginx -s reload. Wenn das Kommando fehlschlägt, loggt der NGINX Ingress Controller den Fehler und betrachtet das Reloaden als fehlgeschlagen. Wenn das Kommando erfolgreich ist, überprüft der NGINX Ingress Controller periodisch die Konfigurationsversion, indem er ein HTTP-Anfrage an den Konfigurationsversion-Server auf unix:/var/lib/nginx/nginx-config-version.sock sendet. Sobald der NGINX Ingress Controller die richtige Konfigurationsversion von NGINX zurückerhält, betrachtet er das Reloaden als erfolgreich. Wenn er die richtige Konfiguration nicht nach der konfigurierbaren Timeout ( -nginx-reload-timeout) erkennt, betrachtet er das Reloaden als fehlgeschlagen. Der NGINX Ingress Controller Control Loop wird während eines Reloads unterbrochen, damit er keine Auswirkungen auf Konfigurationsdateien oder NGINX neu laden kann, solange der aktuelle Reload erfolgreich oder fehlgeschlagen ist.

Allgemein wird jederzeit, wenn eine überwachte Ressource geändert wird, der NGINX Ingress Controller die Konfiguration neu generieren und NGINX neuausladen. Es gibt drei speziellen Fälle: Start. Wenn der NGINX Ingress Controller gestartet wird, verarbeitet er alle Ressourcen im Cluster und reloadet NGINX erst dann. Dadurch wird vermieden, dass es zu einem "Neuauslagerungswirbel" kommt, indem nur einmal neuausgeladen wird. Batch Updates. Wenn der NGINX Ingress Controller mehrere gleichzeitige Anfragen von der Kubernetes-API erhält, wird er die Neuauslagerungen von NGINX pausieren, solange die Aufgabenwarteschlange leer ist. Dadurch wird die Anzahl der Neuauslagerungen reduziert, um den Einfluss von Batch Updates zu minimieren und das Risiko von OOM (Out of Memory) Fehlern zu reduzieren. NGINX Plus. Wenn der NGINX Ingress Controller NGINX Plus verwendet, wird er NGINX Plus nicht für Änderungen an den Endpoints-Ressourcen neuausladen. In diesem Fall verwendet der NGINX Ingress Controller die NGINX Plus API, um die entsprechenden upstreams zu aktualisieren und die Neuauslagerung zu überspringen.
