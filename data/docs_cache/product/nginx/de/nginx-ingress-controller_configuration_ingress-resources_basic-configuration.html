Grundlegende Konfiguration
Dieses Dokument zeigt eine Grundlegende Ressourcendefinition für den F5 NGINX Ingress Controller. Es verteilt Anfragen für zwei Dienste als Teil einer einzigen Anwendung. yaml Copy

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cafe-ingress
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - cafe.example.com
    secretName: tls-secret
  rules:
  - host: cafe.example.com
    http:
      paths:
      - path: /tea
        pathType: Prefix
        backend:
          service:
            name: tea-svc
            port:
              number: 80
      - path: /coffee
        pathType: Prefix
        backend:
          service:
            name: coffee-svc
            port:
              number: 80

Hier eine Zusammenfassung, was diese Ressourcendefinition bedeutet: Das metadata.name-Feld definiert den Namen der Ressource cafe-ingress. Das spec.tls-Feld setzt SSL/TLS-Terminierung ein: Das hosts-Feld legt die Zertifikat und Schlüssel für den cafe.example.com-Host fest. Das secretName-Feld verweist auf eine geheime Ressource durch ihren Namen, cafe-secret. Die geheime Ressource muss dem gleichen Namespace wie die Ingress angehören und der Art kubernetes.io/tls sein und die Schlüssel tls.crt und tls.key enthalten, die die Zertifikate und den privaten Schlüssel enthalten, wie hier beschrieben. Wenn die geheime Ressource nicht existiert oder ungültig ist, bricht NGINX jede Versuch, eine TLS-Verbindung zu den Hosts aufzubauen, zu denen die geheime Ressource angewendet wird. Das spec.rules-Feld definiert einen Host mit der Domäne cafe.example.com.

Zur Anwendung der geheimen Informationen auf die Hosts. Das Feld spec.rules definiert einen Host mit der Domänen-Adresse cafe.beispiel.com. Das Feld paths definiert zwei Pfad-basierte Regeln: Die Regel mit dem Pfad /tee weist NGINX an, Anfragen mit der URI /tee unter den Pods des tea-Dienstes zu verteilen, der mit dem Namen tea-svc im Cluster bereitgestellt wird. Die Regel mit dem Pfad /kaffee weist NGINX an, Anfragen mit der URI /kaffee unter den Pods des coffee-Dienstes zu verteilen, der mit dem Namen coffee-svc im Cluster bereitgestellt wird. Beide Regeln weisen NGINX an, Anfragen an Port 80 des entsprechenden Dienstes (durch das Feld servicePort) zu verteilen. Um mehr über die Ingress-Ressource zu erfahren, siehe die offizielle Kubernetes-Dokumentation zu Ingress-Ressourcen. Für vollständige Anweisungen zur Bereitstellung von Ingress- und Geheimnis-Ressourcen im Cluster, siehe den vollständigen Beispielcode im GitHub-Repository. Neue Funktionen ab Kubernetes 1.18 Ab Kubernetes 1.18 können Sie die folgenden neuen Funktionen verwenden: Das Feld host unterstützt Wildcard-Domänennamen, wie beispielsweise *.beispiel.com. Das Feld path unterstützt verschiedene Übereinstimmungsregeln mit dem neuen Feld pathType, das die folgenden Werte annimmt: Prefix für prefix-basierte Übereinstimmung, Exact für genauen Übereinstimmung und ImplementationSpecific, was der Standardtyp ist und dasselbe bedeutet wie Prefix.

Für prefixbasierte Übereinstimmung wird Exact für genauen Übereinstimmungen und ImplementationSpecific, das die Standardart ist und dasselbe wie Prefix ist. Beispiel:

Einschränkungen
NGINX Ingress Controller legt folgende Einschränkungen für Ingress-Ressourcen fest:

    

  • Das Feld host ist standardmäßig erforderlich. Um Ingress-Ressourcen das Feld host auszulassen, verwenden Sie den Befehl-line-Argument -allow-empty-ingress-host. Wenn -allow-empty-ingress-host aktiviert ist, ist spec.tls auf Ingress-Ressourcen ohne Host nicht unterstützt. Um TLS zu konfigurieren, verwenden Sie stattdessen den Befehl-line-Argument -default-server-tls-secret.
    • 

    

  • Der Wert von host muss eindeutig unter allen Ingress und VirtualServer-Ressourcen sein, es sei denn, die Ingress-Ressource ist eine mergeable minion.

host-Wert muss eindeutig unter allen Ingress und VirtualServer-Ressourcen sein, außer dem Ingress-Ressource ist eine vereinbarungsfähige Untertanin. Weitere Informationen finden Sie zum Thema Host und Listener-Kollisionen. Das Feld Pfad in spec.rules[].http.paths[] ist erforderlich für Exact und Prefix pathTypes. Die ImplementationSpecific pathType wird wie Prefix pathType behandelt, mit der Ausnahme, dass wenn diese pathType konfiguriert ist, das Feld Pfad in spec.rules[].http.paths[] nicht erforderlich ist. Pfad wird standardmäßig auf / gesetzt, wenn nicht festgelegt, aber die pathType auf ImplementationSpecific gesetzt ist. Fortgeschrittenes Konfiguration NGINX Ingress Controller erstellt NGINX-Konfiguration durch Ausführen einer Vorlage-Datei, die die Konfigurationsoptionen enthält. Diese Optionen werden mit dem Ingress-Ressource und dem NGINX Ingress Controller’s ConfigMap gesetzt. Das Ingress-Ressource erlaubt es nur, die Basisfunktionen von NGINX zu verwenden: host- und Pfadbasierte Routing und TLS-Terminierung. Für fortgeschrittenes Konfiguration gibt es zwei Optionen: Annotations können verwendet werden, um Anfrage-URIs zu überarbeiten oder zusätzliche Antwort-Header einzufügen. Snippets können verwendet werden, um raws NGINX-Konfiguration einzufügen und generierte Dateien zu ändern.
