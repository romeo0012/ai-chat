NGINX Reverse Proxy

Dieser Artikel beschreibt die Grundlegende Konfiguration eines Proxy-Servers. Sie lernen, wie Sie eine Anforderung von NGINX an proxydierte Server über verschiedene Protokolle weiterleiten, die Client-Anforderungskopfzeilen, die an den proxydierten Server gesendet werden, modifizieren und die Buffering von Antworten, die von proxydierten Servern kommen. Einführung
Proxying wird typischerweise verwendet, um die Last auf mehrere Server zu verteilen, den Inhalt von verschiedenen Websites transparent anzuzeigen oder Anforderungen an Anwendungsserver über Protokolle zu senden, die nicht HTTP sind.

Anforderung an einen proxydierten Server, wenn NGINX eine Anforderung proxydet, führt es folgendes aus:

  • Die Anforderung an einen spezifizierten Proxy-Server sendet
  • Die Antwort holt ab
  • Die Antwort an den Client sendet

Es ist möglich, Anforderungen an einen HTTP-proxydierten Server (einen anderen NGINX-Server oder jeden anderen Server) oder an einen nicht-HTTP-Server (der ein Anwendung, das mit einem bestimmten Framework entwickelt wurde, wie PHP oder Python, ausführen kann) über eine spezifizierte Protokoll-Schnittstelle zu proxyden. Unterstützte Protokolle umfassen FastCGI, uwsgi, SCGI und memcached. Um eine Anforderung an einen HTTP-proxydierten Server zu proxyden, wird der Directive proxy_pass innerhalb einer location angegeben. Beispiel:

nginx
location /some/path/ {
    proxy_pass http://www.example.com/link/;
}

Diese Beispielkonfiguration führt dazu, dass alle Anforderungen, die in dieser location verarbeitet werden, an den proxydierten Server an der angegebenen Adresse weitergeleitet werden. Diese Adresse kann ein Domain-Name oder eine IP-Adresse sein. Die Adresse kann auch einen Port enthalten:

nginx
location ~ \.php {
    proxy_pass http://127.0.0.1:9000;
}

In diesem Beispiel wird die Konfiguration angegeben, dass alle Anforderungen, die auf Dateien mit der Erweiterung .php zutreffen, an den proxydierten Server an der Adresse 127.0.0.1 und Port 9000 weitergeleitet werden.

Hinweis: In dem ersten Beispiel oben wird die Adresse des proxied Server folgend von einer URI, /link/, angegeben. Wenn die URI mit der Adresse angegeben wird, wird der Teil der Anfrage-URI, der mit dem Parameter des location übereinstimmt, ersetzt. Beispiel: Die Anfrage mit der URI /some/path/page.html wird proxied an http://www.example.com/link/page.html.

Wenn die Adresse ohne eine URI angegeben wird oder es nicht möglich ist, den Teil der URI zu ermitteln, der ersetzt werden soll, wird die komplette Anfrage-URI übergeben (möglicherweise, modifiziert). Um eine Anfrage an einen nicht-HTTP proxied Server zu senden, sollte das entsprechende **_pass-Directive verwendet werden: fastcgi_pass sendet eine Anfrage an einen FastCGI-Server, uwsgi_pass sendet eine Anfrage an einen uwsgi-Server, scgi_pass sendet eine Anfrage an einen SCGI-Server, memcached_pass sendet eine Anfrage an einen memcached-Server

Hinweis: In diesen Fällen können die Regeln für die Angabe von Adressen unterschiedlich sein. Sie könnten auch zusätzliche Parameter an den Server übergeben müssen (siehe die Referenzdokumentation für weitere Details). Das proxy_pass-Directive kann auch verwendet werden, um Anfragen an eine benannte Gruppe von Servern zu senden. In diesem Fall werden Anfragen unter den Servern der Gruppe verteilt, nach der angegebenen Methode.

Übertragung von Anfrage-Header:

NGINX modifiziert standardmäßig zwei Headerfelder in proxied Anfragen, “Host” und “Connection”, und eliminiert die Headerfelder, deren Werte leere Zeichenfolgen sind.

modifiziert zwei Headerfelder in angeforderten Anfragen über Proxys, „Host“ und „Connection“, und entfernt die Headerfelder, deren Werte leere Zeichenfolgen sind. „Host“ wird auf den Wert der $proxy_host-Variable festgelegt, und „Connection“ auf close. Um diese Einstellungen, sowie andere Headerfelder zu ändern, verwenden Sie den Befehl proxy_set_header. Dieser Befehl kann in einer Location oder höher angegeben werden. Er kann auch in einem bestimmten Serverkontext oder im http Block angegeben werden. Beispiel:

nginx
Copy location /some/path/ {
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_pass http://localhost:8000;
}

In dieser Konfiguration wird das „Host“-Feld auf die $host-Variable festgelegt. Um ein Headerfeld vom angeforderten Server nicht zu übermitteln, legt man es auf eine leere Zeichenfolge fest wie folgt:

nginx
Copy location /some/path/ {
    proxy_set_header Accept-Encoding "";
    proxy_pass http://localhost:8000;
}

Konfigurieren von Buffern
Standardmäßig buffert NGINX Antworten von Proxy-Servern. Eine Antwort wird in den internen Buffern gespeichert und wird dem Client nicht gesendet, bis die gesamte Antwort empfangen wurde. Buffern hilft, die Leistung mit langsamen Clients zu optimieren, die bei der synchronen Übertragung der Antwort vom Proxy-Server an den Client Zeit verschwenden könnten. Allerdings ermöglicht das Aktivieren von Buffern NGINX dem Proxy-Server, Antworten schnell zu verarbeiten, während NGINX die Antworten für so lange speichert, wie die Clients die Antworten herunterladen müssen.

Um schnell auf Antworten zu reagieren und während NGINX die Antworten so lange speichert, wie die Clients sie herunterladen müssen, ist die Direktive verantwortlich, die das Buffern aktiviert und deaktiviert, proxy_buffering. Standardmäßig ist es auf "on" gesetzt und das Buffern aktiviert. Die Direktiven proxy_buffers und proxy_buffer_size steuern, wie NGINX Daten speichert und buffert. Die Direktive proxy_buffers steuert die Größe und die Anzahl von Buffern, die für eine Anfrage reserviert werden. Der erste Teil der Antwort eines proxied Servers wird in einem separaten Buffer gespeichert, dessen Größe mit der Direktive proxy_buffer_size festgelegt wird. Dieser Teil enthält normalerweise eine vergleichsweise kleine Antwort-Headerzeile und kann kleiner als die Buffers für den Rest der Antwort gemacht werden. Im folgenden Beispiel wird die Anzahl der standardmäßig reservierten Buffers erhöht und die Größe des Buffers für den ersten Teil der Antwort kleiner als der Standardwert gemacht.

nginx

Location /some/path/ {
proxy_buffers 16 4k;
proxy_buffer_size 2k;
proxy_pass http://localhost:8000;
}

Wenn das Buffern deaktiviert ist, wird die Antwort dem Client synchron übertragen, während sie von dem proxied Server empfangen wird. Dieses Verhalten kann für schnelle interaktive Clients interessant sein, die so schnell wie möglich die Antwort empfangen sollen.

Verhalten wie das hier beschriebene mag für schnell interaktive Clients interessant sein, die so schnell wie möglich den Antwortbeginn empfangen möchten. Um das Buffern in einer bestimmten Stelle auszuschalten, legt man den proxy_buffering-Befehl in der Location fest, in der der off-Parameter verwendet wird, wie folgt:

nginx 

location /some/path/ {
    proxy_buffering off;
    proxy_pass http://localhost:8000;
}

In diesem Fall verwendet NGINX nur den Buffer, der durch proxy_buffer_size konfiguriert wurde, um den aktuellen Teil der Antwort zu speichern. Ein häufiger Einsatz eines Umkehrproxys ist das Lastenausgleichsverfahren. Siehe HTTP Lastenausgleich und TCP und UDP Lastenausgleich.

Wählen Sie eine Ausgangs-IP-Adresse
Wenn Ihr Proxyserver mehrere Netzwerk-Schnittstellen hat, können Sie manchmal eine bestimmte Quell-IP-Adresse für die Verbindung zu einem proxied Server oder einem upstream auswählen. Dies kann nützlich sein, wenn ein proxied Server hinter NGINX auf Verbindungen aus bestimmten IP-Netzwerken oder IP-Adressbereichen konfiguriert ist. In solchen Fällen können Sie den proxy_bind-Befehl und die IP-Adresse der notwendigen Netzwerk-Schnittstelle angeben:

nginx 

location /app1/ {
    proxy_bind 127.0.0.1;
    proxy_pass http://example.com/app1/;
}
location /app2/ {
    proxy_bind 127.0.0.2;
    proxy_pass http://example.com/app2/;
}

Die IP-Adresse kann auch mit einer Variable angegeben werden. Beispielhaft passt die $server_addr-Variable die IP-Adresse der Netzwerk-Schnittstelle durch, die die Anfrage akzeptiert hat:

nginx 

location /app3/ {
    proxy_bind $server_addr;
    proxy_pass http://example.com/app3/;
}
