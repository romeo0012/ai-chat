Konfigurieren der Protokollierung
Die Protokollierung ist essentiell für die Problembehandlung und das Verständnis, wie Verkehr durch Ihre Infrastruktur fließt. Dieser Artikel erklärt, wie Sie Fehler- und Zugriffsprotokolle in NGINX und NGINX Plus konfigurieren, die Protokollierungsformatierung anpassen, Lärm reduzieren, indem Sie bedingte Protokollierung einsetzen, und Protokolle an syslog weiterleiten, um sie zentral gesammelt zu halten.

Einrichten des Fehlerprotokolls
NGINX schreibt ein Fehlerprotokoll, das Probleme verschiedener Schweregradstufen aufzeichnet. Die error_log-Direktive setzt die Protokollierungsstelle und die Schweregradstufe fest. Die Protokollierungsstelle kann ein bestimmtes Dateiobjekt, stderr oder syslog sein. Standardpfad
Standardmäßig befindet sich das Fehlerprotokoll an logs/error.log, aber der absolute Pfad hängt von dem Betriebssystem und der Installationsmethode ab. Sie können den Pfad zum Fehlerprotokoll durch Ausführen des Befehls nginx -V und Extrahieren des Werts von --error-log-path=: Copy nginx -V 2>&1|sed -n 's/.*--error-log-path=\([^ ]*\).*/\1/p'

Der Ausgabewert hängt vom Betriebssystem ab. Für RHEL-basierte, Debian, Ubuntu: Copy /var/log/nginx/error.log
Für FreeBSD: Copy /usr/local/var/log/nginx/error.log
Für Docker-Images wird er an Containerprotokolle (stderr) über Symlinks /var/log/nginx/error.log -> /dev/stderr weitergeleitet.

Schweregradstufe
Die Schweregradstufe der Fehler folgt dem syslog-Klassifizierungssystem. Das Protokoll enthält Nachrichten von allen Schweregradstufen oberhalb der angegebenen Stufe. Das folgende Beispiel ändert den minimalen Schweregrad der Fehlernachrichten, um Nachrichten von Fehler zu Warn zu protokollieren: Copy error_log logs/error.

Der folgende Beispiel ändert den minimalen Schweregrad von Fehlermeldungen, die in das Log geschrieben werden sollen, von Fehler auf Warn:

error_log logs/error.log warn;

Mit dieser Einstellung werden Meldungen oberhalb des Warn-Levels in das Log geschrieben. Das umfasst die Schweregrade Warn, Error, crit, alert und emerg. Für Debug-Logging siehe Debugging NGINX. Fehler-Log-Formate

Die error_log-Direktive schreibt Fehler-Meldungen im standardmäßigen NGINX-Text-Fehler-Log-Format. In NGINX Plus unterstützt die error_log-Direktive auch strukturiertes JSON-Ausgabeformat über einen json-Parameter:

error_log /var/log/nginx/error.json error json;

Beispiel eines JSON-formatierten Fehler-Eintrags:

Fehler-Log-Erbschaft

Die Standard-Einstellung des Fehler-Logs funktioniert global. Um sie zu überschreiben, muss die error_log-Direktive in den Hauptkontext (main) der Konfiguration platziert werden. Einstellungen im Hauptkontext werden immer von anderen Konfigurationsniveaus (http, server, location) geerbt. Die error_log-Direktive kann auch auf den http, stream, server und location-Niveaus gesetzt werden. Einstellungen auf niedrigeren Niveaus übertragen die Einstellungen, die von den höheren Niveaus geerbt wurden. Jede Fehler-Meldung wird nur einmal in das Fehler-Log am nächsten Level, an dem der Fehler aufgetreten ist, geschrieben.

Jede Fehler-Nachricht wird nur einmal in den Fehlerprotokoll am nächsten Ebene, an der die Fehlersituation aufgetreten ist, geschrieben. Wenn jedoch mehrere error_log-Direktiven auf derselben Ebene angegeben sind, wird die Nachricht in alle angegebenen Protokolle geschrieben. Stellen Sie die Zugriffslog NGINX so ein, dass die Clientanfragen in das Zugriffprotokoll direkt nach der Bearbeitung eingetragen werden. Die access_log-Direktive gibt die Position des Protokolls und dessen Format an. Standardsmäßig befindet sich das Zugriffprotokoll in logs/access.log. Das Format der eingetragenen Nachrichten ist die vorgegebene kombinierte Formatierung. Um das Format der eingetragenen Nachrichten zu ändern, verwenden Sie die log_format-Direktive. Das Log-Format wird durch Variablen definiert. Das folgende Beispiel erweitert die vorgegebene kombinierte Formatierung, indem es das Schlüsselwort gzip_ratio angeben. Dadurch wird die Antwort auf einer virtuellen Server durch gzip-Kompression komprimiert.

nginx

log_format compression '$remote_addr - $remote_user [$time_local] ' '"$request" $status $body_bytes_sent ' '"$http_referer" "$http_user_agent" "$gzip_ratio"';
server {
    gzip on;
    access_log /spool/logs/nginx-access.log compression;
    ...
}

Ein weiteres Beispiel für das Log-Format ermöglicht die Verfolgung verschiedener Zeitwerte zwischen NGINX und einem upstream-Server. Dadurch kann eine Verzögerung Ihrer Website diagnostiziert werden.

log_format upstream_time '$remote_addr - $remote_user [$time_local] ' '"$request" $status $body_bytes_sent ' '"$http_referer" "$http_user_agent" "$request_time" "$upstream_response_time"';
server {
    ...
    access_log /spool/logs/nginx-access.log upstream_time;
    ...
}

tracking verschiedene Zeitwerte zwischen NGINX und einem upstream-Server. Dies kann bei der Diagnose einer Verlangsamung Ihrer Website helfen. Sie können die folgenden Variablen verwenden, um die angezeigten Zeitwerte zu protokollieren: $upstream_connect_time – Die Zeit, die für die Herstellung einer Verbindung mit einem upstream-Server benötigt wird $upstream_header_time – Die Zeit zwischen der Herstellung einer Verbindung und der Empfang des ersten Bytes des Antwortkopfes vom upstream-Server $upstream_response_time – Die Zeit zwischen der Herstellung einer Verbindung und der Empfang des letzten Bytes des Antwortkörpers vom upstream-Server $request_time – Die Gesamtzeit, die für die Bearbeitung einer Anfrage benötigt wird Alle Zeitwerte werden in Sekunden mit Millisekundenauflösung gemessen.

nginx

Kopiere http {
log_format upstream_time '$remote_addr - $remote_user [$time_local] ' '"$request" $status $body_bytes_sent ' '"$http_referer" "$http_user_agent"' 'rt="$request_time" uct="$upstream_connect_time" uht="$upstream_header_time" urt="$upstream_response_time"';
server {
access_log /spool/logs/nginx-access.log upstream_time;
...
}

- $remote_user [$time_local] ' '"$request" $status $body_bytes_sent ' '"$http_referer" "$http_user_agent"' 'rt="$request_time" uct="$upstream_connect_time" uht="$upstream_header_time" urt="$upstream_response_time"'; server { access_log /Spool/Logs/nginx-access.log upstream_time; ... } }

Beim Lesen der ergebnissenhaften Zeitwerte ist folgendes zu beachten:
Wenn eine Anfrage über mehrere Server verarbeitet wird, enthält die Variable mehrere Werte getrennt durch Kommas
Bei einem internen Weiterleitung von einer upstream-Gruppe auf eine andere werden die Werte getrennt durch Semikolon
Bei einer Anfrage, die kein upstream-Server erreichen kann oder kein vollständiges Header empfangen kann, enthält die Variable 0 (Null)
Bei internen Fehlern beim Verbinden zu einem upstream oder bei der Nutzung des Caches enthält die Variable - (Minuszeichen)
Die Logdatei kann durch Aktivieren des Buffers und des Caches optimiert werden. Mit dem Parameter für den Buffer aktiviert, werden die Nachrichten zunächst in den Buffer geschrieben. Wenn der Buffer voll ist (oder in anderen Fällen) werden die Nachrichten in die Logdatei geschrieben. Um die Logdatei-Deskriptoren zu cache, verwenden Sie den open_log_file_cache-Directive. Ähnlich dem error_log-Directive, wird die access_log-Anweisung auf einer bestimmten Konfigurationsstufe die Einstellungen der vorherigen Stufen überbaut. Bei der Bearbeitung einer Anfrage wird die Nachricht in die Logdatei geschrieben, die auf der aktuellen Stufe konfiguriert ist, oder die von den vorherigen Stufen geerbt wird.

Der Nachricht wird in das Log geschrieben, das auf dem aktuellen Level konfiguriert ist, oder von den vorherigen Levels geerbt wird. Wenn ein Level mehrere Zugriffsprotokolldefinitionen hat, wird die Nachricht in allen geschrieben. Die bedingte Protokollierung ermöglicht es, unbedeutende oder triviale Protokollaufzeichnungen aus dem Zugriffsprotokoll auszuschließen. In NGINX wird die bedingte Protokollierung durch das if-Parameter zur access_log-Direktive aktiviert. Dieses Beispiel ausschließt Anfragen mit HTTP-Statuscodes 2xx (Erfolg) und 3xx (Leitung):

nginx
map $status $loggable {
 ~^[23] 0;
 default 1;
}
access_log /pfad/zu/access.log combined if=$loggable;

Anwendungsfall: Proben von TLS-Parametern
Viele Clients verwenden TLS-Versionen älter als TLS 1.3. Obwohl viele Verschlüsselungen als ungesichert erklärt wurden, verwenden ältere Implementierungen sie noch; ECC-Zertifikate bieten größere Leistung als RSA, aber nicht alle Clients können sie akzeptieren. Viele TLS-Angriffe basieren auf einem "Mann im Mittel", der die Verschlüsselungshandshake-Übertragung abfangt und den Client und Server dazu zwingt, eine weniger sichere Verschlüsselung zu wählen. Daher ist es wichtig, F5 NGINX Plus so zu konfigurieren, dass keine schwachen oder veralteten Verschlüsselungen unterstützt werden, aber das tun kann alte Clients ausschließen. Sie können die SSL-Daten, die vom Client bereitgestellt werden, bewerten und bestimmen, wie groß der Anteil der Clients ist, die ausgeschlossen werden, wenn die Unterstützung für ältere SSL-Protokolle und Verschlüsselungen entfernt wird.

Der Client und bestimmen, welcher Anteil der Clients ausgeschlossen wird, wenn die Unterstützung für ältere SSL-Protokolle und Verschlüsselungsverfahren entfernt wird. Hier folgt ein Beispiel für eine Konfiguration, die die SSL-Protokolle, Verschlüsselung und den Header User-Agent aller verbundenen TLS-Clients protokolliert, wobei jede Client-Verbindung durch seine eindeutige Kombination aus IP-Adresse und User-Agent identifiziert wird. In diesem Beispiel wird jede Client-Instanz durch ihre eindeutige Kombination aus IP-Adresse und User-Agent identifiziert. Definiere den benutzerdefinierten Log-Format "sslparams", der die Version des SSL-Protokolls ($ssl_protocol), die verwendeten Verschlüsselungsmethoden ($ssl_cipher), die Client-IP-Adresse ($remote_addr) und den Wert des standardmäßigen User-Agent-HTTP-Anfragefelds ($http_user_agent) enthält:

nginx 

log_format sslparams '$ssl_protocol $ssl_cipher ' '$remote_addr "$http_user_agent"';

Definiere ein key-value-Speicher, der die IP-Adresse des Clients und seinen User Agent speichert, z.B. clients:

keyval_zone zone=clients:80m timeout=3600s;

Erzeuge eine Variable, z.B. $seen für jede eindeutige Kombination von $remote_addr und User-Agent-Header:

nginx 

keyval $remote_addr:$http_user_agent $seen zone=clients;

server {
listen 443 ssl;
ssl_protocols TLSv1 TLSv1.1 TLSv1.2;
ssl_ciphers HIGH:!aNULL:!MD5;
if ($seen = "") {
set $seen 1;
set $logme 1;
}
access_log /tmp/sslparams.log sslparams if=$logme;

...


}

Protokollierung in syslog Die syslog-Umgebung ist ein Standard für das Computerprotokollieren von Meldungen und ermöglicht die Sammlung von Protokollmeldungen von verschiedenen Geräten auf einem einzigen syslog-Server. In NGINX wird die Protokollierung in syslog über das syslog-Präfix in den Direktiven error_log und access_log konfiguriert. Syslog-Nachrichten können an einen Server gesendet werden, der ein Domänenname, eine IP-Adresse oder ein UNIX-Domänen-Sockett-Pfad sein kann. Ein Domänenname oder IP-Adresse kann mit einem Port angegeben werden, um den Standardport 514 zu überschreiben. Ein UNIX-Domänen-Sockett-Pfad kann nach dem unix: Präfix angegeben werden:

nginx 

error_log syslog:server=unix:/var/log/nginx.sock debug;
access_log syslog:server=[2001:db8::1]:1234,facility=local7,tag=nginx,severity=info;

In diesem Beispiel werden NGINX-Fehlerprotokollierungsnachrichten an einen UNIX-Domänen-Sockett auf dem debug-Protokollierungsniveau geschrieben, und das Zugriffsprotokoll wird an einen syslog-Server mit einer IPv6-Adresse und Port 1234 geschrieben. Der Parameter facility= gibt an, welchen Typ des Programms die Nachricht protokolliert. Der Standardwert ist local7. Mögliche weitere Werte sind: auth, authpriv, daemon, cron, ftp, lpr, kern, mail, news, syslog, user, uucp, local0 ... local7. Der Parameter tag= gibt einem syslog-Nachrichten einen benutzerdefinierten Tag (nginx in unserem Beispiel)
