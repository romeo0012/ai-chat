Modul ngx_http_rewrite_module Direktiven

Das Modul ngx_http_rewrite_module wird verwendet, um die Anfrage-URI mittels PCRE-Regulären Ausdrücken zu ändern, Rückgaberichtlinien zu generieren und konfigurationenabhängig auszuwählen. Die break, if, return, rewrite und set Direktiven werden in der folgenden Reihenfolge verarbeitet: die Direktiven dieses Moduls, die auf Serverebene angegeben sind, werden sequenziell ausgeführt; sukzessive: eine Location wird nach der Anfrage-URI durchsucht; die Direktiven dieses Moduls, die innerhalb der gefundenen Location angegeben sind, werden sequenziell ausgeführt; der Schleifenlauf wird wiederholt, wenn die Anfrage-URI nachbearbeitet wurde, aber nicht mehr als 10 Mal.

Direktiven Syntax: 

break;

Standard: —
Kontext: server, location, if
Beendet die aktuelle Menge von ngx_http_rewrite_module Direktiven. Wenn eine Direktive innerhalb der Location angegeben ist, wird die Weiterverarbeitung der Anfrage in dieser Location fortgesetzt.

Beispiel: 

if ($slow) {
    limit_rate 10k;
    break;
}

Syntax: 
if (bedingung) {
    ...
}

Standard: —
Kontext: server, location
Die angegebene Bedingung wird bewertet. Wenn wahr, werden die Direktiven dieses Moduls innerhalb der geschweiften Klammern ausgeführt, und die Anfrage wird der Konfiguration innerhalb des if-Direktivs zugewiesen. Konfigurationen innerhalb der if-Direktive erben sich von der vorherigen Konfigurationsstufe. Eine Bedingung kann jedes der folgenden sein: ein Variablenname; falsch, wenn der Wert einer Variable eine leere Zeichenkette oder "0" ist;

Vor Version 1.0.

folgendes: ein Variablenname; falsch, wenn der Wert einer Variablen ein leerer Zeichenfolgen- oder "0"-Wert ist; Bis zur Version 1.0.1 wurde jede Zeichenfolge, die mit "0" beginnt, als falscher Wert betrachtet. Vergleich einer Variablen mit einer Zeichenfolge mithilfe der "=" und "!="-Operatoren; Übereinstimmung einer Variablen mit einem regulären Ausdruck mithilfe der "~" (für sensitives Vergleichen) und "~*" (für insensitives Vergleichen) Operatoren. Reguläre Ausdrücke können Captures enthalten, die für spätere Wiederverwendung in den $1..$9 Variablen verfügbar gemacht werden. Negative Operatoren "!~" und "!~*" sind auch verfügbar. Wenn ein regulärer Ausdruck die Zeichen "}" oder ";" enthält, sollte das gesamte Ausdruck in einzelnen oder doppelten Anführungszeichen eingeschlossen werden. Überprüfung der Datei-Existenz mit den " -f " und "!-f" Operatoren; Überprüfung der Verzeichnis-Existenz mit den " -d " und "!-d" Operatoren; Überprüfung der Datei, Verzeichnis oder Symlink-Existenz mit den " -e " und "!-e" Operatoren; Überprüfung auf eine ausführbare Datei mit den " -x " und "!-x" Operatoren. Beispiele:

if ($http_user_agent ~ MSIE) {
    rewrite ^(.*)$ /msie/$1 break;
}
if ($http_cookie ~* "id=([^;]+)(?:;|$)") {
    set $id $1;
}
if ($request_method = POST) {
    return 405;
}
if ($slow) {
    limit_rate 10k;
}
if ($invalid_referer) {
    return 403;
}

Ein Wert der $invalid_referer eingebetteten Variablen wird durch die valid_referers Direktive festgelegt. Syntax: return code [text];return code URL;return URL; Standard: — Kontext: server, location, if Unterbricht die Verarbeitung und gibt dem Client das angegebene Code zurück.

TEXT:
[text];return URL;return-URL; Standard: — Kontext: server, location, if
Das Verarbeitung und Rückgabe des angegebenen URLs an den Client wird beendet. Der nicht-standard-Code 444 schließt eine Verbindung ohne Senden einer Antwort-Header. Ab der Version 0.8.42 ist es möglich, entweder einen Umleitung-URL (für Codes 301, 302, 303, 307 und 308) oder die Antwort-Text-Body (für andere Codes) zu spezifizieren. Eine Antwort-Text-Body und Umleitung-URL können Variablen enthalten. Als Sonderfall kann eine Umleitung-URL als URI lokal auf diesem Server angegeben werden, in dem Fall wird der vollständige Umleitung-URL nach dem Anforderungsschema ($scheme) und den Direktiven server_name_in_redirect und port_in_redirect gebildet. Zusätzlich kann eine URL für eine temporäre Umleitung mit dem Code 302 als einziger Parameter angegeben werden. Solche Parameter sollten mit dem "http://", "https://", oder "$scheme"-String beginnen. Eine URL kann Variablen enthalten. Nur die folgenden Codes konnten vor Version 0.7.51 zurückgegeben werden: 204, 400, 402 – 406, 408, 410, 411, 413, 416, und 500 – 504. Der Code 307 wurde als Umleitung bis Versionen 1.1.16 und 1.0.13 nicht behandelt. Der Code 308 wurde als Umleitung bis Version 1.13.0 nicht behandelt. Siehe auch die error_page-Direktive. Syntax: rewrite regex Ersatz [flag]; Standard: — Kontext: server, location, if
Wenn die angegebene reguläre Ausdrucks-Muster einer Anforderungs-URI entspricht, wird die URI entsprechend der Ersatz-Zeichenfolge geändert. Die rewrite-Direktiven werden in der Reihenfolge ihrer Auftritte in der Konfigurations-Datei ausgeführt.

In dem folgenden Text werden die Umbuchungsanweisungen genau wie im Ersetzungsfeld angegeben. Die Umbuchungsanweisungen werden in der Reihenfolge ihrer Aufstellung im Konfigurationsdatei ausgeführt. Es ist möglich, die Weiterverarbeitung der Anweisungen mittels Flaggen zu beenden. Wenn ein Ersetzungsfeld mit „http://“, „https://“ oder „$scheme“ beginnt, wird die Verarbeitung beendet und der Leiter zum Client zurückgegeben. Ein optionaler Flag-Parameter kann einer der folgenden sein: last beendet die Verarbeitung der aktuellen Menge von ngx_http_rewrite_module-Anweisungen und startet eine Suche nach einer neuen Lokation, die der geänderten URI entspricht; break beendet die Verarbeitung der aktuellen Menge von ngx_http_rewrite_module-Anweisungen wie beim break-Anweisung; redirect gibt eine temporäre Umleitung mit dem 302-Code zurück; wird verwendet, wenn das Ersetzungsfeld nicht mit „http://“, „https://“ oder „$scheme“ beginnt; permanent gibt eine permanente Umleitung mit dem 301-Code zurück. Der vollständige Umleitung-URL wird nach dem Anforderungsschema ($scheme) und den Direktiven server_name_in_redirect und port_in_redirect gebildet. Beispiel: server { ... rewrite ^(/download/.*)/media/(.*)\..*$ $1/mp3/$2.mp3 last; rewrite ^(/download/.*)/audio/(.*)\..*$ $1/mp3/$2.ra last; return 403; ... }

Wenn diese Anweisungen jedoch innerhalb der „/download/“-Lokation stehen, muss der last-Flag durch break ersetzt werden, andernfalls wird nginx 10 Zyklen durchführen und den 500-Fehler zurückgeben:

location /download/ {
rewrite ^(/download/.*)/media/(.*)\..*$ $1/mp3/$2.mp3 break;
rewrite ^(/download/.*)/audio/(.*)\..*$ $1/mp3/$2.ra break;
return 403;
...
}

Nginx wird 10 Zyklen durchführen und den Fehlercode 500 zurückgeben:

location /download/ {
    rewrite ^(/download/.*)/media/(.*)\..*$ $1/mp3/$2.mp3 break;
    rewrite ^(/download/.*)/audio/(.*)\..*$ $1/mp3/$2.ra break;
    return 403;
}

Wenn eine Ersetzungsszeichenkette die neuen Anforderungsargumente enthält, werden die vorherigen Anforderungsargumente nach ihnen angehängt. Falls dies unerwünscht ist, wird ein Fragezeichen am Ende einer Ersetzungsszeichenkette verhindert, dass sie angehängt werden, z.B.:

rewrite ^/users/(.*)$ /show?user=$1? last;

Wenn eine reguläre Ausdruckszeichenkette die Zeichen "}" oder ";" enthält, sollte die gesamte Ausdruckszeichenkette in einfache oder doppelte Anführungszeichen eingeschlossen werden.

Syntax:

rewrite_log on | off;

Standard: rewrite_log off;

Kontext: http, server, location, if

Aktiviert oder deaktiviert die Protokollierung der ngx_http_rewrite_module-Moduldirektivenverarbeitungsergebnisse in das Fehlerprotokoll auf der Notizenniveau.

Syntax:

set $variable value;

Standard: —

Kontext: server, location, if

Legt einen Wert für die angegebene Variable fest. Der Wert kann Text, Variablen und deren Kombinationen enthalten.

Syntax:

uninitialized_variable_warn on | off;

Standard: uninitialized_variable_warn on;

Kontext: http, server, location, if

Steuert, ob Warnungen über uninitialisierte Variablen protokolliert werden.

Internes Implementierung

Die ngx_http_rewrite_module-Moduldirektiven werden während der Konfigurationsphase in interne Anweisungen kompiliert, die während der Anfrageverarbeitung interpretiert werden. Ein Interpreter ist eine einfache virtuelle Stapelmaschine.

Die Konfigurationsstufe wird in interne Befehle umgewandelt, die während der Bearbeitung von Anfragen interpretiert werden. Ein Interpreter ist ein einfaches virtuelles Stack-Maschinenmodell. Beispielhaft wird die Direktive location /download/ { ... } in diese Befehle übersetzt:

Wenn die Bedingung wahr ist, wird eine Anfrage dieser Konfiguration zugewiesen, bei der limit_rate auf 10k festgelegt ist.
