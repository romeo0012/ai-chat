Dienstatisches Inhalt Dieser Abschnitt beschreibt, wie man NGINX und F5 NGINX Plus konfiguriert, um statisches Inhalt zu bereitstellen, wie man die zu suchenden Pfade definiert, um angeforderte Dateien zu finden, wie man Indexdateien einrichtet und wie man NGINX und NGINX Plus, sowie den Kernel, für optimale Leistung tun. Wurzelverzeichnis und Indexdateien Der root-Direktivwert gibt das Verzeichnis an, das verwendet wird, um nach einer Datei zu suchen. Um den Pfad einer angeforderten Datei zu erhalten, sucht NGINX den Wert des root-Direktivs mit dem angeforderten URI zusammen. Der Direktivwert kann auf jeder Ebene innerhalb der http {}, server {}, oder location {} Kontexte platziert werden. Im folgenden Beispiel wird der root-Direktivwert für einen virtuellen Server definiert. Er gilt für alle location {} Blöcke, wo der root-Direktivwert nicht explizit umdefiniert wird, um den Wert des root-Direktivs zu überschreiben:

nginx 

server {
    root /www/data;
    location / { }
    location /images/ { }
    location ~ \.(mp3|mp4) { root /www/media; }
}

Hier sucht NGINX nach einem URI, der mit /images/ beginnt, im Verzeichnis /www/data/images/ im Dateisystem. Wenn der URI jedoch mit der .mp3 oder .mp4 Erweiterung endet, sucht NGINX stattdessen nach der Datei im Verzeichnis /www/media/, weil es in der entsprechenden location-Block definiert ist. Wenn eine Anfrage mit einem Schrägstrich endet, behandelt NGINX sie als Anfrage nach einem Verzeichnis und versucht, eine Indexdatei in dem Verzeichnis zu finden. Der index-Direktivwert definiert den Namen der Indexdatei (der Standardwert ist index.html).

Suche nach einem Index-Datei in dem Verzeichnis. Der Index-Anweisung wird der Name des Index-Dateis (der Standardwert lautet index.html) zugewiesen. Um weiterzumachen mit dem Beispiel, wenn die Anfrage-URI /images/some/pfad/ ist, liefert NGINX das Datei /www/data/images/some/pfad/index.html, wenn es vorhanden ist. Wenn es nicht ist, liefert NGINX standardmäßig den HTTP-Statuscode 404 (Nicht gefunden) aus. Um NGINX zu konfigurieren, dass es stattdessen eine automatisch generierte Verzeichnisliste zurückgibt, muss man den Parameter on zum autoindex-Anweisung hinzufügen:

nginx

Location /images/ {
autoindex on;
}

Man kann mehr als einen Dateinamen im Index-Anweisung hinzufügen. NGINX sucht nach Dateien in der angegebenen Reihenfolge und liefert den ersten, den es findet zurück.

nginx

Location / {
index index.$geo.html index.htm index.html;
}

Der $geo-Variable, die hier verwendet wird, ist eine benutzerdefinierte Variable, die über die geo-Anweisung gesetzt wird. Der Wert der Variable hängt von der IP-Adresse des Clients ab. Um den Index-Datei zurückzugeben, prüft NGINX auf dessen Existenz und fügt dann eine interne Umleitung auf die URI auf, die durch das Anhängen des Namens des Index-Dateis an die Basis-URI erhalten wird. Die interne Umleitung erfolgt zu einem neuen Standortsuche und kann zu einem anderen Standort führen, wie im folgenden Beispiel zu sehen ist:

nginx

Location / {
root /data;
index index.html index.php;
}

location ~ \.php {
fastcgi_pass localhost:8000; #...
}

Hier wird bei einer Anfrage-URI /pfad/ angenommen, dass /data/pfad/index.html nicht vorhanden ist, aber /data/pfad/index.php vorhanden ist. Die interne Umleitung auf /pfad/index.php wird auf den zweiten Standort zugeordnet.

/Pfad/, und /data/Pfad/index.html existiert nicht, aber /data/Pfad/index.php existiert, die interne Umleitung auf /path/index.php ist auf die zweite Lokation zugeordnet. Dadurch erfolgt die Proxying des Anfrage. Versuche mehrere Optionen Die try_files-Direktive kann verwendet werden, um zu überprüfen, ob der angegebene Datei oder Verzeichnis existiert; NGINX führt eine interne Umleitung durch, wenn es existiert, oder gibt einen angegebenen Statuscode zurück, wenn es nicht existiert. Beispielhaft kann man die Existenz einer Datei, die der Anfrage-URI entspricht, wie folgt mit der try_files-Direktive und der $uri-Variable verwenden:

nginx

server {
 root /www/data;
 location /images/ {
 try_files $uri /images/default.gif;
 }
}

In diesem Fall wird die Datei im Form der URI verarbeitet, die mit den Direktiven root oder alias im Kontext der aktuellen Lokation oder Virtual Server gesetzt wurde. Im Falle, dass die Datei, die der Original-URI entspricht, nicht existiert, führt NGINX eine interne Umleitung auf die URI, die durch den letzten Parameter angegeben wurde, zurück, also /www/data/images/default.gif. Der letzte Parameter kann auch einen Statuscode (vorausgehend durch den Gleichheitszeichen) oder den Namen einer Lokation sein. Im folgenden Beispiel wird ein 404-Fehler zurückgegeben, wenn keiner der Parameter der try_files-Direktive auf eine existierende Datei oder Verzeichnis zeigt.

nginx

location / {
 try_files $uri $uri/ $uri. =404;
}

Zur Adresse try_files-Direktive sollte es sich um einen vorhandenen Datei- oder Verzeichnisbezeichner handeln. nginx 

location / {
    try_files $uri $uri/ $uri.html =404;
}

Im nächsten Beispiel wird die Anfrage, wenn der ursprüngliche URI oder der URI mit angehängtem Trailing Slash nicht auf einen vorhandenen Datei- oder Verzeichnisbezeichner zeigt, umgeleitet auf die angegebene Location, die sie an einen proxied Server weiterleitet. nginx 
location / {
    try_files $uri $uri/ @backend;
}

location @backend { proxy_pass http://backend.example.com; }

Leistungsoptimierung für die Datenübertragung Die Ladezeit ist ein entscheidender Faktor bei der Übertragung von jedem Inhalt. Durch kleine Optimierungen in Ihrer NGINX-Konfiguration können Sie die Produktivität steigern und die optimalen Leistungen erreichen. Aktivieren Sie sendfile
Voreingestellt wird NGINX die Übertragung von Dateien selbst durchführen und kopiert den Dateiinhalt in den Puffer, bevor er gesendet wird. Aktivieren Sie die sendfile-Direktive, um den Schritt des Kopierens des Dateninhalts in den Puffer zu eliminieren und das Direktkopieren von Daten von einer Datei-Descriptor zu einer anderen zu ermöglichen. Alternativ können Sie, um einen schnellen Verbindung zu komplett verhindern, dass er den Worker-Prozess komplett ausfüllt, die sendfile_max_chunk-Direktive verwenden, um die Menge an übertragenen Daten in einem einzelnen sendfile()-Aufruf (in diesem Beispiel auf 1 MB zu begrenzen): 

location /mp3 {
    sendfile on;
    sendfile_max_chunk 1m;
    #...
}

Einzelner sendfile()-Aufruf (in diesem Beispiel, zu 1 MB): nginx
Kopierlocation /mp3 {
sendfile an;
sendfile_max_Chunk 1m;  #...
}
Aktiviere tcp_nopush
Verwende die tcp_nopush-Direktive zusammen mit der sendfile an;-Direktive. Dadurch ermöglicht NGINX, HTTP-Antwortkopfzeilen in einem Paket sofort nach dem durch sendfile() erhaltenen Datenpaket zu senden.
nginx
Kopierlocation /mp3 {
sendfile an;
tcp_nopush an;  #...
}
Aktiviere tcp_nodelay
Die tcp_nodelay-Direktive ermöglicht die Überprüfung von Nagles-Algorithmus, der ursprünglich entwickelt wurde, um Probleme mit kleinen Paketen in langsamen Netzen zu lösen. Der Algorithmus konsolidiert eine Anzahl kleiner Pakete zu einem größeren und sendet das Paket mit einem 200 ms-Verzögerung. Heutzutage, wenn große statische Dateien gesendet werden, kann die Datenmenge sofort gesendet werden, unabhängig von der Paketgröße. Der Verzögerung wird auch Online-Anwendungen (ssh, Online-Spiele, Online-Handel usw.) betroffen. Voreingestellt ist die tcp_nodelay-Direktive auf on gesetzt, was bedeutet, dass Nagles-Algorithmus deaktiviert ist. Verwende diese Direktive nur für keepalive-Verbindungen:
nginx
Kopierlocation /mp3 {
tcp_nodelay an;
keepalive_timeout 65;  #...
}
Optimieren Sie die Backlog-Warteschlange
Eine wichtige Faktoren ist, wie schnell NGINX eingehende Verbindungen verarbeiten kann. Die allgemeine Regel ist, wenn eine Verbindung hergestellt wird, wird sie in die "listen"-Warteschlange des listen-Socket gesetzt. Unter normaler Belastung ist entweder die Warteschlange klein oder es gibt keine Warteschlange überhaupt.

queue einer Listendurchlauf-Socket. Unter normaler Belastung ist die Warteschlange meist klein oder es gibt keine Warteschlange überhaupt. Unter hoher Belastung kann die Warteschlange jedoch dramatisch anwachsen, was sich auf ungleichmäßige Leistung, abgebrochene Verbindungen und erhöhte Verzögerung auswirkt. Um die aktuelle Warteschlange anzeigen zu lassen, führen Sie den folgenden Befehl aus: Copy netstat -Lan

Die Ausgabe könnte wie folgt aussehen, was zeigt, dass in der Warteschlange auf Port 80 10 unbearbeitete Verbindungen gegenüber der konfigurierten Maximalanzahl von 128 abgewartete Verbindungen vorhanden sind. Dieses Szenario ist normal. Copy Aktuelle Warteschlangegrößen (qlen/incqlen/maxqlen)

Listen Local Address 0/0/128 *.12345 10/0/128 *.80 0/0/128 *.8080

Im Gegensatz dazu überschreitet die Anzahl der unbearbeiteten Verbindungen (192) im folgenden Befehl die Grenze von 128. Dies ist häufig der Fall, wenn eine Website stark frequentiert wird. Um die optimale Leistung zu erreichen, müssen Sie die maximale Anzahl der Verbindungen, die von NGINX für die Annahme abgewartet werden können, in Ihrem Betriebssystem und der NGINX-Konfiguration erhöhen. Copy Aktuelle Warteschlangegrößen (qlen/incqlen/maxqlen)
Listen Local Address 0/0/128 *.12345 192/0/128 *.80 0/0/128 *.8080

Stellen Sie die Betriebssystemeinstellungen so um: Erhöhe den Wert des net.core.somaxconn-Kernelparameters von seinem Standardwert (128) auf einen Wert, der für einen großen Lastspitzenverkehr hoch genug ist. In diesem Beispiel wird er auf 4096 erhöht. Für FreeBSD: Führen Sie den Befehl aus: Copy sudo sysctl kern.ipc.somaxconn=4096

Für Linux: Führen Sie den Befehl aus: Copy sudo sysctl -w net.core.somaxconn=4096

Verwenden Sie einen Texteditor, um die folgende Zeile in /etc/sysctl.conf hinzuzufügen: Copy net.core.somaxconn = 4096

Stellen Sie NGINX so um: Wenn Sie den somaxconn-Kernelparameter auf einen Wert größer als 512 festgelegt haben, müssen Sie den backlog-Parameter der NGINX-Listenanweisung anpassen, um zu stimmen: nginx Copy server { listen 80 backlog=4096; # ... }
