Tato sekce popisuje, jak nakonfigurovat NGINX a F5 NGINX Plus k tomu, aby sloužil statické obsah, jak definovat cesty, které se hledají k nalezení požadovaných souborů, jak nastavit indexové soubory a jak nakonfigurovat NGINX a NGINX Plus, stejně jako jádro, pro optimální výkon. Adresář Kořenový adresář a Indexové soubory Direktiva root určuje adresář kořenový, který se použije k hledání souboru. Chcete-li získat cestu požadovaného souboru, NGINX připojí k cestě určené direktivou root URI požadavku. Tato direktiva může být umístěna na libovolné úrovni v kontextech http {}, server {}, nebo location {}. V následujícím příkladu je definována direktiva root pro virtuální server. Platí pro všechny bloky location {} v kontextu, kde není explicitně direktiva root přidána k přesnému předefinování kořene:

nginx 

server {
    root /www/data;
    location / { }
    location /images/ { }
    location ~ \.(mp3|mp4) { root /www/media; }
}

Zde hledá NGINX požadavek, který začíná /images/ v adresáři /www/data/images/ v systému souborů. Ale pokud požadavek končí na konci .mp3 nebo .mp4 rozšíření, NGINX místo toho hledá soubor v adresáři /www/media/ protože je definován v odpovídajícím bloku location. Pokud požadavek končí zpětnou lomítkou, NGINX považuje to za požadavek na adresář a pokouší se najít indexový soubor v adresáři. Direktiva index definuje jméno indexového souboru (výchozí hodnota je index.html).

Hledejte indexový soubor v adresáři. Direktiva index určuje jméno indexového souboru (výchozí hodnota je index.html). Pokračujeme v příkladu, pokud je požadavek URI /images/some/cesta/, NGINX poskytne soubor /www/data/images/some/cesta/index.html, pokud existuje. Pokud neexistuje, NGINX vrací výchozí HTTP kód 404 (Nebylo nalezeno) jako standard. Chcete-li NGINX nastavit na vrácení automaticky generovaného seznamu adresářů místo toho, zahrňte parametr on do příkazu autoindex:

nginx

location /images/ {
 autoindex on;
}

Můžete zahrnout více než jeden název souboru do příkazu index. NGINX hledá soubory v uvedeném pořadí a vrátí první, který najde.

nginx

location / {
 index index.$geo.html index.htm index.html;
}

Zde použitá proměnná $geo je vlastní proměnná nastavená prostřednictvím příkazu geo. Hodnota proměnné závisí na adrese IP klienta. Chcete-li vrátil indexový soubor, NGINX kontroluje jeho existenci a poté provádí vnitřní přesměrování na URI získaný tím, že připojí název indexového souboru k základní URI. Vnitřní přesměrování vede k novému vyhledání lokace a může skončit v jiné lokaci, jako v následujícím příkladu:

nginx

location / {
 root /data;
 index index.html index.php;
}
location ~ \.php {
 fastcgi_pass localhost:8000; #...
}

Zde, pokud je v požadavku URI /cesta/ a /data/cesta/index.html neexistuje, ale /data/cesta/index.php existuje, vnitřní přesměrování na /cesta/index.php je mapováno na druhou lokaci.

Cesta/, a cesta/data/cesta/index.html neexistuje, ale cesta/data/cesta/index.php existuje, interní přesměrování na /path/index.php je mapováno na druhou lokaci. Výsledkem je, že požadavek je proxyován. Zkoušení Různých Možností Lze použít příkaz try_files, aby se ověřilo, zda zadaný soubor nebo adresář existuje; NGINX provádí interní přesměrování, pokud existuje, nebo vrátí určený stavový kód, pokud neexistuje. Například, aby se ověřil existenci souboru, který odpovídá požadovanému URI, můžete použít příkaz try_files a proměnnou $uri následovně:

nginx

server {
    root /www/data;
    location /images/ {
        try_files $uri /images/default.gif;
    }
}

V tomto případě, pokud soubor odpovídající původní URI neexistuje, NGINX provádí interní přesměrování na URI zadaný posledním parametrem, vrátí /www/data/images/default.gif. Poslední parametr může být také stavový kód (předcházený rovnítkem) nebo název lokace. V následujícím příkladu se vrací 404 chyba, pokud žádný z parametrů příkazu try_files neodpovídá existujícímu souboru nebo adresáři.

nginx

location / {
    try_files $uri $uri/ $uri.;
}

Přesunout se na příkaz try_files direktivu na existující soubor nebo adresář. nginx 

location / {
    try_files $uri $uri/ $uri.html =404;
}

V následujícím příkladu, pokud ani původní URI ani URI s připojeným závěrem složky nevedou na existující soubor nebo adresář, požadavek je přesměrován na zadanou lokaci, která ho přesměruje na server proxied. nginx 
location / {
    try_files $uri $uri/ @backend;
}

Lokace @backend 
location @backend {
    proxy_pass http://backend.example.com;
}

Zde se dozvíte, jak zlepšit výkon webu a získat hloubější znalosti o možnostech NGINX pro ukládání do mezipaměti. Zlepšit výkon při službě obsahu Nápadně rychlost zobrazování obsahu je klíčovým faktorem při poskytování jakékoli obsahu. Provedení malých úprav konfigurace NGINX může zvýšit výkon a pomoci dosáhnout optimálního výkonu. Povolit sendfile Výchozím nastavením NGINX spravuje vlastní přenos souborů a kopíruje soubor do bufferu před odesláním. Povolením příkazu sendfile directive odstraní krok kopírování dat do bufferu a umožní přímý přenos dat z jednoho popisovače do druhého. Alternativně, aby jedna rychlá spojení necelé obsadila procesor pracovníka, můžete použít příkaz sendfile_max_chunk directive k omezení množství dat přenesených v jednom volání sendfile() (v tomto příkladu na 1 MB):

nginx 

location /mp3 {
    sendfile on;
    sendfile_max_chunk 1m;
    #...
}

Povolit tcp_nopush
Použijte příkaz tcp_nopush společně s příkazem sendfile on;. Tímto se povolí NGINX poslat HTTP hlavičky odpovědi v jednom balíčku ihned po získání dat pomocí sendfile().
nginx
Kopie lokace /mp3 { sendfile on; tcp_nopush on; #... }
Povolit tcp_nodelay
Příkaz tcp_nodelay umožňuje přepsat algoritmus Nagle, původně navržený k řešení problémů s malými balíčky v pomalých sítích. Algoritmus shromažďuje určitý počet malých balíčků do většího a odesílá balíček s 200 ms zpožděním. V současné době, kdy se služí velké statické soubory, mohou data být odeslána okamžitě bez ohledu na velikost balíčku. Zpoždění také ovlivňuje online aplikace (ssh, online hry, online obchod, a tak dále). Výchozí nastavení příkazu tcp_nodelay je na on, což znamená, že algoritmus Nagle je vypnutý. Použijte tento příkaz pouze pro udržovací spojení:
nginx
Kopie lokace /mp3 { tcp_nodelay on; keepalive_timeout 65; #... }
Optimizovat frontu čekajících spojení Jedna z důležitých faktorů je, jak rychle NGINX může zpracovávat přicházející spojení. Obecná pravidla jsou, že při vytvoření spojení je uloženo do fronty čekajících spojení "listen" fronty posluchače. Při normální zátěži je buď fronta malá nebo neexistuje vůbec.

Pro Linux: Spusťte následující příkaz: Copy sudo sysctl -w net.core.somaxconn=4096

Použijte textový editor, abyste do souboru /etc/sysctl.conf přidali následující řádek: Copy net.core.somaxconn = 4096
