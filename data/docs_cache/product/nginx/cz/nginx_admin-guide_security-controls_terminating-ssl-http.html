Tento oddíl popisuje, jak nakonfigurovat server HTTPS na NGINX a F5 NGINX Plus. Nastavení serveru HTTPS
Chcete-li nastavit server HTTPS, upravte v souboru nginx.conf parametr ssl na příkazu listen v bloku serveru, poté určete umístění souborů s certifikátem serveru a souboru s klíčem privátním:

nginx
server {
    listen 443 ssl;
    server_name www.example.com;
    ssl_certificate www.example.com.crt;
    ssl_certificate_key www.example.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
    #...
}

Certifikát serveru je veřejná entita. Je odeslán každému klientovi, který se připojí k serveru NGINX nebo NGINX Plus. Klíč privátní je zabezpečená entita a by měl být uložen v souboru s omezeným přístupem. Nicméně proces hlavního NGINX musí mít možnost čtení tohoto souboru. Alternativně může být klíč uložen ve stejném souboru jako certifikát:

nginx
server {
    listen 443 ssl;
    server_name www.example.com;
    ssl_certificate www.example.com.cert;
    ssl_certificate_key www.example.com.cert;
}

V tomto případě je důležité omezit přístup k souboru. Poznamenejte si, že i když v tomto případě certifikát a klíč jsou uloženy v jednom souboru, pouze certifikát je odeslán klientům. Direktivy ssl\_protocols a ssl\_ciphers mohou být použity k tomu, aby klienti používali pouze silné verze a šifry SSL/TLS při navazování spojení. Od verze 1.23.4 podporuje NGINX tyto výchozí nastavení:

nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers HIGH:!aNULL:!MD5;

Připojení SSL/TLS kódování. Od verze 1.23.4 NGINX používá tyto výchozí nastavení: nginx Copy ssl_protocols TLSv1.2 TLSv1.3; ssl_ciphers HIGH:!aNULL:!MD5; Nalezne se často chyby v návrhu starších kódování a doporučujeme je v moderní konfiguraci NGINX zakázat (nevhodně, že výchozí konfigurace se snadno nezměnit, protože je z důvodu zpětné kompatibility pro existující nasazení NGINX). Upozornění, že mohou být CBC-mode kódování náchylné k řadě útoků (zejména útok BEAST, jak je popisováno v CVE-2011-3389), a doporučujeme nevyužívat SSLv3 z důvodu útoku POODLE, pokud není nutné podporovat staré klienty. OCSP ověřování certifikátů klienta NGINX může být konfigurován k použití Online Certificate Status Protocol (OCSP), aby kontroloval platnost X.509 certifikátů klienta, které jsou předány. OCSP požadavek na stav certifikátu klienta je odeslán na OCSP odpovědění, které kontroluje platnost certifikátu a vrátí odpověď s informací o stavu certifikátu: Dobrý - certifikát není zrušen Zrušený - certifikát je zrušen Neznámý - o klientském certifikátu není k dispozici žádná informace o klientovi Chcete-li povolit OCSP ověřování certifikátů klienta SSL, zadejte přímořský ssl_ocsp příkaz společně s příkazem ssl_verify_client, který povolí ověřování certifikátů: nginx Copy server { posluchávač 443 ssl; ssl_certifikát /etc/ssl/foo.example.com.crt; ssl_certifikát_klíč /etc/ssl/foo.example.com.key; }

Spolu s direktivou ssl_verify_client, která umožňuje ověřování certifikátu, nakonfigurujeme nginx:

server {
    listen 443 ssl;
    ssl_certificate /etc/ssl/foo.example.com.crt;
    ssl_certificate_key /etc/ssl/foo.example.com.key;
    ssl_verify_client on;
    ssl_trusted_certificate /etc/ssl/cachain.pem;
    ssl_ocsp on;
    # Enable OCSP validation
    #...
}

NGINX odesílá požadavek na OCSP validaci k URI OCSP zahrnutému v certifikátu klienta, pokud není definováno jiné URI pomocí direktivy ssl_ocsp_responder. Podporují se pouze respondery HTTP://:

#...
ssl_ocsp_responder http://ocsp.example.com/;
#...

Chcete-li uložit OCSP odpovědi do jedné paměťové zóny sdílené všemi pracovními procesy, můžete definovat direktivu ssl_ocsp_cache, aby určila jméno a velikost zóny. Odpovědi jsou uloženy po 1 hodinu, pokud není v odpovědi OCSP hodnota nextUpdate s jinou hodnotou:

#...
ssl_ocsp_cache shared:one:10m;
#...
`
Výsledek ověřování certifikátu klienta je dostupný v proměnné $ssl_client_verify, včetně důvodu selhání OCSP.

  1. Povolení udržování spojení pro odesílání několika požadavků prostřednictvím jednoho spojení
    2. 

    

  1. Použití parametrů SSL relace k vyhnutí se SSL handshake pro souběžné a následné spojení
    2. 

Relace se ukládají do cache SSL relací sdílené mezi procesy pracovníků a konfigurované pomocí příkazu ssl_session_cache. Jedna megabajt cache obsahuje asi 4000 relací. Výchozí časový limit je 5 minut. Tento limit lze zvětšit pomocí příkazu ssl_session_timeout. Níže je ukázkový konfigurační soubor optimizovaný pro systém s více jádry a s 10 megabajt cache relací sdílenou:
nginx

worker_processes auto;
http {
ssl_session_cache shared:SSL:10m;
ssl_session_timeout 10m;
server {
listen 443 ssl;
server_name www.example.com;
keepalive_timeout 70;
ssl_certificate www.example.com.crt;
ssl_certificate_key www.example.com.key;
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers HIGH:!aNULL:!MD5;
#...
}
} 
SSL Certifikátní řetězce
Některé prohlížeče mohou protestovat proti certifikátu podepsanému známou certifikační autoritou, zatímco jiné prohlížeče mohou akceptovat certifikát bez problémů.
 Text v češtině:
Mohou se stávet obavy ohledně certifikátu podepsaného známou certifikační autoritou, zatímco jiné prohlížeče mohou přijmout certifikát bez potíží. Toto se stává, protože vydavatel certifikátu podepsal certifikát serveru pomocí intermediárního certifikátu, který není v základní sadě známých důvěryhodných certifikačních autorit, která se distribuuje v určitém prohlížeči. V tomto případě poskytuje autorita balíček spojených certifikátů, které by měly být spojeny s podepsaným certifikátem serveru. Výsledný soubor by měl být použit v příkazu ssl_certificate: nginx

server {
listen 443 ssl;
server_name www.example.com;
ssl_certificate www.example.com.chained.crt;
ssl_certificate_key www.example.com.key;
#...
} 

Pokud serverový certifikát a balíček spojených certifikátů nebyly spojeny v pořadí, NGINX se nezdaří spustit a zobrazí následující chybovou zprávu:

SSL_CTX_use_PrivateKey_file(" ... /www.example.com.key") failed (SSL: error:0B080074:x509 certificate routines: X509_check_private_key:key values mismatch) 

Tato chyba nastane, protože NGINX se pokusil použít soukromý klíč s certifikátem balíčku namísto certifikátu serveru. Prohlížeče obvykle ukládají intermediární certifikáty, které obdrží a podepsali důvěryhodní autority.
 Certifikát místo serverového certifikátu. Prohlížeče obvykle ukládají intermediální certifikáty, které obdrží a které jsou podepsány důvěryhodnými autoritami. Aktivně používané prohlížeče mohou už mít požadované intermediální certifikáty a nemusí se žalovat o certifikát poslaný bez spojeného balíčku. Chcete-li se ujistit, že server posílá celou řetězovou certifikátovou složku, může se k tomu použít nástroj openssl příkazového řádku:
shell
openssl s_client -connect www.godaddy.com:443

Ve většině případů se vyskytne problém, kdy jsou konfigurovány dva nebo více serverů HTTPS, které poslouchají na stejnou IP adresu:

server {
listen 443 ssl;
server_name www.example.com;
ssl_certificate www.example.com.crt;
#...
}
server {
listen 443 ssl;
server_name www.example.org;
ssl_certificate www.example.org.crt;
#...
} 

S těmito nastaveními prohlížeč obdrží certifikát výchozího serveru. V tomto případě je to www.example.com bez ohledu na požadovaný server. Tento problém je způsoben chováním samotného protokolu SSL. SSL spojení je zahájeno před tím, než prohlížeč odesílá požadavek HTTP a NGINX nemá informace o požadovaném serveru. Proto může nabízet pouze certifikát výchozího serveru. Nejlepší řešení problému je přidělení oddělené IP adresy každému serveru HTTPS:

server {
listen 192.168.1.1:443 ssl;
server_name www.example.com;
ssl_certificate www.example.com.crt;
#...
}
server {
listen 192.168.1.2:443 ssl;
server_name www.example.org;
ssl_certificate www.example.org.crt;
#...
} 

Upozornění: Existují také určité nastavení proxy pro upstreamy HTTPS (proxy_ssl_ciphers, proxy_ssl_protocols, a proxy_ssl_session_reuse), která mohou být použita pro finální nastavení SSL mezi NGINX a upstream serverem. Další informace o těchto nastaveních můžete nalézt v dokumentaci HTTP proxy module.

Existují další způsoby, jak sdílet jeden IP adresář mezi několika serverů HTTPS. Všechny však mají své nevýhody. Jedna z možností je použití certifikátu s několika názvy v poli SubjectAltName certifikátu, například www.příklad.cz a www.příklad.sk. Však délka pole SubjectAltName je omezená. Další možností je použití certifikátu s divokou zástupnou hvězdičkou, například *.příklad.sk. Divoký certifikát zabezpečuje všechny poddomény zadaného domény, ale pouze na jedné úrovni. Tento certifikát odpovídá www.příklad.sk, ale neodpovídá příklad.sk nebo www.pod.příklad.sk. Tyto dvě metody mohou být kombinovány. Certifikát může obsahovat přesné a divoké názvy v poli SubjectAltName. Například příklad.sk a *.příklad.sk. Lepší je umístit soubor certifikátu s několika názvy a soubor soukromého klíče na úrovni http vaší konfigurace, aby se dostaly jediná kopie v paměti všech serverů:
nginx

ssl_certificate common.crt;
ssl_certificate_key common.key;
server {
listen 443 ssl;
server_name www.příklad.cz;
#...
}
server {
listen 443 ssl;
server_name www.příklad.sk;
#...
} 

 Obecný certifikát SSL (common.crt); Klíč SSL (common.key); server { posluchač 443 ssl; název_serveru www.example.com; #... } server { posluchač 443 ssl; název_serveru www.example.org; #... } Indikace jména serveru Výraznější řešení pro běh více serverů HTTPS na jednom IP adresáři je rozšíření pro SSL Indikaci jména serveru (SNI, RFC 6066), které umožňuje prohlížeči přenést požadované jméno serveru během SSL handshake. Díky tomuto řešení server pozná, kterou certifikát má použít pro spojení. Přestože SNI je široce podporováno moderními prohlížeči, některé staré prohlížeče mohou stále nedostatkovat v podpoře pro toto rozšíření. Hlavní prohlížeče podporují SNI od následujících verzí: Chrome 105 (Windows verze podporuje SNI od verze Vista nebo vyšší také) Firefox 2.0 a další prohlížeče používající platformu Mozilla Platform rv:1.8.1 Microsoft Internet Explorer 7.0 (ale pouze na Windows Vista nebo vyšší) Opera 8.0 Safari 3.2.1 (Windows verze podporuje SNI od verze Vista nebo vyšší) Může být přenášen pouze doménové jméno v SNI. Nicméně některé prohlížeče budou přenášet IP adresu serveru jako jeho jméno, pokud požadavek obsahuje adresu IP. Nejlepší je toto nevěřit. Poznámky k kompatibilitě
Podpora SNI byla ukázána přepínačem -V od verzí 0.8.21 a 0.7.62. Parametr ssl příkazu listen byl podporován od verze 0.7.14. Před verzí 0.8.21 mohl být určen pouze společně s parametrem default. SNI byla podporována od verze 0.5.23. Podpora sdílené SSL session cache byla podporována od verze 0.5.6. Protokoly SSL Verze 1.27.3 a novější: výchozí protokoly SSL jsou TLSv1.2 a TLSv1.3 (pokud je podporováno OpenSSL knihovnou). V opačném případě, kdy se používá OpenSSL 1.0.0 nebo starší, výchozí protokoly SSL jsou TLSv1 a TLSv1.1. Verze 1.23.4 a novější: výchozí protokoly SSL jsou TLSv1, TLSv1.1, TLSv1.2 a TLSv1.3 (pokud je podporováno OpenSSL knihovnou). Verze 1.9.1 a novější: výchozí protokoly SSL jsou TLSv1, TLSv1.1 a TLSv1.2 (pokud je podporováno OpenSSL knihovnou). Od verzí 0.7.
