Module ngx_http_upstream_module

← Chat

Modul ngx_http_upstream_module se používá k definování skupin serverů, které mohou být odkazovány přímořskými direktivami proxy_pass, fastcgi_pass, uwsgi_pass, scgi_pass, memcached_pass a grpc_pass.

Příklad Konfigurace 

upstream backend {
    server backend1.example.com weight=5;
    server backend2.example.com:8080;
    server unix:/tmp/backend3;
    server backup1.example.com:8080 backup;
    server backup2.example.com:8080 backup;
}
server {
    location / {
        proxy_pass http://backend;
    }
}

Dynamicky konfigurovatelná skupina s periodickými kontrolami stavu je k dispozici jako součást našich komerčních předplatných:

resolver 10.0.0.1;
upstream dynamic {
    zone upstream_dynamic 64k;
    server backend1.example.com weight=5;
    server backend2.example.com:8080 fail_timeout=5s slow_start=30s;
    server 192.0.2.1 max_fails=3;
    server backend3.example.com resolve;
    server backend4.example.com service=http resolve;
    server backup1.example.com:8080 backup;
    server backup2.example.com:8080 backup;
}
server {
    location / {
        proxy_pass http://dynamic;
        health_check;
    }
}

Syntaxe Direktiv: upstream name { ... }

Výchozí: —

Kontext: http

Definuje skupinu serverů. Servery mohou poslouchat na různých portech. Další možností je smíchání serverů poslouchajících na TCP a UNIX-doménové sockety.

Překlad:

O serverech. Servery mohou poslouchat na různých portech. Dále mohou se slučovat servery poslouchající TCP a UNIX-doménové sockety. Příklad:

upstream backend {
  server backend1.example.com weight=5;
  server 127.0.0.1:8080 max_fails=3 fail_timeout=30s;
  server unix:/tmp/backend3;
  server backup1.example.com backup;
}

Výchozí metoda rozdělení požadavků mezi servery je pomocí metody zatěžovacího kruhu s váhou. V předchozím příkladu bude každých 7 požadavků rozděleno následovně: 5 požadavků bude směrováno na backend1.example.com a jeden požadavek na každý druhý a třetí server. Pokud dojde k chybě při komunikaci s serverem, bude požadavek přesměrován na další server a tak dále až do zkoušení všech funkčních serverů. Pokud se nezdaří získat úspěšný odpověď z žádného z serverů, klient získá výsledek komunikace s posledním serverem.

Syntaxe: server adresa [parametry]; Výchozí: — Kontext: upstream Definuje adresu a další parametry serveru. Adresa může být určena jako doménové jméno nebo IP adresa, s možným portem, nebo jako UNIX-doménový socket cestou určenou po předponě "unix:". Pokud není zadán port, použije se port 80. Doménové jméno, které se rozšiřuje na více IP adres, definuje servery současně. Následující parametry mohou být definovány: weight=číslo nastavuje váhu serveru, výchozí hodnota je 1.

Poznámka: Tento překlad se týká pouze čistého textu. Technické termíny, kódy, příkazy, cesty souborů a URL zůstávají v původní anglické podobě. Struktura odstavců zůstává zachována.

Následující parametry mohou být definovány:
weight=číslo nastavuje váhu serveru, výchozí hodnota je 1. max_conns=číslo omezuje maximální počet současných aktivních připojení k proxovanému serveru (1.11.5). Výchozí hodnota je nula, což znamená, že není omezeno. Pokud serverová skupina nebyla umístěna do sdílené paměti, omezení platí pro každý pracovní proces. Pokud jsou připojení v režimu idle keepalive, mnoho pracovníků a sdílená paměť jsou povoleny, celkový počet aktivních a neaktivních připojení k proxovanému serveru může přesáhnout hodnotu max_conns. Od verze 1.5.9 až do verze 1.11.5 bylo toto parametro včleněno jako součást našich komerčních předplatných. max_fails=číslo nastavuje počet neúspěšných pokusů o spojení s serverem, které by měly proběhnout v časovém intervalu daném parametrem fail_timeout, aby se považoval server za nek dispozici také v časovém intervalu daném parametrem fail_timeout. Výchozí hodnota je nastavena na 1. Nula zde znamená, že se nepočítá počet pokusů. Co je považováno za neúspěšný pokus definuje příkazy proxy_next_upstream, fastcgi_next_upstream, uwsgi_next_upstream, scgi_next_upstream, memcached_next_upstream, a grpc_next_upstream. fail_timeout=čas nastavuje časový interval, během kterého by měly proběhnout určený počet neúspěšných pokusů o spojení s serverem, aby se považoval server za nek dispozici; a časový interval, během kterého bude server považován za nek dispozici.

Server měl by se v případě, že by se server považoval za nedostupný; a dobu, za kterou se server bude považovat za nedostupný. Výchozí hodnota je nastavena na 10 sekund. Backup označuje server jako záložní server. Budou mu přiřazovány požadavky, když primární servery nejsou dostupné. Tento parametr nelze použít společně s hash, ip_hash a náhodnou distribucí zatížení. Down označuje server jako trvale nedostupný. Resolve monitoruje změny IP adres, které odpovídají doménovému jménu serveru, a automaticky upraví konfiguraci upstream bez nutnosti restartovat nginx (1.5.12). Serverová skupina musí být umístěna v paměti sdílené. Pro to, aby tento parametr fungoval, musí být příkaz resolver určen v bloku http nebo v odpovídajícím bloku upstream. Před verzí 1.27.3 byl tento parametr k dispozici pouze jako součást našich komerčních předplatných. service=name umožňuje rozlišování záznamů DNS SRV a nastavuje název služby (1.9.13). Pro to, aby tento parametr fungoval, je nutné určit parametr resolve pro server a určit hostname bez čísla portu. Pokud název služby neobsahuje tečku (“.”), pak se vytvoří RFC-kompatibilní název a protokol TCP je přidán k prefixu služby. Například pro vyhledání záznamu _http._tcp.backend.example.com SRV je nutné určit příkaz: server backend.example.

Služba prefix. Například k vyhledání záznamu SRV _http._tcp.backend.example.com je nutné určit direktivu: server backend.example.com service=http resolve; Pokud jméno služby obsahuje jeden nebo více teček, pak je jméno vytvářeno spojením prefixu služby a jména serveru. Například k vyhledání záznamů SRV _http._tcp.backend.example.com a server1.backend.example.com je nutné určit direktivy: server backend.example.com service=_http._tcp resolve; server example.com service=server1.backend resolve; Nejvyšší prioritní záznamy SRV (záznamy s nejnižším počtem prioritních hodnot) se řeší jako primární servery, ostatní záznamy SRV se řeší jako záložní servery. Pokud je pro server určen parametr backup, nejvyšší prioritní záznamy SRV se řeší jako záložní servery, ostatní záznamy SRV se ignorují. Před verzí 1.27.3 byl tento parametr k dispozici pouze jako součást našich komerčních předplatných. route=string nastavuje jméno cesty serveru. Před verzí 1.29.6 byl tento parametr k dispozici pouze jako součást našich komerčních předplatných. drain umístí server do režimu "draining" (1.13.6). V tomto režimu budou k serveru přesměrovávány pouze požadavky vázané na server. Před verzí 1.13.6 mohl být tento parametr změněn pouze pomocí modulu API. Před verzí 1.29.6 byl tento parametr k dispozici pouze jako součást našich komerčních předplatných.

Použitím modulu API. Před verzí 1.29.6 byl parametr dostupný pouze jako součást našich komerčních předplatných. Další parametry, které jsou k dispozici jako součást našich komerčních předplatných, zahrnují: slow_start=čas nastavuje dobu, během které server obnoví svou váhu z nuly na hodnotu nominační, kdy se nezdravý server stane zdravým, nebo když se server stane dostupným po určitém času, kdy byl považován za nedostupný. Hodnota výchozí je nula, tedy rychlý start je vypnutý. Tento parametr nelze použít společně s hashováním, ip_hash a náhodným zatížením. Pokud je v skupině jen jeden server, parametry max_fails, fail_timeout a slow_start jsou ignorovány, a takový server nikdy nebude považován za nedostupný. Syntaxe: zóna jméno [velikost]; Výchozí: — Kontext: upstream Tento příkaz se objevil v verzi 1.9.0. Definuje jméno a velikost sdílené paměti zóny, která uchovává konfiguraci a stav běhu skupiny, který je sdílen mezi procesy pracovníků. Několik skupin může sdílet stejnou zónu. V tomto případě stačí určit velikost pouze jednou. Dále, jako součást našich komerčních předplatných, takové skupiny umožňují změnu skupiny členů nebo úpravy nastavení určitého serveru bez nutnosti restartovat nginx. Konfigurace je dostupná prostřednictvím modulu API (1.13.3). Před verzí 1.13.3 byla konfigurace dostupná pouze prostřednictvím speciální lokace zpracovávané upstream_conf.

API modul (1.13.3). Před verzí 1.13.3 byla konfigurace dostupná pouze prostřednictvím specialního umístění, které řídil upstream_conf. Syntax: stav soubor; Výchozí: — Kontext: upstream Tento příkaz se objevil v verzi 1.9.7. Určuje soubor, který udržuje stav dynamicky konfigurované skupiny. Příklady: stav /var/lib/nginx/stav/servers.conf; # cesta pro Linux stav /var/db/nginx/stav/servers.conf; # cesta pro FreeBSD Stav je momentálně omezen na seznam serverů se jejich parametry. Soubor se čte při analýze konfigurace a se aktualizuje každýkrát, kdy je konfigurace upstream změněna. Změna obsahu souboru přímo by měla být vyhnuta. Tento příkaz nelze použít společně s příkazem server. Změny provedené při obnovení konfigurace nebo aktualizaci binárního balíčku mohou být ztraceny. Tento příkaz je k dispozici jako součást našich komerčních předplatných. Syntax: hash klíč [konzistentní]; Výchozí: — Kontext: upstream Tento příkaz se objevil v verzi 1.7.2. Určuje metodu rozdělování zatížení pro skupinu serverů, kde mapování klienta na server se zakládá na hodnotě hashovaného klíče. Klíč může obsahovat text, proměnné a jejich kombinace. Pozor, že přidání nebo odstranění serveru z skupiny může vést k přemapování většiny klíčů na různé servery. Metoda je kompatibilní s Cache::Memcached Perl knihovnou. Pokud je parametr consistent zadán, bude se místo toho použít metoda ketama consistent hashing.

S použitím Perl knihovny Cache::Memcached. Pokud je zadán parametr consistent, bude použit metodický ketama consistent hashing místo toho. Tento metodický postup se zajistí, že pouze málo klíčů bude přesměrováno na různé servery při přidání nebo odstranění serveru z skupiny. Tímto způsobem se dosahuje vyššího poměru cache hit pro servery s uložením. Tento metodický postup je kompatibilní s Perl knihovnou Cache::Memcached::Fast s parametrem ketama_points nastaveným na 160. Syntaxe: ip_hash; Výchozí: — Kontext: upstream
Umožňuje definovat skupinu, která se má rozdělit na servery pomocí metody rozložení zatížení, kde požadavky jsou rozděleny mezi servery podle IP adres klienta. První tři oktety IPv4 adres klienta, nebo celá IPv6 adresa, se používají jako klíč k hashingu. Tímto způsobem se zajistí, že požadavky z jednoho klienta budou vždy přesměrovány na stejný server, pokud tento server není dostupný. V případě, že server není dostupný, budou požadavky klienta přesměrovány na jiný server. Nejpravděpodobněji, bude to vždy stejný server. Podpora IPv6 adres začíná od verzí 1.3.2 a 1.2.2. Pokud je potřeba jeden z serverů dočasně odstranit, musí být označen parametrem down, aby se zachovala aktuální hashing adres klienta. Příklad:

upstream backend {
ip_hash;
server backend1.example.com;
server backend2.example.com;
server backend3.example.com down;
server backend4.example.com;
}

Před verzí 1.3.1 a 1.2 se nedále používalo.

Příklad: upstream backend { ip_hash; server backend1.example.com; server backend2.example.com; server backend3.example.com down; server backend4.example.com; } Do verzí 1.3.1 a 1.2.2 nebylo možné určit váhu pro servery pomocí metody ip_hash pro balancování zátěže. Syntaxe: keepalive connections [local]; Výchozí: keepalive 32 local; Kontext: upstream Tento příkaz se objevil v verzi 1.1.4. Povoluje nebo zakazuje uchovávání dočasných spojení pro upstream servery. Od verze 1.29.7, v případě výchozího nastavení je aktivován cache pro spojení a tyto spojení nejsou sdíleny mezi různými lokacemi. Parametr local (od verze 1.29.7) zakazuje sdílení dočasných spojení s uloženým cachem pro spojení mezi různými lokacemi, i když adresa upstream serveru odpovídá. Pokud není zadán parametr local, libovolné shodné dočasné spojení k stejnému upstream serveru mohou být znovu použita bez ohledu na lokaci. Parametr connections nastavuje maximální počet nečinných dočasných spojení k upstream serverům, která jsou uložena v cache každého procesu pracovníka. Když je tento počet překročen, nejméně nečinná spojení jsou zavřena. Hodnota nula zakazuje dočasná spojení k upstream serverům. Od verze 1.29.7 jsou dočasná spojení povolená výchozími nastaveními, s výchozím limitem 32 spojení na každého pracovníka. Významně si všimnout je nutno, že příkaz keepalive neomezuje celkový počet spojení k upstream serverům, které může otevřít pracovník nginx.

Poznámka: Všechny technické termíny, kódy, příkazy, cesty souborů a adresy URL zůstávají v původním anglickém jazyce.

Přenosový direktivu keepalive není možné omezit celkový počet souběžných spojení k serverům vzdáleným v procesu pracovníka nginx. Parametr spojení by měl být nastaven na číslo dostatečně malé, aby serverům vzdáleným mohly zpracovat nové příchozí spojení. Před verzí 1.29.7 bylo nutné aktivovat metody rozvržení zátěže jiné než výchozí metoda round-robin před direktivou keepalive. Následující konfigurace upstream pro memcached s aktivovanými spojeními keepalive:

upstream memcached_backend {
    server 127.0.0.1:11211;
    server 10.0.0.2:11211;
    keepalive 32;
}
server {
    ...
    location /memcached/ {
        set $memcached_key $uri;
        memcached_pass memcached_backend;
    }
}

Pro HTTP je nutné nastavit přímočarovou verzi protokolu proxy_http_version na "1.1" (od verze 1.29.7) nebo na "2" a pole hlavičky "Connection" by mělo být vymazáno. Následující příklad je pro verze před 1.29.7:

upstream http_backend {
    server 127.0.0.1:8080;
    keepalive 16;
}
server {
    ...
    location /http/ {
        proxy_pass http://http_backend; # proxy_http_version 1.1; # před verzí 1.29.7 # proxy_set_header Connection ""; # před verzí 1.29.7 ...
    }
}

Alternativně lze pro HTTP/1.0 použít trvalá spojení tím, že se přenese pole hlavičky "Connection: Keep-Alive" k serveru vzdálenému, avšak tento způsob není doporučován. Pro FastCGI serverům je nutné nastavit fastcgi_keep_conn pro to, aby fungovaly spojení keepalive:

upstream fastcgi_backend {
    server 127.0.0.1:9000;
    keepalive 8;
}
server {
    ...
}

Požadavek na nastavení fastcgi_keep_conn pro práci s připojením s využitím zachycených spojení:

upstream fastcgi_backend {
    server 127.0.0.1:9000;
    keepalive 8;
}
server {
    ...
    location /fastcgi/ {
        fastcgi_pass fastcgi_backend;
        fastcgi_keep_conn on;
        ...
    }
}

Připojení k vzdálenému serveru bude zůstat otevřené. Syntax: ntlm; Výchozí: — Kontext: upstream Tento příkaz se objevil v verzi 1.9.2. Umožňuje proxyování požadavků s autentizací NTLM.
