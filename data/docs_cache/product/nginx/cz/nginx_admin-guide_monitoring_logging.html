Nastavování záznamu událostí
Záznamy událostí jsou důležité pro řešení potíží a pochopení toku provozu skrze vaši infrastrukturu. Tento článek vysvětluje, jak nastavit záznam chyb a přístupových záznamů v NGINX a NGINX Plus, upravit formát přístupových záznamů, snížit šum s podmíněným záznamem a přesměrovat záznamy do syslog pro centralizovanou sběr. Nastavte záznam chyb NGINX zapisuje záznam chyb, který zaznamenává problémy různých úrovní důležitosti. Direktiva error_log nastavuje umístění záznamu a úrovně důležitosti. Umístění záznamu může být konkrétní soubor, stderr nebo syslog. Výchozí cesta By výchozím způsobem se záznam chyb nachází v cestě logs/error.log, ale absolutní cesta závisí na operačním systému a metodě instalace. Můžete najít cestu k záznamu chyb spuštěním příkazu nginx -V a extrahováním hodnoty --error-log-path=: Copy nginx -V 2>&1|sed -n 's/.*--error-log-path=\([^ ]*\).*/\1/p' Výstup závisí na operačním systému. Pro RHEL-based, Debian, Ubuntu: Copy /var/log/nginx/error.log Pro FreeBSD: Copy /usr/local/var/log/nginx/error.log Pro obrázky Docker, je odeslán do kontrolních záznamů (stderr) prostřednictvím symlinků /var/log/nginx/error.log -> /dev/stderr. Úroveň důležitosti Úroveň důležitosti chyb následuje systému klasifikace syslog. Záznam obsahuje zprávy z všech úrovní důležitosti vyšších než určená úroveň. Následující příklad změní minimální úroveň důležitosti chyb zpráv na záznam z chyb do varování: Copy error_log logs/error.

Následující příklad nastaví minimální úroveň těžkosti zpráv chybových zpráv na zaznamenání z chyby na upozornění: Copy error_log logs/error.log warn; Tímto nastavením se zaznamenávají zprávy nad úrovní upozornění. To zahrnuje upozornění, chyby, kritické, varování a hrozby. Pro zaznamenávání ladicích zpráv se přečtěte Ladění NGINX. Formáty chybových zpráv Národní direktiva error_log zapisuje chybové zprávy v standardním formátu textových chybových zpráv NGINX. V NGINX Plus podporuje chybový log také formátovaný výstup JSON pomocí parametru json: Copy error_log /var/log/nginx/error.json error json; Příklad JSON-formátované záznamu chyby: json Copy { "level": "error", "timestamp": "2026-05-04T10:30:15.042+00:00", "pid": 12345, "tid": 12345, "cnum": 3, "msg": "connect() failed", "client": "192.168.1.10", "server": "example.com", "request": "GET /api HTTP/1.1", "upstream": "http://127.0.0.1:8080/api", "errno": 111, "errtext": "Connection refused" } Zaznamenávání chybových zpráv Národní direktiva error_log pracuje globálně výchozími nastaveními. Chcete-li toto nastavení přepsat, umístěte direktivu error_log v kontextu hlavní (nejvyšší) konfigurace. Nastavení v kontextu hlavním jsou vždy děděna ostatními konfiguračními úrovněmi (http, server, location). Direktiva error_log můžete také zadat na úrovni http, stream, server a location. Nastavení na nižších úrovních přepisují nastavení děděná z vyšších úrovní. Každá chybová zpráva se zapisuje pouze jednou do chybového logu nejbližšího úrovni, kde se chyba odehrála.

Každá zpráva o chybě se zapisuje pouze jednou do blízkého chybového logu, kde se chyba stala. Pokud jsou však na stejné úrovni uvedeny více příkazů error_log, zpráva se zapisuje do všech uvedených logů. Nastavte si pro NGINX log pro přístupy, aby se záznamy o klientských požadavcích zaznamenávaly v logu po zpracování požadavku. Příkaz access_log určuje umístění logu a jeho formát. Výchozí umístění logu je v adresáři logs/access.log. Formát zaznamenaných zpráv je předdefinovaný kombinovaný formát. Chcete-li změnit formát zaznamenaných zpráv, použijte příkaz log_format. Formát logu je definován pomocí proměnných. Následující příklad rozšiřuje předdefinovaný kombinovaný formát tím, že určí klíč slova gzip_ratio pro zaznamenání poměru komprese gzip v virtuálním serveru. Tímto způsobem se komprimuje odpověď v virtuálním serveru.

nginx
Copy http {
  log_format compression '$remote_addr - $remote_user [$time_local] ' '"$request" $status $body_bytes_sent ' '"$http_referer" "$http_user_agent" "$gzip_ratio"';
  server {
    gzip on;
    access_log /spool/logs/nginx-access.log compression;
    ...
  }
}

Další příklad formátu logu umožňuje sledovat různé hodnoty času mezi NGINX a serverem v poslední řadě. To může pomoci při diagnostice zpomalování vaší webové stránky.

nginx
Copy http {
  log_format time_upstream '$remote_addr - $remote_user [$time_local] ' '"$request" $status $body_bytes_sent ' '"$http_referer" "$http_user_agent" "$request_time" "$upstream_response_time";
  server {
    ...
  }
}

překlad:

Následující proměnné mohou být použity k zaznamenání různých hodnot času mezi NGINX a serverem v poslední straně: $upstream_connect_time – Čas, který byl potřeba pro vytvoření spojení s serverem v poslední straně $upstream_header_time – Čas mezi vytvořením spojení a přijetím prvního bajtu hlavičky od serveru v poslední straně $upstream_response_time – Čas mezi vytvořením spojení a přijetím posledního bajtu těla odpovědi od serveru v poslední straně $request_time – Celkový čas strávený na zpracování požadavku Všechny hodnoty času jsou měřeny v sekundách s rozlišením na milisekundy.

S povoleným parametrem buferu budou zprávy uloženy do buferu nejprve. Když bufer dosáhne kapacity (nebo v jiných případech), zprávy budou zapisovány do logu. Chcete-li umožnit uložení popisovačů logovacích souborů, použijte příkaz open_log_file_cache. Podobně jako příkaz error_log, příkaz access_log definovaný na určitém úrovni konfigurace přesahuje nastavení z předchozích úrovní. Při dokončení zpracování požadavku je zpráva zapisována do logu, který je konfigurován na aktuální úrovni nebo zděděn z předchozích úrovní.

V NGINX je kondiční protokolování povoleno pomocí parametru if k příkazu access_log. Tento příklad vyloučí požadavky s HTTP stavovými kódy 2xx (Úspěch) a 3xx (Přesměrování):

nginx 

map $status $loggable {
 ~^[23] 0;
 default 1;
}
access_log /cesta/k/access.log combined if=$loggable;

Použití: vzorkování parametrů SSL
Mnoho klientů používá verze TLS starší než TLS 1.3. Ačkoli mnoho šifr je označeno jako nebezpečné, starší implementace ještě je používá; ECC certifikáty nabízejí větší výkon než RSA, ale nikoliv všechny klienty mohou je akceptovat. Mnoho útoků na TLS závisí na „člověku ve středu“, který zachytí šifrovací negociaci rukou a donutí klienta a server k vybrání méně bezpečné šifry. Proto je důležité konfigurovat F5 NGINX Plus tak, aby nepodporoval slabé nebo zastaralé šifry, ale to může vyloučit starší klienty. Můžete vyhodnotit SSL data získaná od klienta a určit, jaká procenta klientů se vyloučí, pokud je podpora starších protokolů a šifrů odebrána.

Text v češtině:

Klienta a určit, jaká je úroveň klientů, které jsou vyloučeny, pokud je podpora starších protokolů SSL a šifrů odstraněna. Následující konfigurační příklad zaznamenává protokol SSL, šifru a hlavičku User-Agent každého připojeného TLS klienta, předpokládá-li se, že každý klient vybere nejnovější dostupný protokol a nejbezpečnější šifry. V tomto příkladu každý klient identifikován je svou unikátní kombinací IP adresy a hlavičky User-Agent. Definujte vlastní formát logu s názvem sslparams, který zahrnuje verzi protokolu SSL ($ssl_protocol), šifry použité v připojení ($ssl_cipher), IP adresu klienta ($remote_addr) a hodnotu standardní hlavičky User Agent HTTP žádosti ($http_user_agent): nginx 

log_format sslparams '$ssl_protocol $ssl_cipher ' '$remote_addr "$http_user_agent"';

Definujte zónu uložení klíč-hodnot, která uloží IP adresu klienta a jeho User Agent, například clients: 
keyval_zone zone=clients:80m timeout=3600s;

Vytvořte proměnnou, například $seen pro každou unikátní kombinaci $remote_addr a hlavičky User-Agent:
nginx 
keyval $remote_addr:$http_user_agent $seen zone=clients;

server {
listen 443 ssl;
ssl_protocols TLSv1 TLSv1.1 TLSv1.2;
ssl_ciphers HIGH:!aNULL:!MD5;
if ($seen = "") {
set $seen 1;
set $logme 1;
}
access_log /tmp/sslparams.log sslparams if=$logme;

...


}

Syslog je standard pro záznam zpráv počítačů a umožňuje shromažďovat zprávy záznamu z různých zařízení na jednom serveru syslog. V NGINX je záznam do syslog konfigurován pomocí prefixu syslog: v příkazech error_log a access_log. Zprávy syslog mohou být odeslány na server=, který může být doménový název, IP adresa nebo cesta k UNIX-doménovému socketu. Doménový název nebo IP adresa mohou být určeny s portem, aby se přeskočil výchozí port, 514. Cesta k UNIX-doménovému socketu může být určena po prefixu unix:: nginx Kopíruj error_log syslog:server=unix:/var/log/nginx.sock debug; access_log syslog:server=[2001:db8::1]:1234,facility=local7,tag=nginx,severity=info; V příkladu jsou zprávy chyb z NGINX zaznamovány do UNIX doménového socketu na úrovni záznamu debug, a záznam přístupu je zaznamováván do syslog serveru s IPv6 adresou a portem 1234. Parametr facility= určuje typ programu, který zaznamovává zprávu. Výchozí hodnota je local7. Další možné hodnoty jsou: auth, authpriv, daemon, cron, ftp, lpr, kern, mail, news, syslog, user, uucp, local0 ... local7. Parametr tag= přiřadí zprávám syslog vlastní značku (nginx v našem příkladu).
