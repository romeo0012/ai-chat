Přehled zabalancování na HTTP
Zabalancování mezi více instancí aplikace je běžnou technikou pro optimalizaci využití zdrojů, maximizaci propustnosti, snižování latence a zlepšování odolnosti vůči selhání. NGINX a NGINX Plus poskytují zabalancování na aplikační vrstvě (Layer 7) pro HTTP a HTTPS provoz. Můžete si vybrat z mnoha algoritmů zabalancování, od základního Round Robin po pokročilejší metody jako Least Connections, Least Time a metody hashing. NGINX Plus poskytuje další možnosti, jako je slow-start, který pomalu vrací zotavené servery, a persistence relací ("sticky" relace), která směruje požadavky klienta na stejný server vzduchu. Pro zabalancování na transportní vrstvě (Layer 4) se přečtěte si TCP a UDP zabalancování.

Zprostředkujte HTTP provoz skupině serverů
Použijte NGINX nebo NGINX Plus k zabalancování skupiny serverů. Nejprve definujte skupinu serverů pomocí příkazu upstream. Umístěte příkaz do kontextu http. Servery v skupině konfigurujete pomocí příkazu server (neboť se nesmí zaměňovat s blokem serveru, který definuje virtuální server běžící na NGINX). Například následující konfigurace definuje skupinu s názvem backend a tvoří tři konfigurace serveru. To může vyřešit více než tři skutečné servery:

nginx

http {
    upstream backend {
        server backend1.example.com weight=5;
        server backend2.example.com;
        server 192.0.0.0;
    }
}

Do více než třech skutečných serverů: nginx 

http {
    upstream backend {
        server backend1.example.com weight=5;
        server backend2.example.com;
        server 192.0.0.1 backup;
    }
}

Chtěte-li odeslat požadavky do skupiny serverů, zadejte jméno skupiny v přímocei proxy_pass. Pokud používáte alternativní protokol jako například fastcgi, použijte vlastní protokolový příkaz místo tohoto. Seznam alternativních příkazů pro přenos je: fastcgi_pass, memcached_pass, scgi_pass, uwsgi_pass. Následující příklad ukazuje, jak virtuální server běžící na NGINX přenáší všechny požadavky do skupiny backend upstream definované výše: 
nginx
server {
    location / {
        proxy_pass http://backend;
    }
}

Následující příklad kombinuje oba výše uvedené snippety a ukazuje, jak přenášet požadavky HTTP na server skupinu backend. Skupina tvoří tři servery, dvě z nich běží instancie stejné aplikace, zatímco třetí je server zálohy. 
nginx
http {
    upstream backend {
        server backend1.example.com;
        server backend2.example.com;
        server 192.0.0.1 backup;
    }
    server {
        location / {
            proxy_pass http://backend;
        }
    }
}

Zvolte metodu rozdělování zatížení
NGINX Open Source podporuje pět metod rozdělování zatížení: Round Robin, Least Connections, Least Time, IP Hash, a Generic Hash. NGINX Plus podporuje šest metod rozdělování zatížení: všechny výše uvedené, plus Random.

Nejrychlejší čas, IP Hash a Obecný Hash. NGINX Plus podporuje šest metod rozdělování zátěže: všechny výše uvedené, plus náhodný. Poznámka: Při konfiguraci jakékoliv metody kromě Round Robin umístěte odpovídající direktivu (hash, ip_hash, least_conn, least_time, nebo random) nad seznamem direktiv serverů v bloku upstream {}. Round Robin – Požadavky jsou rozděleny rovnoměrně mezi servery, s váhou serverů vzít v úvahu. Tato metoda se používá výchozími nastaveními; není nutné ji aktivovat pomocí žádného direktivu.

nginx
Kopírovat blok upstream backend {
# Není zadán žádný metodu pro rozdělování zátěže pro Round Robin server backend1.example.com;
server backend2.example.com;
}

Nejméně spojení – Požadavek je odeslán na server s nejméně aktivními spojeními. Tato metoda také vzít v úvahu váhu serverů.

nginx
Kopírovat blok upstream backend {
least_conn;
server backend1.example.com;
server backend2.example.com;
}

IP Hash – Server, na který je odeslán požadavek, je určen z adresy klienta IP. V tomto případě se používá buď prvních tří oktetů adresy IPv4 nebo celá adresa IPv6 k výpočtu hodnoty hash. Tato metoda zajišťuje, že požadavky z jedné adresy se dostanou na stejný server, pokud není dostupný.

nginx
Kopírovat blok upstream backend {
ip_hash;
server backend1.example.com;
server backend2.example.com;
}

Pokud je nutné dočasně odstranit server z rotace rozdělování zátěže, může být označen parametrem down.

Překlad textu z angličtiny na češtinu:

Pokud je nutné server zatím odstranit z rotace rozdělování zátěže, může být označen parametrem down. Tím se zachovává aktuální hashing klientských IP adres. Požadavky, které byly určeny pro zpracování tímto serverem, jsou automaticky odeslány na další server v skupině. nginx 

upstream backend {
    server backend1.example.com;
    server backend2.example.com;
    server backend3.example.com down;
}

Obecný Hash – Server, na který je odeslán požadavek, je určen podle klíče, který je definován uživatelem. Tento klíč může být textová řetězcovka, proměnná nebo kombinace. Například klíč může být párován s IP adresou zdroje a portem. Tento příklad používá URI:
nginx 
upstream backend {
    hash $request_uri consistent;
    server backend1.example.com;
    server backend2.example.com;
}

Volitelný parametr consistent k direktivě hash umožňuje ketamu konzistentní hashování rozdělování zátěže. Požadavky jsou rovnoměrně rozděleny mezi všechny upstream servery podle hodnoty uživatelem definovaného hashed klíče. Pokud je upstream server přidán nebo odstraněn z upstream skupiny, jsou pouze několik klíčů přemapovány, což minimalizuje chyby v cache. To je užitečné pro rozdělování zátěže na serverech s cachem nebo jiných aplikacích, které akumulují stav.

Nejmenší čas – Pro každý požadavek vybere NGINX server s nejnižším průměrným časem odpovědi a nejmenším počtem aktivních spojení. Nejnižší průměrný čas odpovědi je vypočítán podle parametru zahrnutého v direktivě least_time.

Nejnižší počet aktivních spojení. Nejnižší průměrná zpoždění se vypočítá na základě parametru zahrnutého s příkazem least_time. Tento parametr může být jedním z následujících: header – Čas, po kterém obdržíte první bajt z serveru last_byte – Čas, po kterém obdržíte celou odpověď z serveru last_byte inflight – Čas, po kterém obdržíte celou odpověď z serveru, bráníc se neúplným požadavkům.

nginx Kopírovat zadávací server backend { least_time header; server backend1.example.com; server backend2.example.com; }

Náhodný (pouze pro NGINX Plus) – Každý požadavek bude přesměrován na náhodně vybraný server. Tento způsob brání do úvah serverovým váhám. Pokud je zadán dvouparametrem, NGINX nejdříve náhodně vybere dva servery, poté vybere mezi těmito servery pomocí následujících metod: least_conn – Nejnižší počet aktivních spojení least_time=header (NGINX Plus) – Nejnižší průměrný čas, po kterém obdržíte odpověď hlavičky z serveru ($upstream_header_time) least_time=last_byte (NGINX Plus) – Nejnižší průměrný čas, po kterém obdržíte celou odpověď z serveru ($upstream_response_time)

nginx Kopírovat zadávací server backend { random two least_time=last_byte; server backend1.example.com; server backend2.example.com; server backend3.example.com; server backend4.example.com; }

Metoda náhodného zatížení by měla být použita pro rozptýlené prostředí, ve kterém se více balancerů přesměruje na stejnou sadu backends.

Metoda by měla být použita pro distribuované prostředí, kde více balancérů zatížení přesouvají požadavky k stejnému sadě back-endů. Pro prostředí, kde balancér zatížení má plnou viditelnost všech požadavků, by měly být použity jiné metody balancování zatížení. Vahy Serverů Určité metody balancování zatížení, včetně Round Robin, Least Connections a Random, rozdělují požadavky podle váh serverů. Parametr weight k direktivě server nastavuje váhu serveru. Pokud není nastavena žádná váha, výchozí hodnota je 1: nginx

upstream backend {
    server backend1.example.com weight=5;
    server backend2.example.com;
    server 192.0.0.1 backup;
}

V příkladu výše má backend1.example.com váhu 5, zatímco další dva servery mají výchozí váhu (1). Však ten s IP adresou 192.0.0.1 je označen jako záložní server a požadavky k němu nejsou odesílány, pokud oba ostatní servery nejsou dostupné. Tímto uspořádáním váh se z každých 6 požadavků 5 posílají na backend1.example.com a 1 na backend2.example.com.

Server slow-start

Funkce server slow-start zabraňuje nově obnovenému serveru být přetěžen požadavky, které mohou selhat a způsobit, že server bude znovu označen jako nefunkční. Tato funkce je k dispozici pouze v NGINX Plus. Slow-start umožňuje upstream serveru postupně se vzpamatovat na svou váhu z nuly po jeho obnovení nebo stavu dostupnosti.

Připojený server se postupně vrací na svou hmotnost z nuly až na hodnotu nominační po obnově nebo k dispozici. Toto lze provést pomocí parametru slow_start k direktivě server v nginxu:

nginx

upstream backend {
    server backend1.example.com slow_start=30s;
    server backend2.example.com;
    server 192.0.0.1 backup;
}

Hodnota času (zde 30 sekund) nastavuje dobu, během které se NGINX Plus postupně zvětšuje počet připojení k serveru na celkovou hodnotu. Pokud není hodnota zadána, výchozí hodnota je 0, což znecháze slow-start. Poznámka: Pokud je v skupině pouze jeden server, parametry max_fails, fail_timeout a slow_start k direktivě server jsou ignorovány a server nikdy není považován za nek dispozici. Persistence relací

Persistence relací znamená, že NGINX Plus identifikuje relace uživatelů a řídí všechny požadavky v dané relaci k stejnému připojenému serveru. NGINX Plus podporuje tři metody persistence relací. Metody jsou nastaveny pomocí direktivy sticky. (Pro persistence relací s nginxem Open Source použijte direktivy hash nebo ip_hash, jak je popsáno výše.) Cookie relace – NGINX Plus přidá do prvního odpovědi z připojené skupiny cookie relace a identifikuje server, který vyslal odpověď. Další požadavek klienta obsahuje hodnotu cookie, a NGINX Plus řídí požadavek k připojenému serveru, který odpověděl na první požadavek. Toto je nejjednodušší metoda persistence relací.

nginx

upstream backend {
    server backend1.example.com;
}
server {
    listen 80;
    location / {
        sticky cookie relace;
        proxy_pass http://backend;
    }
}

Tento odpovídal na první požadavek. Jedná se o nejprostější metodu zachovávání sezení. nginx

upstream backend {
    server backend1.example.com;
    server backend2.example.com;
    sticky cookie srv_id expires=1h domain=.example.com path=/;
}

V příkladu výše parametr srv_id nastavuje jméno cookies. Volitelný parametr expires nastavuje čas, po kterém prohlížeč má cookies uložit (zde 1 hodina). Volitelný parametr domain definuje doménu pro kterou je nastavena cookies, a volitelný parametr path definuje cestu pro kterou je nastavena cookies. Sticky route – Použijte parametr route k server directive, aby bylo možné přiřadit identifikátor cesty každému serveru. NGINX Plus přiřadí jeden z identifikátorů cesty klientovi, když obdrží jeho první požadavek. Následující požadavky pak porovnávají tyto identifikátory cesty, které jsou buď uloženy v cookies nebo přenášeny v adresáři požadavku.

upstream backend {
    server backend1.example.com route=a;
    server backend2.example.com route=b;
    sticky route $route_cookie $route_uri;
}

V příkladu výše je nejprve kontrolován cookies pro identifikátor cesty. Pokud není žádný, pak je kontrolován URI druhotně. Sticky learn – NGINX Plus najde identifikátory sezení tím, že prochází požadavky a odpovědi. Poté NGINX Plus "učí" se, kterému upstream serveru odpovídá která identifikátor sezení. Obvykle jsou tyto identifikátory přenášeny v HTTP cookies.

NGINX Plus se učí, kterému serveru v pořadí vrstvy streamu odpovídá určitý identifikátor relace. Obvykle se tyto identifikátory přenášejí v HTTP cookie. Pokud požadavek obsahuje identifikátor relace již učený NGINX Plus, směruje požadavek k odpovídajícímu serveru:

nginx
upstream backend {
    server backend1.example.com;
    server backend2.example.com;
    sticky learn create=$upstream_cookie_examplecookie lookup=$cookie_examplecookie zone=client_sessions:1m timeout=1h;
}

V příkladu jeden z upstream serverů vytváří relaci tím, že nastaví cookie EXAMPLECOOKIE v odpovědi. Parametr create je povinný a určuje, jak vzniká nová relace. V příkladu vznikají nové relace z cookie EXAMPLECOOKIE odeslaného upstream serverem. Parametr lookup je také povinný a určuje, jak hledat existující relace. V našem příkladu hledajíme existující relace v cookie EXAMPLECOOKIE odeslaném klientem. Parametr zone je povinný a určuje zónu paměti sdílené, ve které je uložena všechna informace o relacích s připevněním. V našem příkladu je zóna pojmenována client_sessions a má velikost 1 megabajtu. Tento způsob persistence relací je složitější než předchozí dva, protože nevyžaduje ukládání žádných cookie na straně klienta: všechny informace jsou uloženy server-side v zóně paměti sdílené.

Tento text nevyžaduje uchovávání žádných cookies na straně klienta: všechny informace jsou uchovávány server-side v zóně sdílené paměti. Pokud jsou v clusteru několik instancí NGINX, které používají metodu "sticky learn", je možné synchronizovat obsah jejich zón paměti pod podmínkami:

  • Zóny mají stejné jméno
  • Funkce zone_sync je konfigurována na každé instanci
  • Parametr sync je určen

nginx Copy
sticky learn create=$upstream_cookie_examplecookie lookup=$cookie_examplecookie zone=client_sessions:1m timeout=1h sync;
}

S NGINX Plus je možné omezit počet aktivních připojení k upstream serveru. Parametr max_conns nastaví maximální počet připojení k upstream serveru. Direktiva queue umožňuje přebytečná připojení uchovávat v frontě. Tato direktiva vyžaduje maximální počet pro frontu a timeout. Pokud je dosaženo limitu max_conns, je požadavek umístěn do fronty pro další zpracování. Pokud je dosaženo limitu fronty, pokud není určen žádný parametr queue nebo pokud klient dosáhne časového limitu v frontě, klient obdrží chybu.

nginx Copy upstream backend {
server backend1.example.com max_conns=3;
server backend2.example.com;
queue 100 timeout=70;
}
Poznámka: Limite max_conns je ignorován, pokud jsou v jiných procesech pracovníky otevřené idelní spojení s upstream serverem.

100 timeout=70; }

Poznámka: Hodnota max_conns je ignorována, pokud jsou v jiných pracovních procesech otevřeny nečinné zachovávající se spojení. V důsledku toho mohou být celkové počty spojení s serverem přesáhnout hodnotu max_conns v konfiguraci, kde je paměť sdílena mezi více pracovními procesy. Nastavte kontrolu stavu
NGINX může neustále kontrolovat vaše HTTP serverové skupiny upstream, vyhýbat se serverům, které selhaly, a poměrně přidávat do skupiny zatížení balancování. Viz HTTP Kontrola stavu pro instrukce, jak nastavit kontrolu stavu pro HTTP.

Sdílení dat s více pracovními procesy
Pokud v bloku upstream není zahrnut příkaz zone, každý pracovní proces udržuje vlastní kopii konfigurace skupiny serverů a udržuje vlastní sadu souvisejících kontrolních počtů. Tyto kontrolní počty zahrnují aktuální počet spojení k každému serveru v skupině a počet neúspěšných pokusů o přenos požadavku na server. V důsledku toho není dynamicky upravitelná konfigurace skupiny serverů. Když je příkaz zone zahrnut do bloku upstream, je konfigurace skupiny upstream uložena do paměťové oblasti sdílené všemi pracovními procesy. Tento scénář je dynamicky upravitelný, protože pracovní procesy přistupují k stejné kopii konfigurace skupiny a používají stejné související kontrolní počty. Příkaz zone je nutný pro aktivní kontrolu stavu a dynamickou konfiguraci skupiny upstream. Tento příkaz je povinný.

Tento text se týká stejných souvisejících radičů. Direktiva zone je povinná pro aktivní kontrolu zdravotního stavu a dynamickou konfiguraci skupiny horních bodů. Nicméně další funkce skupin horních bodů mohou zlepšit použití tohoto direktivy také. Například, pokud konfigurace skupiny není sdílena, každý proces pracovníka udržuje vlastní radič pro neúspěšné pokusy o přenos požadavku na server (nastavený parametrem max_fails). V tomto případě každý požadavek přichází pouze na jeden proces pracovníka. Když proces pracovníka, který byl vybrán k zpracování požadavku, selže přenos požadavku na server, ostatní procesy pracovníka nic o tom nevědí. Zatímco nějaký proces pracovníka může považovat server za nek dispozici, jiné mohou stále posílat požadavky na tento server. Chcete-li server definitivně považovat za nek dispozici, musí počet neúspěšných pokusů v časovém rozmezí daném parametrem fail_timeout rovnat max_fails násobené počtem procesů pracovníka. Na druhé straně garantuje direktiva zone očekávané chování. Podobně, metoda Least Connections pro rovnoměrné zatížení může fungovat neočekávaným způsobem bez direktivy zone, alespoň pod nízkým zatížením. Tato metoda přenáší požadavek na server s nejmenším počtem aktivních spojení. Pokud konfigurace skupiny není sdílena, každý proces pracovníka používá vlastní radič pro počet spojení a může posílat požadavek na stejný server, na který jenom před chvílí poslal požadavek jiný proces pracovníka.

Překlad:

Připojení a může odeslat požadavek na stejný server, na který jiný proces práce už poslal požadavek. Nicméně můžete zvýšit počet požadavků, aby se snížil tento efekt. Při vysoké zátěži požadavky jsou rozděleny mezi procesy práce rovnoměrně, a metoda Nejméně spojení funguje tak, jak by se měla. Nastavte velikost zóny Paměťová zóna je možné doporučit ideální velikost paměťové zóny, protože vzorce použití se velmi liší. Požadované množství paměti je určeno tím, které funkce (například trvalá relace, kontrola stavu nebo obnovování DNS) jsou povoleny a jak jsou upstream servery identifikovány. Například s metodou trvalé relace sticky_route a pouze jednou kontrolou stavu povolenou, může 256 KB velká zóna uložit informace o uvedeném počtu upstream serverů: 128 serverů (každý definovaný jako IP-adresa:port pár) 88 serverů (každý definovaný jako hostname:port pár, kde hostname odpovídá jedné IP adrese) 12 serverů (každý definovaný jako hostname:port pár, kde hostname odpovídá více IP adres) Nastavení HTTP balancování pomocí DNS Konfigurace skupiny serverů může být upravena v reálném čase pomocí DNS. Pro servery v upstream skupině, které jsou v serverovém příkazu identifikovány doménovým jménem, může NGINX Plus monitorovat změny v seznamu IP adres v odpovídajícím DNS záznamu, a automaticky aplikovat změny na balancování pro upstream skupinu, bez nutnosti restartu.

Poznámka: Tento překlad je určen pouze pro účely ilustrace a nemá být použit v žádném komerčním nebo oficiálním kontextu. Pro přesnou a kvalitní technickou překladatelskou práci je třeba využít profesionálního překladatele.

Tento odpovídající záznam DNS a automaticky aplikuje změny na zatížení pro skupinu upstream, bez nutnosti restartu. Toto lze provést vkládáním direktivy resolver do bloku http spolu s parametrem resolve k direktivě server:

http {
    resolver 10.0.0.1 valid=300s ipv6=off;
    resolver_timeout 10s;
    server {
        location / {
            proxy_pass http://backend;
        }
    }
    upstream backend {
        zone backend 32k;
        least_conn;
        # ...
        server backend1.example.com resolve;
        server backend2.example.com resolve;
    }
}

V příkladu parametr resolve k direktivě server říká NGINX Plus Plus, aby periodicky opětovně rezoloval domény backend1.example.com a backend2.example.com do IP adres. Direktiva resolver definuje IP adresu DNS serveru, na který NGINX Plus odesílá požadavky (zde 10.0.0.1). Výchozí frekvence rezolování DNS záznamů je daná hodnotou času-na-živý (TTL) v záznamu, ale můžete ji přepsat pomocí parametru valid; v příkladu je to 300 sekund, nebo 5 minut. Parametr ipv6=off znamená, že pouze IPv4 adresy jsou použity pro zatížení, ale resolvování obou IPv4 a IPv6 adres je podporováno výchozími nastaveními. Pokud se doména rezoluje do několika IP adres, jsou tyto adresy uloženy do konfigurace upstream a zatížena. V našem příkladu jsou servery zatíženy podle metody Nejméně Požadavků.

Přepravování a zatížení vztahem. V našem příkladu jsou servery zatíženy podle metody Nejméně spojení. Pokud se seznam IP adres pro server změnil, NGINX Plus okamžitě začne zatížit přes novou sadu adres. Zatížení serverů Microsoft Exchange v NGINX Plus Release 7 a novějších verzích je možné nastavit tak, aby NGINX Plus proxy provoz Microsoft Exchange k serveru nebo skupině serverů a zatížil jej. K nastavení zatížení serverů Microsoft Exchange: V bloku lokace nakonfigurujte proxyování do skupiny vzorce Microsoft Exchange serverů pomocí příkazu proxy_pass:

nginx 

location / {
    proxy_pass https://exchange; # ...
}

Pro přenos Microsoft Exchange spojení ke vzorcovým serverům v bloku lokace nastavte hodnotu příkazu proxy_http_version na 1.1, a příkaz proxy_set_header na "", stejně jako pro trvalou spojení:

nginx 

location / {
    # ...
    proxy_http_version 1.1;
    proxy_set_header Connection ""; # ...
}

V bloku http nakonfigurujte skupinu vzorce Microsoft Exchange serverů pomocí bloku upstream s názvem stejným jako název skupiny vzorce určený příkazem proxy_pass v kroku 1. Poté nastavte příkaz ntlm, aby serverům v skupině umožnily přijímat požadavky s autentizací NTLM:

nginx 

http {
    # ...
    upstream exchange {
        zone exchange 64k;
        ntlm;
        # ...
    }
    # ...
}

Přijme požadavky s autentizací NTLM: nginx

Kopírovat do souboru http { # ... upstream exchange { zóna exchange 64k; ntlm; # ... } }

Přidejte Microsoft Exchange servery do skupiny serverů v zásobníku a volitelně určete metodu rozdělování zátěže: nginx

Kopírovat do souboru http { # ... upstream exchange { zóna exchange 64k; ntlm; server exchange1.example.com; server exchange2.example.com; # ... } }

Dokončený příklad NTLM nginx

Kopírovat do souboru http { # ... upstream exchange { zóna exchange 64k; ntlm; server exchange1.example.com; server exchange2.example.com; } } server { poslucháva 443 ssl; ssl_certifikát /etc/nginx/ssl/company.com.crt; ssl_certifikát_klíč /etc/nginx/ssl/company.com.key; ssl_protokoly TLSv1.2 TLSv1.3; umístění / { proxy_pass https://exchange; proxy_http_verze 1.1; proxy_set_header Connection ""; } } }

Další informace o konfiguraci Microsoft Exchange a NGINX Plus naleznete v průvodci nasazení Balancování zátěže Microsoft Exchange Servers s NGINX Plus.

Poznámka o kompatibilitě

Metoda least_time je podporována v NGINX Plus od verze 6 a v NGINX Open Source od verze 1.31.0.
