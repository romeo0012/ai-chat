Beispielkonfiguration¶
Datei (YAML) 

entryPoints:
  web:
    address: :80
    http:
      redirections:
        entryPoint:
          to: websecure
          scheme: https
          permanent: true
      observability:
        accessLogs: false
        metrics: false
        tracing: false
    websecure:
      address: :443
      http:
        tls: {}
      middlewares:
        - default-auth@kubernetescrd
        - default-strip@kubernetescrd

_unterstrichenHeadersStrategy¶ Optional, Standard=behalten
Der _unterstrichenHeadersStrategy-Option definiert, wie Anfrage-Header mit Unterstrichen in ihren Namen behandelt werden, bevor sie geroutet werden:
behalten: Anfrage-Header mit Unterstrichen werden unverändert weitergeleitet (Standard).
löschen: jeder Anfrage-Header, dessen Name ein Unterstrich-Zeichen enthält, wird ohne Warnung aus der Anfrage entfernt.
ablehnen: jede Anfrage, die ein Header enthält, dessen Name ein Unterstrich-Zeichen enthält, wird mit einer 400 Bad Request-Antwort abgelehnt.
 Die folgende Textstelle enthält ein Unterstrich-Zeichen, das im Anfrage-Objekt stumm gelöscht wird. Abweisung: Jede Anfrage, die einen Kopfzeilen-Namen mit einem Unterstrich enthält, wird mit einem 400 Bad Request-Antwortcode abgelehnt. Unterstriche sind gültige Zeichen in HTTP-Kopfzeilen-Namen, aber Go normalisiert nur Kopfzeilen-Namen an Bindestriche, sodass ein Middleware, der einen Kopfzeilen-Namen in seiner Bindestrich-Form verwaltet (z.B. X-Auth-User mit der ForwardAuth authResponseHeaders-Option), keinen Unterstrich-Variante (z.B. X_Auth_User) sehen oder entfernen kann. Sicherheits-Backends, die beide Formen auf dieselbe Variable abbilden (CGI, WSGI, PHP, ...), können mit der Unterstrich-Variante eines verwalteten Kopfzeilen-Namens gefälscht werden. Die Einstellung des unterstrichHeadersStrategy-Options auf löschen oder ablehnen wird empfohlen, wenn solche Backends ausgeliefert werden. Weitere Details finden Sie in der Sicherheitsdokumentation für Kopfzeilen mit Unterstrichen. Vorwärtsgehende Header¶
Sie können Traefik konfigurieren, um die Informationen über vorwärtsgehende Header (X-Forwarded-*) zu vertrauen.
forwardedHeaders.trustedIPs
Vertrauen Sie auf Vorwärts-Header-Informationen von spezifischen IPs.
Datei (YAML)## Statische Konfiguration
yaml
entryPoints:
web:
address: ":80"
forwardedHeaders:
trustedIPs:
- "127.0.0.1/32"
- "192.168.1.7" 

Datei (TOML)## Statische Konfiguration
toml
[entryPoints]
[entryPoints.web]
address = ":80"
[entryPoints.web.forwardedHeaders]
trustedIPs = ["127.0.0.1/32", "192.168.1.7"] 

CLI## Statische Konfiguration
bash
--entryPoints.web.address=:80 --entryPoints.web.forwardedHeaders.trustedIPs=127.0.0.1/32,192.168.1.7

Traefik beachtet die Connection-Optionen aus dem Client-Anfrage-Header gemäß RFC 7230. Dadurch werden alle Headerfeld(s), die in der Anfrage-Connection-Header-Liste aufgeführt sind, sowie das leere Headerfeld selbst sofort nach der Verarbeitung durch Traefik entfernt. Die Entfernung erfolgt sofort, sodass die entfernten Header nicht mehr verfügbar sind, wenn die Anfrage durch das Middleware-Chain passt. Die Connection-Option listet die erlaubten Connection-Header auf, die den Middleware-Chain vor ihrer Entfernung durchlaufen.
Datei (YAML)## Statische Konfiguration
entryPoints:
  web:
    adresse: ":80"
    forwardedHeaders:
      connection:
        - foobar
Datei (TOML)## Statische Konfiguration
[entryPoints]
[entryPoints.web]
adresse = ":80"
[entryPoints.web.forwardedHeaders]
connection = ["foobar"]
CLI## Statische Konfiguration
--entryPoints.web.adresse=:80
--entryPoints.web.forwardedHeaders.connection=foobar
HTTP3¶
Da HTTP/3 tatsächlich UDP verwendet, startet Traefik, wenn es mit einer TCP-Eingangspunkt-Konfiguration auf Port N mit HTTP/3 aktiviert ist, automatisch auch einen unterlegenden HTTP/3-Server auf UDP-Port N. Dadurch bedeutet dies, dass Port N nicht von einem anderen UDP-Eingangspunkt verwendet werden kann. Da HTTP/3 die Verwendung von TLS erfordert, sind nur Routers mit TLS aktiviert nutzbar, die mit HTTP/3 verwendet werden können.
 Folge aus diesem Sachverhalt bedeutet, dass Port N nicht von einer weiteren UDP entryPoint verwendet werden kann. Da HTTP/3 die Verwendung von TLS erfordert, werden nur Router mit TLS aktiviert nutzbar sein, die mit HTTP/3 verwendet werden können. ProxyProtocol und Load-Balancers¶ Die Ersetzung der Remote-Client-IP-Adresse erfolgt nur für IP-Adressen, die in trustedIPs aufgeführt sind. Hier spezifizieren Sie Ihre Load-Balancer-IPs oder CIDR-Bereiche. Wenn Traefik hinter einem anderen Load-Balancer gestellt wird, muss PROXY-Protokoll auf beiden Seiten konfiguriert werden. Anderenfalls könnte es in Ihrem System einen Sicherheitsrisiko einführen (Aktivierung von Anforderungsfälschung).

Routers können diese Werte in ihrer eigenen Beobachtungskonfiguration überschreiben. Mögliche Werte sind: minimal: erzeugt einen Server-Span und einen Client-Span für jede von einem Router verarbeitete Anfrage. detailed`: ermöglicht die Erstellung zusätzlicher Spans für jede Middleware, die für jede von einem Router verarbeitete Anfrage ausgeführt wird.
