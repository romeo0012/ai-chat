Anbieter sind Infrastrukturkomponenten, unabhängig ob sie Orchestrierungssysteme, Container-Engines, Cloud-Anbieter, oder Schlüssel-Wert-Speicher sind. Der Gedanke ist, dass Traefik die Anbieter-APIs abfragen möchte, um relevante Informationen über die Routing zu finden, und wenn Traefik eine Änderung erkennt, aktualisiert es die Routen dynamisch. Anbieterkategorien¶
Jeder Anbieter ist anders, aber Sie können jeden als gehörend zu einer von vier Kategorien denken: Etikettbasiert: jedes bereitgestellte Container hat eine Menge von Etiketten angehängt, Key-Wert-basiert: jedes bereitgestellte Container aktualisiert einen Schlüssel-Wert-Speicher mit relevanten Informationen Annotationbasiert: ein separates Objekt, mit Anmerkungen, definiert die Eigenschaften des Containers Dateibasiert: nutzt Dateien, um die Konfiguration zu definieren
Anbieter-Namespace¶
Wenn Sie bestimmte Objekte in der dynamischen Konfiguration von Traefik deklarieren, wie z. B. Middleware, Dienste, TLS-Optionen oder Server-Transporte, befinden sie sich im Namespace des Anbieters. Beispielhaft, wenn Sie ein Middleware-Objekt mit Hilfe eines Docker-Labels deklarieren, befindet es sich im Namespace des Docker-Anbieters. Wenn Sie mehrere Anbieter verwenden und ein solches Objekt in einem anderen Anbieter referenzieren möchten (z. B. das Referenzieren eines querschnittsgrenzübergreifenden Objekts wie Middleware), dann sollte der Objektname mit dem @-Trennzeichen suffixiert werden, und der Anbietername. Für die Liste der Anbieternamen siehe den untenstehenden Unterstützungstabelle.

Kubernetes Namespace vs Traefik Namespace

Da Kubernetes auch seine eigene Vorstellung von Namespace hat, sollten Sie sich nicht verirren, den Anbieternamespace mit dem Kubernetes Namespace eines Ressourcen im Kontext der querschnittsgerechten Nutzung zu verwechseln. Im Falle der querschnittsgerechten Nutzung ist es sinnlos, ein Kubernetes Namespace bei der Verweisung auf das Ressource zu spezifizieren, da die Definition einer Traefik dynamischen Konfigurationsobjekt nicht in Kubernetes definiert ist.

Andererseits würde es passen, wenn Sie ein Middleware als benutzerdefiniertes Ressource in Kubernetes deklarieren und die nicht-CRD Ingress-Objekte verwenden. In diesem Fall müssten Sie den Kubernetes Namespace des Middleware in der Annotation wie folgt hinzufügen <middleware-namespace>-<middleware-name>@kubernetescrd.
