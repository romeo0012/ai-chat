} ] } Aktionen 📄
Aktionen geben Informationen über die durchgeführte Operation an, die das Log erstellt hat. Sie gehören in einige Kategorien. Allgemeine Aktionen - sie sind mit den meisten Ressourcentypen wie Servern, Laufwerken und Snapshots verbunden:

  • create: Während der Ressourcenerstellung
  • update: Während der Ressourcenaktualisierung
  • delete: Während der Ressourcenabnutzung
  • change_owner: Die Eigentumsveränderung des Ressourcen hat sich durchgeführt. Derzeit können nur CloudSigma-Mitarbeiter die Eigentumsveränderung einer Ressource durchführen.
  • clone_src: Die Ressource wird als Klonquelle verwendet
  • clone_dst: Die Ressource ist das Ziel des Klonens - das neu geklonte Laufwerk.

Laufwerksspezifische Aktionen - sie sind nur mit Laufwerken verbunden:

  • move: Das Laufwerk wird auf ein anderes physisches Speichersystem verschoben. Nur Mitarbeiter können Laufwerke verschieben.
  • convert_to_Library: Das Laufwerk wird in eine Bibliothekslaufwerks umgewandelt. Nur Mitarbeiter können Laufwerke umwandeln.
  • converted_from_Library: Das Laufwerk wird in ein reguläres Laufwerk von einer Bibliothekslaufwerks umgewandelt. Nur Mitarbeiter können Laufwerke umwandeln.
  • init_upload: Der Laufwerk-Upload wird initialisiert.

Server-spezifische Aktionen - sie sind nur mit Servern verbunden:

  • start_send: Versuch, einen Server zu starten: Das Ergebnis einer start Operation.
  • stop_send: Versuch, einen Server zu stoppen.
  • stop: Das Ergebnis einer stop Operation.
  • open_vnc: Öffnen Sie den VNC-Kanal zu einem Server
  • close_vnc: Schließen Sie den VNC-Kanal zu einem Server
  • shutdown_ACPI_send: Eine ACPI-Herunterfahrensanforderung wird an den Server gesendet.
  • heal: Der Server wurde geheilt, weil seine aufgezeichnete Zustandsdaten nicht mit der physischen Infrastruktur übereinstimmten. Beispiel: Ein Server wird als unverfügbar markiert, aber er läuft gut.

Zustand stimmt nicht mit der physischen Infrastruktur überein. Beispielhaft sei ein Server als unverfügbar markiert, aber er läuft problemlos. Fehler 🔍
Wenn das Feld success als False markiert ist, bedeutet das, dass ein Fehler während der Operation aufgetreten ist. Die Fehlerdetails werden in den folgenden Feldern gespeichert: error_type - Gibt den Fehlertyp an error_point - Weist auf den Fehlerursachen hin und wird hauptsächlich für Validierungsfehler verwendet error_message - Ist ein menschlicher lesbarer Fehlertext, der mit dem Fehler assoziiert ist. Das Muster ist das gleiche, wenn ein Server gestoppt wird: ein Protokollauftrag mit action stop_send wird gespeichert, der den Status des Stop-Anforderungsantrags an einen Server repräsentiert. Wenn dies erfolgreich war, also der Stop-Anforderungsantrag erfolgreich gesendet wurde, können Sie auf einen Log mit action stop, der den Status des Stop-Vorgangs repräsentiert, vertrauen, also der Server gestoppt wurde.

Gesendet, können Sie sich auf ein Log mit der Aktion "stop" erwarten, das den Status der Aktion "stoppen" darstellt, also den Server ist gestoppt. Hinweis: Wenn Sie einen Server von innen stoppen, wird nur ein Logeintrag mit der Aktion "stop" hinzugefügt. Dadurch können Sie feststellen, ob der Server über die API gestoppt wurde oder nicht: Wenn es 2 Logeinträge "stop_send" und "stop" gibt, wurde der Server über eine API-Anfrage gestoppt. Wenn nur "stop" (kein "stop_send") vorhanden ist, bedeutet das, dass der Server durch andere Mittel (von innen gestoppt, abgestürzt usw.) gestoppt wurde.
