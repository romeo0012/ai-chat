Server Kontext 🔍
Der Serverkontext ist eine Möglichkeit, der VM Informationen zu geben, wie sie eingerichtet wurde, also ihre Definition zu erhalten. Der Serverkontext wird über ein virtuelles serielles Portgerät übertragen, das auf UNIX-ähnlichen Betriebssystemen normalerweise als /dev/ttyS1 und auf Windows als COM2 auftritt. Das serielle Portgerät für den Serverkontext ist das zweite serielle Gerät, das an die VM angeschlossen ist, da einige UNIX-Betriebssysteme eine serielle Konsole auf dem ersten seriellen Port konfigurieren. Die Definition des Servers ist für die VM zugänglich, was in verschiedenen Situationen nützlich sein kann. Zum Beispiel kann man leicht von innerhalb der VM bestimmen, welche Netzwerk-Schnittstellen mit der öffentlichen und welche mit der privaten Netzwerk verbunden sind. Eine weitere Verwendung ist es, einige Daten an die Initialisierungsskripte der VM zu übergeben, wie z. B. den Hostnamen auf den VM-Namen oder die SSH-Öffentlichen Schlüssel über die Server-Metadaten zu übermitteln. Zunächst könnte es verwickelt sein, mit der Anwesenheit beider 'server context' und 'server metadata'. 'server metadata' ist tatsächlich ein Unterteil von 'server context'. 'server metadata' selbst ist ein Schlüssel-Wert-Speicher für von Benutzern definierte Daten auf einer Serverdefinition. 'server context' hingegen ist ein Schritt weiter. Es umfasst die vollständige Serverdefinition, sowie die Server-Metadata und die Definition der angehängten Laufwerke. Schema des Kontexts 🔍
Der Serverkontext hat fast dieselbe Schema wie die /server/<uuid>/detail/ API-Anfrage-Schema. Es unterscheidet sich dadurch, dass es an Eigentümer, Abonnements, Status und Laufzeitinformationen fehlt.

Selbe Schema wie die API-Anfrage-Schema von /server/<uuid>/detail/. Es unterscheidet sich darin, dass es keine Eigentümer-, Abonnements-, Status- und Laufzeitinformationen enthält. Die andere Differenz besteht darin, dass die Attribut-Eigenschaften der Laufwerke auf die entsprechenden /drive/<uuid>/detail/ erweitert werden, die ebenfalls Eigentümer- und Laufzeitinformationen fehlen. Es gibt auch ein global_context-Attribut, das den Kontext auf allen Servern (siehe Laufwerk bearbeiten) enthält.

Die Einrichtung der virtuellen seriellen Ports

Der virtuelle serielle Port-Gerät ist nicht mit einem Hardware-Gerät auf der anderen Seite verbunden, sodass die Einstellungen der seriellen Port-Hardware, wie Baudrate und Paritätsbits, die tatsächliche Kommunikation nicht beeinflussen. Auf Unix-ähnlichen Betriebssystemen kann es jedoch erforderlich sein, die virtuelle Terminal-Verbindung zum seriellen Gerät einzurichten. Im Allgemeinen ist es empfehlenswert, den Terminal im raws Mode zu betreiben, damit alle Zeichen uninterpretiert empfangen werden. Es ist auch wichtig, dass empfangene Antworten nicht zurückgegeben werden, weil sie den Empfangs-Buffer füllen können, was ausstehende Anfragen ejecten kann. Um den Terminal auf meisten Unix-Systemen in raws Mode zu konfigurieren, benötigt man den folgenden Befehl:

stty -F /dev/ttyS1 raw -echo

Es ist auch möglich, einen kooked mode Terminal für die Überprüfung von Daten an der Befehlszeile zu verwenden, indem man Standard-Utilitäten wie echo, read und cat verwendet.

Um Daten über die Befehlszeile mit Hilfe des gekochten Modus Terminals überprüfen zu können, verwenden Sie Standard-Utilitäten wie echo, read und cat. Da alle Antworten mit einem neuen Zeilenumbruch und einem End-of-Transmission-Zeichen (meistens als ^D oder "\0x04" dargestellt) enden, würde das Festlegen des Terminals auf gekochten Modus dazu führen, dass das EOT-Zeichen als End-of-File-Bedingung interpretiert wird, was es ermöglicht, read und cat auf dem Terminal-Geräte-Dateipfad (/dev/ttyS1) zu empfangen. Um den cooked-Modus zu konfigurieren, verwenden Sie den folgenden Befehl:

stty -F /dev/ttyS1 cooked -echo

Wenn der Standard-EOF-Zeichen-Charakter auf Ihrem Terminal anders ist, muss er möglicherweise geändert werden:

stty -F /dev/ttyS1 cooked -echo eol ^D

Server-Kontext-Protokoll
Anfragen des vollständigen Server-Kontexts

Es gibt ein einfaches Protokoll, um den Server-Kontext von der seriellen Geräte-Schnittstelle abzurufen. Um den gesamten Server-Kontext abzurufen, muss man zwei Zeilen mit Ungleichheitszeichen (auch als spitze Klammern, Winkelklammern bezeichnet) versenden. Die Zeile kann entweder CRLF oder nur LF sein. In den meisten Programmiersprachen sieht die zu sendende Zeichenkette wie "<\n\n>" aus. Die Antwort ist ein einzeiliger JSON-String, der die Definition der VM darstellt, gefolgt von einem Zeilenvorschub (Zeilenumbruchzeichen) und einem End-of-Transmission-Zeichen (meistens als ^D oder "\0x04" dargestellt). Auf Unix-ähnlichen Betriebssystemen kann es möglich sein, dass das EOT-Zeichen, wenn das Terminal auf cooked-Modus festgelegt ist, als End-of-File interpretiert und nicht in der Antwort enthalten ist.

Deutsch:

Im gekochten Modus ist es möglich, dass der EOT-Zeichencharakter als End-Of-File interpretiert und nicht in der Antwort enthalten ist. Das folgende Beispiel gilt für einen Server mit der folgenden Definition:

GET /api/2.0/servers/e0fcf2ae-020e-45e1-bf69-982b17da4b6a/ HTTP/1.1

Authorization: Basic SWYgeW91IGZvdW5kIHRoaXMsIGhhdmUgYSBjb29raWUsIHlvdSBkZXNlcnZlIGl0IDop

Dies wird auf python 2.6 und python 2.7 funktionieren

s = serial.Serial("/dev/ttyS1") # initialisieren eine serielle Verbindung zu '/dev/ttyS1'
s.write("&lt;\n\n&gt;") # schreibe ein leeres Anfrage, um die volle Kontext zu erhalten, da es in der Kontext keine Zeilenumbruche gibt
context_str_raw = s.readline() # lese eine Zeile, die die gesamte Kontext ist, da es in der Kontext keine Zeilenumbruche gibt

Entferne alle vorhandenen Zeilenumbruche und \x04-Symbole aus der Kontextzeichenfolge

context_str = context_str_raw.strip("\x04\n")
print context_str # drucke die Kontext in stdout
