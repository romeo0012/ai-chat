Allgemeine URL-Formatierung 📄
API-URLs haben folgendes allgemeines Format: https://{api_endpoint}/api/{api_version}/{resource}/{object_id}/action/?{get_request_parameters}

Hier eine Liste der möglichen URL-Formate, die sich auf die Basis-URL (https://{api_endpoint}/api/{api_version}) beziehen:

  • /{resource}/
    Diese URLs zeigen meist auf eine Liste von Ressourcen wie /servers/ oder /drives/. Sie kann auch auf ein einzelnes Ressourcenobjekt zeigen, wie z.B. /profile/.
  • /{resource}/{object_id}/
    Diese URLs zeigen auf ein einzelnes Ressource aus einer Liste von Ressourcen, z.B. eine einzelne Server-URL kann wie folgt aussehen: /servers/6e5ceaaa-0cf8-417a-bf47-53e56d4fcaaa/
  • /{resource}/{object_id}/action/?do={action_name}
    Einige Objekte haben Aktionen. Der Name der Aktion wird im 'do=' GET-Parameter angegeben. Z.B. hat ein Server-Objekt eine start-Aktion, die auf folgender URL aufgerufen wird: /servers/6e5ceaaa-0cf8-417a-bf47-53e56d4fcaaa/action/?do=start

Authentifizierung 📄
Die API unterstützt die folgenden Authentifizierungsmethoden: HTTP Basic, HTTP Digest, Cookie basierte Authentifizierung für web/browser basierte Clients.

HTTP Basic Auth 📄
HTTP Basic Authentifizierung wird mit dem Authorization-Header durchgeführt. Der Wert des Headers ist Basic base64_encode({user email}:{password}). Z.B. ergibt sich für einen Benutzer mit E-Mail-Adresse user.email@domain.tld und Passwort pass123 ein Wert von user.email@domain.tld:pass123.

Grundlage ist die Base64-Verschlüsselung ({Benutzer-E-Mail}:{Passwort}). Beispielhaft ergibt sich für einen Benutzer mit der E-Mail-Adresse user.email@domain.tld und dem Passwort pass123 der Wert user.email@domain.tld:pass123, der bei Base64-Verschlüsselung folgenden Header ergibt:

Authorization: Basic dXNlci5lbWFpbEBkb21haW4udGxkOnBhc3MxMjM=

Siehe RFC 2617#section-2 für eine ausführlichere Diskussion zur HTTP-Basisauthentifizierung. Digest-Zugriffssicherheit 
Um Digest-Authentifizierung nutzen zu können, sollten Clients die Anfrage ohne jegliche Authentifizierung machen, was zu einer 401 Unauthorized-Antwort führen wird. Die Antwort enthält eine Herausforderung im WWW-Authenticate-Header, die wie folgt aussieht:

WWW-Authenticate: Digest nonce="1363185031.81:FCF2:443b657bfd1a7340a0841c704d93a579", realm="users", algorithm="MD5", opaque="d7d89a75f4f6e3044626c6c251456e6b401401e7", qop="auth"

Drei Hashes (wir nennen sie HA1 und HA2 und RESPONSE im Beispiel) müssen berechnet werden, um die Antwort auf die Herausforderung zu generieren und zu authentifizieren. Die API verwendet den md5-Hashalgorithmus (algorithm=”MD5”) und den “auth”-Qualitätsstandard (qup=”auth”):

HA1 = MD5({username}:{realm}:{password})
HA2 = MD5({method}:{uri})
RESPONSE = MD5(HA1:{nonce}:{nc}:{cnonce}:{qop}:HA2)

Die Werte für realm, nonce und qop sind in dem Herausforderungshauptteil WWW-Authenticate enthalten. Der Client muss den Benutzernamen, das Passwort, den cnonce und den nc bereitstellen.

Und die qop sind in der Herausforderungskopfzeile WWW-Authenticate angegeben. Der Client muss den Benutzernamen, das Passwort, den cnonce und nc bereitstellen. Der cnonce oder der Client-Nonce ist ein zufälliger Wert, der vom Client erzeugt wird, und nc oder der Nonce-Counter ist ein hexadezimaler Counter, der bei jeder folgenden Anfrage erhöht werden soll. Der Client soll einen Authorization-Header senden, der alle Werte aus der WWW-Authenticate-Antwort-Header-Zeile enthält, zusammen mit den folgenden Werten username, uri, cnonce, nc und response, die den berechneten RESPONSE-Hash enthält. Im oben genannten Beispiel könnte ein Benutzer mit der E-Mail-Adresse user.email@domain.tld und dem Passwort pass123 den folgenden Authorization-Header in der nächsten Anfrage senden:

Authorization: Digest username="user.email@domain.tld", realm="users", nonce="1363188235.48:54A3:135f43a8227a1ca54c91da95b0111802", uri="/api/2.0/servers/", cnonce="MDI4Nzcx", nc=00000001, qop=auth, response="06238b01fabaeea8d7923c502a037bb5", opaque="5f0604df80b0c2d09330e802ed47ba5288e5440c", algorithm="MD5"

Weitere Informationen zu Digest-Zugriffssicherung finden Sie in RFC 2617#section-3 oder im Wikipedia-Artikel über Digest Access Authentication.

Cookie-basierte Authentifizierung
Browser-basierte Clients können cookie-basierte Authentifizierung verwenden. Die Authentifizierung wird in einem sessionid-Cookie gespeichert. Alle Anfragen außer GET und OPTIONS benötigen zusätzlich auch einen CSRF-Token. Der CSRF-Token ist notwendig, um Cross-site Request Forgery zu verhindern. Er wird als benutzerdefinierter Header X-CSRFToken auf jede Anfrage gesetzt.

Ausnahme von GET und OPTIONS erfordert zusätzlich auch eine CSRF-Token. Das CSRF-Token dient dazu, Cross-site Request Forgery zu verhindern. Es wird als benutzerdefinierter Header X-CSRFToken auf jedem Anforderung festgelegt. Der Wert für das CSRF-Token wird vom Server in der csrftoken-Cookie festgelegt. Um eine Sessionid und csrftoken-Cookies zu erhalten, muss ein Login-Anforderung mit einem POST an /api/2.0/accounts/action/?do=login gesendet werden, mit einem Objekt, das die Felder "username" und "password" enthält mit den entsprechenden Benutzernamen und Kennwörtern:

POST /api/2.0/accounts/action/?do=login HTTP/1.1
Content-Type: application/json

{"username": "user.email@domain.tld", "password": "pass123"}

Die Antwort enthält die beiden Cookies:

Set-Cookie: csrftoken=J24Zr4nEcxZcHtdoaNG02WiWoA0qXFg5; expires=Tue, 11-Mar-2014 15:47:14 GMT; Max-Age=31449600; Path=/
Set-Cookie: sessionid=c38919b96789c3a12c6c204676d63308; expires=Tue, 26-Mar-2013 15:47:14 GMT; httponly; Max-Age=1209600; Path=/

Alle folgenden Anforderungen sollten beide sessionid und csrftoken in der Cookie-Header und csrftoken in der X-CSRFToken-Header enthalten:

Cookie: sessionid=c38919b96789c3a12c6c204676d63308; csrftoken=J24Zr4nEcxZcHtdoaNG02WiWoA0qXFg5
X-CSRFToken: J24Zr4nEcxZcHtdoaNG02WiWoA0qXFg5

Um sich abzumelden (die aktuelle sessionid und csrftoken zu invalidieren), muss ein POST an /api/2.0/accounts/action/?do=logout gesendet werden, mit einem leeren Objekt:

POST /api/2.0/accounts/action/?do=logout HTTP/1.1
Content-Type: application/json
{}

Der API wird sowohl das JSON als auch das XML-Datenformat unterstützt.

Datenformat (Content Types) 📄
Die API unterstützt beide die JSON und XML Datenformate. Voreingestellt ist JSON. Die Anforderungsformatierung wird durch den Content-Type Header angegeben und ist für Operationen erforderlich, die einen Anforderungskörper haben. Die Antwortformatierung kann in Anfragen durch den Accept Header angegeben werden. Die Antwort enthält einen Content-Type Header, der die zurückgegebene Datenformatierung angibt. Sie können auch eine URI-Parameter ?format=json oder ?format=xml verwenden, um den Inhaltstyp der Antwort anzugeben, wenn Sie eine GET-Anfrage senden. Dies ist nützlich, um die API manuell zu fragen (über den Webbrowser) und sollte nicht verwendet werden, wenn Sie Anfragen programmgesteuert senden. Wenn sowohl der Content-Type als auch der URI-Parameter verwendet werden, hat der URI-Parameter Vorrang. Wenn es widersprüchliche URI-Parameter gibt, hat der letzte angegebene Parameter Vorrang. Wenn sowohl application/json als auch application/xml im Accept Header angegeben werden, wird JSON zurückgegeben.

Angegebener Parameter hat Vorrang. Im Falle, dass sowohl application/json als auch application/xml in einem Accept-Header angegeben sind, wird JSON zurückgegeben. Wenn der Accept-Header sowohl */* als auch application/xml oder application/json enthält, wird das */* ignoriert und der spezifiziertere Inhaltstyp verwendet. Antwortstatuscodes 🔍 Die API verwendet die standardmäßigen HTTP-Statuscode-Klassen, wobei ein Code von 200 bis 299 Erfolg bedeutet. Fehlerhafte Anforderungen haben Statuscodes zwischen 400 und 499, und Serverseitige Fehler haben Codes zwischen 500 und 599. Die folgenden Statuscodes werden von der API zurückgegeben: Erfolgstatuscodes:

  • 200: OK. Erfolgreiche Anforderung.
  • 201: Objekt erstellt. Diese Anforderung wird für Anrufe verwendet, die neue Objekte erstellen, wie z.B. create drive oder create server. Der Antwortheader Location enthält die URI des neu erstellten Objekts.
  • 202: Akzeptiert. Dieser Header wird für langlaufende oder asynchrone Operationen wie starten eines Servers oder Klonen eines Laufwerks verwendet. Der Header impliziert auch, dass die Anforderung möglicherweise nicht erfolgreich ist und abgebrochen werden kann.
  • 204: Kein Inhalt. Die Anforderung war erfolgreich und es gibt keinen Inhalt in der Antwortkörper. Dieser Status wird für erfolgreiche DELETE-Anforderungen verwendet. Client sollten sich bewusst sein, dass sie den Inhalt nicht parsen sollten, da er leer ist und kein gültiges JSON oder XML-Dokument ist. API-Fehler enthalten meistens einen Körper, der die Fehlerbeschreibung enthält.

Bitte beachten Sie, dass die Analyse des Körpers nicht durchgeführt werden sollte, da er leer ist und kein gültiges JSON oder XML-Dokument darstellt. API-Fehler enthalten meistens einen Körper, der die Fehlermeldung beschreibt. Überprüfen Sie den Abschnitt "Fehler" für Erklärung des Fehler-Nachrichten-Formats. Statuscodes von Fehlerantworten:

400: Bad Request. Dieser Status bedeutet, dass es im Anforderungsbereich ein Fehler gibt. Der Fehler im Anforderungsbereich kann ein Fehler im Datenformat (ungültiges JSON oder XML) oder ein ungültiger Wert sein.

401: Unauthorized. Die bereitgestellten Anmeldeinformationen sind falsch oder fehlen. Dieser Antwortstatus ist ein normaler Bestandteil von digest-Authentifizierung, in dem Fall, wird die Antwort einen WWW-Authentifizierungs-Header mit einer Authentifizierungsforderung enthalten.

402: Payment Required. Dieser Fehler bedeutet, dass es nicht genügend Gelder im Konto gibt, um die Aktion abzuschließen. Er tritt auf, wenn versucht wird, eine Abonnement-Abonnierung ohne ausreichende Gelder im Konto zu erhalten, oder wenn versucht wird, einen Server zu starten ohne ausreichende Gelder für die 5-tägige Spitzenlast zu haben.

403: Forbidden. Die bereitgestellten Anmeldeinformationen sind korrekt, aber der Benutzer ist nicht berechtigt, die Aktion auszuführen. Dieser Status wird für den "Zugriff verweigert"- oder "Operation nicht erlaubt"-Fehler verwendet.

404: Not Found. Das angeforderte Objekt existiert nicht. Dieser Fehler tritt auf, wenn ein nicht existierendes Ressource angefordert wird. Das Ressource wurde möglicherweise nie erstellt, oder es wurde gelöscht.

405: Method Not Allowed. Dieser Fehler tritt auf, wenn eine unzutreffende HTTP-Methode auf einer URL verwendet wird. Beispiel: DELETE-Anfragen sind nicht erlaubt auf der URL /profile/ und werden einen 405-Status zurückgeben.

406: Not Acceptable. Dieser Fehler tritt auf, wenn eine unzutreffende HTTP-Methode auf einer URL verwendet wird. Beispiel: DELETE-Anfragen sind nicht erlaubt auf der URL /profile/ und werden einen 405-Status zurückgeben.

Dieser Fehler tritt auf, wenn auf einer URL eine falsche HTTP-Methode verwendet wird. Beispiel: DELETE-Anfragen sind auf der URL /profile/ nicht erlaubt und werden einen 405-Status zurückgeben. 406: Nicht akzeptabel. Dieser Fehler tritt auf, wenn durch den Accept-Header die vom API nicht unterstützte Inhaltsart angefordert wird. Von der API unterstützte Inhaltsarten sind application/json, application/xml und */*, was auf application/json festgelegt wird. Wenn der Accept-Header der Anfrage keine dieser Inhaltsarten enthält, wird ein 406-Status zurückgegeben. Systemfehlerstatuscode 500: Interner Serverfehler. Dieser Status bedeutet, dass ein Systemfehler aufgetreten ist. Bitte kontaktieren Sie den Support, wenn Sie solchen Fehler erfahren. 503: Dienst nicht verfügbar. Dieser Status bedeutet, dass das System momentan die Anfrage nicht erfüllen kann. Dieser Status wird für zeitgleiche Updates zurückgegeben, wenn der Client mehrere zeitgleiche Anfragen stellt, die versuchen, die gleichen Werte zu aktualisieren, oder wenn das System aus Kapazitätsgründen nicht mehr verfügbar ist. Die API ermöglicht das Filtern von zurückgegebenen Ressourcen über GET-Parameter. Spezielle Filteroptionen werden im Schema aufgelistet. Es gibt zwei Arten von Filtern: genau: Passt dem genauen Wert des Feldes entsprechend. enthält: Passt, unabhängig von Groß- und Kleinschreibung, einem Unterstring des Werts entsprechend. Die Semantik der Filter ist wie folgt:

AND: Trennt GET-Parameter miteinander ANDer. Beispiel:?name=test&tag__name=test_tag
Es wird zurückgegeben, Ressourcen die folgende Bedingung erfüllen: (name = test) UND (hat ein Tag mit name = test_tag)

Dieselbe Filteranwendung zweimal ist immer noch ANDer: Beispiel:?tag__name=test_tag1&tag__name=test_tag2
Es wird zurückgegeben, Ressourcen die folgende Bedingung erfüllen: (hat ein Tag mit name = test_tag1) UND (hat ein Tag mit name = test_tag2)

OR: Innerhalb eines GET-Parameters werden Werte durch Komma getrennt und ORer zusammen. Beispiel:?name=name1,name2
Es wird zurückgegeben, Ressourcen die folgende Bedingung erfüllen: (name = name1) ODER (name = name2)

Kommas können durch einen einzelnen Backslash entweder nicht verwendet werden und Backslashes, die vor einem Komma stehen, können durch einen Backslash entweder nicht verwendet werden, um die Kommas zu erlauben, durch Kommas zu teilen: Beispiel:?name=name\,long\\,name2
Es wird zurückgegeben, Ressourcen die folgende Bedingung erfüllen: (name = name,long\) ODER (name = name2)

OR hat eine höhere Priorität als AND. Beispiel:?name=name1,name2&tag__name=test_tag
Es wird zurückgegeben, Ressourcen die folgende Bedingung erfüllen: ((name = name1) ODER (name = name2)) UND (hat ein Tag mit name = test_tag)
