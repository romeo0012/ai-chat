Verze API 📝
Verze API je zahrnutá do adresy URL.

Prostředním automatizovaného způsobu získat všechny aktuálně dostupné umístění. API Verze 📄
Začlení verze API do URL je standardní. Aktuální verze je '2.0', například <https://zrh.cloudsigma.com/api/2.0/>.

Formát URL 📄
URL API mají následující obecný formát: <https://{api_endpoint}/api/{api_verze}/{resource}/{object_id}/action/?{get_request_parameters}>
Níže je seznam možných formátů URL vztahujících se k základnímu URL (<https://{api_endpoint}/api/{api_verze}>):

  • /{resource}/
    Tato URL většinou ukazuje na seznam prostředků, například /servers/ nebo /drives/. Může také ukazovat na jeden prostředek, například /profile/.
  • /{resource}/{object_id}/
    Tato URL ukazuje na jeden prostředek z seznamu prostředků, například jeden serverový URL může vypadat takto: /servers/6e5ceaaa-0cf8-417a-bf47-53e56d4fcaaa/.
  • /{resource}/{object_id}/action/?do={action_name}
    Některé objekty mají akce. Název akce je určen v 'do=' parametru GET. Například serverový objekt má akci start, která je spuštěna na následující adrese URL: /servers/6e5ceaaa-0cf8-417a-bf47-53e56d4fcaaa/action/?do=start

Autentizace 📄
API podporuje následující metody autentizace:

  • HTTP Basic
  • HTTP Digest
  • Autentizace na základě cookies pro webové/prohlížečové klienty.

Autentizace HTTP Basic 📄
HTTP Basic Authentication se provádí pomocí hlavičky Authorization. Hodnota hlavičky je Basic base64_encode({user email}:{password}). Například uživatel s e-mailem user.email@domain.tld a heslem pass123 vede k hodnotě hlavičky user.email@domain.tld:pass123.

Je to základní base64_encode({uživatel email}:{heslo}). Například uživatel s e-mailem user.email@domain.tld s heslem pass123 vede k hodnotě user.email@domain.tld:pass123, která po kódování v Base64 vede k následující hlavičce: Authorization: Basic dXNlci5lbWFpbEBkb21haW4udGxkOnBhc3MxMjM= Viz RFC 2617#section-2 pro podrobnější diskusi o HTTP Basic Autentizaci. Digestová autentizace

Chcete-li použít digestovou autentizaci, musí klient požádat o autentizaci bez jakékoliv autentizace, což vede k odpovědi 401 Neautorizovaný. Odpověď obsahuje výzvu v hlavičce WWW-Authenticate, která vypadá následovně: WWW-Authenticate: Digest nonce="1363185031.81:FCF2:443b657bfd1a7340a0841c704d93a579", realm="users", algorithm="MD5", opaque="d7d89a75f4f6e3044626c6c251456e6b401401e7", qop="auth"

Třebaže se vyskytují tři hashovací hodnoty (v následujícím příkladu HA1, HA2 a RESPONSE), musí být vypočítány pouze dvě hashovací hodnoty (HA1 a RESPONSE) k generování odpovědi na výzvu a k autentizaci. API používá algoritmus hashování MD5 (algorithm=”MD5”) a “auth” kvalitu ochrany (qup=”auth”):

HA1 = MD5({uživatelské jméno}:{realm}:{heslo})
HA2 = MD5({metoda}:{uri})
RESPONSE = MD5(HA1:{nonce}:{nc}:{cnonce}:{qop}:HA2)

Hodnoty pro realm, nonce a qop jsou uvedeny v hlavičce WWW-Authenticate výzvy. Klient musí poskytnout uživatelské jméno, heslo, cnonce a nc.

Cnonce nebo klientský nonce je náhodná hodnota, kterou vytvoří klient a nc nebo nonce counter je šestnáctkový početátor, který by měl být zvýšen o jeden pro každý následující požadavek. Autentizace pomocí cookie Klienty prohlížeče mohou používat autentizaci pomocí cookie. Autentizace je token uložen v cookie sessionid. Všechny požadavky, které nejsou GET nebo OPTIONS, vyžadují také token CSRF. Token CSRF je potřeba k prevenci Cross-site Request Forgery. Je určen jako vlastní hlavička X-CSRFToken na každém požadavku.

Formát dat (Content Types)
API podporuje oba formáty dat JSON a XML. Výchozí formát je JSON. Formát požadavku je určen pomocí hlavičky Content-Type a je požadován pro operace, které mají tělo požadavku. API používá různé metody HTTP pro různé typy operací. Chcete-li zobrazit dostupné metody HTTP na adrese URL, použijte metodu OPTIONS na ni. Příklad:
Požadavek: OPTIONS /2.0/servers/ HTTP/1.1
Odpověď: HTTP/1.0 200 OK GET,PUT,DELETE,POST

Následující tabulka určuje významy metod HTTP, které mohou být použity klienty API:
GET: Získat prostředek nebo seznam prostředků.
PUT: Aktualizovat existující prostředek. Aktualizace implikuje idempotentní akci (žádost, která se opakuje s týmiž argumenty vždy vydá stejný výsledek).
POST: Vytvořit prostředek, nebo provést akci na objektu (např. provést akci start na serveru).

WHEN: Opakuje se s stejnými argumenty vždy vrací stejný výsledek). POST: Vytvořit prostředky, nebo provést akci na objektu (například spustit akci na serveru). POST se používá pro neidempotentní požadavky (požadavky, které mohou mít různé výsledky, pokud je opakováno vícekrát, i když je stejná vstupní data). DELETE: Odstranit prostředek. OPTIONS: Získat seznam oddělený čárkami podporovaných HTTP metod na URL. Odpověďový kódy stavů 📄 API používá standardní kódy stavů HTTP, kde kód od 200 do 299 znamená úspěch. Chyby požadavků mají kódy mezi 400 a 499, a chyby serveru mají kódy mezi 500 a 599. Následující kódy stavů vrací API:

Úspěšné stavové kódy:

  • 200: OK. Úspěšný požadavek.
  • 201: Object Created. Tento požadavek se používá pro volání, která vytváří nové objekty, jako je vytvořit disk nebo vytvořit server. Hlavička odpovědi Location obsahuje URI nově vytvořeného objektu.
  • 202: Accepted. Tato hlavička se používá pro dlouhé nebo asynchronní operace, jako je spuštění serveru nebo kopírování disku. Tato hlavička také implikuje, že požadavek může selhat a může být zrušen.
  • 204: No Content. Požadavek byl úspěšný a odpověď nemá obsah v těle. Tento stav se používá pro úspěšné požadavky DELETE. Klienti by měli být vědomi, aby neparsovali tělo, protože je prázdné a není platný JSON nebo XML dokument. Chyby API obvykle obsahují tělo, které popisuje chybu.

Pozor, aby se nezpracovala tělo, protože je prázdné a není platný JSON nebo XML dokument. Chybové odpovědi obvykle obsahují tělo, které popisuje chybu. Zkontrolujte část Chyby pro vysvětlení formátu zprávy o chybě. Chybové stavy odpovědi:

400: Bad Request. Tento status znamená, že je chyba v požadavku. Chyba požadavku může být chyba formátu dat (neplatný JSON nebo XML) nebo neplatná hodnota.

401: Unauthorized. Poskytnutá autentizace je neplatná nebo chybí. Tento stav odpovědi je běžnou součástí ověřování s digestem, ve kterém případě bude odpověď obsahovat hlavičku WWW-Authenticate s ověřovacím výzvou.

402: Payment Required. Tato chyba znamená, že není dostatek prostředků na účtu k dokončení akce. Vzniká při pokusu o zakoupení předplatného bez dostatečných prostředků na účtu, nebo při pokusu o spuštění serveru bez dostatečných prostředků pro pružnou spotřebu 5 dní.

403: Forbidden. Poskytnutá autentizace je platná, ale uživatel není povolen k dokončení akce. Tento status je použit pro chybu "práv" nebo "operace není povolena".

404: Not Found. Požadovaný objekt neexistuje. Tato chyba vzniká při požadavku na neexistující zdroj. Zdroj mohl nikdy nebyt vytvořen, nebo mohl být odstraněn.

405: Method Not Allowed. Tato chyba vzniká, když se používá nesprávný HTTP metoda na URL. Například DELETE požadavky nejsou povoleny na /profile/ URL, a vrátí 405 stav.

406: Not Acceptable. Tato chyba vznikne, když se používá neplatný HTTP metoda na URL. Například DELETE požadavky nejsou povoleny na /profile/ URL, a vrátí 405 stav.

Tato chyba vzniká, při použití nesprávného HTTP metody na URL. Například požadavky DELETE nejsou povoleny na URL /profile/ a vrátí se 405 stav. 406: Neakceptováný obsah. Tato chyba vzniká, když požadovaný obsahový typ požadavku v hlavičce Accept není podporován API. Podporované obsahové typy API jsou application/json, application/xml a */*, což se výchozí hodnotou nastaví na application/json. Pokud hlavička požadavku neobsahuje žádný z těchto obsahových typů, vrátí se 406 stav. Chyba stavu systému 500: Vnitřní chyba serveru. Tento stav znamená, že se v systému vyskytla chyba. Pokud se taková chyba vyskytne, kontaktujte podporu. 503: Služba nedostupná. Tento stav znamená, že systém momentálně nemůže splnit požadavek. Tento stav se vrací při souběžných aktualizacích, kdy klient vytváří více souběžných požadavků, které se pokoušejí aktualizovat stejné hodnoty, nebo kdy systém dosahuje kapacity. Pouze speciálním případem je \0, které končí řetězec. Filtrování 🔍 API umožňuje filtrování vrácených prostředků pomocí GET parametrů. Konkrétní možnosti filtrování jsou uvedeny v schématu. Existují dva typy filtrů: přesný: Odpovídá přesné hodnotě pole obsahuje: Odpovídá, necitlivě na velká a malá písmena, podřetězci hodnoty. Pravidla filtrů jsou následující: AND: Rozdělení GET parametrů ANDem: Příklad:?name=test&tag__name=test_tag Vrací prostředky, které odpovídají: (name = test) A (ma tag s názvem = test_tag) Stejný filtr aplikovaný dvakrát je stále ANDed: Příklad:?tag__name=test_tag1&tag__name=test_tag2 Vrací prostředky, které odpovídají: (ma tag s názvem = test_tag1) A (ma tag s názvem = test_tag2) OR: V jednom GET parametru jsou hodnoty rozděleny čárkou a ORed: Příklad:?name=name1,name2 Vrací prostředky, které odpovídají (name = name1) A (name = name2) Čáry mohou být unikátně zkresleny jedním zpáčkem a nebudou použity k rozdělení: Příklad:?name=name\,long\\,name2 Vrací prostředky, které odpovídají (name = name,long\) A (name = name2) Poznámka: OR má vyšší prioritu než AND. Příklad:?name=name1,name2&tag__name=test_tag Vrací prostředky, které odpovídají ((name = name1) OR (name = name2)) A (ma tag s názvem = test_tag)
