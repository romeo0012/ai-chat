Politiky Všechno v Vault je závislé na cestách, a politiky nejsou výjimkou. Politiky poskytují deklarativní způsob udělení nebo zákazu přístupu k určitým cestám a operacím v Vault. Tato část diskutuje o pracovních postupech a syntaxích politik. Politiky jsou v základní verzi zamítnuté, takže prázdná politika uděluje žádnou oprávnění v systému. Pracovní postup autorizace před přístupem lidmi nebo strojů musí být konfigurován správcem Vault pomocí metody auth. Autentizace je proces, při kterém lidské nebo strojové informace se ověřují proti vnitřní nebo vnějšímu systému. Viz následující diagram, který ilustruje kroky, které tým bezpečnosti provede k nastavení Vault k autentizaci pomocí instalace LDAP nebo ActiveDirectory společnosti. Hlavně v tomto příkladu se používá LDAP, ale koncept se týká všech metod auth. Tým bezpečnosti konfiguruje Vault k připojení k metodě auth. Tato konfigurace se liší podle metody auth. V případě LDAP potřebuje Vault adresu LDAP serveru a zda se připojit pomocí TLS. Důležité je si uvědomit, že Vault neukládá kopii databáze LDAP - Vault bude delegovat autentizaci metodě auth. Tým bezpečnosti vytvoří politiku (nebo použije existující politiku), která uděluje přístup k cestám ve Vault. Politiky se psou v HCL v editoru vašeho preference a ukládají se na disk. Obsahem politiky se nahrává a ukládá do Vault a odkazuje se na něj po jménu.

Poznámka: Tento překlad je určen pouze pro informační účely a nemá být použit v žádném komerčním nebo kritickém prostředí.

Cesty v Vault. Politiky se psané v HCL se vytváří v editoru vašeho preference a ukládají na disk. Obsahem politiky se zabýváte a nahráváte a ukládáte do Vault a odkazujete se na ně jménem. Můžete si představit, že jméno politiky slouží jako ukazatel nebo odkaz na její sadu pravidel. Nejdůležitější je, že tým bezpečnosti mapuje data v metodě autentizace na politiku. Například tým bezpečnosti může vytvořit mapování jako: Členové skupiny OU "dev" mapují na Vault politiku nazvanou "readonly-dev". či Členové skupiny OU "ops" mapují na Vault politiky "admin" a "auditor". Nyní má Vault vnitřní mapování mezi zadným systémem autentizace a vnitřní politikou. Když uživatel se pokusí autentizovat v Vault, je skutečná autentizace delegována na metodu autentizace. Jako uživatel se toto vyvíjí následovně: Uživatel se pokusí autentizovat v Vault pomocí svých LDAP kredenčí, poskytují Vault své LDAP uživatelské jméno a heslo. Vault navazuje spojení s LDAP a požaduje od LDAP serveru ověřit zadaná kredenčí. Předpokládejme, že to je úspěšné, LDAP server vrátí informace o uživateli, včetně skupin OU. Vault mapuje výsledek z LDAP serveru na politiky uvnitř Vault pomocí mapování nakonfigurovaného týmem bezpečnosti v předchozí části. Vault poté vytváří token a připojuje k nim odpovídající politiky. Vault token vrací uživateli. Tento token má přiřazená právě ta politika, jak je určeno mapováním konfigurací, kterou nastavil tým bezpečnosti v předchozí fázi.

Poznámka: Technické termíny, kódy, příkazy, cesty souborů, URL a formátování zůstávají ve stejném tvaru jako v původním textu.

Politiky. Skrýtá schránka Vault vrací token uživateli. Tento token má přiřazena správná práva, jak je určeno konfigurací mapování, kterou předem nastavila tým bezpečnosti. Poté uživatel používá Vault token k budoucím operacím. Pokud uživatel opakuje kroky autentizace, dostane nový token. Nový token bude mít stejná oprávnění, ale skutečný token bude jiný. Opakovaná autentizace nezruší původní token. Syntaxe politik
Politiky jsou psány v HCL nebo JSON a popisují, které cesty v Vault může uživatel nebo stroj přístupovat. Níže je velmi jednoduchá politika, která uděluje čtení schopností cestě KVv1 "tajemství/foo": 

path "tajemství/foo" {
  schopnosti = ["čtení"]
}

Pokud je tato politika přiřazena tokenu, může token číst z "tajemství/foo". Ale token nemůže aktualizovat nebo odstranit "tajemství/foo", protože schopnosti to neumožňují. Protože politiky jsou vyloučeny v praxi, token by neměl žádný jiný přístup v Vault. Níže je více podrobné politiky a je zde dokumentováno inline: 
# Tato část uděluje všechny schopnosti na "tajemství/*". Další omezení mohou být

přidány do této široké politiky, jak je ukázáno níže.

path "tajemství/*" {
  schopnosti = ["vytvořit", "čtení", "upravit", "patch", "odstranit", "seznamovat", "obnovit"]
}

Ačkoli povolili tajemství/*, následující řádek explicitně znepřístupňuje


tajemství/super-tajné. Toto má přednost.

"patch", "delete", "list", "recover"] # Ačkoliv povolili jsme secret/*, tato řádek explicitně odmítá # secret/super-sekret. Tato pravidla má přednost. cesta "secret/super-sekret" { schopnosti = ["zakázat"] } # Pravidla mohou také specifikovat povolené, zakázané a požadované parametry. zde # klíč "secret/restricted" může obsahovat "foo" (libovolnou hodnotu) a "bar" (jedna z "zip" nebo "zap"). cesta "secret/restricted" { schopnosti = ["vytvořit"] allowed_parametry = { "foo" = [] "bar" = ["zip", "zap"] } } Pravidla používají cestově závislou shodu k porovnání sad schopností s požadavkem. Pravidlo cesty může specifikovat přesnou cestu k shodě, nebo může specifikovat globový vzor, který instruuje Vault k předponové shodě: # Povolit čtení pouze "secret/foo". připojený token nemůže číst "secret/food" ani "secret/foo/bar". cesta "secret/foo" { schopnosti = ["čtení"] } # Povolit čtení všeho pod "secret/bar". připojený token mohl číst # "secret/bar/zip", "secret/bar/zip/zap", ale ne "secret/bars/zip". cesta "secret/bar/*" { schopnosti = ["čtení"] } # Povolit čtení všeho předponovaného s "zip-". připojený token mohl číst # "secret/zip-zap" nebo "secret/zip-zap/zong", ale ne "secret/zip/zap cesta "secret/zip-*" { schopnosti = ["čtení"] } Další + může být použit k označení libovolného počtu znaků v jednom segmentu cesty (toto se objevilo v Vault 1).

"tajné/zip-*" { schopnosti = ["čtení"] } Dalším symbolem "+", můžete označit libovolný počet znaků v jednom segmentu cesty (tento se objevil ve Vault 1.1): # Umožňuje čtení cesty "teamb" pod libovolnou kořenovou cestou pod tajné/ cestu "tajné/+/teamb" { schopnosti = ["čtení"] } # Umožňuje čtení tajné/foo/bar/teamb, tajné/bar/foo/teamb, atd. cesta "tajné/+/+/teamb" { schopnosti = ["čtení"] } Architektura Vaultu je podobná systému souborů. Každá akce v Vault má odpovídající cestu a schopnost - i Vaultovy vnitřní konfigurační koncepční body žijí pod cestou "sys/". Politiky definují přístup k těmto cestám a schopnostem, což ovlivňuje přístup tokenu k kredenzím v Vault. Příoritní odpovídání Poznámka: Pravidla, která Vault aplikuje, jsou určena nejvýraznějším shodným způsobem dostupným, podle následujících prioritních pravidel. To může být přesná shoda nebo nejdelší předpona globu. Pokud stejný vzor se objeví v několika politikách, bereme se schopnosti v unionu. Pokud se různé vzory objeví v platných politikách, bereme pouze nejvyšší prioritní shodu z těchto politik. To znamená, pokud definujete politiku pro "tajné/foo*", politika by také odpovídala "tajné/foobar".

Vault's architecture is similar to a filesystem. Every action in Vault has a corresponding path and capability - even Vault's internal core configuration endpoints live under the "sys/" path. Policies define access to these paths and capabilities, which controls a token's access to credentials in Vault. Priority matching Note: The policy rules that Vault applies are determined by the most-specific match available, using the priority rules described below. This may be an exact match or the longest-prefix match of a glob. If the same pattern appears in multiple policies, we take the union of the capabilities. If different patterns appear in the applicable policies, we take only the highest-priority match from those policies. This means if you define a policy for "secret/foo*", the policy would also match "secret/foobar".

Nejvyšší prioritní odpovídající z těchto politik. Tímto znamená, že pokud definujete politiku pro "secret/foo*", politika by také odpovídala "secret/foobar". Konkrétně, když mohou být potenciálně několik odpovídajících cest politik, P1 a P2, následující kritéria pro odpovídající cesty se použijí:

  • Pokud první zástupný znak (+) nebo glob (*) v P1 vyskytuje dříve než v P2, P1 má nižší prioritu
  • Pokud P1 končí na * a P2 ne, P1 má nižší prioritu
  • Pokud P1 obsahuje více + (zástupné znaky), P1 má nižší prioritu
  • Pokud P1 je kratší, má nižší prioritu
  • Pokud P1 je menší lexikograficky, má nižší prioritu

Například, pokud jsou zadány dvě cesty, "secret/*" a "secret/+/+/foo/*", první zástupný znak se vyskytuje ve stejném místě, obě končí na * a poslední má dva zástupné znaky, zatímco první má žádné. Takže dospíváme k pravidlu (3), a dáme "secret/+/+/foo/*" nižší prioritu. Další příklad s využitím Vault namespaces, kdy jsou definovány vložené namespaces ns1/ns2/ns3 a dvě cesty, "secret/*" a "ns1/ns2/ns3/secret/apps/*", kde secret je mountpoint v namespace ns3. První cesta je definována v politice v namespace ns3, zatímco druhá cesta je definována v politice v kořenovém namespace. Obě cesty končí na * ale první je kratší. Takže dospíváme k pravidlu (4), a dáme "secret/*" nižší prioritu.

Při poskytování schopnosti seznamu je důležité si uvědomit, že se vždycky provádí na předponě, proto musí být politiky prováděny na předponě, protože Vault sanitizuje požadavky na cesty tak, aby byly předpony. Schopnosti Každá cesta musí definovat alespoň jednu nebo více schopností, které poskytují jemnou kontrolu nad povolenými (nebo zamítnutými) operacemi. Jako ukázka jsou schopnosti vždy zadávány jako seznam řetězců, i když je jedna schopnost. Chcete-li určit schopnosti potřebné k provedení konkrétní operace, můžete k CLI příkazu přidat vlajku -output-policy. Pro ukázku se přečtěte část Tisknutelné požadavky na politiku dokumentu. Seznam schopností zahrnuje následující:

create (POST/PUT) - Dovoluje vytváření dat v dané cestě. Většina částí Vault neodlišuje mezi vytvářením a aktualizací, takže většina operací vyžaduje obě schopnosti vytváření a aktualizace. Části Vault, které poskytují takovou odlišnost, jsou uvedeny v dokumentaci.

read (GET) - Dovoluje čtení dat v dané cestě.

update (POST/PUT) - Dovoluje změnu dat v dané cestě. Ve většině částí Vault to implicitně zahrnuje schopnost vytvořit počáteční hodnotu v cestě.

patch (PATCH) - Dovoluje částečné aktualizace dat v dané cestě.

Většina částí Vault, což znamená i schopnost vytvořit počáteční hodnotu v dané cestě. patch (PATCH) - Umožňuje parciální aktualizaci dat v dané cestě. delete (DELETE) - Umožňuje smazání dat v dané cestě. list (LIST) - Umožňuje zobrazení hodnot v dané cestě. Poznamenejte si, že klíče vrácené operací list nejsou filtrovány podle politik. Nezakódujte citlivou informaci v názvech klíčů. Ne všechny back-endy podporují listování. V seznamu výše jsou spojené HTTP verbům zobrazeny vedle schopností. Při tvorbě politiky je často užitečné se podívat na dokumentaci API HTTP pro cesty a HTTP verby a mapovat je zpět na schopnosti. Mapping není vždy 1:1, ale často jsou velmi podobně odpovídající. Kromě standardní sady existují některé schopnosti, které se neodpovídají HTTP verbům. sudo - Umožňuje přístup k cestám, které jsou chráněny kořenovým uživatelem. Tokens nemohou interagovat s těmito cestami, pokud nemají schopnost sudo (kromě ostatních nutných schopností pro provedení akce proti této cestě, jako je například čtení nebo smazání). Například upravování záznamů záznamů auditu vyžaduje token s právy sudo. deny - Zakazuje přístup. Tato schopnost vždy převládá bez ohledu na jakékoliv jiné definované schopnosti, včetně sudo. subscribe - Umožňuje přihlášení k událostem pro danou cestu.

Překlad:

Akce a politiky tokenů, které jsou definovány na základě metody přihlášení nebo, v případě explicitního vytvoření tokenu prostřednictvím API, jsou vstupem do vytváření tokenu. Následující text se týká pouze politik tokenů: politiky identit tokenů nelze ovládat, kromě toho, že se upravují podkladní entitami, skupinami a členstvím ve skupinách. Tokeny jsou při vytváření spojeny s jejich politikami. Například: $ vault token create -policy=dev-readonly -policy=logs Normálně mohou být uvedeny pouze ty politiky, které jsou přítomny v aktuálních politikách tokenu (tedy nového tokenu rodiče). Však kořenoví uživatelé mohou přiřadit libovolné politiky. Není možné upravit politiky spojené s tokenem po vydání tokenu. Token musí být zrušen a nový získán, aby se získaly nové politiky. Však obsah politik je analýzován v reálném čase každýkrát, když je token použit. V důsledku toho, pokud je politika upravena, nové pravidlo bude platné dalšíkrát, když se token s tímto politikou připojí k provedení volání k Vault. Požadavky na UI politiky Nastavte UI politiky před povolením UI Vám není umožněno provedení úprav nebo přepsání koncových bodů ui/mounts a ui/resultant-acl po povolení rozhraní Vault UI. Vault ignoruje aktualizace politik, které cíle tyto cesty s explicitními zákaznými schopnostmi.
