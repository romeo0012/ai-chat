Policies

← Chat

Politiken ist in Vault Pfad-basiert und Policies sind keine Ausnahme. Policies bieten eine deklarative Möglichkeit, Zugriff auf bestimmte Pfade und Operationen in Vault zu gewähren oder zu verweigern. In diesem Abschnitt werden Policy-Workflows und Syntaxen diskutiert. Policies sind standardmäßig verweigert, also erlaubt ein leeres Policy keinen Zugriff im System.

Policy-Autorisierungsworkflow

Bevor ein Mensch oder eine Maschine Zugang erlangen kann, muss ein Administrator Vault mit einem Auth-Method konfigurieren. Authentifizierung ist der Prozess, bei dem menschlich oder maschinenbasiertes Informationen gegen ein internes oder externes System verifiziert werden. Betrachte die folgende Diagramm, das die Schritte einer Sicherheitsmannschaft zeigt, die Vault so konfiguriert, dass es sich authentifizieren kann, indem es auf eine Unternehmens-LDAP- oder ActiveDirectory-Installation verweist. Obwohl dieses Beispiel auf LDAP basiert, gilt der Konzept für alle Auth-Methods. Die Sicherheitsmannschaft konfiguriert Vault, um es mit einem Auth-Method zu verbinden. Diese Konfiguration variiert je nach Auth-Method. Im Fall von LDAP muss Vault wissen, wo der LDAP-Server liegt und ob über TLS verbunden werden soll. Es ist wichtig zu beachten, dass Vault keine Kopie des LDAP-Datenbank-Systems speichert - Vault delegiert die Authentifizierung an den Auth-Method. Die Sicherheitsmannschaft schreibt eine Policy (oder verwendet eine vorhandene Policy), die Zugriff auf Pfade in Vault gewährt. Policies werden in HCL in Ihrem bevorzugten Editor geschrieben und auf den Datenträger gespeichert. Die Inhalte der Policy werden in Vault hochgeladen und gespeichert und mit dem Namen referenziert.

Pfade in Vault. Politik werden in HCL in Ihrer bevorzugten Texteditor-Umgebung geschrieben und auf den Datenträger gespeichert. Die Politikinhalte werden hochgeladen und in Vault gespeichert und nach Name referenziert. Denken Sie daran, dass der Name der Politik wie ein Zeiger oder ein Symbolink auf ihre Regelensammlung zeigt. Wichtigstes ist, dass die Sicherheitsmannschaft Daten in der auth-Methode auf eine Politik zuordnet. Beispielsweise könnte die Sicherheitsmannschaft Mapping wie folgt definieren: Mitglieder der OU-Gruppe "dev" werden auf die Vault-Politik "readonly-dev" zugeordnet. oder Mitglieder der OU-Gruppe "ops" werden auf die Vault-Politiken "admin" und "auditor" zugeordnet. Jetzt verfügt Vault über eine interne Zuordnung zwischen einem Backend-Authentifizierungssystem und einer internen Politik. Wenn ein Benutzer sich bei Vault authentifiziert, wird die tatsächliche Authentifizierung an die auth-Methode delegiert. Als Benutzer sieht die Ablaufweise wie folgt aus: Ein Benutzer versucht sich bei Vault zu authentifizieren, indem er seine LDAP-Anmeldeinformationen bereitstellt, was Vault seinen LDAP-Benutzernamen und -Kennwort bereitstellt. Vault stellt eine Verbindung zu LDAP her und fragt den LDAP-Server nach der Überprüfung der angegebenen Anmeldeinformationen. Im Erfolgsfall gibt der LDAP-Server Informationen über den Benutzer zurück, einschließlich der OU-Gruppen. Vault mappt das Ergebnis des LDAP-Servers auf Inhalte innerhalb von Vault mithilfe der von der Sicherheitsmannschaft in der vorherigen Abschnitt konfigurierten Zuordnung. Vault erstellt dann ein Token und verknüpft die entsprechenden Politiken. Vault gibt das Token dem Benutzer zurück. Dieses Token hat die richtigen Politiken zugewiesen, wie von der vorgebenen Zuordnungskonfiguration der Sicherheitsmannschaft bestimmt.

(Code, Kommandos, Dateipfade und URLs bleiben unverändert.)

Politiken. Die Vault-Instanz gibt dem Benutzer einen Token zurück, das die richtigen Politik-Einstellungen enthält, wie von der Sicherheiteam vorab eingerichtet. Der Benutzer verwendet dieses Vault-Token für zukünftige Operationen. Wenn der Benutzer die Authentifizierungsschritte erneut durchführt, erhält er ein neues Token. Das Token hat die gleichen Berechtigungen, aber das tatsächliche Token ist anders. Eine erneute Authentifizierung führt nicht zur Invalidierung des ursprünglichen Tokens. Syntax der Politik
Politiken werden in HCL oder JSON geschrieben und beschreiben, welche Pfade in Vault ein Benutzer oder eine Maschine zugreifen darf. Hier ist ein sehr einfaches Beispiel für eine Politik, die Schreibzugriff auf den KVv1-Pfad "secret/foo" gewährt:

path "secret/foo" {
  capabilities = ["read"]
}

Wenn diese Politik einem Token zugewiesen wird, kann das Token aus "secret/foo" lesen. Allerdings kann das Token "secret/foo" nicht aktualisieren oder löschen, da die Fähigkeiten dies nicht erlauben. Da Politiken standardmäßig verweigern, hat das Token keinen anderen Zugriff auf Vault. Hier ist ein detaillierteres Politik-Beispiel, das auch dokumentiert ist:

auf diese breite Politik angewendet werden, wie unten gezeigt.

path "secret/*" {
  capabilities = ["create", "read", "update", "patch", "delete", "list", "recover"]
}

Policies können auch erlaubte, verwehrte und erforderliche Parameter spezifizieren. Hier
die Schlüssel "secret/beschränkt" können nur "foo" (beliebiger Wert) und "bar" (eines von "zip" oder "zap") enthalten.
path "secret/beschränkt" {
capabilities = ["create"]
allowed_parameters = {
"foo" = []
"bar" = ["zip", "zap"] } }

Policies verwenden Pfadbasierte Überprüfung, um die festgelegten Fähigkeiten gegenüber einer Anfrage zu testen. Eine Policy-Pfad kann ein genaues Pfad zum Abgleichen angeben oder ein glob-Muster, das Vault dazu auffordert, eine Präfix-Übereinstimmung zu verwenden:

Lesen nur "secret/foo" erlauben. Ein angehängter Token kann "secret/food" oder "secret/foo/bar" nicht lesen.


path "secret/foo" {
capabilities = ["read"] }

Lesen alles unter "secret/bar" erlauben. Ein angehängter Token könnte "secret/bar/zip", "secret/bar/zip/zap" lesen, aber nicht "secret/bars/zip".


path "secret/bar/*" {
capabilities = ["read"] }

Lesen alles, das mit "zip-" beginnt, erlauben. Ein angehängter Token könnte "secret/zip-zap" oder "secret/zip-zap/zong" lesen, aber nicht "secret/zip/zap" lesen.


path "secret/zip-*" {
capabilities = ["read"] }

Zusätzlich kann ein + verwendet werden, um jeden beliebigen Wert innerhalb eines einzelnen Pfadsegments anzugeben (das ist in Vault 1 erschienen).

"geheim/zip-*" { Fähigkeiten = ["lesen"] } Zusätzlich kann ein + verwendet werden, um jeden beliebigen Zeichenfolgenanteil innerhalb eines einzelnen Pfadsegments anzugeben (das erschien in Vault 1.1): # Lesen des "teamb" Pfads unter jedem obersten Pfad unter geheim/ Pfad "geheim/+/teamb" { Fähigkeiten = ["lesen"] } # Lesen von secret/foo/bar/teamb, secret/bar/foo/teamb, usw. Pfad "geheim/+/+/teamb" { Fähigkeiten = ["lesen"] }

Vaults Architektur ist ähnlich einer Dateisystemarchitektur. Jede Aktion in Vault hat eine entsprechende Pfad und Fähigkeit - auch die internen Kernkonfiguration Endpunkte von Vault leben unter dem "sys/" Pfad. Policies definieren den Zugriff auf diese Pfade und Fähigkeiten, was den Zugriff eines Tokens auf Credentials in Vault kontrolliert.

Das kann ein genaues Treffen oder der längste Präfix-Treffer eines Globs sein. Wenn dasselbe Muster in mehreren Politiks vorhanden ist, nehmen wir die Vereinigung der Fähigkeiten. Wenn verschiedene Muster in den anwendbaren Politiks vorhanden sind, nehmen wir nur den höchsten-Prioritäts-Treffer aus diesen Politiks. Das bedeutet, wenn Sie eine Politik für "geheim/foo*" definieren, würde die Politik auch für "geheim/foobar" passen.

höchste Priorität finden sich in den angegebenen Politik-Einstellungen. Das bedeutet, wenn Sie eine Politik für "secret/foo*" definieren, würde diese auch für "secret/foobar" passen. Genauere Angaben: Wenn es möglicherweise mehrere passende Politik-Pfade gibt, P1 und P2, wird folgendes Prioritätskriterium angewendet: Wenn das erste Wildcard-Zeichen (+) oder Glob-Zeichen (*) früher in P1 vorkommt, ist P1 niedriger priorisiert. Wenn P1 mit * endet und P2 nicht, ist P1 niedriger priorisiert. Wenn P1 mehr +-Wildcard-Segmente enthält, ist P1 niedriger priorisiert. Wenn P1 kürzer ist, ist es niedriger priorisiert. Wenn P1 kleiner lexikographisch ist, ist es niedriger priorisiert. Beispiel: Gegeben die beiden Pfade "secret/*" und "secret/+/+/foo/*", taucht das erste Wildcard-Zeichen in derselben Stelle auf, beide enden mit * und das letzte hat zwei Wildcard-Segmente, während das erste keines hat. Daher gelten die Regel (3) und man gibt "secret/+/+/foo/*" niedriger Priorität. Ein weiteres Beispiel mit Vault-Namespaces: Gegeben die eingeschachtelten Namespaces ns1/ns2/ns3 und zwei Pfade, "secret/*" und "ns1/ns2/ns3/secret/apps/*", wo secret ein Mountpunkt in Namespace ns3 ist. Der erste Pfad ist in einer Politik innerhalb/relativ zu Namespace ns3 definiert, während der zweite Pfad in einer Politik im Wurzel-Namespace definiert ist. Beide Pfade enden mit * aber der erste ist kürzer. Daher gelten die Regel (4) und man gibt "secret/*" niedriger Priorität. Hinweis: Das Glob-Zeichen, das in dieser Dokumentation verwendet wird, ist der Stern (*). Es ist kein regulärer Ausdruck und wird nur als letztes Zeichen des Pfads unterstützt!

Wie in den Beispielen oben gezeigt, werden Fähigkeiten immer als Liste von Zeichenfolgen angegeben, auch wenn es nur eine Fähigkeit gibt. Um die Fähigkeiten zu bestimmen, die für eine spezifische Operation erforderlich sind, kann der Flag -output-policy dem CLI-Befehl hinzugefügt werden. create (POST/PUT) - Erlaubt das Erstellen von Daten an der angegebenen Stelle. Es werden nur sehr wenige Teile von Vault zwischen Erstellen und Aktualisieren unterscheiden, sodass die meisten Operationen beide Erstellungs- und Aktualisierungsrechte erfordern. Teile von Vault, die solche Unterscheidung bieten, werden in der Dokumentation erwähnt.

read (GET) - Erlaubt das Lesen der Daten an der angegebenen Stelle.

update (POST/PUT) - Erlaubt das Ändern der Daten an der angegebenen Stelle. In den meisten Teilen von Vault impliziert dies automatisch die Möglichkeit, das Initialwert an der Stelle zu erstellen.

patch (PATCH) - Erlaubt es, die Daten an der angegebenen Stelle teilweise zu aktualisieren.

Folgende Teile von Vault sind betroffen, was implizit die Fähigkeit zur Erstellung der initialen Wert beim Pfad einschließt. patch (PATCH) - Erlaubt es, die Daten an einem gegebenen Pfad teilweise zu aktualisieren. delete (DELETE) - Erlaubt es, die Daten an dem gegebenen Pfad zu löschen. list (LIST) - Erlaubt es, die Werte an dem gegebenen Pfad aufzulisten. Token haben zwei Sätze von Politik: Identitätspolitiken, die auf der Basis der Entität und ihren Gruppen berechnet werden, und Tokenpolitiken, die entweder auf der Basis des Anmeldeverfahrens definiert sind oder, im Fall von expliziten Token-Erstellungen über die API, ein Eingabewert zum Token-Erstellungsprozess sind.

und Token-Politiken, die entweder auf der Anmeldemethode basiert oder, im Fall von expliziten Token-Erstellungen über die API, Teil der Token-Erstellung sind. Was folgt, betrifft Token-Politiken ausschließlich: die Identitäts-Politiken eines Tokens können nur durch Änderung der unterliegenden Entitäten, Gruppen und Gruppenmitgliedschaften beeinflusst werden. Tokens werden ihren Politiken bei der Erstellung zugeordnet. Beispiel: $ vault token create -policy=dev-readonly -policy=logs

Normalerweise können nur solche Politiken angegeben werden, die in den aktuellen Token-Politiken (also den Eltern-Politiken des neuen Tokens) vorhanden sind. Allerdings können root-Benutzer beliebige Politiken zuweisen. Es gibt keine Möglichkeit, die mit einem Token verbundenen Politiken nach der Ausstellung des Tokens zu ändern. Der Token muss revokiert und ein neues erworben werden, um eine neue Menge von Politiken zu erhalten. Allerdings werden die Inhalte der Politiken bei jeder Nutzung des Tokens in Echtzeit geparsed. Folglich gilt, wenn eine Politik geändert wird, die geänderten Regeln ab dem nächsten Mal gelten, wenn ein Token mit dieser Politik angehängt wird, um eine Anfrage an Vault zu machen.
