Bezpečnost¶ Argo CD prošel rigorózními vnitřními zkoumáními a testováním prolomení zabezpečení, aby splnil požadavky na PCI kompatibilitu. Následující jsou některé zabezpečení témat a implementační podrobnosti Argo CD. Autentizace¶ Autentizace k Argo CD API serveru probíhá pouze pomocí JSON Web Tokens (JWTs). Tokens uživatelského jména/hesla nesou se pro autentizaci. JWT je získán/spravován jedním z následujících způsobů: Pro lokálního správce je uživatelské jméno/heslo vyměněno za JWT pomocí /api/v1/session koncektoru. Tento token je podepsán a vydán Argo CD API serverem samotným a platí 24 hodin (původně neplatil, viz CVE-2021-26921). Když se heslo správce aktualizuje, všechny existující JWT pro správce jsou okamžitě zrušeny. Heslo je uloženo jako bcrypt hash v argocd-secret Secret. Pro uživatele Single Sign-On provedou uživatelé OAuth2 přihlašovací tok k nakonfigurovanému OIDC identitářovému poskytovateli (nebo přes vloženého Dex poskytovatele, nebo přímo k samostatně spravovanému OIDC poskytovateli). Tento JWT je podepsán a vydán IDP, a platnost a zrušení je řízeno poskytovatelem. Tokens Dex platí 24 hodin. Automatizační tokeny jsou vytvořeny pro projekt pomocí /api/v1/projects/{project}/roles/{role}/token koncektoru, a jsou podepsány a vydány Argo CD. Tyto tokeny mají omezený rozsah a práva, a mohou být použity pouze k správě prostředků aplikace v projektu, který patří.

Podepsáno a vydáno Argo CD. Tyto tokeny mají omezený rozsah a oprávnění a mohou být použity pouze k řízení prostředků aplikace v projektu, který patří k němu. Projektové JWTs mají konfigurovatelnou dobu trvání a mohou být okamžitě zrušeny odstraněním odkazu ID JWT role z projektu. Autorizace¶ Autorizace probíhá iterací seznamu skupin členství v JWT skupinách uživatele a porovnáváním každé skupiny s rolemi/pravidly v RBAC politice. Každé odpovídající pravidlo umožňuje přístup k požadavku na API. TLS¶ Všechny komunikace probíhají přes TLS, včetně komunikace mezi službami mezi třemi komponentami (argocd-server, argocd-repo-server, argocd-application-controller). Argo CD API server může nutil k použití TLS 1.2 pomocí následujícího příkazu: --tlsminversion 1.2. Komunikace s Redis probíhá výchozími nastaveními přes HTTP bez TLS. TLS může být nastaveno pomocí příkazového řádku. Git & Helm Repositories¶ Git a helm repozitáře spravují samostatný služba, nazývaná repo-server. Repo-server nemá žádná Kubernetes oprávnění a neukládá přihlašovací údaje k žádným službám (včetně git). Repo-server je odpovědný za klonování repozitářů, které byly povoleny a důvěryhodné Argo CD operátory, a generování Kubernetes manifestů v dané cestě v repozitáři.

Při konfiguraci git repozitářů, které může Argo CD nasadit, je nutno brát v úvahu bezpečnostní aspekty. V krátkém přehledu znamená neautorizované psaní do git repozitáře, které je důvěryhodné pro Argo CD, vážné bezpečnostní následky, které jsou níže uvedeny.

Neautorizované nasazení¶ Protože Argo CD nasaduje Kubernetes prostředky definované v git, může útočník s přístupem k důvěryhodnému git repozitáři ovlivnit prostředky Kubernetes, která jsou nasazena. Například útočník může aktualizovat manifest nasazení a nainstalovat do prostředí škodlivé obrázky kontejneru, nebo odstranit prostředky v git, což způsobí, že budou odstraněny v živém prostředí.

Vyvolání nástrojů příkazového řádku¶ Kromě raws YAML podporuje Argo CD nativně dvě populární nástroje pro správu konfigurací Kubernetes, helm a kustomize. Při generování manifestů Argo CD spouští tyto nástroje konfiguračních správ (např. helm template, kustomize build) k vytvoření manifestů. Je možné, že útočník s psaním do důvěryhodného git repozitáře vytvoří škodlivé helm charty nebo kustomizace, které se pokoušejí číst soubory mimo strom.

Vytvořte manifesty. Je možné, že útočník s psacími právy v důvěryhodném git repozitáři vytvoří škodlivé helm charty nebo kustomizace, které se pokouší číst soubory mimo strom. Toho se týkají i sousední git repozitáře, stejně jako soubory na samotném serveru repozitářů. Zda to je riziko pro vaši organizaci závisí na tom, zda obsah v git repozitářích obsahuje citlivé informace. Výchozí nastavení neobsahuje citlivé informace, ale může být nakonfigurováno s Pluginy správy konfigurace, které to mohou (např. klíče pro dekryptaci). Pokud se tyto pluginy používají, musíte brát extrémní opatrnost, aby obsah repozitáře mohl být vždy důvěryhodný. Volitelně mohou být nainstalované nástroje pro správu konfigurace individuálně vypnuty. Pokud víte, že vaši uživatelé nebudou potřebovat určitý nástroj pro správu konfigurace, doporučujeme ho vypnout. Další informace naleznete v článku Tool Detection.

Závislosti na helm charty a kustomizace vzdálených základních repozitářů¶ Repozitáře Argo CD umožňují pouze omezit počáteční repozitář, který se klonuje. Nicméně kustomize a helm obsahují funkce pro odkazování a následování dalších repozitářů (např. kustomize remote bases, helm chart dependencies), které mohou být mimo repozitář, který je v repozitáři allow-listu. Operátoři Argo CD musí pochopit, že uživatelé s psacími právy v důvěryhodném git repozitáři mohou odkazovat na další vzdálené git repozitáře obsahující Kubernetes zdroje, které nejsou snadno hledatelné nebo auditovatelné v konfigurovaných git repozitářích.

Musíte si uvědomit, že uživatelé s právem zápisu do důvěryhodných git repozitářů mohou odkazovat na jiné vzdálené git repozitáře obsahující Kubernetes prostředky, které nejsou snadno hledatelné nebo auditovatelné v konfigurovaných git repozitářích. Citlivá informace¶ Tajné informace¶ Argo CD nikdy nevrátí citlivá data z jeho API, a cenzuruje všechna citlivá data v payloadech API a protokolech. Toto zahrnuje:

  • kredence clusteru
  • kredence Gitu
  • tajné klientské klíče OAuth2
  • hodnoty Kubernetes Secretů
  • Tajné informace o vnějším clusteru¶ K vedení vnějších clusterů slouží Argo CD k ukládání tajných informací o vnějším clusteru jako Kubernetes Secret v argocd namespace. Tento tajný klíč obsahuje K8s API bearer token spojený s argocd-manager ServiceAccount vytvořeným během argocd cluster add, spolu s možnostmi připojení k tomuto API serveru (konfigurace TLS/certifikátů, AWS role-arn, atd...). Informace se používají k obnově REST config a kubeconfig pro cluster používaný službami Argo CD. Záznamy API¶ Záznamy Argo CD zahrnují plnění většiny požadavků API, kromě požadavků, které jsou považovány za citlivé, jako je /cluster.ClusterService/Create, /session.SessionService/Create atd. Radí se namísto toho konfigurovat záznam IP adres v proxy serveru, který sedí před API serverem.

Od většiny API serveru je typicky před proxy. Místo toho je doporučeno konfigurovat záznam IP adres v proxy serveru, který je umístěn před API serverem. Omezení použití paměti adresáře aplikace¶ 2.2.10, 2.1.16, >2.3.5 Aplikace typu adresář (ty, jejichž zdroj je soubory JSON nebo YAML) mohou spotřebovat velké množství paměti serveru úložiště, podle velikosti a struktury souborů YAML. Chcete-li zabránit přesužití paměti serveru úložiště (potenciálně způsobující zastavení a odmítnutí služby), nastavte možnost config argocd-cmd-params-cm reposerver.max.combined.directory.manifests.size. Tato možnost omezuje celkový rozsah všech JSON nebo YAML souborů v jednotlivé aplikaci. Poznamenejte si, že in-memory reprezentace manifestu může být až 300x větší než manifest na disku. Také si poznamenejte, že limit je na aplikaci. Pokud jsou manifesty generovány pro více aplikací najednou, bude použití paměti vyšší. Příklad: Předpokládejme, že server úložiště má paměť 10G, a máte deset aplikací, které používají soubory JSON nebo YAML.

Překlad:

Použití více aplikací najednou znamená vyšší spotřebu paměti. Příklad: Předpokládejme, že váš server repa má limit paměti 10G a máte deset aplikací, které používají rawní JSON nebo YAML soubory. Chcete-li spočítat maximální bezpečnější kombinovaný souborový rozsah pro každou aplikaci, rozdělte 10G na 300 * počet aplikací (300 je faktor růstu paměti nejhoršího případu pro manifesty). 10G / 300 * 10 = 3M, takže důrazně bezpečná konfigurace pro tento nastavení by mohla být omezení na 3M pro každou aplikaci.

apiVersion: v1
kind: ConfigMap
metadata:
name: argocd-cmd-params-cm
data:
reposerver.max.combined.directory.manifests.size: '3M'

Tento poměr 300x předpokládá zločinně navržený soubor manifestu. Pokud chcete chránit pouze před neoprávněným růstem paměti, je pravděpodobné, že můžete použít menší poměr. Vzaměte si na to, že pokud může zločinec vytvořit další aplikace, může zvýšit celkovou spotřebu paměti. Udělujte práva k vytváření aplikací opatrně.

Poznámka: Tento překlad je určen pouze pro účely vysvětlení a není určen pro použití v životě. Vždy se doporučuje zkontrolovat přesně a prověřit překlad s odborníkem.
