Vysoká dostupnost¶ Argo CD je většinou statická. Všechny data jsou uložena jako objekty Kubernetes, která jsou uložena v etcd Kubernetes. Redis se používá pouze jako dočasný cache a může být bezpečně obnoveno bez zásahů do služby. Nabídka HA manifestů je k dispozici pro uživatele, kteří chtějí spouštět Argo CD v módě vysoké dostupnosti. Tato spouští více kontejnerů a spouští Redis v módě HA. Poznámka: Instalace vysoké dostupnosti vyžaduje alespoň tři různé uzly z důvodu pravidla proti-afinitní v specifikacích. Dalším nepodporovaným je pouze cluster IPv6. Navýšování kapacit¶ argocd-repo-server¶ nastavení: Argo CD je odpovědný za klonování Git repozitáře, udržování jeho aktuality a generování manifestů pomocí vhodného nástroje. Argo CD používá nástroje pro správu konfigurace fork/exec k generování manifestů. Fork může selhat z důvodu nedostatku paměti nebo omezení počtu OS vláken. Zastavíte se na --parallelismlimit, který kontroluje počet souběžných generací manifestů a pomáhá vyhnout se OOM kills. Argo CD se ujistí, že repozitář je v čistém stavu během generování manifestů pomocí nástrojů pro správu konfigurace jako je Kustomize, Helm nebo vlastní plugin. Výsledkem je, že Git repozitáře s více aplikacemi mohou ovlivnit výkon serveru repozitáře. Další informace naleznete v Scaling Monorepo Considerations. Argo CD klonuje repozitář do /tmp (nebo cesty určené v proměnné prostředí TMPDIR).

Poznámka: Vysoká dostupnost vyžaduje alespoň tři různé uzly z důvodu pravidla proti-afinitní v specifikacích. Dalším nepodporovaným je pouze cluster IPv6.

Monorepo Scaling Considerations¶

Server Argo CD repo udržuje jeden klon repozitáře místně a používá ho k generování manifestů aplikací. Pokud generování manifestu vyžaduje změnu souboru v místním klonu repozitáře, pak pouze jeden současný proces generování manifestu na serverovém instance je povolen. Tato omezení mohou významně zpomalit Argo CD, pokud máte monorepo s více aplikací (50+).

Použijte Celé Kvalifikované Git Reference¶ Když určíte targetRevision v vašich Manifestech aplikací, použití celých kvalifikovaných cest k Git referencím místo krátkých názvů může významně zlepšit výkon serveru s repozitářem, zejména v velkých monorepo s setinkami a tagy desetitisíců. Výkon: Když rozšiřuje Git referenci (např. převede main na SHA commit), Argo CD musí:

  1. Načíst všechny Git referenze (větvě a tagy)
  1. Projít všemi referencemi, aby nalezl shodu
  1. Rozložit symbolické referenze, pokud je to nutné

Pro repozitáře s mnoha referencemi je tento proces náročný na CPU a paměť. Použití celých kvalifikovaných referencí umožní Argo CD optimálně upravit proces rozpoznávání a využít caching efektivněji. Doporučený přístup:

❌ Méně efektivní - vyžaduje procházení všech refs


spec:
source:
targetRevision: main

✅ Výkonnější - přímo identifikuje typ reference


spec:
source:
targetRevision: refs/heads/main

Obvyklé formáty celých kvalifikovaných referencí:

Větvě: refs/heads/<branch-name> (např. refs/heads/main, refs/heads/develop)

Pokud generace manifestu nemá vedlejší účinky, pak žádosti jsou zpracovávány souběžně bez významného zpomalení výkonu. Následující jsou známé případy, které mohou způsobit pomalost a jejich řešení:

  • Více aplikací Helm závislých na stejném adresáři v jednom Git repozitáři: pro historické důvody Argo CD generoval Helm manifesty v pořadí. Od verze 3.0 Argo CD generuje Helm manifesty v souběžném režimu vůbec jako výchozí nastavení.
  • Více aplikací s vlastními pluginy: vyhýte se vytváření dočasných souborů během generování manifestu a vytvořte soubor .argocd-allow-concurrency v adresáři aplikace, nebo použijte možnost sidecar pluginu, který každou aplikaci zpracovává pomocí dočasného kopie repozitáře.
  • Více aplikací Kustomize v jednom repozitáři s přepsanými parametry: V současné době je pro tento omezení žádný řešení.

Vlastnost plug-inu, která každou aplikaci zpracovává pomocí dočasné kopie repozitáře. V jednom repozitáři se nacházejí více aplikací Kustomize s přepsanými parametry: V současné době neexistuje žádný způsob, jak se toto omezení vyhnout. Cesty k Manifestům Anotace¶ Argo CD agresivně uchovává generované manifesty a používá SHA commitu repozitáře Git jako klíč pro uchování cache. Nový commit do repozitáře Git zruší cache pro všechny aplikace konfigurované v repozitáři. To může negativně ovlivnit repozitáře s více aplikacemi. Můžete použít anotaci Application CRD argocd.argoproj.io/manifest-generate-paths k řešení tohoto problému a zlepšení výkonu. Poznámka: Anotace argocd.argoproj.io/manifest-generate-paths je k dispozici pro použití s webhooky. Od verze Argo CD 2.11 může být tato anotace také použita bez konfigurace žádných webhooků. Webhooks nejsou předpokladem pro tuto funkci. Můžete se spolehnout pouze na anotaci k optimalizaci generování manifestů pro všechny aplikace. Anotace argocd.argoproj.io/manifest-generate-paths obsahuje seznam oddělovaný tečkou a semikolonem cest v repozitáři Git, které se používají při generování manifestů. Využije cesty uvedené v anotaci k porovnání poslední uložené revize s posledním commitem. Pokud žádný soubor nebyl změněn, který odpovídá cestám uvedeným v argocd.argoproj.io/manifest-generate-paths, pak nebude spuštěna reconciliace aplikace a existující cache bude považována za platnou pro nový commit.

Synchronizace aplikace & Jitter¶ Argo CD má limit pro synchronizaci aplikací. Budou se pro každou aplikaci periodicky spouštět aktualizace, když dojde k vypršení limitu. S velkým počtem aplikací to způsobí špičku v frontě aktualizací a může způsobit špičku na komponentě repo-server. Chcete-li toto vyhnout, můžete nastavit jitter pro limit synchronizace, který rozptýlí aktualizace a dá čas komponentě repo-server na zachycení. Jitter je maximální doba, kterou může být přidána k limitu synchronizace, takže pokud limit synchronizace je 5 minut a jitter je 1 minut, pak skutečný limit bude mezi 5 a 6 minutami. Chcete-li nastavit jitter, můžete nastavit následující proměnné prostředí:

ARGOCD_RECONCILIATION_JITTER - Jitter, který se přidá k limitu synchronizace.

Časový limit skutečného zpracování bude mezi 5 a 6 minutami. Chcete-li nastavit jitter, můžete nastavit následující prostředníkové proměnné: ARGOCD_RECONCILIATION_JITTER - Jitter, který se aplikuje na časový limit synchronizace. Zakázáno, pokud je hodnota 0. Výchozí hodnota je 60. Omezení rychlosti aplikace synchronizací¶ Chcete-li zabránit vysokému spotřebování zdrojů kontroléru nebo vzniku smyček způsobených chováním nevhodných aplikací nebo jinými faktory specifickými pro prostředí, můžeme nastavit omezení rychlosti pro workqueues používané kontrolérem aplikace. Existují dva typy omezení rychlosti, která mohou být nastavena: Omezení rychlosti globální Omezení rychlosti na položku

Konečný omezovač rychlosti používá kalculaci kombinovanou z obou a vypočítá konečný zpomalovací čas jako max(globalBackoff, perItemBackoff). Omezení rychlosti globální¶ Toto je vypnuté v základní verzi, jedná se o jednoduchý omezovač rychlosti na položky, který omezuje počet položek, které mohou být umístěny do fronty za sekundu. To je užitečné k tomu, aby se zabránilo, aby se velké množství aplikací umístilo do fronty najednou. Chcete-li nastavit omezovač fronty, můžete nastavit následující prostředníkové proměnné: WORKQUEUE_BUCKET_SIZE - Počet položek, které mohou být umístěny do fronty v jednom výstřelu. Výchozí hodnota je 500. WORKQUEUE_BUCKET_QPS - Počet položek, které mohou být umístěny do fronty za sekundu. Výchozí hodnota je MaxFloat64, což zneškodňuje omezovač. Omezení rychlosti na položku¶ Toto vypouští výchozí fixní zpoždění/zpomalovací čas, ale může být nastaveno na hodnoty exponenciální. Omezovač rychlosti na položku omezuje početkrát, jak může být položka umístěna do fronty.

Strategie HTTP požadavku na opakování¶
V případech, kdy dochází k nestabilitě sítě nebo k transientním chybám serveru, se strategie opakování zajistí robustnost komunikace HTTP tím, že automaticky opakuje neúspěšné požadavky. Využívá kombinaci maximálního počtu opakování a odkladů mezi opakováním k prevenci přetížení serveru nebo třesení sítě. Konfigurace opakování¶
Logika opakování může být upravena následujícími proměnnými prostředí:
  • ARGOCD_K8SCLIENT_RETRY_MAX - Maximální počet opakování pro každý požadavek. Požadavek bude opuštěn po dosažení tohoto počtu. Výchozí hodnota je 0 (žádné opakování).
  • ARGOCD_K8SCLIENT_RETRY_BASE_BACKOFF - Iniciální odklad na první pokus o opakování v ms. Následující opakování se zdvojnou tento odklad do maximální hranice. Výchozí hodnota je 100ms.

Strategie odkladu¶
Strategie odkladu, kterou používáme, je jednoduchá exponenciální odklad bez jitteru. Odklad se zvětšuje exponenciálně s každým pokusem o opakování až do dosažení maximálního odkladu.

Strategie odkladu používá následující proměnnou:

  • WORKQUEUE_BASE_DELAY_NS - Bázový odklad mezi opakováním v ns.
  • WORKQUEUE_MAX_DELAY_NS - Maximální odklad mezi opakováním v ns.
  • WORKQUEUE_BACKOFF_FACTOR - Faktor zvětšování odkladu mezi opakováním.
  • numRequeue - Počet opakování.

100ms. Strategie zpětné sledování¶ Strategie zpětného sledování, kterou používáme, je jednoduchá exponenciální zpětná sledování bez zrychlení. Doba zpětného sledování se zvětšuje exponenciálně s každým pokusem o znovupokus až do dosažení maximální doby zpětného sledování. Vzorec pro výpočet doby zpětného sledování je: backoff = min(retryWaitMax, baseRetryBackoff * (2 ^ retryAttempt)) Kde retryAttempt začíná na nule a zvětšuje se o 1 pro každý následující pokus. Maximální doba čekání¶ Existuje limit na dobu zpětného sledování, aby se zabránilo nadměrně dlouhým časům mezi pokusy o znovupokus. Tento limit je definován jako: retryWaitMax - Maximální doba čekání před znovupokusem. Tím se zajistí, že znovupokusy probíhají v rozumném časovém rámci. Výchozí hodnota je 10 sekund. Nepokusatelné podmínky¶ Ne všechny odpovědi HTTP jsou kandidáty na znovupokus. Následující podmínky nebudou spouštět znovupokus: Odpovědi s kódem stavu označujícím chyby klienta (4xx) kromě 429 Too Many Requests. Odpovědi s kódem stavu 501 Not Implemented. Profilování CPU/paměti¶ Argo CD opčně poskytuje profilovací koncový bod, který může být použit k profilování spotřeby CPU a paměti komponenty Argo CD. Profilovací koncový bod je dostupný na metrickém portu každé komponenty. Další informace o portu naleznete v metrikách. Pro bezpečnostní důvody je profilovací koncový bod vypnutý v případě výchozího nastavení. Koncový bod můžete zapnout nastavením server.profile.enabled, applicationsetcontroller.profile.enabled, reposerver.profile.enabled nebo controller.profile.enabled.

Metriky pro další informace o portu. Pro bezpečnostní důvody je koncový bod pro profilování vypnutý v základní konfiguraci. Koncový bod můžete povolit nastavením klíče argocd-cmd-params-cm ConfigMap server.profile.enabled, applicationsetcontroller.profile.enabled, reposerver.profile.enabled nebo controller.profile.enabled na hodnotu true. Po povolení koncového bodu můžete použít nástroj go profile k shromažďování profilů CPU a paměti. Příklad: $ kubectl port-forward svc/argocd-metrics 8082:8082 $ go tool pprof http://localhost:8082/debug/pprof/heap

Shallow klonování¶ Repozitáře s velkými historiemi nebo velkými soubory v minulých revizích mohou být pomalé k klonování a aktualizování. Chcete-li zrychlit proces klonování, můžete použít možnost hloubky repozitáře:
apiVersion: v1
stringData:
depth: "1"
type: "git"
url: "https://github.com/argoproj/argocd-example-apps.git"
kind: Secret
metadata:
annotations:
managed-by: argocd.argoproj.io
labels:
argocd.argoproj.io/secret-type: repository
name: my-repo
namespace: argocd
type: Opaque

Poznámka: Můžete použít příkaz argocd repo add <repo-url> --depth k přidání repozitáře s povoleným klonováním s hloubkou. Při klonování se repozitář klonuje s hloubkou 1, což znamená, že se klonuje pouze požadovaný commit namísto celé historie. Tento přístup smysl má, když repozitář má velkou historii.
