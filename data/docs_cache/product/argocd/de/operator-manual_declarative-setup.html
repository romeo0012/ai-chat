Erklärungsbasierter Setup¶ Argo CD-Anwendungen, Projekte und Einstellungen können deklarativ mithilfe von Kubernetes-Manifests definiert werden. Diese können über kubectl apply aktualisiert werden, ohne dass das argocd-Befehlszeilentool berührt werden muss. Schnellzugriff¶ Alle Ressourcen, einschließlich der Anwendung und AppProject-Spezifikationen, müssen in dem Argo CD-Namespace installiert werden (standardmäßig argocd). Konfigurationsdatei argocd-tls-certs-cm.yaml:
Diese Konfigurationsdatei definiert den ConfigMap argocd-tls-certs-cm, der spezielle TLS-Zertifikate enthält, um Git-Repositorys über HTTPS (ab Version 1.2 und später) zu verbinden.

Konfigurationsdatei argocd-ssh-known-hosts-cm.yaml:
Diese Konfigurationsdatei definiert den ConfigMap argocd-ssh-known-hosts-cm, der SSH-bekannte Hostdaten enthält, um Git-Repositorys über SSH (ab Version 1.2 und später) zu verbinden.

Hinweis:
Für jeden spezifischen Typ von ConfigMap- und Secret-Ressourcen gibt es nur eine einzige unterstützte Ressourcenname (wie in der oben angegebenen Tabelle aufgeführt) - wenn Sie Dinge zusammenführen müssen, müssen Sie dies vor der Erstellung tun.

Warnung:
Ein Hinweis zu ConfigMap-Ressourcen: Stellen Sie sicher, dass Sie Ihre ConfigMap-Ressourcen mit den Anmerkungen versehen, indem Sie die Label app.kubernetes.io/part-of: argocd anwenden, sonst kann Argo CD sie nicht verwenden.

Die Application CRD ist das Kubernetes-Ressourcenobjekt, das eine in einem Umgebung bereitgestellte Anwendungsinstanz darstellt. Es wird durch zwei wesentliche Stückinformationen definiert: eine Referenz auf den gewünschten Zustand in Git (Repository, Revision, Pfad, Umgebung) eine Referenz auf das Zielcluster und Namespace. Für den Cluster kann entweder Server oder Name verwendet werden, aber nicht beides (was zu einem Fehler führen wird). Unter der Hood wird bei der Abwesenheit des Servers berechnet und für alle Operationen verwendet. Ein minimaler Application spec ist wie folgt:
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
name: guestbook
namespace: argocd
spec:
project: default
source:
repoURL: https://github.com/argoproj/argocd-example-apps.git
targetRevision: HEAD
path: guestbook
destination:
server: https://kubernetes.default.svc
namespace: guestbook
Siehe application.yaml für zusätzliche Felder. Solange Sie den ersten Schritt der Anleitung erfüllt haben, können Sie dieses mit kubectl apply -n argocd -f application.yaml anwenden und Argo CD wird die guestbook-Anwendung bereitstellen.
Hinweis Der Namespace muss mit dem Namespace Ihrer Argo CD-Instanz übereinstimmen - typischerweise ist dies argocd.
Hinweis Bei der Erstellung einer Anwendung aus einem Helm-Repository muss das Attribut chart anstelle des Pfad-Attributs innerhalb von spec.source angegeben werden.
spec:
project: default
source:
repoURL: https://argoproj.io
chart: argocd-example-apps
targetRevision: HEAD
namespace: argocd

spec:

App of Apps¶
Sie können eine Anwendung erstellen, die andere Anwendungen erstellt, die wiederum weitere Anwendungen erstellen können. Dadurch können Sie eine Gruppe von Anwendungen, die gemeinsam bereitgestellt und konfiguriert werden können, deklarativ verwalten. Siehe Knotenstart.
Projects¶
Die AppProject CRD ist das Kubernetes-Ressourcenobjekt, das eine logische Gruppierung von Anwendungen darstellt. Es wird durch die folgenden wichtigen Informationen definiert:
sourceRepos Referenz auf die Repositories, aus denen Anwendungen innerhalb des Projekts Manifeste abrufen können.
destinations Referenz auf Cluster und Namespaces, auf die Anwendungen innerhalb des Projekts bereitstellen können.
roles Liste von Entitäten mit Definitionen ihrer Zugriffsrechte auf Ressourcen innerhalb des Projekts.

Hinweis: Projekte, die in das Argo CD Namespace bereitstellen können, gewähren Admin-Zugriff
Wenn die Konfiguration der destinations eines Projekts es erlaubt, in dem Namespace zu bereitstellen, in dem Argo CD installiert ist, haben Anwendungen unter diesem Projekt Admin-Zugriff.

Repositories¶
Hinweis: Einige Git-Hoster - insbesondere GitLab und möglicherweise auch lokale GitLab-Instanzen - erfordern, dass Sie das .git-Suffix im Repository-URL-Feld angeben, sonst werden Sie eine HTTP 301-Leitstelle erhalten, die den Repository-URL-Feld mit .git erweitert. Argo CD folgt diese Leitstellen nicht, sodass Sie Ihre Repository-URL entsprechend anpassen müssen. Die Repository-Details werden in Geheimnissen gespeichert. Um ein Repo zu konfigurieren, erstellen Sie ein Geheimnis, das die Repository-Details enthält. Überlegen Sie es, bitnami-labs/sealed-secrets zu verwenden, um eine verschlüsselte Geheimnisdefinition als Kubernetes-Manifest zu speichern. Jedes Repo muss ein url-Feld und, je nachdem, ob Sie über HTTPS, SSH oder GitHub App verbinden, benutzername und passwort (für HTTPS), sshPrivateKey (für SSH) oder githubAppPrivateKey (für GitHub App) haben. Die Anmeldeinformationen können auf ein Projekt beschränkt werden, indem das optional Felder Projekt verwendet wird. Wenn es fehlt, wird die Anmeldeinformation als Standard für alle Projekte ohne beschränkte Anmeldeinformation verwendet.

Um für Argo CD eine Credential-Vorlage für einen bestimmten Repository zu verwenden, müssen die folgenden Bedingungen erfüllt sein:

  • Das Repository muss entweder überhaupt nicht konfiguriert sein, oder wenn es konfiguriert ist, muss es keine Zugangsdaten (z.B. sshPrivateKey, username, password) enthalten.
  • Die URL einer Credential-Vorlage (z.B. https://github.com/argoproj) muss als Präfix für die Repository-URL (z.B. https://github.com/argoproj/argocd-example-apps) entsprechen.

Hinweis: Die Übereinstimmung von Credential-Vorlage-URL-Präfixen erfolgt auf Best-Effort-Basis, also wird der längste (beste) Matching-Vorlage-URL-Präfix den Vorrang haben. Die Reihenfolge der Definition ist unerheblich, im Gegensatz zu der vor v1.4.

In the above example, every repository accessed via HTTPS whose URL is prefixed with https://github.com/argoproj would use a username stored in the key username and a password stored in the key password of the secret private-repo-creds for connecting to Git. In order for Argo CD to use a credential template for any given repository, the following conditions must be met:

  • The repository must either not be configured at all, or if configured, must not contain any credential information (i.e. contain none of sshPrivateKey, username, password )
  • The URL configured for a credential template (e.g. https://github.com/argoproj) must match as prefix for the repository URL (e.g. https://github.com/argoproj/argocd-example-apps).

Note: Matching credential template URL prefixes is done on a best match effort, so the longest (best) match will take precedence. The order of definition is not important, as opposed to pre v1.4 configuration.

Repositories, die sich selbst signierte TLS-Zertifikate verwenden (oder von einem benutzerdefinierten CA signiert werden)¶ Sie können die verwendeten TLS-Zertifikate zum Überprüfen der Authentizität Ihrer Repository-Server in einem ConfigMap-Objekt namens argocd-tls-certs-cm verwalten. Der data-Abschnitt sollte eine Map enthalten, mit dem Hostnameteil (nicht der komplette URL) als Schlüssel und den Zertifikaten in PEM-Format als Daten. Somit, wenn Sie auf ein Repository mit der URL https://server.beispiel.com/repos/my-repo zugreifen, sollten Sie server.beispiel.com als Schlüssel verwenden. Das Zertifikat-Daten sollte entweder der Server-Zertifikat (für den Fall eines selbst signierten Zertifikats) oder das Zertifikat der CA sein, die das Server-Zertifikat signiert hat. Sie können für jeden Server mehrere Zertifikate konfigurieren, z.B. wenn Sie ein Zertifikat-Rollover geplant haben. Wenn für einen Repository-Server keine spezifischen Zertifikate konfiguriert sind, wird der Systemstandard-Vertrauensspeicher verwendet, um den Server-Repository zu validieren. Das sollte genügend sein für die meisten (wenn nicht alle) öffentlichen Git-Repository-Dienste wie GitLab, GitHub und Bitbucket sowie die meisten privat gehosteten Seiten, die Zertifikate von bekannten CAs verwenden, einschließlich Let's Encrypt-Zertifikate.

SSH bekannte Host-Public-Keys¶
Wenn Sie Repositorys konfigurieren, um SSH zu verwenden, benötigt Argo CD die SSH-Public-Keys der Repository-Server. Um über SSH mit Argo CD verbunden zu sein, müssen die Public-Keys für jeden Repository-Server vorab in Argo CD konfiguriert sein (anders als TLS-Konfiguration), sonst scheitern die Verbindungen zum Repository. Sie können die SSH-bekannten Hosts-Daten im ConfigMap argocd-ssh-known-hosts-cm verwalten. Dieses ConfigMap enthält eine einzige Eintragung, ssh_known_hosts, mit den Public-Keys der SSH-Server als Wert.

Du kannst die SSH bekannte Hostdaten im ConfigMap argocd-ssh-known-hosts-cm verwalten. Dieser ConfigMap enthält eine einzige Eintragung, ssh_known_hosts, mit den öffentlichen Schlüsseln der SSH-Server als Wert. Der Wert kann aus einem beliebigen vorhandenen ssh_known_hosts-Datei gefüllt werden, oder aus der Ausgabe der ssh-keyscan-Utility (die Teil des OpenSSH-Client-Pakets ist). Die Grundformatierung lautet <server_name> <keytype> <base64-codierter_Schlüssel>, ein Eintrag pro Zeile. Hier ist ein Beispiel für die Ausführung von ssh-keyscan:

$ für host in bitbucket.org github.com gitlab.com ssh.dev.azure.com vs-ssh.visualstudio.com ; do ssh-keyscan $host 2> /dev/null ; done

Für Ihr Repository kann der Proxy in dem Feld proxy der Repository-Geheimnis-Konfiguration angegeben werden, zusammen mit einer entsprechenden noProxy-Konfiguration. Argo CD verwendet diese Proxy/noProxy-Konfiguration, um auf das Repository zugreifen und verwandte helm/kustomize-Operationen durchzuführen. Argo CD sucht nach den standardmäßigen Proxy-Umgebungsvariablen im Repository-Server, wenn die benutzerdefinierte Proxy-Konfiguration fehlt. Ein Beispiel für ein Repository mit Proxy und noProxy:
yaml
apiVersion: v1
kind: Secret
metadata:
name: private-repo
namespace: argocd
labels:
argocd.argoproj.io/secret-type: repository
stringData:
type: git
url: https://github.com/argoproj/private-repo
proxy: https://proxy-server-url:8888
noProxy: ".internal.example.com,company.org,10.123.0.0/16"
password: my-password
username: my-username 

Eine Bemerkung zum noProxy: Argo CD verwendet exec, um mit verschiedenen Werkzeugen wie helm und kustomize zu interagieren. Nicht alle dieser Werkzeuge unterstützen die gleiche noProxy-Syntax wie das httpproxy-go-Paket. Falls Sie mit noProxy Probleme haben, die nicht beachtet werden, könnten Sie versuchen, den vollständigen Domainnamen statt einer Wildcard-Muster oder IP-Adressbereich zu verwenden, um eine Syntax zu finden, die von allen Werkzeugen unterstützt wird.
 Kein Proxy wird respektiert, versuchen Sie es bitte mit der Verwendung der vollständigen Domäne anstelle eines Wildcard-Musters oder eines IP-Bereichs auszuprobieren, um eine allgemeine Syntax zu finden, die von allen Werkzeugen unterstützt wird. Überspringen von Cluster-Reconciliation¶
Sie können verhindern, dass der Application-Controller alle Apps, die einem Cluster zugeordnet sind, synchronisiert, indem Sie dem Cluster-Geheimnis die Anmerkung argocd.argoproj.io/skip-reconcile: "true" hinzufügen. Dies nutzt die gleiche Anmerkung wie Skip Application Reconcile, aber auf Clusterebene angewendet. Der Cluster bleibt in API-Antworten (argocd cluster list) sichtbar, aber der Controller behandelt ihn als unverwaltet.
yaml
apiVersion: v1
kind: Secret
metadata:
name: mycluster-secret
labels:
argocd.argoproj.io/secret-type: cluster
argocd.argoproj.io/skip-reconcile: "true" 

 Im Kontext des Clusters. Der Cluster bleibt in den API-Antworten (argocd cluster list) sichtbar, aber der Controller behandelt ihn als unverwaltet.
apiVersion: v1
kind: Secret
metadata:
  name: mycluster-secret
  labels:
    argocd.argoproj.io/secret-type: cluster
  annotations:
    argocd.argoproj.io/skip-reconcile: "true"
type: Opaque
stringData:
  name: mycluster.example.com
  server: https://mycluster.example.com
  config: |
    {
     "bearerToken": "&lt;authentication token&gt;",
     "tlsClientConfig": {
       "insecure": false,
       "caData": "&lt;base64 encoded certificate&gt;"
     }
    }
Um einen bestehenden Cluster zu überspringen:

kubectl -n argocd annotate secret mycluster-secret argocd.argoproj.io/skip-reconcile=true 
Um die Vergleichung wieder aufzunehmen:

kubectl -n argocd annotate secret mycluster-secret argocd.argoproj.io/skip-reconcile-

Ressourcen-Ausschluss/Einschluss¶
Ressourcen können aus der Entdeckung und Synchronisation ausgeschlossen werden, sodass Argo CD von ihnen unbewusst ist. Beispiel: die apiGroup/kind-Ereignisse events.k8s.io/*, Metriken.k8s.io/* und Koordination.k8s.io/Lease werden immer ausgeschlossen. Anwendungsfälle: Sie haben zeitliche Probleme und möchten problematische Ressourcen ausblenden. Es gibt viele Ressourcen, die das Leistungsvermögen von Argo CD beeinflussen. Beschränken Sie den Zugriff von Argo CD auf bestimmte Ressourcen-Arten, z.B. Geheimnisse. Siehe security.md#cluster-rbac. Um dies zu konfigurieren, bearbeiten Sie die argocd-cm Konfigurationsmappe: kubectl edit configmap argocd-cm -n argocd Fügen Sie resource.exclusions hinzu, z.B.: apiVersion: v1 data: resource.exclusions: | - apiGroups: - "*" kinds: - "*" clusters: - https://192.168.0.20 kind: ConfigMap
Der resource.exclusions-Knoten ist eine Liste von Objekten. Jedes Objekt kann:
    

  • apiGroups: Eine Liste von Globs, um die API-Gruppe zu matchen.
    • 

    

  • kinds: Eine Liste von Arten, um zu matchen. Kann "*" sein, um alles zu matchen.
    • 

    

  • clusters: Eine Liste von Globs, um die Cluster-URL zu matchen. Wenn alle drei passen, wird die Ressource ignoriert.
    • 

Zusätzlich können Sie die Liste der eingeschlossenen Ressourcen mithilfe der resource.inclusions-Einstellung konfigurieren. Standardmäßig sind alle Ressourcengruppen/Arten eingeschlossen.
 Drei Treffer, dann wird der Ressource die Ignorierung zugestanden. Neben den Ausnahmen können Sie die Liste der enthaltenen Ressourcen mithilfe der Einstellung resource.inclusions konfigurieren. Voreingestellt sind alle Ressourcengruppen/Arten enthalten. Die Einstellung resource.inclusions ermöglicht es, die Liste der enthaltenen Gruppen/Arten anzupassen:
yaml
apiVersion: v1
data:
resource.inclusions: |
- apiGroups: - "*"
kinds:
- Deployment
clusters:
- https://192.168.0.20
kind: ConfigMap 

Die Einstellungen resource.inclusions und resource.exclusions können gemeinsam verwendet werden. Die endgültige Liste der Ressourcen umfasst Gruppen/Arten, die in resource.inclusions aufgeführt sind, abzüglich der Gruppen/Arten, die in der resource.exclusions-Einstellung angegeben sind.
Hinweise: Um Verarbeitungsfehler zu vermeiden, zitieren Sie in Ihrem YAML Globs. Ungültige Globs führen zu der Ignorierung des gesamten Regels. Wenn Sie eine Regel hinzufügen, die auf vorhandene Ressourcen zutrifft, werden diese im Benutzeroberflächen-Interface als OutOfSync angezeigt. Einige ausgeschlossene Objekte können bereits im Controller-Cache vorhanden sein. Eine Neustartung des Controllers ist erforderlich, um sie aus dem Anwendungs-Ansicht zu entfernen.

Autoachtung RBAC für den Controller¶
Der Argo CD-Controller kann mithilfe des nur für den Controller RBAC erstellt werden, ohne dass man die Ressourcen-Ausnahmen manuell konfigurieren muss.
 Geheimnisse. resource.sensitive.mask.annotations: openshift.io/token-secret.value, api-key Automatische Achtung für RBAC für Controller¶
Argo CD-Controller kann durch nur die Controller-RBAC für die Erkennung/Synchronisierung bestimmter Ressourcen eingeschränkt werden, ohne dass man die Ressourcen-Ausschlüsse manuell konfigurieren muss. Diese Funktion kann aktiviert werden, indem das resource.respectRBAC-Schlüssel in argocd cm gesetzt wird. Sobald es gesetzt ist, wird der Controller automatisch auf Ressourcen aufhören, die er nicht listen/zugreifen kann. Mögliche Werte für resource.respectRBAC sind:
    

  • strikt: Diese Einstellung prüft, ob der von Controller ausgeführte Listenaufruf verboten/unautorisiert ist und wenn ja, wird eine Überprüfung der Berechtigung durch einen SelfSubjectAccessReview-Aufruf für die Ressource durchgeführt.
    • 

    

  • normal: Dies wird nur prüfen, ob der Listenaufrufantwort verboten/unautorisiert ist und den SelfSubjectAccessReview-Aufruf überspringen, um jede zusätzliche api-Server-Aufrufe zu minimieren.
    • 

    

  • leer/ungesetzt (Standard): Dies deaktiviert die Funktion und der Controller wird weiterhin auf alle Ressourcen überwachen. Nutzer, die mit einem Anstieg der kube api-Server-Aufrufe zufrieden sind, können sich für die strikte Option entscheiden, während Nutzer, die sich mit höheren api-Aufrufen und eine Reduktion der Genauigkeit zufriedengeben, die normale Option wählen können.
    • 

 api-Server-Aufrufe können sich für die strikte Option wählen, während Nutzer, die sich um eine höhere Anzahl an API-Aufrufen und bereit sind, auf Genauigkeit zu verzichten, sich für die normale Option entscheiden können. Hinweis: Wenn für den Einsatz des strikten Modus die Berechtigung zum Erstellen eines SelfSubjectAccessReview-Ressourcen erforderlich ist, muss der Controller RBAC-Berechtigungen besitzen. Der SelfSubjectAccessReview-Anforderung wird nur für die Liste-Verb verbaut, es wird angenommen, dass wenn Liste für ein Ressource erlaubt ist, dann sind auch alle anderen Berechtigungen für den Controller verfügbar. Beispiel: argocd cm mit resource.respectRBAC auf "strict" festgelegt:

apiVersion: v1
kind: ConfigMap
metadata:
name: argocd-cm
data:
resource.respectRBAC: "strict"
