Sicherheit¶ Argo CD hat sich an internen Sicherheitsprüfungen und Penetrationstests unterzogen, um die Anforderungen an die PCI-Komplianz zu erfüllen. Hier sind einige Sicherheitsaspekte und Umsetzungselemente von Argo CD. Authentifizierung¶ Die Authentifizierung an der Argo CD API-Server erfolgt ausschließlich über JSON Web Tokens (JWTs). Benutzername/Passwort-Trägertokens werden für die Authentifizierung nicht verwendet. Der JWT wird/wird in einer der folgenden Weisen verwaltet: Für den lokalen Administrator wird ein Benutzername/Passwort gegen einen JWT ausgetauscht, indem die Endpunktadresse /api/v1/session verwendet wird. Dieser Token wird von der Argo CD API-Server selbst signiert und ausgestellt und läuft nach 24 Stunden ab (vorher war dieser Token unbegrenzt gültig, siehe CVE-2021-26921). Wenn der Administrator-Passwort aktualisiert wird, werden alle bestehenden Administrator-JWT-Tokens sofort deaktiviert. Das Passwort wird als bcrypt-Hash im argocd-secret Secret gespeichert. Für Single Sign-On-Benutzer erfolgt die Authentifizierung über einen OAuth2-Anmeldestrom zum konfigurierten OIDC-Identitätsanbieter (entweder über den integrierten Dex-Anbieter oder direkt an einen selbst verwalteten OIDC-Anbieter). Dieser JWT wird von dem IDP signiert und ausgestellt, und Ablauf und Deaktivierung wird vom Anbieter verarbeitet. Dex-Tokens laufen nach 24 Stunden ab. Automatisierungstokens werden für ein Projekt über die Endpunktadresse /api/v1/projects/{project}/roles/{role}/token erstellt und von Argo CD signiert. Diese Tokens sind auf Scope und Rechte beschränkt und können nur verwendet werden, um Ressourcen von der Anwendung im Projekt zu verwalten, dem sie angehören.

Projekte JWTs haben eine konfigurierbare Ablaufzeit und können sofort durch Löschen der JWT-Referenz-ID aus dem Projektrolle revokiert werden. Autorisierung¶ Die Autorisierung erfolgt durch Iteration der Liste der Gruppenmitgliedschaften in den JWT-Gruppenansprüchen des Benutzers und das Vergleichen jeder Gruppe gegen die Rollen/Regeln in der RBAC-Politik. Jede passende Regel ermöglicht den Zugriff auf die API-Anfrage. TLS¶ Alle Netzwerkkommunikation erfolgt über TLS, einschließlich des service-to-service-Kommunikations zwischen den drei Komponenten (argocd-server, argocd-repo-server, argocd-application-controller). Der Argo CD API-Server kann die Verwendung von TLS 1.2 durch das Flag festlegen: --tlsminversion 1.2. Die Kommunikation mit Redis erfolgt standardmäßig über ein unverschlüsseltes HTTP. TLS kann mit Befehlszeilenargumenten eingerichtet werden. Git & Helm-Repositorys¶ Git und Helm-Repositorys werden von einem separaten Dienst, dem repo-server, verwaltet. Der repo-server hat keine Kubernetes-Rechte und speichert keine Zugangsdaten zu irgendeinen Diensten (einschließlich Git). Der repo-server ist für das Klonen von Repositorys zuständig, die von den Argo CD-Operatorn zugelassen und vertrauenswürdig sind, und für die Erstellung von Kubernetes-Manifests an einer gegebenen Stelle im Repository.

(inklusive von Git). Der Repo-Server ist verantwortlich für das Klonen von Repositorys, die von den Argo CD-Betreibern zugelassen und vertrauenswürdig sind, und für die Erstellung von Kubernetes-Manifests an einer bestimmten Stelle im Repository an einer gegebenen Stelle im Repository. Zur Leistungs- und Bandbreiteneffizienz wird der Repo-Server lokale Klone dieser Repositorys aufbewahrt, damit weitere Commit-Änderungen im Repository effizient heruntergeladen werden. Es gibt Sicherheitsaspekte bei der Konfiguration von git-Repositorys, die Argo CD bereitstellen darf. In Kürze bedeutet es, dass unautorisierte Schreibzugriff auf ein git-Repository, das von Argo CD vertrauenswürdig ist, ernsthafte Sicherheitsimplicationen haben, die unten ausführlich beschrieben werden. Unautorisierte Bereitstellungen¶ Da Argo CD die Kubernetes-Ressourcen definiert, die in git definiert sind, wäre ein Angreifer mit Zugriff auf ein vertrauenswürdiges git-Repo in der Lage, die Kubernetes-Ressourcen zu beeinflussen, die bereitgestellt werden. Beispielsweise könnte ein Angreifer die Bereitstellungsmanifest aktualisieren, um schädliche Container-Images in die Umgebung zu laden, oder Ressourcen in git löschen, was dazu führen würde, dass sie im lebenden Umfeld gelöscht werden. Tool-Befehl-Ausführung¶ Zusätzlich zu Roh-YAML unterstützt Argo CD zwei beliebte Kubernetes-Konfigurations-Management-Tools nativ, helm und kustomize. Wenn Manifeste gerendert werden, führt Argo CD diese Konfigurations-Management-Tools (z.B. helm template, kustomize build) aus, um die Manifeste zu generieren. Es ist möglich, dass ein Angreifer mit Schreibzugriff auf ein vertrauenswürdiges git-Repository maliziöse helm-Charts oder kustomizations konstruiert, die versuchen, Dateien aus dem Baum zu lesen.

Erzeugen Sie die Manifests. Es ist möglich, dass ein Angreifer mit Schreibzugriff auf einen vertrauenswürdigen Git-Repository maliciously gefertigte Helm-Charts oder Kustomizations erstellt, die versuchen, Dateien aus dem Verzeichnis zu lesen. Dies betrifft auch benachbarte Git-Repositories, sowie Dateien auf dem Repository-Server selbst. Ob dies ein Risiko für Ihre Organisation ist, hängt davon ab, ob die Inhalte in den Git-Repositories sensibel sind. Standardmäßig enthält der Repository-Server selbst keine sensiblen Informationen, aber kann möglicherweise mit Config Management Plugins konfiguriert sein, die solche enthalten (z.B. Entschlüsselungsschlüssel). Wenn solche Plugins verwendet werden, muss vielseitige Vorsicht walten, um sicherzustellen, dass die Inhalte des Repositories immer vertrauenswürdig sind. Optional können die integrierten Konfigurationsverwaltungswerkzeuge individuell deaktiviert werden. Wenn Sie wissen, dass Ihre Benutzer kein bestimmtes Konfigurationsverwaltungswerkzeug benötigen, ist es ratsam, dieses Werkzeug auszuschalten. Weitere Informationen finden Sie unter Tool Detection. Remote-Basen und Helm-Chart-Abhängigkeiten¶ Die Zugriffsliste des Argo CD-Repositories beschränkt sich nur auf den initial zu klonenden Repository. Allerdings enthalten beide kustomize und helm Funktionen, um zusätzliche Repositories (z.B. kustomize Remote-Basen, helm Chart-Abhängigkeiten) zu referenzieren und zu folgen, die möglicherweise nicht in der Repository-Zugriffsliste sind. Argo CD-Operator müssen verstehen, dass Benutzer mit Schreibzugriff auf vertrauenswürdige Git-Repositories andere remote verfügbare Git-Repositories mit Kubernetes-Ressourcen referenzieren können, die in den konfigurierten Git-Repositories schwer zu finden oder auditable sind.

Verstehen Sie, dass Benutzer mit Schreibzugriff auf vertrauenswürdige Git-Repositorys andere entfernte Git-Repositorys referenzieren können, die Kubernetes-Ressourcen enthalten, die in den konfigurierten Git-Repositorys schwer suchen oder auditable sind. Sensible Information¶ Geheimdaten¶ Argo CD gibt nie sensible Daten aus seiner API zurück, und streicht alle sensible Daten in API-Payloads und Protokollen. Das umfasst:

  • Kluster-Kredentiale
  • Git-Kredentiale
  • OAuth2-Client-Geheimnisse
  • Kubernetes-Secret-Werte
  • Externe Cluster-Kredentiale

Um externe Cluster zu verwalten, speichert Argo CD die Kredentiale des externen Clusters als Kubernetes-Geheimnis im argocd-Namespace. Dieses Geheimnis enthält den K8s-API-Bearer-Token, der mit dem argocd-manager-ServiceAccount erstellt wurde, während argocd-Cluster hinzugefügt wurde, sowie Verbindungsoptionen zu diesem API-Server (TLS-Konfiguration/Zertifikate, AWS-Role-ARN usw...). Die Informationen werden verwendet, um eine REST-Konfiguration und kubeconfig für den Cluster zu erstellen, der von Argo CD-Diensten verwendet wird. Um den Bearer-Token von Argo CD zu rotieren, kann er gelöscht werden (z.B. mithilfe von kubectl), was Kubernetes dazu veranlasst, ein neues Geheimnis mit einem neuen Bearer-Token zu generieren. Das neue Token kann in Argo CD eingegeben werden, indem argocd cluster add erneut ausgeführt wird. Führen Sie die folgenden Befehle gegen den verwalteten Cluster aus:

mithilfe eines kubeconfigs für den extern verwalteten Cluster


kubectl delete secret argocd-manager-token-XXXXXX -n kube-system
argocd cluster add CONTEXTNAME

Hinweis: Ab Kubernetes 1.24 wird automatisch kein Token mehr für Service Accounts erstellt.

# Ausführen mit einem kubeconfig für die extern verwaltete Cluster

kubectl löschen secret argocd-manager-token-XXXXXX -n kube-system
argocd cluster hinzufügen CONTEXTNAME

Hinweis: Ab Kubernetes 1.24 wird automatisch kein Token für Service Accounts mehr erstellt. Ab Argo CD 2.4 erstellt argocd cluster add ein ServiceAccount und ein nicht ablaufiges Service Account token Secret, wenn Sie 1.24 Cluster hinzufügen. In Zukunft wird Argo CD Unterstützung für den Kubernetes TokenRequest API hinzugefügt, um langlebige Tokens zu vermeiden. Um Argo CDs Zugriff auf eine verwaltete Cluster zu entziehen, löschen Sie die RBAC-Artefakte gegen die verwaltete Cluster, und entfernen Sie die Cluster-Eintragung aus Argo CD:

Ausführen mit einem kubeconfig für die extern verwaltete Cluster

kubectl löschen sa argocd-manager -n kube-system
kubectl löschen clusterrole argocd-manager-role
kubectl löschen clusterrolebinding argocd-manager-role-binding
argocd cluster löschen https://your-kubernetes-cluster-addr

Hinweis: Für AWS EKS Cluster wird der get-token Befehl verwendet, um sich bei der externen Cluster anzumelden, die stattdessen IAM Rollen anstelle von lokal gespeicherten Tokens verwenden, sodass Token-Rotation nicht erforderlich ist, und die Entfernung durch IAM behandelt wird.

Cluster RBAC¶

Standardmäßig verwendet Argo CD eine clusterweite Rolle auf Ebene admin, um:

  • auf den Clusterzustand zugreifen
  • Ressourcen auf dem Cluster bereitzustellen

Obwohl Argo CD clusterweite Leserechte an Ressourcen in der verwalteten Cluster benötigt, um ordnungsgemäß zu funktionieren, benötigt es nicht notwendigerweise vollständige Schreibrechte für den Cluster.

Zur Cluster-Gruppe

Obwohl Argo CD clusterweite Leserechte an Ressourcen des verwalteten Clusters benötigt, um ordnungsgemäß zu funktionieren, benötigt es nicht notwendigerweise vollständige Schreibrechte für den Cluster. Die verwendet ClusterRole von argocd-server und argocd-application-controller kann so modifiziert werden, dass Schreibrechte nur auf die Namespaces und Ressourcen beschränkt werden, die Sie Argo CD zulassen möchten, um zu verwalten. Um die Rechte extern verwalteter Cluster zu feinjustieren, bearbeitet Sie die ClusterRole der argocd-manager-rolle # mit einem kubeconfig für den extern verwalteten Cluster kubectl edit clusterrole argocd-manager-rolle

Um die Rechte, die Argo CD gegenüber seinem eigenen Cluster hat (z.B. https://kubernetes.default.svc), zu feinjustieren, bearbeitet Sie die folgenden Clusterrollen, in denen Argo CD läuft: # mit einem kubeconfig für den Cluster, in dem Argo CD läuft kubectl edit clusterrole argocd-server kubectl edit clusterrole argocd-application-controller

Tippe: Wenn Sie Argo CD Zugriff auf eine bestimmte Ressource verweigern möchten, fügen Sie sie als ausgeschlossene Ressource hinzu.

Auditing¶

Als GitOps-Bereitstellungswerkzeug bietet die Git-Commit-Geschichte eine natürliche Audit-Protokollierung der Änderungen an Anwendungskonfigurationen, der Zeitpunkte der Änderungen und derjenigen, die sie vornahmen. Allerdings gilt dieses Audit-Protokoll nur für was in Git geschehen ist und korreliert nicht notwendigerweise ein-zu-eins mit Ereignissen, die sich in einem Cluster abspielen.

Sie wurden erstellt, und von wem. Allerdings bezieht sich diese Audit-Protokollierung nur auf Ereignisse, die in Git stattgefunden haben, und korreliert nicht notwendigerweise ein-zu-eins mit Ereignissen, die in einem Cluster stattfinden. Beispielhaft könnte User A mehrere Commits an Anwendungsmanifesten vorgenommen haben, während User B die Änderungen erst später dem Cluster synchronisiert hat. Für Logs, die mit einer Anwendung in Verbindung stehen, wird Argo CD die folgenden standardmäßigen Felder protokollieren:

  • application: die Anwendungsbezeichnung, ohne den Namespace
  • app-namespace: der Namespace der Anwendung
  • project: das Projekt der Anwendung

ApplicationSets¶
Die Funktion ApplicationSets von Argo CD hat eigene Sicherheitsaspekte. Bitte beachten Sie diese Probleme vor der Verwendung von ApplicationSets.

Begrenzung des Speicherverbrauchs von App-Verzeichnis-Speicher¶
2.2.10, 2.1.16, >2.3.5
Verzeichnis-artige Anwendungen (d.h. solche, deren Quelle raw JSON oder YAML-Dateien sind) können je nach Größe und Struktur der YAML-Dateien erhebliche Speicherplatzverbrauch im Repo-Server verursachen. Um den Speicherplatzverbrauch im Repo-Server zu begrenzen (potenziell zu einer Crash- und Dienstleistungsverweigerung führen), sollte die Konfigurationsoption reposerver.max.combined.directory.manifests.size in argocd-cmd-params-cm konfiguriert werden. Diese Option begrenzt die Gesamtmenge aller JSON oder YAML-Dateien in einer einzelnen Anwendung. Hinweis: Die in-Memory-Darstellung einer Manifestdatei kann bis zu 300x der Größe der Manifestdatei auf dem Datenträger sein. Außerdem ist die Grenze pro Anwendung. Wenn Manifestdateien für mehrere Anwendungen gleichzeitig erstellt werden, wird der Speicherverbrauch höher sein. Beispiel: Ver supposiere Ihr Repo-Server eine Speichergröße von 10G hat, und Sie haben zehn Anwendungen, die raw JSON oder YAML-Dateien verwenden.

multiple Anwendungen gleichzeitig, wird die Speicherausnutzung höher sein. Beispiel: Veranschauliche, dass Ihr Repo-Server einen Speicherlimit von 10G hat, und Sie zehn Anwendungen haben, die unbearbeitete JSON- oder YAML-Dateien verwenden. Um die maximale sichere kombinierte Dateigröße pro Anwendung zu berechnen, teilen Sie 10G durch 300 * 10 Anwendungen (300 ist der schlimmste Fall für die Speichererweiterung der Manifeste). 10G / 300 * 10 = 3M So eine vernünftige Konfiguration für diesen Aufbau wäre ein 3M-Limit pro App.

apiVersion: v1
kind: ConfigMap
metadata:
name: argocd-cmd-params-cm
data:
reposerver.max.combined.directory.manifests.size: '3M'

Der 300x-Faktor setzt voraus, dass es sich um eine absichtlich gestaltete Manifest-Datei handelt. Wenn Sie nur unabsichtliches überschüssiges Speicherverbrauch schützen möchten, ist es wahrscheinlich sicher, einen kleineren Faktor zu verwenden. Denken Sie daran, dass ein böswilliger Nutzer zusätzliche Anwendungen erstellen kann, um die Gesamt-Speicherausnutzung zu erhöhen. Erteilt App-Erstellungsrechte vorsichtig.
