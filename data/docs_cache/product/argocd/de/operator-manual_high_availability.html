Hoch Verfügbarkeit ¶
Argo CD ist hauptsächlich stateless. Alle Daten werden als Kubernetes-Objekte gespeichert, die wiederum in Kubernetes' etcd gespeichert werden. Redis wird nur als verwerfliche Cache-Speicherung verwendet und kann ohne Dienstausfall sicher neu aufgebaut werden. Eine Menge von HA-Manifests werden für Nutzer bereitgestellt, die Argo CD in einem hochverfügbareren Modus betreiben möchten. Dies führt zu mehr Containern und führt Redis in HA-Modus. Hinweis: Die HA-Installation erfordert mindestens drei verschiedene Knoten aufgrund der Pod-Anti-Affinität-Regel in den Spezifikationen. Zusätzlich werden IPv6 nur-Cluster nicht unterstützt. Der Argo CD Repo-Server verwaltet ein lokales Repository-Clone und verwendet es für die Erstellung der Anwendungsmanifeste. Wenn die Manifestgenerierung ein Dateiänderung im lokalen Repository-Clone erfordert, ist nur eine gleichzeitige Manifestgenerierung pro Serverinstanz erlaubt. Diese Einschränkung könnte Argo CD signifikant verlangsamen, wenn Sie eine Monorepo mit mehr als 50 Anwendungen verwenden.

Leistungswirkung: Wenn ein Git-Referenzwert (z.B. main in einen Commit-SHA umgewandelt wird), muss Argo CD:

  1. Alle Git-Referenzen (Branchs und Tags) laden
  1. Durch alle Referenzen iterieren, um einen Treffer zu finden
  1. Symbolische Referenzen, wenn erforderlich, auflösen

Für Repositories mit vielen Referenzen ist dieser Prozess CPU- und Speichereintensiv. Durch den Einsatz von voll qualifizierten Referenzen kann Argo CD den Auflösungsprozess optimieren und die Caching effektiver nutzen. Empfohlene Vorgehensweise:

Wenn die Manifestgenerierung keine Nebenwirkungen hat, werden Anfragen parallel verarbeitet, ohne eine Leistungsschwäche zu verursachen. Mehrere Helm basierte Anwendungen, die auf demselben Verzeichnis in einem Git-Repository zeigen: historische Gründe haben dazu geführt, dass Argo CD Helm-Manifests in Folge erstellte. Mehrere Kustomize-Anwendungen in demselben Repository mit Parameter-Überschreibungen: zurzeit gibt es keinen Workaround für diese Einschränkung.

Pfade der Manifeste¶ Argo CD aggressiv cachet erzeugte Manifeste und verwendet den SHA der Git-Repository-Commit als Cache-Schlüssel. Ein neuer Commit im Git-Repository löscht den Cache für alle in dem Repository konfigurierten Anwendungen. Dies kann sich negativ auf Repositories mit mehreren Anwendungen auswirken. Sie können die argocd.argoproj.io/manifest-generate-Paths Anwendungs-CRD-Annotation nutzen, um dieses Problem zu lösen und die Leistung zu verbessern. Hinweis: Die argocd.argoproj.io/manifest-generate-Paths Annotation ist für die Verwendung mit Webhooks verfügbar. Seit Argo CD v2.11 kann diese Annotation auch ohne die Konfiguration von Webhooks verwendet werden. Webhooks sind keine Voraussetzung für diese Funktion. Sie können sich auf die Annotation alleine verlassen, um die Manifest-Erstellung für alle Anwendungen zu optimieren. Die argocd.argoproj.io/manifest-generate-Paths Annotation enthält eine Semikolon-getrennte Liste von Pfaden innerhalb des Git-Repositorys, die während der Manifest-Erstellung verwendet werden. Sie wird die in der Annotation aufgeführten Pfade verwenden, um den letzten abgelegten Revision mit dem neuesten Commit zu vergleichen. Wenn keine geänderten Dateien den Pfaden entsprechen, die in argocd.argoproj.io/manifest-generate-Paths angegeben sind, dann wird keine Anwendungsausschöpfung ausgelöst und der bestehende Cache wird für den neuen Commit als gültig betrachtet.

Anwendung Sync Timeout & Jitter¶
Argo CD hat einen Timeout für Anwendungssyncs. Es wird eine Aktualisierung für jede Anwendung periodisch ausgelöst, wenn der Timeout abläuft. Bei einer großen Anzahl von Anwendungen wird dies zu einem Spike im Aktualisierungswarteschlange führen und kann zu einem Spike beim repo-server-Komponente. Um dies zu vermeiden, können Sie eine Jitterung zum Sync Timeout setzen, die die Aktualisierungen verteilt und Zeit gibt, damit der repo-server aufholen kann. Die Jitterung ist die maximale Dauer, die zur Sync Timeout hinzugefügt werden kann, also wenn der Sync Timeout 5 Minuten beträgt und die Jitterung 1 Minute, dann beträgt der tatsächliche Timeout zwischen 5 und 6 Minuten. Um die Jitterung zu konfigurieren, können Sie die folgenden Umgebungsvariablen festlegen:

ARGOCD_RECONCILIATION_JITTER - Die Jitterung, die zur Sync Timeout anzuwenden ist.

Zeitliche Verzögerung wird zwischen 5 und 6 Minuten liegen. Um die Jitter-Konfiguration zu ändern können Sie folgende Umgebungsvariablen festlegen: ARGOCD_RECONCILIATION_JITTER - Die Jitter-Verzögerung, die auf die Sync-Verzögerung angewendet werden soll. Deaktiviert, wenn der Wert 0 ist. Der Standardwert beträgt 60. Rate Limiting Application Reconciliations¶ Um hohes Verbrauch von Steuerungsknoten oder Sync-Schleifen zu verhindern, die durch fehlerhafte Apps oder Umgebungsfaktoren verursacht werden, können wir Rate-Limits für die verwendeten Workqueues des Anwendungs-Controllers konfigurieren. Es können zwei Arten von Rate-Limits konfiguriert werden: Global rate limits Per-Item rate limits Das finale Rate-Limiter verwendet eine Kombination beider und berechnet den finalen Verzögerungswert als max(globalBackoff, perItemBackoff). Global rate limits¶ Dies ist standardmäßig deaktiviert, es handelt sich um einen einfachen Bucket-basierten Rate-Limiter, der die Anzahl der zu queuenden Elemente pro Sekunde begrenzt. Dies ist nützlich, um eine große Anzahl von Apps gleichzeitig zu queuen zu verhindern. Um den Bucket-Limiter zu konfigurieren können Sie folgende Umgebungsvariablen festlegen: WORKQUEUE_BUCKET_SIZE - Die Anzahl der Elemente, die in einem einzelnen Burst queued werden können. Der Standardwert beträgt 500. WORKQUEUE_BUCKET_QPS - Die Anzahl der Elemente, die pro Sekunde queued werden können. Der Standardwert beträgt MaxFloat64, was den Limiter deaktiviert. Per-Item rate limits¶ Dies gibt standardmäßig einen festen Basisverzögerungswert/Rückschrittswert zurück, aber kann konfiguriert werden, um exponentielle Werte zurückzugeben. Der Per-Item Rate-Limiter begrenzt die Anzahl der Mal, die ein bestimmtes Element queued werden kann.

Standard gibt eine festgelegte Basisverzögerung/Wiedereinstellung, kann jedoch konfiguriert werden, um exponentielle Werte zurückzugeben. Einzelstücks-Rate-Limiter begrenzt die Anzahl der Mal, dass ein bestimmtes Stück in der Warteschlange platziert werden kann. Dies basiert auf exponentieller Verzögerung, wobei die Verzögerungszeit für ein Stück exponentiell zunimmt, wenn es mehrfach in einer kurzen Zeit in der Warteschlange platziert wird, aber die Verzögerung automatisch auf null zurückgesetzt wird, wenn ein konfigurierter Abkühlungszeitraum seit dem letzten Mal, dass das Stück in der Warteschlange platziert wurde, verstrichen ist. Um den Einzelstücks-Limiter zu konfigurieren, können die folgenden Umgebungsvariablen festgelegt werden:

WORKQUEUE_FAILURE_COOLDOWN_NS : Der Abkühlungszeitraum in Nanosekunden, nachdem der Zeitraum für ein Stück abgelaufen ist, wird die Verzögerung automatisch auf null zurückgesetzt. Exponentielle Verzögerung wird deaktiviert, wenn auf 0 gesetzt (Standardwert), z.B. Werte: 10 * 10^9 (=10s)
WORKQUEUE_BASE_DELAY_NS : Die Basisverzögerung in Nanosekunden, dies ist die initiale Verzögerung, die in der exponentiellen Verzögerungsformel verwendet wird. Standards: 1000 (=1μs)
WORKQUEUE_MAX_DELAY_NS : Die maximale Verzögerung in Nanosekunden, dies ist die maximale Verzögerungsgrenze. Standards: 3 * 10^9 (=3s)
WORKQUEUE_BACKOFF_FACTOR : Der Verzögerungsfaktor, dies ist der Faktor, durch den die Verzögerung für jede Wiederholung erhöht wird. Standards: 1.5

Die Formel, die zur Berechnung der Verzögerungszeit für ein Stück verwendet wird, wobei numRequeue die Anzahl der Mal ist, dass das Stück in der Warteschlange platziert wurde und lastRequeueTime die Zeit ist, zu der das Stück letztmals in die Warteschlange platziert wurde:

Wenn WORKQUEUE_FAILURE_COOLDOWN_NS != 0 : backoff = time.Since(lastRequeueTime) >= WORKQUEUE_FAILURE_COOLDOWN_NS ? backoff = WORKQUEUE_FAILURE_COOLDOWN_NS : backoff = time.Since(lastRequeueTime)

Die Verzögerungszeit wird dann berechnet, indem die Formel verwendet wird, die in der Variablen WORKQUEUE_BASE_DELAY_NS, WORKQUEUE_MAX_DELAY_NS und WORKQUEUE_BACKOFF_FACTOR definiert ist. Die Verzögerungszeit wird dann für das nächste Mal, dass das Stück in die Warteschlange platziert wird, verwendet.

HTTP-Anforderungswiederholungsstrategie¶
In Fällen von Netzinstabilität oder transienten Serverfehlern sichert die Wiederholungsstrategie die Robustheit der HTTP-Kommunikation, indem sie fehlgeschlagene Anforderungen automatisch erneut versendet. Sie nutzt eine Kombination aus maximalen Wiederholungen und Abstimmungsintervallen, um den Server oder das Netzwerk nicht zu überlasten oder zu schleudern. Konfigurieren von Wiederholungen¶
Das Wiederholungsverhalten kann mit den folgenden Umgebungsvariablen fein abgestimmt werden:

ARGOCD_K8SCLIENT_RETRY_MAX - Die maximale Anzahl von Wiederholungen für jede Anforderung. Die Anforderung wird nach Erreichen dieser Anzahl fallen gelassen. Standardeinstellung ist 0 (keine Wiederholungen).

ARGOCD_K8SCLIENT_RETRY_BASE_BACKOFF - Der initiale Abstimmungsabstand für den ersten Versuch einer Wiederholung in ms. Subsequent retries will double this backoff time up to a maximum threshold. Standardeinstellung ist 100ms.

Wiederholungsstrategie¶
Die eingesetzte Wiederholungsstrategie ist eine einfache exponentielle Wiederholung ohne Jitter. Der Abstimmungsabstand steigt exponentiell mit jedem Versuch einer Wiederholung an, bis ein maximales Abstimmungsintervall erreicht wird.

In den folgenden Zeilen wird die Code-Logik für die Wiederholungsstrategie dargestellt:

Wenn WORKQUEUE_FAILURE_COOLDOWN_NS != 0 :
backoff = time.Since(lastRequeueTime) >= WORKQUEUE_FAILURE_COOLDOWN_NS ? WORKQUEUE_BASE_DELAY_NS : min( WORKQUEUE_MAX_DELAY_NS, WORKQUEUE_BASE_DELAY_NS * WORKQUEUE_BACKOFF_FACTOR ^ (numRequeue) )

Wenn WORKQUEUE_FAILURE_COOLDOWN_NS = 0 :
backoff = WORKQUEUE_BASE_DELAY_NS

100ms. Backoff-Strategie ¶ Die eingesetzte Backoff-Strategie ist eine einfache exponenzielle Backoff-Strategie ohne Jitter. Die Backoff-Zeit steigt exponentiell mit jedem Versuch einer Wiederholung an, bis ein maximales Backoff-Zeitraum erreicht wird. Die Formel zur Berechnung der Backoff-Zeit lautet: backoff = min(retryWaitMax, baseRetryBackoff * (2 ^ retryAttempt))
Wobei retryAttempt ab 0 beginnt und für jede weitere Wiederholungsversuche um 1 erhöht wird. Maximale Wartezeit ¶ Es gibt eine Schranke für die Backoff-Zeit, um unzumutbare Wartezeiten zwischen Wiederholungen zu verhindern. Diese Schranke ist definiert durch: retryWaitMax - Die maximale Dauer, die gewartet wird, bevor wiederholt wird. Dadurch werden Wiederholungen innerhalb eines angemessenen Zeitrahmens durchgeführt. Standardeinstellung lautet 10 Sekunden. Nicht wiederholbare Bedingungen ¶ Nicht alle HTTP-Antworten sind für Wiederholungen geeignet. Die folgenden Bedingungen werden keine Wiederholung auslösen: Antworten mit einem Statuscode, der auf Fehler des Clients (4xx) hinweist, außer 429 Too Many Requests. Antworten mit dem Statuscode 501 Not Implemented. Tiefe Klonierung¶ Repositories mit großen Historien oder großen Dateien in vergangenen Revisionen können langsam geklont und aktualisiert werden. Um den Klonprozess zu beschleunigen, können Sie die Tiefe-Option des Repositorys verwenden:
apiVersion: v1
stringData:
depth: "1"
type: "git"
url: "https://github.com/argoproj/argocd-example-apps.git"
kind: Secret
metadata:
annotations:
managed-by: argocd.argoproj.io
labels:
argocd.argoproj.io/secret-type: repository
name: my-repo
namespace: argocd
type: Opaque

Hinweis: Sie können den Befehl argocd repo add <repo-url> --depth verwenden, um ein Repository mit tiefer Klonierung aktiviert zu erstellen. Wenn Sie tiefe Klonierung verwenden, wird das Repository mit einer Tiefe von 1 geklont, was bedeutet, dass nur der erforderliche Commit geklont wird, anstatt die komplette Geschichte. Dieser Ansatz ist sinnvoll, wenn das Repository eine große Geschichte hat.
