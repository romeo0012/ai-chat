Der Mechanismus oder Komponente, der die Lastenausgleichsoperation durchführt, heißt Lastenausgleichsanlage. In web-Umgebungen werden diese Komponenten als "Netzwerk Lastenausgleichsanlage" oder häufiger als "Lastenausgleichsanlage" bezeichnet, da diese Aktivität weitestgehend die bekannteste Anwendung von Lastenausgleich darstellt. Eine Lastenausgleichsanlage kann wie folgt handeln:

  • auf Schichtsebene: dies wird als Schicht Lastenausgleich bezeichnet und besteht darin, zu entscheiden, welche Netzwerkverbindung ein Paket zu senden ist;
  • auf Netzwerksebene: dies wird als Netzwerk Lastenausgleich bezeichnet und besteht darin, zu entscheiden, welche Route eine Reihe von Paketen folgen soll;
  • auf Serversebene: dies wird als Server Lastenausgleich bezeichnet und besteht darin, zu entscheiden, welcher Server eine Verbindung oder Anfrage verarbeiten soll. Zwei unterschiedliche Technologien existieren und adressieren unterschiedliche Anforderungen, allerdings mit einigem Überlappung. In jedem Fall ist es wichtig zu beachten, dass Lastenausgleich das Verkehrsfluss von seiner natürlichen Richtung ablenkt und dass dies immer ein Mindestmaß an Sorgfalt erfordert, um den erforderlichen Grad an Konsistenz zwischen allen Routenentscheidungen zu gewährleisten.   • ein HTTP-Reverse-Proxy (im HTTP-Terminologie als "Gateway" bezeichnet): Es stellt sich als Server dar, empfängt HTTP-Anfragen über Verbindungen, die auf einem lauschenden TCP-Socket akzeptiert werden, und leitet die Anfragen von diesen Verbindungen an Server weiter, indem es verschiedene Verbindungen verwendet. Es kann auf jeder Seite beliebig viele Kombinationen von HTTP/1.x oder HTTP/2 verwenden und wird auch automatisch erkennen, welches Protokoll auf jeder Seite gesprochen wird, wenn ALPN über TLS verwendet wird.

Wie HAProxy funktioniert

HAProxy ist ein event-getriebener, nicht-blockender Motor, der eine sehr schnelle E/A-Schicht mit einer prioritätsbasierten, multi-threaded Scheduler kombiniert. Da es mit einem Ziel der Datenübertragung entwickelt wurde, ist seine Architektur optimiert, um Daten so schnell wie möglich zu verschieben und mit den wenigsten möglichen Operationen zu arbeiten. Daher implementiert es ein modulares Modell, das Umgehungsmöglichkeiten an jedem Level anbietet, um sicherzustellen, dass die Daten nicht höhere Ebenen erreichen, solange nicht notwendig ist. Die meisten Verarbeitungen erfolgen im Kernel, und HAProxy versucht, dem Kernel so schnell wie möglich zu helfen, die Arbeit auszuführen, indem es einige Hinweise gibt oder bestimmte Operationen vermeidet, wenn es vermutet, dass sie später zusammengefasst werden könnten. 3.3.4 Grundlegende Funktionen: Hochverfügbarkeit

Wie jede ernsthafte Lastverteilerin, setzt HAProxy viel Wert auf die Verfügbarkeit, um die beste globale Dienstleistung zu gewährleisten:

  • Nur gültige Server werden verwendet; die anderen werden automatisch aus den Lastverteilungsfarmen entfernt; unter bestimmten Bedingungen ist es jedoch noch möglich, sie trotzdem zu verwenden;
  • Unterstützung für einen sanften Absturz, sodass es möglich ist, Server aus einem Farm auszuschalten, ohne irgendeine Verbindung zu beeinflussen;
  • Unterstützung für Reserve-Server, die automatisch verwendet werden, wenn aktive Server ausfallen und sie ersetzen, damit Sitzungen nicht verloren gehen, wenn möglich. Dies ermöglicht es auch, mehrere Wege zu nutzen, um auf denselben Server zuzugreifen (z.B. mehrere Schnittstellen);

HAProxy leistet viel, um die Verfügbarkeit der Dienste zu maximieren, und dafür macht es große Anstrengungen, um Server gegen Überlastung und Angriffe zu schützen. Der erste Grund ist, dass HAProxy die Protokoll-Elemente finden muss, die es benötigt, um sich mit dem Byte-Stream zu synchronisieren, und der zweite Grund ist, dass bis die Anfrage vollständig ist, es keinen Weg gibt, zu wissen, ob einige Elemente ihre Bedeutung ändern werden. Der direkte Vorteil daraus ist, dass die Server nicht den ungültigen oder unvollständigen Anfragen ausgesetzt sind. Dies ist eine sehr wirksame Schutzmaßnahme gegen Slowloris-Angriffe, die auf HAProxy fast keinen Einfluss haben.   1. Begleitprodukte und Alternativen

HAProxy integriert sich relativ gut mit bestimmten Produkten, die hier aufgelistet sind, obwohl sie nicht direkt mit HAProxy in Verbindung stehen.

4.1. Apache HTTP-Server
Apache ist der de-facto Standard HTTP-Server. Es handelt sich um ein sehr umfassendes und modulares Projekt, das sowohl Dateien als auch dynamische Inhalte unterstützt. Es kann als Frontend für bestimmte Anwendungsserver dienen. Es kann sogar Anfragen proxen und Antworten cachen. In allen diesen Fällen ist ein Frontend-Load Balancer häufig erforderlich. Apache kann in verschiedenen Modi arbeiten, einige sind schwerer als andere. Bestimmte Module erfordern noch den schwereren vorforkten Modus und verhindern so, dass Apache gut skaliert kann, wenn es viele Verbindungen hat. In diesem Fall kann HAProxy eine großartige Hilfe sein, indem es die pro-Server-Verbindungsgrenzen auf einen sicheren Wert festlegt und die Serverleistung und die Ressourcen erheblich beschleunigt und erhalten.

Hilfe durch die Festlegung der pro-Server-Verbindungslimits auf einen sicheren Wert, was die Serverleistung erheblich beschleunigt und deren Ressourcen besser für die Anwendung nutzt. Apache kann den IP-Adressen des Clients aus dem X-Forwarded-For-Header mithilfe der "mod_rpaf"-Erweiterung extrahieren. HAProxy übermittelt diesen Header automatisch, wenn "option forwardfor" in seiner Konfiguration angegeben ist. HAProxy bietet zudem eine schöne Sicherheit für Apache an, wenn es dem Internet ausgesetzt ist, wo es besser widerstehen kann, eine große Anzahl von Arten von DoS-Angriffen.

4.2. NGINX
NGINX ist der zweite de-facto Standard-HTTP-Server. Genauso wie Apache bietet es eine breite Palette an Funktionen. NGINX basiert auf einem ähnlichen Modell wie HAProxy, sodass es kein Problem hat, mit Tausenden von gleichzeitigen Verbindungen umzugehen. Wenn es als Gateway zu einigen Anwendungen (z.B. mithilfe der enthaltenen PHP FPM) verwendet wird, kann es oft vorteilhaft sein, Frontend-Verbindungslimits einzurichten, um die Last auf den PHP-Anwendung zu reduzieren. HAProxy wird dort offensichtlich nützlich, sowohl als regulärer Lastenausgleicher als auch als Verkehrsregulator, um PHP zu beschleunigen, indem es es entlastet. Außerdem nutzen beide Produkte sehr wenig CPU, da sie auf einem event-getriebenen Architekturmodell basieren, sodass es oft leicht ist, beide auf demselben System zu installieren. NGINX implementiert das HAProxy-PROXY-Protokoll, sodass es leicht ist, dass HAProxy den Verbindungsinformationen des Clients an NGINX übermittelt, sodass die Anwendung alle relevanten Informationen erhält.

4.3. Varnish
Varnish ist ein intelligenter Cache-Reverse-Proxy, der am besten als Web-Anwendungs-Beschleuniger beschrieben werden kann. Varnish implementiert SSL/TLS nicht und will alle seiner CPU-Zyklen für das Beste verwenden. Varnish implementiert auch das PROXY-Protokoll von HAProxy, sodass HAProxy sehr leicht vor Varnish als SSL-Offloader sowie als Lastenausgleich bereitgestellt werden kann und alle relevanten Informationen des Clients weitergeleitet werden kann. Außerdem unterstützt Varnish natürlich die Entdekompression aus dem Cache, wenn ein Server einen komprimierten Objekt bereitgestellt hat, aber nicht komprimiert. HAProxy kann dann verwendet werden, um ausgehende Daten zu komprimieren, wenn die Backend-Server keine Kompression implementieren, obwohl es selten sinnvoll ist, auf dem Lastenausgleich zu komprimieren, wenn das Verkehrsaufkommen niedrig ist. Wenn große Cache-Farmen auf mehreren Knoten aufgebaut werden, kann HAProxy die konstante URL-Hashing nutzen, um die Last intelligent auf die Cache-Knoten zu verteilen und die Cache-Duplikation zu vermeiden, was zu einem insgesamt größeren Cache führt, der die Summe aller Cache-Knoten ist.

konsequente URL-Hashing dient dazu, die Last intelligenterweise auf die Caching-Knoten zu verteilen und Cache-Duplikate zu vermeiden, was zu einem insgesamt gesamten Cache-Speicher führt, der die Summe aller Caching-Knoten ist.
