ArbeitslastenVerstehen Sie Pods, das kleinste berechnungsfähige Objekt in Kubernetes, und die höheren Abstraktionen, die Ihnen helfen, sie zu betreiben. Eine Arbeitslast ist eine Anwendung, die auf Kubernetes läuft. Ob Ihre Arbeitslast ein einzelnes Komponente oder mehrere Komponenten ist, die zusammenarbeiten, führen Sie sie auf Kubernetes innerhalb einer Menge von Pods aus. In Kubernetes repräsentiert ein Pod eine Menge von einem oder mehreren laufenden Containern in Ihrem Cluster.

Kubernetes-Pods haben eine definierte Lebenszyklus. Beispielhaft bedeutet dies, dass wenn ein Pod in Ihrem Cluster läuft, eine kritische Störung auf dem Knoten, auf dem das Pod läuft, bedeutet, dass alle Pods auf diesem Knoten scheitern. Kubernetes behandelt dieses Niveau an Fehlern als endgültig: Sie müssten ein neues Pod erstellen, um zu erholen, selbst wenn der Knoten später gesund ist.

Um das Leben jedoch erheblich einfacher zu machen, müssen Sie jeden Pod nicht direkt verwalten. Stattdessen können Sie Arbeitslastressourcen verwenden, die eine Menge von Pods für Sie verwalten. Diese Ressourcen konfigurieren Controller, die sicherstellen, dass die richtige Anzahl der richtigen Art von Pods laufen, um der angegebenen Zustandszuordnung zu entsprechen.

Kubernetes bietet mehrere integrierte Arbeitslastressourcen an:

  • Deployment und ReplicaSet (ersetzt den Legacy-Ressource ReplicationController). Deployment ist ein gutes Mittel, um eine statische Anwendung auf Ihrem Cluster zu verwalten, bei der jedes Pod in der Deployment austauschbar ist und ersetzt werden kann, wenn nötig.
  • StatefulSet ermöglicht es, eine oder mehrere miteinander verwandte Pods zu betreiben, die irgendwie Zustand verfolgen.

Auf deiner Cluster-Umgebung, wo jedes Pod in der Bereitstellung beliebig ausgetauscht und ersetzt werden kann, falls dies notwendig ist. StatefulSet ermöglicht es Ihnen, eine oder mehrere verwandte Pods zu starten, die irgendwie Zustand verfolgen. Beispielsweise, wenn Ihre Arbeitsspeicher Daten persistenterweise speichern, können Sie eine StatefulSet starten, die jedem Pod einen PersistentVolume zuordnet. Ihre Code, der in den Pods für diesen StatefulSet läuft, kann Daten an andere Pods in demselben StatefulSet kopieren, um die Gesamtverfügbarkeit zu verbessern.

DaemonSet definiert Pods, die lokale Funktionen bereitstellen. Jede Mal, wenn Sie einem Cluster ein neues Knoten hinzufügen, das der Spezifikation in einem DaemonSet entspricht, planen die Steuerungsebene einen Pod für diesen DaemonSet auf dem neuen Knoten. Jedes Pod in einem DaemonSet führt eine ähnliche Aufgabe wie ein Systemdämon auf einem klassischen Unix / POSIX-Server aus. Ein DaemonSet kann fundamental für die Funktion Ihres Clusters sein, wie z.B. ein Plugin zum Ausführen von Cluster-Netzwerk, es kann Ihnen helfen, den Knoten zu verwalten, oder es kann optionales Verhalten bereitstellen, das die Container-Plattform, die Sie ausführen, verbessert.

Job und CronJob bieten verschiedene Möglichkeiten, Aufgaben zu definieren, die bis zum Abschluss laufen und dann aussetzen. Sie können einen Job verwenden, um eine Aufgabe zu definieren, die nur einmal ausgeführt wird. Sie können einen CronJob verwenden, um die gleiche Aufgabe mehrfach nach einem Zeitplan auszuführen.

Im breiteren Kubernetes-Ökosystem können Sie außerdreits externe Arbeitsspeicherressourcen finden, die zusätzliche Verhaltensweisen bereitstellen.

Du kannst mit Hilfe eines CronJobs das gleiche Job mehrfach laufen lassen, je nach einem Zeitplan. Im breiteren Kubernetes-Ökosystem findest du dritte-Partei-Arbeitslastressourcen, die zusätzliche Verhalten bereitstellen. Mithilfe einer benutzerdefinierten Ressourcendefinition kannst du eine dritte-Partei-Arbeitslastressource einfügen, wenn du ein spezifisches Verhalten benötigst, das nicht Teil des Kubernetes-Kerns ist. Beispielsweise könnte man ein Extension installieren oder implementieren, das die Fähigkeit bietet, eine Gruppe von Pods für eine Anwendung zu starten, aber die Arbeit nur fortzuführen, wenn alle Pods verfügbar sind (zum Beispiel für eine hohe Durchsatz-verteilte Aufgabe).

Arbeitslastplatzierung
ZUSTANDSSTAGE: Kubernetes v1.35 [alpha](standardmäßig deaktiviert)

Während standardmäßige Arbeitslastressourcen (zum Beispiel Bereitstellungen und Jobs) die Lebenszyklus von Pods verwalten, können komplexe Zeitplananforderungen vorliegen, bei denen Gruppen von Pods als einzelne Einheit behandelt werden müssen.

Die Workload-API erlaubt es, PodGroupTemplates zu definieren, um Pods zu gruppieren und auf sie zusätzliche Zeitplanpolitiken anzuwenden, wie zum Beispiel Gang-Zeitplanung. Controller erzeugen PodGroup-Objekte aus diesen Vorlagen während der Ausführung, und Pods verweisen auf ihre PodGroup über das spec.schedulingGroup-Feld. Dies ist besonders nützlich für Batch-Verarbeitungs- und Maschinelerneingangsarbeiten, wo "alles-oder-nichts"-Platzierung erforderlich ist.

Um die Mechanismen von Kubernetes zu erfahren, wie es Code von der Konfiguration trennt, besuchen Sie Configuration.

Es gibt zwei unterstützende Konzepte, die Hintergründe über die Art und Weise bieten, wie Kubernetes Pods für Anwendungen verwaltet:

  • Garbage collection bereinigt Objekte aus Ihrem Cluster nach dem Entfernen ihres eigenen resourcenbesitzenden Objekts.
  • Das time-to-live nach dem beendeten Controller entfernt Jobs, sobald eine definierte Zeit seit ihrem Abschluss vergangen ist.

Nachdem Ihre Anwendung läuft, möchten Sie sie möglicherweise im Internet als Service oder, für Web-Anwendungen nur, mithilfe eines Ingress verfügbar machen.
