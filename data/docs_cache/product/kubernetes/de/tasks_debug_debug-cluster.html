Beheben von ClusterproblemenDebuggen von häufigen Clusterproblemen.Dieses Dokument handelt von der Behebung von Clusterproblemen; wir gehen davon aus, dass Sie bereits Ihre Anwendung als Ursache des auf Ihnen auftretenden Problems ausgeschlossen haben. Siehe die Anwendungsbehebungsführung für Tipps zur Anwendungsbehebung. Sie können auch das Überblickdokument zur Behebung überprüfen, um mehr Informationen zu erhalten.

Für die Behebung von kubectl beziehen Sie sich auf Troubleshooting kubectl.

Auslisten Ihres Clusters
Das erste, was Sie bei Ihrem Cluster debuggen sollten, ist, ob alle Knoten richtig registriert sind. Führen Sie den folgenden Befehl aus: 

kubectl get nodes

Und überprüfen Sie, dass alle Knoten angezeigt werden, die Sie erwarten, und dass sie alle im Ready-Zustand sind.
Um umfassendes Informationen über den Gesamtzustand Ihres Clusters zu erhalten, können Sie folgen: 
kubectl cluster-info dump

Beispiel: Beheben eines abgestürzten/unerreichbaren Knotens
Beim Debuggen kann es nützlich sein, den Status eines Knotens anzuzeigen - z.B. weil Sie merkwürdige Verhalten eines auf dem Knoten laufenden Pods beobachtet haben, oder um zu erfahren, warum ein Pod nicht auf dem Knoten platziert werden kann. Wie bei Pods können Sie kubectl describe node und kubectl get node -o yaml verwenden, um umfassende Informationen über Knoten zu erhalten. Hier ist ein Beispiel, was Sie sehen, wenn ein Knoten abgestürzt ist (z.B. weil er vom Netz getrennt ist, oder kubelet stirbt und nicht neu gestartet wird usw.). Zurzeit geht es um das Eindringen tiefer in den Cluster, indem Sie sich auf die relevanten Maschinen einloggen. Hier sind die Standorte der relevanten Logdateien. Auf systemd-basierten Systemen können Sie stattdessen journalctl anstelle der Untersuchung von Logdateien verwenden.

Control Plane nodes:

  • /var/log/kube-apiserver.log - API Server, verantwortlich für die Bereitstellung der API
  • /var/log/kube-scheduler.log - Scheduler, verantwortlich für die Entscheidungen zur Verteilung
  • /var/log/kube-controller-manager.log - ein Komponente, die die meisten Kubernetes integrierten Controller ausführt, mit der Ausnahme der Verteilung (das kube-scheduler übernimmt die Verteilung)

Worker Nodes:

  • /var/log/kubelet.log - Logs vom kubelet, verantwortlich für das Ausführen von Containern auf dem Knoten
  • /var/log/kube-proxy.log - Logs von kube-proxy, verantwortlich für die Richtung des Verkehrs zu Service Endpunkten
