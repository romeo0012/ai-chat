Erstellung eines Clusters mit kubeadm
Mit kubeadm können Sie einen minimal funktionsfähigen Kubernetes-Cluster erstellen, der den besten Praxisempfehlungen entspricht. Tatsächlich können Sie kubeadm verwenden, um einen Cluster zu erstellen, der die Kubernetes-Konformitätsprüfungen bestanden hat. kubeadm unterstützt auch weitere Clusterlebenszyklusfunktionen, wie Bootstrap-Tokens und Cluster-Upgrades. Der kubeadm-Tool ist gut, wenn Sie:

  • Eine einfache Möglichkeit haben, Kubernetes zu testen, möglicherweise zum ersten Mal.
  • Eine Möglichkeit haben, bestehende Nutzer bei der Automatisierung der Cluster-Einrichtung und der Testung ihrer Anwendung zu unterstützen.
  • Ein Baustein in anderen Ökosystemen und/oder Installer-Tools mit einem größeren Umfang sind.

Sie können kubeadm auf verschiedenen Maschinen installieren und verwenden: Ihrem Laptop, einer Gruppe von Cloud-Servern, einem Raspberry Pi und mehr. Ob Sie in die Cloud oder lokal einsetzen, können Sie kubeadm in Bereitstellungs-Systemen wie Ansible oder Terraform integrieren.

Vor dem Start
Um dieses Handbuch zu verfolgen, benötigen Sie:

  • Eine oder mehrere Maschinen, die mit einem deb/rpm-kompatiblen Linux-Betriebssystem laufen; z.B.: Ubuntu oder CentOS.
  • 2 GiB oder mehr RAM pro Maschine - weniger lässt wenig Raum für Ihre Apps.
  • Mindestens 2 CPUs auf dem Maschine, die Sie als Control-Plane-Knoten verwenden.
  • Vollständige Netzwerkverbindung unter allen Maschinen im Cluster. Sie können entweder eine öffentliche oder eine private Netzwerkverbindung verwenden.

Sie benötigen auch eine Version von kubeadm, die die Version von Kubernetes ermöglichen kann, die Sie in Ihrem neuen Cluster verwenden möchten.

Die Versionierungspolitik von Kubernetes für Version und Versionsskew gilt auch für kubeadm.

Sie können die Version von Kubernetes wählen, die Sie in Ihrer neuen Cluster verwenden möchten. Die Versionierungspolitik von Kubernetes und der Versionabstand unterstützen auch kubeadm sowie Kubernetes insgesamt. Überprüfen Sie diese Politik, um zu erfahren, welche Versionen von Kubernetes und kubeadm unterstützt werden. Diese Seite ist für Kubernetes v1.36 geschrieben.

Das Tool kubeadm hat insgesamt den Feature-Status General Availability (GA). Einige Unter-Features sind noch im aktiven Entwicklungsstadium. Die Implementierung der Clustererstellung kann sich leicht ändern, während das Tool weiterentwickelt wird, aber die Gesamtimplementierung sollte sich relativ stabil verhalten.

Hinweis: Alle Befehle unter kubeadm Alpha sind, definiert, auf einem alpha-Niveau unterstützt.

Netzwerkaufbau

Kubeadm ähnelt anderen Kubernetes-Komponenten darin, dass es versucht, eine nutzbare IP auf den Netzwerkinterfaces zu finden, die mit einem Standard-Gateway auf einem Host verbunden sind. Solche eine IP wird dann für die Werbung und/oder das Hören von Komponenten verwendet.

Um herauszufinden, welche IP dies auf einem Linux-Host ist, kannst du folgendes verwenden: 

ip route show

(Suchen Sie nach einer Zeile, die mit "default via" beginnt)

Hinweis:
Wenn zwei oder mehrere Standard-Gateways auf dem Host vorhanden sind, versucht ein Kubernetes-Komponente, den ersten zu verwenden, der eine geeignete globale Unicast-IP-Adresse hat. Während dieser Auswahl kann die genaue Reihenfolge der Gateways zwischen verschiedenen Betriebssystemen und Kernelversionen variieren.

Kubernetes-Komponenten akzeptieren keine benutzerdefinierte Netzwerkinterface-Option, daher muss eine benutzerdefinierte IP-Adresse als Flag an alle Instanzen von Komponenten, die eine solche benutzerdefinierte Konfiguration benötigen, übergeben werden.

Hinweis:
Wenn der Host kein Standard-Gateway hat und eine benutzerdefinierte IP-Adresse nicht an eine Kubernetes-Komponente übergeben wird, kann die Komponente mit einem Fehler beendet werden.

Um die Werbung-Adresse des API-Servers für Control-Plane-Knoten zu konfigurieren, die mit beidem init und join erstellt wurden, kann das Flag --apiserver-advertise-address verwendet werden. Vorzugsweise kann diese Option in der kubeadm-API als InitConfiguration.localAPIEndpoint und JoinConfiguration.controlPlane.localAPIEndpoint gesetzt werden.

Das Flag --apiserver-advertise-address kann verwendet werden. Empfehlenswert ist, dass diese Option in der kubeadm-API als InitConfiguration.localAPIEndpoint und JoinConfiguration.controlPlane.localAPIEndpoint festgelegt werden kann. Für kubelets auf allen Knoten kann die --node-ip-Option in .nodeRegistration.kubeletExtraArgs innerhalb einer kubeadm-Konfigurationsdatei (InitConfiguration oder JoinConfiguration) übergeben werden. Für dual-stack siehe Dual-Stack-Unterstützung mit kubeadm.

Die IP-Adressen, die für die control-plane-Komponenten zugewiesen werden, werden in den X.509-Zertifikaten der subject alternative name Felder eingetragen. Eine Änderung dieser IP-Adressen erfordert die Erstellung neuer Zertifikate und den Neustart der betroffenen Komponenten, damit die Änderung in den Zertifikatdateien widerspiegelt wird. Weitere Details zu diesem Thema finden Sie unter Manuelle Zertifikatsneuvergabe.

Warnung: Das Kubernetes-Projekt empfiehlt es, dieses Ansatz (Konfigurierung aller Komponenteninstanzen mit benutzerdefinierten IP-Adressen) zu vermeiden. Stattdessen empfehlen die Kubernetes-Maintainer, das Hostnetzwerk einzurichten, sodass die Standard-Gateway-IP diejenige ist, die die Kubernetes-Komponenten automatisch erkennen und verwenden. Auf Linux-Knoten können Befehle wie ip route verwendet werden, um die Netzwerkeinstellungen zu konfigurieren; Ihr Betriebssystem könnte auch höherstufige Netzwerkverwaltungswerkzeuge bereitstellen. Wenn die Standard-Gateway-IP der Knoten eine öffentliche IP-Adresse ist, sollten Sie Paketfilterung oder andere Sicherheitsmaßnahmen einrichten, die die Knoten und Ihren Cluster schützen.

Verwaltete Knoten-Labels
Bei Standard-Einstellungen aktiviert kubeadm den NodeRestriction-Zugangskontroll-Controller, der die Verwendung von Labels einschränkt, die von kubelets während der Registrierung selbst angegeben werden können. Die Dokumentation zum Zugangskontroll-Controller enthält Informationen über die Labels, die für die Verwendung mit dem kubelet --node-labels-Option zugelassen sind.

Achtung: Aufgrund des NodeRestriction-Zugangskontroll-Controllers kannst du das kubelet --node-labels-Flag nicht verwenden, um beschränkte Labels (wie node-role.kubernetes.io/*) während der Initialisierung anzuwenden.

Wenn du versuchst, beschränkte Labels durch Verwendung dieses kubelet-Flags hinzuzufügen, wird der Knoten nicht mit dem API-Server registriert.

Versuchen Sie, beschränkte Etiketten durch Verwenden dieses kubelet-Flags hinzuzufügen, dann wird der Knoten nicht mit dem API-Server registriert. Um diese Etiketten manuell anwenden zu können, müssen Sie nach dem Beitritt des Knotens das kubectl label verwenden. Stellen Sie sicher, dass Sie ein privilegiertes kubeconfig verwenden, wie z.B. das kubeadm-verwaltete /etc/kubernetes/admin.conf.

Isolierung der Kontrollknoten
Standardmäßig wird Ihr Cluster Pods nicht auf den Kontrollknoten schicken, da Sicherheitsgründen. Wenn Sie Pods auf den Kontrollknoten schicken möchten, z.B. für einen einzelnen Kubernetes-Cluster, führen Sie folgenden Befehl aus:

kubectl taint nodes --all node-role.kubernetes.io/control-plane-

Das Ausgabe wird etwas wie folgt aussehen:

node "test-01" untainted ...

Dies entfernt den node-role.kubernetes.io/control-plane:NoSchedule Taint von jedem Knoten, der es hat, einschließlich der Kontrollknoten, was bedeutet, dass der Scheduler dann Pods überall schicken kann.

Zusätzlich können Sie folgenden Befehl ausführen, um das label node.kubernetes.io/exclude-from-external-load-balancers von der Kontrollknoten zu entfernen, was sie von der Liste der Backend-Servern ausschließt:

kubectl label nodes --all node.kubernetes.io/exclude-from-external-load-balancers-

Clean up
Wenn Sie für Ihren Cluster disposable Servers verwendet haben, z.B. für Testzwecke, können Sie diese ausschalten und keine weitere Bereinigung durchführen. Sie können kubectl config delete-cluster verwenden, um Ihre lokalen Verweise auf den Cluster zu löschen.

Wenn Sie jedoch Ihren Cluster sauberer deprovisionen möchten, sollten Sie zunächst den Knoten entleeren und sicherstellen, dass der Knoten leer ist, dann den Knoten dekonfigurieren.

Entfernen des Knotens
Mit den passenden Credentials sprechen Sie mit dem control-plane-Knoten: kubectl drain <node name> --delete-emptydir-data --force --ignore-daemonsets

Bevor Sie den Knoten entfernen, sollten Sie den Zustand durch kubeadm reset zurücksetzen: kubeadm reset

Der Reset-Prozess setzt jedoch keine Regeln für iptables oder IPVS-Tabellen zurück oder bereinigt.

Die von kubeadm installierte Konfiguration: kubeadm reset Das Reset-Prozess löscht nicht automatisch iptables-Regeln oder IPVS-Tabellen. Falls Sie die iptables-Regeln löschen möchten, müssen Sie dies manuell tun:

iptables -F &amp;&amp; iptables -t nat -F &amp;&amp; iptables -t mangle -F &amp;&amp; iptables -X

Falls Sie die IPVS-Tabellen löschen möchten, müssen Sie folgenden Befehl ausführen:

ipvsadm -C

Danach löschen Sie den Knoten:

kubectl delete node &lt;node name&gt;

Version Skew Policy
Während kubeadm Version Skew gegen einige von ihm verwaltete Komponenten zulässt, wird empfohlen, die kubeadm Version mit den Versionen der Control-Plane-Komponenten, kube-proxy und kubelet zu harmonisieren.

kubeadm's Skew gegen die Kubernetes-Version
kubeadm kann mit Kubernetes-Komponenten verwendet werden, die die gleiche Version wie kubeadm oder eine Version älter sind. Die Kubernetes-Version kann kubeadm über das --kubernetes-version Flag von kubeadm init oder das ClusterConfiguration.kubernetesVersion Feld bei Verwendung von --config übergeben werden. Diese Option steuert die Versionen von kube-apiserver, kube-controller-manager, kube-scheduler und kube-proxy.

Beispiel:

kubeadm ist bei 1.36
kubernetesVersion muss bei 1.36 sein oder 1.

Ähnlich wie die Kubernetes-Version kann kubeadm mit einer kubelet-Version verwendet werden, die die gleiche Version wie kubeadm oder drei Versionen älter ist. Beispiel: kubeadm ist auf Version 1.36, kubelet auf dem Host muss auf Version 1.36, 1.35, 1.34 oder 1.33 festgelegt sein.

Auch bei der kubeadm-Version gibt es bestimmte Einschränkungen, wie diese Befehle auf bestehenden Knoten oder ganzen Clustern, die von kubeadm verwaltet werden, ausgeführt werden können. Wenn neue Knoten dem Cluster hinzugefügt werden, muss der kubeadm-Binary für kubeadm join mit der letzten Version von kubeadm übereinstimmen, die entweder zum Erstellen des Clusters mit kubeadm init oder zum Aktualisieren desselben Knotens mit kubeadm upgrade verwendet wurde. ähnliche Regeln gelten für die restlichen kubeadm-Befehle mit der Ausnahme von kubeadm upgrade.

Beispiel für kubeadm join: kubeadm Version 1.36 wurde verwendet, um einen Cluster mit kubeadm init zu erstellen. Knoten, die hinzugefügt werden, müssen einen kubeadm-Binary verwenden, der auf Version 1.36 festgelegt ist. Knoten, die aktualisiert werden, müssen eine Version von kubeadm verwenden, die die gleiche MINOR-Version oder eine MINOR-Version älter als die Version von kubeadm ist, die für die Verwaltung des Knotens verwendet wurde.

Beispiel für kubeadm upgrade: kubeadm Version 1.35 wurde verwendet, um den Knoten zu erstellen oder zu aktualisieren. Die Version von kubeadm, die für die Aktualisierung des Knotens verwendet wird, muss auf 1.35 oder 1.36 festgelegt sein.

Einschränkungen

Die hier erstellte Cluster hat nur eine Control-Plane-Knoten mit einem einzelnen etcd-Datenbank-Laufzeitumgebung, die auf diesem Knoten läuft. Dadurch kann es passieren, dass der Control-Plane-Knoten ausfällt und das Cluster Daten verliert und neu erstellt werden muss.

Workarounds:

Regelmäßig etcd zurückfahren. Die etcd-Datenverzeichnis, das von kubeadm konfiguriert wird, befindet sich auf dem Control-Plane-Knoten unter /var/lib/etcd.

Verwenden Sie mehrere Control-Plane-Knoten. Sie können sich in Options for Highly Available topology eine Cluster-Topologie auswählen, die eine hohe Verfügbarkeit bietet.

Plattformkompatibilität

kubeadm deb/rpm-Pakete und Binaries werden für amd64, arm (32-Bit), arm64, ppc64le und s390x erstellt, was dem multi-platform proposal entspricht.

Multiplatform-Container-Images für die Control-Plane und Addons werden seit v1.12 unterstützt.

Nur einige der Netzwerkanbieter bieten Lösungen für alle Plattformen an. Bitte beachten Sie die Liste der Netzwerkanbieter oben oder die Dokumentation jedes Anbieters, um herauszufinden, ob der Anbieter Ihre gewählte Plattform unterstützt.
