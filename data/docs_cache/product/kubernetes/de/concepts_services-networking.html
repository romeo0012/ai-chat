Dienste, Last-Balance-Lösungen und Netzwerk

Konzepte und Ressourcen hinter dem Netzwerk in Kubernetes.

Das Kubernetes-Netzwerk-Modell

Das Kubernetes-Netzwerk-Modell besteht aus mehreren Teilen:
Jede Pod in einem Cluster erhält eine einzigartige, clusterweite IP-Adresse.
Eine Pod hat ihr eigenes privates Netzwerk-Namespace, das von allen Containern innerhalb der Pod geteilt wird. Prozesse, die in verschiedenen Containern in der gleichen Pod laufen, können sich miteinander über localhost kommunizieren.
Das Pod-Netzwerk (auch als Cluster-Netzwerk bezeichnet) regelt die Kommunikation zwischen Pods. Es sichert ab, dass (außer bei bewusstem Netzwerksegmentierung):
Alle Pods miteinander kommunizieren können, unabhängig davon, ob sie auf demselben Knoten oder auf verschiedenen Knoten laufen. Pods können miteinander kommunizieren, ohne die Verwendung von Proxys oder Adressübersetzung (NAT) zu benutzen.
Auf Windows gilt diese Regel nicht für host-network-Pods.
Agenten auf einem Knoten (z.B. Systemdämonen oder kubelet) können sich mit allen Pods auf diesem Knoten kommunizieren.
Das Service-API ermöglicht es Ihnen, eine stabil (langlebige) IP-Adresse oder Hostname für einen Dienst bereitzustellen, der von einem oder mehreren Backend-Pods implementiert wird, wobei die einzelnen Pods, die den Dienst ausmachen, sich über die Zeit ändern können.
Kubernetes verwaltet automatisch EndpointSlice-Objekte, um Informationen über die Pods zu bereitstellen, die derzeit den Service unterstützen.

Der Dienst kann im Laufe der Zeit verändert werden. Kubernetes verwaltet automatisch EndpointSlice-Objekte, um Informationen über die aktuell hinter einem Dienst stehenden Pods bereitzustellen. Eine Implementierung des Dienst-Proxy-Moduls überwacht den Satz von Service- und EndpointSlice-Objekten und programmiert die Datenebene, um Dienstverkehr an seine Backends zu leiten, indem es mit Hilfe von Betriebssystem- oder Cloud-Anbieter-APIs Pakete abfangt oder umschreibt. Die Gateway-API (oder ihr Vorgänger, Ingress) ermöglicht es Ihnen, Services für Clients außerhalb des Clusters zugänglich zu machen. Ein einfacherer, aber weniger konfigurierbarer Mechanismus für Cluster-Eingang ist über die Service-API-Typ: LoadBalancer verfügbar, wenn ein unterstützter Cloud-Anbieter verwendet wird. NetworkPolicy ist eine integrierte Kubernetes-API, die Ihnen die Kontrolle über den Verkehr zwischen Pods oder zwischen Pods und der Außenwelt ermöglicht. In älteren Container-Systemen gab es kein automatisches Verbinden von Containern auf verschiedenen Hosts, und es war daher oft notwendig, explizit Links zwischen Containern zu erstellen, oder Container-Ports auf Host-Ports zu mappen, um sie von Containern auf anderen Hosts erreichbar zu machen. Dies ist in Kubernetes nicht notwendig; Kubernetes' Modell ist, dass Pods viel wie VMs oder physische Hosts von der Perspektive der Portzuweisung, Namensgebung, Dienstentdeckung, Lastverteilung, Anwendungskonfiguration und Migration behandelt werden können. Nur einige Teile dieses Modells werden von Kubernetes selbst implementiert.

Übersetzung:

Bei diesem Modell handelt es sich um die Themen Namensgebung, Dienstentdeckung, Lastenausgleich, Anwendungskonfiguration und Migration. Nur einige Teile dieses Modells werden von Kubernetes selbst implementiert. Für die anderen Teile definiert Kubernetes die APIs, aber die entsprechende Funktionalität wird von externen Komponenten bereitgestellt, von denen einige optional sind: Die Einrichtung des Pod-Netzwerk-Namespace wird von Systemsoftware auf Systemebene durchgeführt, die den Container Runtime Interface (CRI) implementiert.

Das Pod-Netzwerk selbst wird von einer Pod-Netzwerk-Implementierung verwaltet. Auf Linux wird die meiste Container-Runtime mit dem Container Networking Interface (CNI) interagieren, um mit der Pod-Netzwerk-Implementierung zu kommunizieren, sodass diese Implementierungen oft als CNI-Plugins bezeichnet werden.

Kubernetes bietet eine Standardimplementierung der Service-Proxying, die kube-proxy heißt, aber einige Pod-Netzwerk-Implementierungen verwenden stattdessen ihren eigenen Service-Proxy, der enger mit dem Rest der Implementierung integriert ist.

Netzwerkpolitik wird in der Regel von der Pod-Netzwerk-Implementierung implementiert. (Einfache Pod-Netzwerk-Implementierungen implementieren Netzwerkpolitik nicht, oder ein Administrator kann die Pod-Netzwerk-Konfiguration ohne Netzwerkpolitik-Unterstützung konfigurieren. In diesen Fällen ist die API weiterhin vorhanden, hat aber keinen Einfluss.)

Es gibt viele Implementierungen der Gateway-API, von denen einige spezifisch für bestimmte Cloud-Umgebungen sind, andere mehr auf "bare metal"-Umgebungen ausgerichtet sind, und andere allgemeiner sind.

Einige von diesen sind spezifisch für bestimmte Cloud-Umgebungen, andere sind mehr auf "bare metal"-Umgebungen ausgerichtet und andere sind generischer. Nächste Schritte

Das Tutorial Connecting Applications with Services ermöglicht Ihnen, über einen praktischen Beispiel über Services und Kubernetes-Netzwerke zu lernen.Cluster-Netzwerke erklären, wie Sie das Netzwerk für Ihren Cluster einrichten und bieten auch eine Übersicht über die beteiligten Technologien.

Um spezifische Netzwerkkonzepte zu erlernen, sehen Sie sich folgendes an:

  • Service - eine Anwendung hinter einem einzigen auswärtigen Endpunkt exponieren
  • Ingress - protocol-aware HTTP/HTTPS-Routing über URIs, Hostnamen und Pfade
  • Gateway API - dynamische Infrastruktur bereitstellung und fortgeschrittenes Verkehrsleitungsrouting
  • Network Policies - den Verkehrsfluss an der IP-Adresse oder Port-Ebene (OSI-Schicht 3 oder 4) steuern
  • DNS für Services und Pods - Dienste innerhalb Ihres Clusters über DNS entdecken
