Creating a cluster with kubeadm

← Chat

Vytváření clusteru pomocí kubeadm Pomocí kubeadm můžete vytvořit minimálně funkční Kubernetes cluster, který odpovídá lepším praxím. Skutečně můžete kubeadm použít k nastavení clusteru, který bude procházet testy Kubernetes Conformance. Kromě toho podporuje kubeadm další funkce životního cyklu clusteru, jako jsou tokeny bootstrap a aktualizace clusteru. Pokud potřebujete:

  • Jednoduchý způsob, jak si zkusit Kubernetes, možná poprvé.
  • Způsob, jak automatizovat nastavení clusteru a testovat svou aplikaci pro existující uživatele.
  • Blok v jiném ekosystému a/nebo instalačním nástroji s větším rozsahem.

Můžete nainstalovat a používat kubeadm na různých strojích: vaši notebook, sadu cloudových serverů, Raspberry Pi a další. Pokud nasazujete do cloudu nebo na místě, můžete kubeadm integrovat do systémů pro zprovoznění, jako je například Ansible nebo Terraform.

Než začnete
Chcete-li následovat tuto návod, potřebujete:

  • Jedno nebo více strojů s operačním systémem deb/rpm kompatibilním s Linuxem; například Ubuntu nebo CentOS.
  • 2 GiB nebo více RAM na každém stroji - méně než toto zanechá málo místa pro vaše aplikace.
  • Nejméně 2 CPU na stroji, který používáte jako uzl control-plane.
  • Celková komunikace mezi všemi stroji v clusteru. Můžete použít veřejnou nebo soukromou sít.

Dále potřebujete použít verzi kubeadm, která může nasadit verzi Kubernetes, kterou chcete použít v novém clusteru.

Podpora verze a verzní šířky Kubernetes se týká kubeadm také jako celého Kubernetes.

Můžete nasadit verzi Kubernetes, kterou chcete používat ve vašem novém clusteru. Politika podpory verzí a verzování se týká také kubeadm a celkově Kubernetes. Zkontrolujte tuto politiku, abyste se dozvěděli o podporovaných verzích Kubernetes a kubeadm. Tato stránka je napsaná pro verzi Kubernetes v1.36.Stav celkových funkcí nástroje kubeadm je Obecná dostupnost (GA). Některé podfunkce jsou stále ve fázi aktivního vývoje. Implementace vytvoření clusteru může mírně změnit, ale celkový implementační proces by měl být velmi stabilní.

Poznámka: Všechny příkazy pod kubeadm alpha jsou, podle definice, podporovány na úrovni alfa.

Kubeadm podobně jako ostatní komponenty Kubernetes snaží se najít použitelný IP na sítových rozhraních spojených s výchozím braníkem na hostiteli. Poté se tento IP používá pro reklamování a/nebo poslechování provedeným komponentou.
Chcete-li zjistit, co je tento IP na Linuxovém hostiteli, můžete to udělat pomocí:

Poznámka:
Pokud na hostiteli existují dvě nebo více výchozí braníků, komponenta Kubernetes bude pokusit se použít první, který se setká s vhodnou globální unicast IP adresou. Během tohoto výběru může se přesunout přesunutí řadů mezi různými operačními systémy a verzemi jádra.
Komponenty Kubernetes nepřijímají vlastní sítové rozhraní jako možnost, proto musí být vlastní IP adresa předána jako příkazový řádek všem instancím komponent, které potřebují takovou vlastní konfiguraci.

Pokud hostitel nemá výchozí braník a vlastní IP adresu není předána komponentě Kubernetes, může se komponenta ukončit s chybou.

Inicializace vašeho uzlu správce plánu
Uzel správce plánu je stroj, na kterém běží komponenty plánu, včetně etcd (databáze clusteru) a API Serveru (který se komunikuje s nástrojem kubectl příkazového řádku).
(Doporučeno) Pokud máte plány na upgrade tohoto jediného uzlu správce plánu kubeadm clusteru na vysokou dostupnost, je nutné nastavit --control-plane-endpoint, aby se nastavil sdílený endpoint pro všechny uzly správce plánu. Tento endpoint může být buď DNS název nebo IP adresa balanceru zatížení.

Vyberte si Pod sítí add-on a ověřte, zda potřebují být kubeadm initu přiřazeny žádné argumenty. Podle toho, kterého třetího poskytovatele vyberete, můžete muset nastavit --pod-network-cidr na hodnotu specifickou pro poskytovatele.

Ověřte, zda potřebuje kubeadm init přijmout žádné argumenty. Podle zvoleného třetího poskytovatele můžete potřebovat nastavit argument --pod-network-cidr na hodnotu specifickou pro poskytovatele. Viz Instalace přídavného modulu sítě pod. (Volitelné) Kubeadm se snaží detekovat runtime kontejneru pomocí seznamu známých koncových bodů. Pokud chcete použít jiný runtime nebo pokud je na zprostředkovaném uzlu instalováno více runtime, zadejte argument --cri-socket do kubeadm. Viz Instalace runtime. Chcete-li inicializovat uzl control-plane, spusťte:

kubeadm init &lt;args&gt;

Poznámky k apiserver-advertise-address a ControlPlaneEndpoint

Pomocí argumentu --apiserver-advertise-address můžete nastavit adresu, kterou bude tento konkrétní uzl control-plane API server reklamovat. Pomocí argumentu --control-plane-endpoint můžete nastavit sdílený koncový bod pro všechny uzly control-plane. --control-plane-endpoint umožňuje použití IP adres i DNS názvů, které mohou mapovat na IP adresy. Kontaktujte prosím správce sítě k hodnocení možných řešení v souvislosti s takovýmto mapováním. Níže je příklad mapování:

192.168.0.102 cluster-endpoint

Kde 192.168.0.102 je IP adresa tohoto uzlu a cluster-endpoint je vlastní DNS název, který mapuje na tuto IP. Tímto způsobem můžete zadat --control-plane-endpoint=cluster-endpoint do kubeadm init a stejný DNS název do kubeadm join. Později můžete upravit cluster-endpoint tak, aby ukazoval na adresu vašeho load-balancer v scénáři vysoké dostupnosti.

Pro připravení kubeadm iniciální fáze a přenos stejného názvu DNS do kubeadm join. Později můžete upravit cluster-endpoint na adresu vašeho balanceru v scénáři vysoké dostupnosti. Přeměna jednoduchého clusteru správce bez --control-plane-endpoint na vysokou dostupnost není podporována kubeadm. Kubeadm iniciální fáze nejprve spustí řadu předkontrol, aby se zjistilo, zda je stroj připraven k běhu Kubernetes. Tyto předkontroly zveřejňují varování a skončí chybou. Kubeadm iniciální fáze poté stahuje a instaluje komponenty clusteru správce. To může trvat několik minut. Po dokončení byste měli vidět:
Vaše Kubernetes správce iniciální fáze byla úspěšně inicializována! Chcete-li začít s použitím vašeho clusteru, musíte spustit následující jako běžný uživatel:
mkdir -p $HOME/.

Po uplynutí přibližně deseti minut byste měl vidět: Vaše Kubernetes řídící plocha byla inicializována úspěšně! Chcete-li začít s použitím vašeho clusteru, musíte spustit následující jako běžný uživatel:

mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

Nyní byste měli nasadit sítí pro Pod do clusteru. Spusťte "kubectl apply -f [podnetwork].yaml" s jednou z možností uvedených na: /docs/concepts/cluster-administration/addons/

Nyní můžete připojit libovolný počet strojů spuštěním následujícího příkazu na každém uzlu jako root:

kubeadm join &lt;control-plane-host&gt;:&lt;control-plane-port&gt; --token &lt;token&gt; --discovery-token-ca-cert-hash sha256:&lt;hash&gt;

Chcete-li, aby se pro vašeho běžného uživatele fungovalo kubectl, spusťte následující příkazy, které jsou také součástí výstupu kubeadm init:

mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

Alternativně, pokud jste root uživatel, můžete spustit:

export KUBECONFIG=/etc/kubernetes/admin.conf

Varování: Soubor kubeconfig admin.conf, který vytvoří kubeadm init, obsahuje certifikát s Názvem organizace: O = kubeadm:cluster-admins, CN = kubernetes-admin. Skupina kubeadm:cluster-admins je vázána na vnitřní ClusterRole ClusterRole. Nezdělejte si admin.conf soubor s kýmkoliv.

Kubeadm init vytvoří další soubor kubeconfig super-admin.conf, který obsahuje certifikát s Názvem organizace: O = system:masters, CN = kubernetes-super-admin.

S přímým kontaktem. Inicializace kubeadm vytvoří další soubor kubeconfig s názvem super-admin.conf, který obsahuje certifikát s následujícím Subjectem: O = system:masters, CN = kubernetes-super-admin. Skupina system:masters je skupina pro přímý přístup, která obchází vrstvu autorizace (například RBAC). Nezdělite si soubor super-admin.conf s kýmkoliv. Doporučujeme přesunout soubor do bezpečné lokace. Další informace o vytváření souborů kubeconfig pro další uživatele naleznete v článku Generating kubeconfig files for additional users.Uložte si záznam z příkazu kubeadm join, který vytvoří kubeadm init. Tento příkaz potřebujete k připojení uzlů k vaší clusteru. Token se používá pro mutual authentication mezi uzlem správy a připojujícími uzly. Token zahrnutý zde je tajný. Udržte ho v bezpečnosti, protože kdo má tento token může přidat ověřené uzly do vašeho clusteru. Tyto tokeny mohou být seznamovány, vytvářeny a odstraňovány pomocí příkazu kubeadm token. Značky uzlů Spravovaný uzl automaticky povoluje kontrolor přístupu NodeRestriction, který omezuje, které značky mohou být samostatně přidávány kubeletem při registraci uzlu. Dokumentace k kontroloru přístupu obsahuje informace o značkách, které mohou být použity s kubeletem --node-labels.

Varování: Pro kontrolor přístupu NodeRestriction nelze použít kubelet --node-labels značky (např. node-role.kubernetes.io/*) při inicializaci. Pokud se pokusíte přidat značky omezené kontrolorem přístupu pomocí tohoto kubelet flagu, uzl nebude moci registrovat se serverem API.

Pokus o přidání omezených etiket pomocí tohoto kubelet flagu bude způsobit, že uzel nebude schopný se registrovat s API serverem. Chcete-li tyto etikety ručně přidat, musíte po spojení uzlu s clusterem použít příkaz kubectl label. Ujistěte se, že používáte privilegovaný kubeconfig, jako je například kubeadm-spravovaný /etc/kubernetes/admin.conf.

Isolace uzlu správceho plánu
Výchozí nastavení vašeho clusteru nebude plánovat nasazování Podů na uzlech správce plánu pro bezpečnostní důvody. Pokud chcete mít možnost nasazovat Pody na uzlech správce plánu, například pro malý Kubernetes cluster na jednom počítači, spusťte: 

kubectl taint nodes --all node-role.kubernetes.io/control-plane

Výstup bude vypadat nějak takto: 
node "test-01" untainted ...

Tato příkaz odstraní taint node-role.kubernetes.io/control-plane:NoSchedule z jakýchkoli uzlů, které ho mají, včetně uzlů správce plánu, což znamená, že schématel bude moci nasazovat Pody na všechny místa.

Další možností je spustit následující příkaz k odstranění etikety node.kubernetes.io/exclude-from-external-load-balancers z uzlu správce plánu, což ho vyloučí z seznamu serverů zadávacích serverů: 

kubectl label nodes --all node.kubernetes.io/exclude-from-external-load-balancers

(Volitelné) Řídění clusterem z počítačů jiných než správce uzlů
Chcete-li mít na nějakém jiném počítači (např. na laptopu) kubectl, který se spojí s vaším clusterem, musíte kopírovat správce kubeconfig soubor z vašeho uzlu správce na svůj pracovní stanici takto:

scp root@<správce-uzel-host>:/etc/kubernetes/admin.conf . kubectl --kubeconfig ./admin.conf get nodes

Poznámka: Příklad výše předpokládá, že je pro root povoleno přístup k SSH. Pokud to není možné, můžete kopírovat soubor admin.conf tak, aby byl dostupný nějakému jinému uživateli a použít scp s tímto jiným uživatelem místo toho.

Soubor admin.conf uděluje uživateli superuživatelská práva nad clusterem. Tento soubor by měl být používán šetrně. Pro normální uživatele je doporučeno vytvořit unikátní kredence, které jim udělíte oprávnění. Můžete to udělat pomocí příkazu kubeadm kubeconfig user --client-name <CN>. Tento příkaz vytiskne KubeConfig soubor na standardní výstup, který byste měli uložit do souboru a rozeslat uživateli. Po tomto kroku můžete oprávnění udělit pomocí příkazu kubectl create (cluster)rolebinding.

Příkaz vytiskne KubeConfig soubor do STDOUT, který byste měli uložit do souboru a rozeslat ho uživateli. Poté udělejte oprávnění pomocí příkazu kubectl create (cluster)rolebinding. (Volitelné) Proxy serveru API k lokálnímu hostiteli
Pokud chcete připojit k serveru API zvenčí clusteru, můžete použít kubectl proxy: scp root@<host_kontrolního_panelu>:/etc/kubernetes/admin.conf . kubectl --kubeconfig ./admin.conf proxy Můžete nyní přístup k serveru API místně na adrese http://localhost:8001/api/v1

Vyčištění
Pokud jste pro svůj cluster používali dispozitivní servery pro testování, můžete je vypnout a neprovádět žádné další vyčištění. Můžete použít kubectl config delete-cluster pro odstranění vašich místních odkazů na cluster.

Však pokud chcete deprovisionovat svůj cluster čistěji, byste měli nejprve vyčistit node a ujistit se, že je prázdná, poté dekonfigurovat node.

Odebrat node
Hovořící se správnými přihlašovacími údaji k uzlu kontrolního panelu, spusťte:
kubectl drain <jméno_node> --delete-emptydir-data --force --ignore-daemonsets

Před odebráním node resetujte stav nainstalovaný kubeadm:
kubeadm reset

Resetovací proces neresetuje nebo vyčistí pravidla iptables nebo tabulky IPVS.

Tato instalace provedena kubeadm:kubeadm reset Resetovací proces nevymaže ani nevypíše pravidla pro iptables ani tabulky IPVS. Pokud chcete resetovat pravidla pro iptables, musíte to provést ručně:

iptables -F
iptables -t nat -F
iptables -t mangle -F
iptables -X

Pokud chcete resetovat tabulky IPVS, musíte spustit následující příkaz:

ipvsadm -C

Nyní odstraňte uzel:

kubectl delete node &lt;jméno_uzlu&gt;

Pokud chcete znovu začít, spusťte kubeadm init nebo kubeadm join se správnými argumenty.

Vyčištění control plane
Můžete použít kubeadm reset na hostiteli control plane k spuštění nejlepšího úsilí vyčištění.
Viz dokumentaci k referenčním příkazům kubeadm reset pro další informace o tomto podpříkazu a jeho možnostech.

Zásady skew verzí
Though kubeadm umožňuje skew verzí pro některé komponenty, které spravuje, je doporučeno, aby se odpovídající verze kubeadm shodovala s verzemi komponent control plane, kube-proxy a kubelet.
Kubeadmův skew vůči verzi Kubernetes
Kubeadm může být použit s komponentami Kubernetes, které mají stejnou verzi jako kubeadm nebo o jednu verzi starší. Verze Kubernetes může být určena kubeadmem pomocí příkazu --kubernetes-version flag kubeadm init nebo pole ClusterConfiguration.kubernetesVersion při použití --config. Tato možnost ovládne verze kube-apiserver, kube-controller-manager, kube-scheduler a kube-proxy.

Příklad:

kubeadm je na 1.36
kubernetesVersion musí být na 1.36 nebo 1.

Možnost bude kontrolovat verze kube-apiserveru, kube-controller-manageru, kube-scheduleru a kube-proxy. Příklad:
kubeadm je na verzi 1.36
kubernetesVersion musí být na verzi 1.36 nebo 1.35
Srovnatelně k verzi Kubernetesu, může se kubeadm použít s verzí kubeletu, která je stejná jako verze kubeadm nebo tři verze starší. Příklad:
kubeadm je na verzi 1.36
kubelet na hostiteli musí být na verzi 1.36, 1.35, 1.34 nebo 1.33
Skew kubeadm vůči kubeadm
Existují určité omezení, jakými jsou kubeadm příkazy, které mohou operovat na existujících uzlech nebo celých clusterů spravovaných kubeadm.
Pokud se k clusteru připojí nové uzly, musí se pro kubeadm join použít stejná verze kubeadm, kterou se použila pro vytvoření clusteru pomocí kubeadm init nebo pro jeho upgrade pomocí kubeadm upgrade. Podobná pravidla se týkají ostatních kubeadm příkazů s výjimkou kubeadm upgrade.
Příklad pro kubeadm join:
kubeadm verze 1.36 byla použita k vytvoření clusteru pomocí kubeadm init
Připojování uzlů musí používat kubeadm binář na verzi 1.36
Uzly, které se upgradeují, musí používat verzi kubeadm, která je stejná MINOR verze nebo jedna MINOR verze novější než verze kubeadm, která byla použita k správě uzlu.
Příklad pro kubeadm upgrade:
kubeadm verze 1.35 byla použita k vytvoření nebo upgrade uzlu
Pro upgrade uzlu musí být použita verze kubeadm na 1.35 nebo 1.36
Další informace o skewu mezi různými komponentami Kubernetesu naleznete v dokumentu Version Skew Policy.

Verze kubeadm použitá k aktualizaci uzlu musí být alespoň 1.35 nebo 1.36 Informace o rozdílech verzí mezi různými komponentami Kubernetes naleznete v politice Verze Skew.

Omezení
Resilience klastru
Klastr, který zde vytvoříte, má jen jeden uzl hlavního uzlu s jednou databází etcd běžící na něm. To znamená, že pokud se uzl hlavního uzlu zhroutí, může vaši databázi ztratit a může se potřebovat vytvořit znovu z nuly.

Nápravy:

  • Pravidelně zabezpečujte etcd. Konfigurovaný adresář dat etcd kubeadm je na uzlu hlavního uzlu na /var/lib/etcd.
  • Použijte více uzlů hlavního uzlu. Můžete si vybrat topologii klastru, která poskytuje vysokou dostupnost, abyste si ji vybrali.

Podpora platform
Balíčky a bináře kubeadm deb/rpm jsou sestavovány pro amd64, arm (32-bit), arm64, ppc64le a s390x podle návrhu multi-platform.
Od verze 1.12 jsou také podporovány multiplatform container images pro uzl hlavního uzlu a doplňky.
Některé z poskytovatelů sítí nabízejí řešení pro všechny platformy. Prozkoumejte seznam poskytovatelů sítí výše nebo dokumentaci každého poskytovatele, abyste se dozvěděli, zda poskytovatel podporuje vaši zvolenou platformu.
