Architektura clusteru
Architektonické koncepce za Kubernetesem.
Kubernetesový cluster se skládá z řídícího panelu a sadu pracovních strojů, nazývaných uzly, které spouští aplikace v kontejnerech. Každý cluster potřebuje alespoň jeden pracovní uzel, aby mohl běžet Pods.
Pracovní uzel(y) hostují Pody, které jsou součástmi zatížení aplikace. Řídící panel spravuje pracovní uzly a Pody v clusteru. V produkčních prostředích běží řídící panel obvykle na více počítačích a cluster běží obvykle na více uzlech, což poskytuje odolnost proti chybám a vysokou dostupnost.
Tento dokument popisuje různé komponenty, které potřebujete mít pro kompletní a funkční Kubernetesový cluster.

kube-apiserver
API server je komponentou Kubernetes řídícího panelu, která vystavuje API Kubernetes. API server je front-end pro Kubernetes řídící panel.
Hlavní implementace serveru API Kubernetes je kube-apiserver. Kube-apiserver je navržený pro horizontální škálování—tedy škáluje se nasazením více instancí. Můžete spustit několik instancí kube-apiserver a rovnoměrně rozložit provoz mezi těmito instancemi.

etcd
Stabilní a vysokojíživý klíč-hodnotový úložiště používané jako podklad pro všechny data klastru Kubernetes.
Pokud používáte Kubernetes klastr jako svůj podklad, ujistěte se, že máte zálohovací plán pro data.

Úloha slouží jako Kubernetesův podporující úložný prostor pro všechny clusterové data.Pokud vaše Kubernetesová cluster používá etcd jako svůj podporující úložný prostor, ujistěte se, že máte zálohovací plán pro data.Můžete najít podrobnější informace o etcd v oficiální dokumentaci.

kube-scheduler Je součástí řídicího plánu, která sleduje vznikající Pody bez přiřazeného uzlu a vybírá pro ně uzl k spuštění.Faktory, které se při rozhodování o rozložení braly v úvahu, zahrnují: individuální a kolektivní požadavky na zdroje, omezení hardware/software/politiky, specifikace přilnavosti a protipřilnavosti, lokality dat, interakce mezi pracovními naloady, a termíny.

kube-controller-manager Je součástí řídicího plánu, která spouští procesy řídicích procesů.Logicky každý řídicí proces představuje samostatný proces, ale k snížení složitosti jsou všechny spojeny do jednoho binářku a spouštějí se v jednom procesu.

Je zde mnoho různých typů řídicích procesů. Několik příkladů zahrnuje:

Node controller: Odpovědný za pozorování a reakci na sestupující uzly.
Job controller: Sleduje objekty Job, které představují jednorázové úkoly, a poté vytváří Pody k provedení těchto úkolů do dokončení.
EndpointSlice controller: Vytváří objekty EndpointSlice (které poskytují odkaz mezi Službami a Pods).
ServiceAccount controller: Vytváří výchozí ServiceAccounty pro nové prostory.

Výše uvedené není úplný seznam.

cloud-controller-manager Je součástí řídicího plánu Kubernetesu, která zabezpečuje logiku specifickou pro cloud.

Výchozí služební účty pro nové prostory. Tento seznam není vyčerpávající.
cloud-controller-manager
Komponenta řídicího panelu Kubernetes, která vkládá cloudově specifickou logiku řízení. Správce řídicího panelu umožňuje vytvořit svůj cluster spojit s API vašeho cloudového poskytovatele a odděluje komponenty, které interagují s touto cloudovou platformou, od komponent, které interagují pouze s vaším clusterem.
Správce řídicího panelu spouští kontrolery, které jsou specifické pro vašeho cloudového poskytovatele. Pokud spouštíte Kubernetes na svých vlastních pozemcích nebo v cvičebním prostředí vlastního počítače, cluster nemá správce řídicího panelu.
Stejně jako kube-controller-manager, cloud-controller-manager kombinuje řadu logicky nezávislých kontrolních smyček do jednoho binářního souboru, který spouštíte jako jeden proces. Můžete horizontálně škatulkovat (spouštět více kopií) k zlepšení výkonu nebo k pomoci tolerovat selhání.
Následující kontrolery mohou mít závislosti na cloudovém poskytovateli:
Node controller: Pro kontrolu cloudového poskytovatele, zda je uzel byl odstraněn v cloudu po tom, co ukončil odpověď
Route controller: Pro nastavení tras v podstatě cloudové infrastruktury
Service controller: Pro vytváření, aktualizaci a odstraňování cloudových poskytovatele zabaláček load balancer
Node komponenty
Node komponenty běží na každém uzlu, udržují běžící pody a poskytují prostředí pro spuštění Kubernetes.
kubelet
Agent, který běží na každém uzlu v clusteru.

Každý uzel, udržující běžící pody a poskytující prostředí pro spouštění Kubernetesu.

kubelet
Je to agent, který běží na každém uzlu v klastru. Jeho hlavní úlohou je zajistit, aby kontejnery běžely v rámci Podu. Kubelet přijímá sadu PodSpeců, které poskytují různé mechanismy a zajistí, aby kontejnery popsané v těchto PodSpecech běžely a byly zdravé. Kubelet nezajímá se o správu kontejnerů, které nebyly vytvořeny Kubernetesem.

(volitelné) kube-proxy
kube-proxy je sítěový proxy, který běží na každém uzlu v vašem klastru, implementující část konceptu služby Kubernetesu. kube-proxy udržuje sítěové pravidla na uzlech. Tyto sítěové pravidla umožňují sítěové komunikace s vašimi Pody z sítěových relací vnitřně nebo vně vašeho klastru. kube-proxy využívá vrstvy filtrování balíčků operačního systému, pokud je k dispozici. V opačném případě kube-proxy sám přesměruje provoz.

Pokud používáte sítěový plugin, který implementuje přesměrování provozu pro služby samostatně a poskytuje stejnou chování jako kube-proxy, pak nemusíte spouštět kube-proxy na uzlech v vašem klastru.

Runtime kontejneru
Jedná se o základní komponentu, která umožňuje Kubernetesu efektivně spouštět kontejnery. Je odpovědný za správu spouštění a životního cyklu kontejnerů v prostředí Kubernetesu.

Kubernetes podporuje různé runtime kontejnerů, jako například containerd, CRI-O a jakékoliv jiné implementace rozhraní Kubernetes CRI (Container Runtime Interface).

Understanding these variations is crucial for designing and maintaining Kubernetes clusters that meet specific operational needs.Systémové plochy ovládacího paneluSložky ovládacího panelu mohou být nasazeny v různých způsobech:
Tradiční nasazení
Složky ovládacího panelu běží přímo na vědeckých strojích nebo virtuálních strojích, obvykle řízené jako služby systemd.
Statické Pody
Složky ovládacího panelu jsou nasazeny jako statické Pody, řízené kubeletem na konkrétních uzlech. Tento způsob nasazení je běžně používán nástroji jako je kubeadm.
Samohostované
Složky ovládacího panelu běží jako Pody v samotném Kubernetes clusteru, řízené nasazováním Deployments a StatefulSets nebo jinými primitivy Kubernetesu.
Služby Kubernetes v cloudu
Obvykle cloudové poskytovatele odstraňují ovládací panel, spravují jeho složky jako součást své služby nabídky.

Kubernetes primitivy. Spravované služby Kubernetes v cloudu
Obvykle cloudové poskytovatele zabývají se odstraňováním kontrolního uzlu, spravujícím jeho komponenty jako součástí svého služebního nabídky.

Vyvážené umístění pracovních zátěží
Umístění pracovních zátěží, včetně komponent kontrolního uzlu, může se lišit podle velikosti clusteru, požadavků na výkon a operativních politik:
V menších nebo vývojových klusterech mohou komponenty kontrolního uzlu a uživatelské pracovní zátěže běžet na stejných uzlech.
Větší produkční klusterům často přiděluje specifické uzly pro kontrolní uzly, oddělující je od uživatelských pracovních zátěží.
Některé organizace spouští kritické doplňky nebo nástroje pro sledování na uzlech kontrolního uzlu.

Nástroje pro správu clusteru
Nástroje jako kubeadm, kops a Kubespray nabízejí různé přístupy k nasazení a správě clusterů, každý s vlastní metodou rozložení a správy komponent.

Přizpůsobitelnost a rozšiřitelnost
Architektura Kubernetes umožňuje významnou přizpůsobitelnost:
Mohou být nasazeny vlastní plánovače, aby pracovaly vedle výchozího plánovače Kubernetes nebo aby je nahradily úplně.
API server může být rozšířen pomocí CustomResourceDefinitions a API Aggregation.
Cloudové poskytovatele mohou integrovat hluboko do Kubernetes pomocí cloud-controller-manager.

Flexibilita architektury Kubernetes umožňuje organizacím přizpůsobit své cluster k určitým potřebám, rovnovážící faktory jako operativní složitost, výkon a náklady na správu.
