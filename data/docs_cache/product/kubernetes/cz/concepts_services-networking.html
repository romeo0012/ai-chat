Model sítě v Kubernetes
Model sítě v Kubernetes je složen z několika částí: Každý pod v clusteru obdrží svou vlastní unikátní IP adresu clusteru širokou. Každý pod má své vlastní soukromé sítové prostorové jméno, které sdílí všechny kontejnery v rámci podu. Procesy běžící v různých kontejneřech v jednom podu mohou se komunikovat mezi sebou přes localhost. Sítová síť podu (také známá jako sítová síť clusteru) řídí komunikaci mezi podmi. Ujistí se, že (kromě úmyslného segmentování sítě): Všechny podmi mohou komunikovat se všemi ostatními podmi, bez ohledu na to, zda jsou na stejném uzlu nebo na různých uzlech. Podmi mohou se komunikovat mezi sebou přímo, bez použití proxy nebo adresního převodu (NAT). Na Windows toto pravidlo neplatí pro podmi s hostovou sítí. Agenti na uzle (například systémové daemony, nebo kubelet) mohou komunikovat se všemi podmi na tomto uzle. Služba API umožňuje poskytnout stabilní (déle trvající) IP adresu nebo hostname pro službu implementovanou jedním nebo více zadávacími podmi, kde individuální podmi, které tvoří službu, mohou změnit během času. Kubernetes automaticky spravuje objekty EndpointSlice, aby poskytla informace o podmich, které aktuálně podporují Službu.

Poznámka: Tento překlad je určen pouze pro účely vzdělávání a neposkytuje žádnou garanci kvality. Pro profesionální použití je nutné si objednat překlad od kvalifikovaného překladatele.

Služba může se přeměnit v průběhu času. Kubernetes automaticky spravuje objekty EndpointSlice, aby poskytl informace o podách, které aktuálně podporují službu. Implementace služby proxy monitoruje sadu objektů Service a EndpointSlice a programuje datovou plochu k routování provozu služby k jejím back-endům, pomocí rozhraní API operačního systému nebo poskytovatele cloudových služeb k přerušování nebo přepsání balíčků. API Brány (nebo jeho předchůdce, Ingress) umožňuje vám, abyste služby dostupné byly pro klienty, které se nacházejí mimo cluster. Prostředky pro clusterový přístup jednodušší, ale méně konfigurovatelný, jsou k dispozici prostřednictvím API služby Type: LoadBalancer, při použití podporovaného poskytovatele cloudových služeb. NetworkPolicy je vlastní API Kubernetes, které vám umožňuje omezit provoz mezi podmi, nebo mezi podmi a vnějším světem. V starších systémech kontejnerů nebylo automatické připojení mezi kontejnery na různých hostech a tak bylo často nutné explicitně vytvářet odkazy mezi kontejnery, nebo mapovat porty kontejnerů na porty hostitele, aby byly dostupné pro kontejnery na jiných hostech. To není nutné v Kubernetes; model Kubernetes je, že podmi mohou být zpracovávány jako VMs nebo fyzické hosty z hlediska alokace portů, jmenování, objevování služeb, zatížení a balancování zatížení, konfigurace aplikací a migrace. Jen několik částí tohoto modelu je implementováno Kubernetesem samotným.

Přejmenování, služební zjišťování, zatížení, konfigurace aplikace a migrace. Samé několik částí tohoto modelu jsou implementovány přímo Kubernetesem. Pro ostatní části Kubernetes definuje API, ale odpovídající funkce poskytuje externí komponenta, některé z nich jsou volitelné:Nastavení prostoru jména sítě podů je řešeno softwarem systémového úrovně implementujícím Container Runtime Interface.Sám pod sítí je spravován implementací pod sítě. Na Linuxu většina runtimeů kontejnerů používá Container Networking Interface (CNI), aby interagovala s implementací pod sítě, takže tyto implementace často nazývají se CNI pluginy.Kubernetes poskytuje výchozí implementaci služebního proxy, nazývanou kube-proxy, ale některé implementace pod sítě místo toho používají svůj vlastní služební proxy, který je těsněji integrovaný s ostatními komponentami.NetworkPolicy je obecně také implementováno pod sítí. (Některé jednodušší implementace pod sítě neimplementují NetworkPolicy, nebo správce může zvolit konfigurovat pod sítě bez podpory NetworkPolicy. V těchto případech bude API stále přítomno, ale nebude mít žádný efekt.)
