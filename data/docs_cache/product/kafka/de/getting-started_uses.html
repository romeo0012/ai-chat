Messaging Kafka funktioniert gut als Ersatz für ein traditionelles Nachrichtenbroker. Nachrichtenbroker werden für eine Vielzahl von Gründen verwendet (zum Entkoppeln der Verarbeitung von Datenproduzenten, zum Buffern unverarbeiterter Nachrichten usw.). Im Vergleich zu den meisten Nachrichtensystemen bietet Kafka besseres Durchsatzvermögen, integrierte Partitionierung, Replikation und Fehlertoleranz, was es zu einem guten Lösungsmittel für großskalige Nachrichtenverarbeitungsanwendungen macht. In unserer Erfahrung werden messaging-Anwendungen oft vergleichsweise niedrige Durchsatzwerte aufweisen, aber möglicherweise eine niedrige End-to-End-Verzögerung erfordern und oft auf die starken Beständigkeitsgarantien von Kafka angewiesen sein. In diesem Bereich ist Kafka vergleichbar mit traditionellen Nachrichtensystemen wie ActiveMQ oder RabbitMQ. Website-Aktivitäts-Protokollierung Das ursprüngliche Anwendungsfall für Kafka war es, eine Benutzeraktivitäts-Protokollierungspipeline als eine Reihe von real-time-Publish-Subscribe-Feeds wiederzubauen. Das bedeutet, dass Website-Aktivitäten (Seitenaufrufe, Suchen oder andere Aktionen, die Benutzer ausführen können) in zentrale Themen veröffentlicht werden, wobei ein Thema pro Aktivitäts-Typ verwendet wird. Diese Feeds sind für die Abonnement für eine Reihe von Anwendungsfällen verfügbar, einschließlich real-time-Verarbeitung, real-time-Monitoring und Laden in Hadoop oder in offline Daten-Warehousing-Systeme für offline Verarbeitung und Berichterstattung. Aktivitäts-Protokollierung ist oft sehr hoher Volumen, da viele Aktivitäts-Nachrichten für jede Benutzer-Seitenaufforderung erstellt werden.

Metriken Kafka wird oft für die operative Überwachungsdaten verwendet. Das betrifft die Aggregation von Statistiken aus verteilten Anwendungen, um zentralisierte Datenströme operativer Daten zu produzieren. Log Aggregation Viele Menschen verwenden Kafka als Ersatz für eine Lösung zur Log-Aggregation. Die Log-Aggregation sammelt meistens physische Log-Dateien von Servern und speichert sie in einem zentralen Ort (einem Dateiserver oder HDFS vielleicht) für die Verarbeitung. Kafka verbergt die Details der Dateien und bietet eine saubere Abstraktion von Log- oder Ereignisdaten als Strom von Nachrichten. Dadurch ist die Verarbeitung mit niedrigerer Verzögerung möglich und es wird leichter Unterstützung für mehrere Datenquellen und verteilte Datenverbrauch bieten. Im Vergleich zu log-zentrierten Systemen wie Scribe oder Flume bietet Kafka gleich gute Leistung, starke Bestandsgarantien durch die Replikation und viel niedrigeres End-to-End-Latency. Stream Processing Viele Nutzer von Kafka verarbeiten Daten in Verarbeitungspipelines, die aus mehreren Stufen bestehen, wo unbearbeitete Eingabedaten aus Kafka-Themen konsumiert und dann aggregiert, bereichert oder anders transformiert werden, um neue Themen für weitere Verarbeitung oder Nachverfolgung zu erstellen.

Neben Kafka Streams stehen alternative offene Stream-Verarbeitungswerkzeuge wie Apache Storm und Apache Samza zur Verfügung. Event Sourcing Event Sourcing ist ein Stil der Anwendungsentwicklung, bei der Änderungen des Zustands als zeitlich geordnete Reihe von Aufzeichnungen geloggt werden. Kafkas Unterstützung für sehr große gespeicherte Logdaten macht es zu einem idealen Backend für eine Anwendung, die in diesem Stil erstellt wurde. Commit Log Kafka kann als Art von externem Commit-Log für ein verteiltes System dienen. Der Log hilft Daten zwischen Knoten zu replizieren und dient als Synchronisierungsmekanismus für gescheiterte Knoten, um ihre Daten wiederherzustellen.
